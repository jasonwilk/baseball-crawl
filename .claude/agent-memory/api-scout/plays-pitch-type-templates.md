The plays endpoint (`GET /game-stream-processing/{event_id}/plays`) emits `at_plate_details[].template` pitch strings with an optional SINGLE trailing parenthetical whose content depends on what the scorekeeper charted. The parenthetical can hold pitch TYPE, pitch SPEED (MPH), or both:

- **Bare** (pitch result only): `"Ball 1"`, `"Foul"`, `"Strike 2 looking"`, `"In play"`
- **Type only**: `"Ball 1 (Fastball)"`, `"Strike 1 looking (Curveball)"` (what real team 133 charted)
- **Speed + type**: `"Strike 1 looking (101 MPH Curveball)"`, `"Ball 1 (75 MPH Fastball)"`
- **Speed only (no type)**: `"Ball 1 (75 MPH)"`

Trailing-parenthetical grammar (3 inner forms): `(<Type>)` | `(<int> MPH <Type>)` | `(<int> MPH)`. 5 of the 6 vocab values OBSERVED in live data (Fastball/Curveball/Slider/Changeup/Cutter — Slider e.g. `"Ball 1 (75 MPH Slider)"`, test team 2026-06-28); only `Unclear` remains unobserved. OPEN QUESTION: does `Unclear` emit a literal `(Unclear)` token or render as type-absent (bare / speed-only `(75 MPH)`)? Unknown — never captured. Capture regex `^(?:(\d+)\s*MPH\s*)?(.*?)$` handles both. Unit is `MPH` (uppercase), speed an integer. ALWAYS a single trailing group — never a second parenthetical, never a structured field (the `at_plate_details` entry has exactly one key, `template`, even on a maximally-charted play — verified against the controlled test team `dw3a8qivTMvA` on 2026-06-28, whose one charted game carried MPH+type).

**Velocity correction:** an earlier note here said pitch velocity is "structurally absent from the GC product" — that was WRONG, based only on real teams that didn't chart speed. Ground truth (test team) shows GC DOES support pitch velocity; it rides inside the same trailing parenthetical as `<int> MPH`, not a separate field. Velocity is a real capturable signal when a team charts it.

The regression-fix strip (`\s*\([^)]*\)\s*$` then match base) recovers `pitch_count`/FPS for ALL forms. To CAPTURE the annotation, sub-parse the stripped inner content with `^(?:(\d+)\s*MPH\s*)?(.*?)$` → optional speed_mph + optional pitch_type (either can be absent).

**The plays template suffix is a FLATTENED render of structured data in the RAW events endpoint (verified 2026-06-28, test team).** `GET /game-streams/{game_stream_id}/events` returns raw events; each `pitch` event's `event_data` (a JSON-encoded string) has `attributes`: `result` (enum: ball/strike_looking/strike_swinging/foul/...), `speed` (int MPH), `speedProvider` ("user" = manual entry; data-quality signal vs future radar), `style` (pitch type lowercase, NULL when speed charted but type wasn't), `advancesCount`/`advancesRunners` (bool) — PLUS `createdAt` (epoch MILLISECONDS, the per-pitch RECORD timestamp). The plays `(75 MPH Curveball)` suffix == events `{speed:75, style:"curveball"}`; `(75 MPH)` == `{speed:75, style:null}`.

**Pitch TIME exists ONLY in the events endpoint, NOT plays.** The plays payload has zero time field (single-key `at_plate_details`). `createdAt` is record time (≈ real pitch tempo for live-scored games; on the test team it's typing cadence since speedProvider=user). For pitch time or clean structured speed/type/result without string-parsing, the events endpoint is the superior source (we have a schema-ready `game_stream_id` column). BIP x/y coordinates live in the spray/player-stats endpoint (`spray_chart_data...defenders[].location.{x,y}`), not plays (plays carries BIP as `"In play (...)"` template + final_details narration only). See `docs/api/endpoints/get-game-streams-game_stream_id-events.md`. The annotation is ALWAYS a TRAILING ` (Word)` group — verified across 5 games, mid-template parenthetical count = 0. **Authoritative closed vocabulary (6 values, user-confirmed from the GC scorekeeper UI 2026-06-28): `Fastball`, `Curveball`, `Slider`, `Changeup`, `Cutter`, `Unclear`.** `Unclear` = a pitch WAS charted but the scorekeeper couldn't identify the type — NOT a real pitch type; treat as "type unknown," still a real pitch event. My 5-game live sample only surfaced 4 (Fastball/Curveball/Slider/Changeup); Cutter/Unclear come from the UI. Even so, the robust fix strips ANY trailing `\s*\([^)]*\)\s*$` parenthetical before exact-match rather than hardcoding the list. Bare and suffixed forms CAN co-occur within a single game (mixed scoring observed: 05-27 had 1 bare + 224 suffixed), so the fix must apply per-event, not per-game. Documented in docs/api/flows/plays-ingestion.md §6 and docs/api/endpoints/get-game-stream-processing-event_id-plays.md (2026-06-28).

**Why it matters:** `src/gamechanger/parsers/plays_parser.py` `_classify_template` uses an EXACT dict lookup (`_PITCH_TEMPLATES.get(template)`). Annotated templates miss the table, fall to the `"other"` bucket → `pitch_count=0` and `is_first_pitch_strike=0` for the whole game. A fully-charted game looks identical to an empty one at the stat level (PA-level outcomes from `final_details`/`name_template` still load fine — only pitch-derived stats collapse).

**Verdict from the 2026-06-28 Empire Netting (teams.id=133) investigation:** physically-impossible report stats (3.4% FPS, 0.2 P/PA) were a PARSER format gap, NOT source-data sparsity. 19 of ~24 games were charted WITH pitch types and silently dropped; the 1 "fully charted" game (06-18) happened to be charted WITHOUT pitch types so it parsed. Evidence: 51-68 of 52-70 PAs per "zero" game had full pitch sequences (194-256 suffixed pitch entries each).

**Velocity — present in product, absent from team 133's games (verified 2026-06-28):** A full-payload sweep across the 5 real team-133 games found ZERO velocity signal (those scorekeepers didn't chart speed). BUT the controlled test team `dw3a8qivTMvA` proved velocity IS a real GC field — it appears as `<int> MPH` inside the trailing parenthetical (see grammar above), NOT as a structured field or second parenthetical. So velocity capture depends entirely on whether a given team charted it. The `at_plate_details` entry is always single-key (`template`) regardless. Pitch speed + type together are the deepest pitch-level signals GC exposes; no coordinates/location/count-state field exists anywhere in the payload.

**How to apply:** When documenting or parsing plays, never assume bare templates. Strip a trailing ` (\w+)` group before exact-match, or match the bare prefix. The pitch TYPE itself is new useful scouting signal worth capturing, not just discarding. docs/api/flows/plays-ingestion.md §6 and the endpoint doc currently list only the bare form — flag for update if not yet done.
