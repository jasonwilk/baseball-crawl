# Step 1d closure smoke: a reconcile-scoreboard FAIL is usually stale-baseline drift, not a fidelity regression

During the Phase 5 Step 1d closure runtime smoke, `bb report reconcile-scoreboard` exits 1 on ANY gated regression vs the committed `.project/baselines/reconciliation-scoreboard.json`. But the smoke's own check-1 (`bb report generate`) MUTATES the shared dev DB, and that DB accumulates games across every dev-time generate — so the live DB routinely holds far MORE games than the baseline snapshot. Comparing current ABSOLUTE abs-Δ / no_plays_units counters against a stale, smaller-DB baseline shows "regressions" that are pure data-volume artifacts, NOT ingestion-fidelity regressions.

**Before treating a reconcile FAIL as an epic-FAIL, verify it is not baseline drift:**
1. Read `metadata.db_game_count` + `snapshot_date` from the baseline JSON, and count live completed games (`SELECT COUNT(*) FROM games WHERE status='completed'`). A large gap (E-261: baseline 213 @ 2026-07-12 vs live 405) = stale baseline.
2. Check `exact%` held high (98-100%) and abs-Δ grew SUBLINEARLY vs the game-count ratio — per-unit fidelity intact, only absolute counts rose with volume.
3. Confirm the volume-independent hard invariants: `self_games == 0` (hard zero) and `dropped_pitch_events == 0`. These are where a real dedup/parser bug would show; if they hold, the code is clean.
4. Direction check against the epic's TN: e.g. E-261 (perspective alignment via dedup/merge) would DECREASE `no_plays_units` per TN-6 — an INCREASE cannot be that epic's fidelity regression; it's added boxscore-only games.

**Resolution is operator-owned, NOT code remediation.** CLAUDE.md: "the operator OWNS every reconciliation-scoreboard.json snapshot — no agent auto-refreshes it." reconcile-scoreboard is a MANUAL operator diagnostic, not a CI gate. When it's drift, escalate for an operator `--update-baseline` re-snapshot; do NOT route into serial remediation. Report the raw exit-1 faithfully (don't declare a blanket "Step 1d PASS"), but give the adjudication + evidence so the main session doesn't misroute a stale-baseline artifact into code fixes. Recurring pattern — a prior re-snapshot (E-257 e9da456) tamed it once but the dev DB drifts again. See [[worktree_pytest_loads_the_worktree_src]] for the sibling "closure signal isn't what it looks like" lesson.

**Companion env-fail nuance (Step 1d preflight):** `bb creds check` audits BOTH a "web" and a "mobile" profile and ALWAYS prints the mobile block dead (mobile has no programmatic refresh — client key not extractable from the iOS binary). The reports/scouting path (`bb report generate`, `morning-run`, boxscore fetch) uses the WEB profile EXCLUSIVELY (bare `GameChangerClient()` → profile="web"). A red mobile block is NOT a preflight fail; confirm the WEB profile is live (API Health `GET /me/user → 200`) before declaring an ENV-FAIL on creds.
