> **STATUS (E-259 DONE, 2026-07-12):** the cutover this file justified SHIPPED — migration 011 DROPPED both tables (E-259-03), the write paths + `aggregate_parity` are DELETED (E-259-02/04), and `src.api.db.get_season_batting`/`get_season_pitching` now derive at QUERY TIME from `player_game_*` (E-259-01). The preconditions and consumer facts below remain the design basis / rationale (KEEP); three points are reconciled inline for post-cutover reality (line-10 rollback + provenance guard, the DISCHARGED line-17 #1 hazard, the line-24 writer-count cross-ref). Line 8's counts/INSERT-sites describe the verified PRE-DROP state that justified the drop.

Post-E-239, `player_season_batting` / `player_season_pitching` are a **pure derived cache** of `player_game_*`: the ONLY INSERT sites are `src/db/season_aggregates.py:250,310`, and both hardcode `'boxscore_only'`. No writer of `full` / `supplemented` provenance survives anywhere in `src/` or `scripts/`. The live `data/app.db` (verified 2026-07-09) holds 67 batting + 48 pitching rows, **100% `boxscore_only`**.

**Why:** this is the load-bearing precondition that JUSTIFIED the E-259 query-time cutover. Because the tables are 100% derivable from `player_game_*`, dropping them cannot lose data — no backup restore needed. **Rollback (corrected post-cutover):** `canonical_recompute` was DELETED in E-259-02, so the old "`git revert` + re-run `canonical_recompute`" advice is WRONG. The accurate rollback is — dev: `bb db reset` + reload; live: git-revert the query-time readers + recreate a migration that rebuilds the tables + reload the per-game data. But `full`/`supplemented` rows would be IRRECOVERABLE (the member `season_stats_loader` that produced them was deleted in E-239, and GC's season-stats endpoint is Forbidden for non-owned teams). The `NOT EXISTS` provenance guard that lived in `canonical_recompute` was **inert even before the cutover** (it protected rows that no longer exist and can never be recreated) — it was DELETED with `canonical_recompute` in E-259-02.

**How to apply:** any DROP or destructive rewrite of `player_season_*` MUST be preceded by an operator preflight asserting
`SELECT COUNT(*) FROM player_season_batting WHERE stat_completeness <> 'boxscore_only'` = 0 (and same for pitching).
Green ⇒ the DROP is data-lossless. Non-zero ⇒ STOP, those rows are irrecoverable.

Two consumer facts that matter for the cutover:
- The stored-row readers used to embody the perspective scoping that `canonical_recompute` applied at write time, so a query-time replacement MUST add `perspective_team_id = team_id` explicitly or opponent-perspective rows double-count. This WAS the #1 cutover bug risk — **DISCHARGED in E-259-01**: the query-time `src.api.db.get_season_batting`/`get_season_pitching` SUM the per-game tables WITH the explicit `perspective_team_id = team_id` filter, guarded by a dedicated perspective double-count test (the story's #1 AC). The stored-row read path no longer exists (tables dropped in migration 011).
- Query-time derivation is free: measured **0.046 ms/team** (index-driven via `idx_pgb_perspective_game`, no table scan) vs 0.004 ms for the stored read. A report touches 1-2 teams.

Mitigation if the preflight ever comes back non-zero: **refuse the cutover**, do not archive. A frozen archive table is a stale-data trap dressed as safety — nothing reads or refreshes it, but it looks authoritative. A member row appearing at all would mean a writer we believe deleted has resurrected; stop and understand that.

Adjacent empirical fact (2026-07-09, same DB): `SELECT COUNT(*) FROM player_game_pitching WHERE appearance_order IS NULL` = 0, and `game_loader.py:1065,1533` populates the column on every load. `bb data backfill-appearance-order` is **dead three times over**: (1) no NULL rows to fix; (2) no writer can produce a new NULL; (3) `src/gamechanger/loaders/backfill.py:28` sets `_DATA_ROOT = data/raw` and builds `root / season_id / teams|scouting / ...`, but the on-disk legacy trees use the RETIRED suffixed-season taxonomy (`data/raw/2026-spring-hs/`) while the DB's `season_id` is the year-only `2026` — so `data/raw/2026/` does not exist and the path never resolves, even where the JSON bytes are on disk. It no-ops on THIS machine, not just fresh ones. (CLAUDE.md documented it as live at the time; **E-256 resolved this — the `bb data backfill-appearance-order` command was DELETED in E-256-02, and its CLAUDE.md + data-model.md references removed in E-256-15.**) The taxonomy mismatch is another leaf of the cross-season machinery the user wants ripped out at the root.
