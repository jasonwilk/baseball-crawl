# Tool-Output Integrity

The harness transport layer can drop or corrupt tool output in bursts -- even on zero-IO commands like a bare `echo` -- and recover on retry. This corruption is not always empty: a nonempty result can be wrong. No tool can detect a garbled-but-nonempty read; only an agent applying this discipline can. **Every rule below was written because something specific went wrong, and the episodes live in the casebook** -- `.project/research/2026-08-01-tool-output-integrity-casebook.md`, referenced below as **CB**, which always means that file, followed by the exact section heading. **Every rule is either stated here in full or pointed at from here**; CB holds the stories, the measured evidence, and the occasional directive that only reads sensibly beside the episode it came from. Read it when a rule looks arbitrary, when you are about to argue with one, or when you need the evidence to settle a dispute. A rule stripped of its incident gets re-litigated -- so the incident is kept, just not resident in every context window.

## Failure taxonomy

Treat any of these as a tool-output FAILURE, not as truth:

- **Empty** -- a read/command returns nothing for a target you know or expect to be non-empty.
- **Truncated** -- output is cut off (tail missing, a partial edit that did not fully land).
- **Garbled** -- output is nonempty but wrong. Examples: line numbers that disagree with an independent count, a different file's bytes, or a command echoed back instead of executed. First-hand evidence for this mode lives in `.project/research/E-231-harness-repro/harness-output-reliability-report.md` -- including corruption of a bare `echo`, which has no file to change and so cannot be explained away by the differential below. Content that merely disagrees with a LATER read is not yet in this class: run the differential below before you name it. → CB § "E-231 — corruption of a bare `echo`"

## Grep is not a witness (four separate ways it lies)

**1. Silent-empty from a tool quirk, not from absence:** the environment's `grep` is ugrep, which returns EMPTY (no error) for `grep -rn "a\|b" <path…>` -- recursive BRE alternation over multiple path args. Use `grep -rnE "a|b"` (ERE), or a single pattern / single path. Treat an unexpected empty grep as an **Empty** FAILURE to cross-check (re-run with `-E` or per-file), never as proof of absence -- driving a deletion-eviction sweep off one would ship a false-clean no-op. **A second route to the same empty, and it is not ugrep's:** an unquoted glob-bearing flag (`--include=*.md`) is expanded by **zsh** before grep sees it, aborting the command with `no matches found` -- so in a multi-check batch **every check after it silently never runs**, and the partial output reads like a pass. Quote the flag. **Its silent sibling, same cause and opposite symptom:** an unquoted `$VAR` pathspec does NOT split -- git receives one bogus path and `git diff --quiet` exits **0, clean**. Loud-then-skip versus silently-vacuous; both are zsh quoting, and a reader meeting one needs the other. (Flagged in E-279 as a clause for this entry, left in a topic file instead, and reproduced by the same author in E-280 -- a worked example of "recorded, not recallable".)

**2. A CORRECT grep pattern silently NARROWS when the document's markup moves beneath it -- a different cause from the ugrep quirk above, and "use ERE" fixes none of it.** Five observed shapes, and **not one was a content change** -- in every case the content was intact and the SHAPE moved: **inline emphasis interpolated inside a phrase**; **blockquote nesting deepened** around a preserved quotation (*indistinguishable from the passage having been deleted*); **a quoted phrase wrapping across a line break** (single-line pattern, EMPTY against text that is present); **hyphenation**; and **letter case**. So a sweep of this repo's prose needs **three normalizations, not one: strip `**`/`__`, expect hyphenation and inflection variants, and match case-insensitively.**

**3. The unifying reflex, which supersedes the narrower "unexpected empty" form: an unexpected COUNT is a cross-check trigger, never a finding -- ANY count you did not predict, in EITHER direction.** One match where there were two looks exactly like a deletion; two hits where you expected none look exactly like a live defect. Both have been wrong here, and each was one step from a fabricated finding. `doc-sweep.md`'s synonym expansion does not reach any of these: they are not synonyms, they are the same words with markup or whitespace between them.

**4. A narrowed pattern does not only go EMPTY -- it can return the WRONG MEMBER and look successful, which is the one case entry 3's reflex cannot catch, because the count is exactly what you expected.** **When the discriminating token is not present at the sites you are ruling on, the check is a JOIN, not a grep**: enumerate where the value is BORN (discriminating), enumerate where it is READ (not discriminating), and match each read to its owner by reading the enclosing function. **An unresolvable site is a finding, not a default to the likelier owner.** Prefer an over-matching enumeration with a resolution step over an under-matching one -- **under-match is silent, over-match is visible** -- but **only while unresolvable sites must be REPORTED**; without that clause over-matching degrades into quiet judgement calls and is no better.

**Two rules that survive the pattern being RIGHT.** **A sweep is a WORKLIST, not a scan, and its failure can sit between SURFACING and RULING rather than in the pattern** -- a site can be surfaced by two independent lists and be wrongly ruled by both. **Every surfaced line gets a WRITTEN verdict, "no change needed" included, and this binds the IMPLEMENTER as much as the reviewer** -- a remedy scoped to the reviewer fixes half the chain. **A verdict can also be PARTIAL rather than wrong -- true about the clause you read, silent about the clause you did not, on the same line -- and an audit asking *did every surfaced site get a written verdict* PASSES on it. A partial ruling is indistinguishable from a complete one at the point of audit**, so state which CLAIM the verdict is about, not merely which site. Do not respond by widening the pattern. And **design the first run so its empty is already interpretable**: a known-present term carried in the same OR-pattern is a free positive control -- if it matches, the pattern ran against the right file and the other alternative's zero is **verified absence** rather than an unexplained empty. → CB § "Why this became its own section", "E-256-15 — ugrep's silent empty", "E-277 — five ways a correct pattern narrows, none of them a content change", "E-277 — an unexpected count in either direction, and the fabrication it nearly justified", "E-277 story 05 — the wrong member returned, and the instruction INVERTED", "E-277 — the site that survived two independent worklists", "E-280 — the partial ruling that passed its own audit"

## A read that disagrees has TWO causes -- run the differential before naming one

A read that disagrees with what you remember has two very different causes: **the transport garbled it**, or **the file moved under you** (an accurate read of a state that no longer exists). Their symptoms are evidentially identical -- a second read disagreeing, and a grep for the remembered text returning zero matches, are produced by BOTH, and both are exactly what the response protocol below tells you to gather. Neither discriminates. So name the cause from evidence that does:

1. **A harness note that the file "has been modified on disk since you last read it" -- including an Edit rejected on that ground -- is PRIMARY EVIDENCE that the file moved.** It is the answer, not a symptom to investigate. In the 2026-07-25 handoff incident it was the one accurate sentence in the whole diagnostic chain, and it was read as a puzzle rather than as the finding.
2. **`stat -c '%y' <file>`** against the time of your read. An mtime later than your read settles it.
3. **Enumerate who else can write this tree** -- a predecessor or concurrent session, a live teammate, an implementer mid-mutation in a dispatch worktree, a background task, a hook. "Nobody else is writing" is an assumption until you have checked it.
4. **grep the other writer's transcript for the text you remember.** `~/.claude/projects/<cwd-slug>/<session-id>.jsonl` plus that session's `<session-id>/subagents/*.jsonl` carry every Write/Edit/Bash payload with timestamps. If your remembered text appears in one, your read was ACCURATE and the diagnosis is settled.

The two causes demand OPPOSITE actions, which is what makes the misfile expensive. "Garbled" says discard what you read. "Moved" says what you read was REAL -- so a defect you saw may genuinely be in the tree, and a later clean read is evidence about a different state, not a refutation of the first. Two rules the record leaves standing: **a read that hands you exactly the defect you were looking for is a cross-check trigger, not a finding** -- and in a dispatch worktree, **an implementer proving a test discriminates IS a writer of the file you are reviewing** (`.claude/rules/worktree-isolation.md` records that same practice destroying that same file). → CB § "E-267 story 03 round 2 — the read was accurate and the file moved"

## Response protocol (cross-check, retry, escalate)

When a target known or expected to be non-empty returns empty, truncated, or garbled output:

1. **Treat it as a FAILURE** -- do not act on it or report it as the result. If what you have is a *disagreement* rather than an empty or truncated result, run the differential above first: "the tool failed" is one of two candidate causes, not the default.
2. **Cross-check via an independent channel** -- a different tool, or a different command against the same target.
3. **Retry** to obtain a clean result.
4. **Escalate rather than assert** if a clean result still cannot be obtained.
5. **Read persisted review/tool findings to completion BEFORE characterizing, summarizing, or triaging them.** A preview, a `head`/`tail`, or a truncated view is not the content; a large output's first screen is not its findings. Never characterize findings, ask to triage them, or co-batch a triage decision with the command that produced them until you have read the full persisted output in your own context. (The ad-hoc main-session triage context is the thin spot.)

When two channels disagree, **the clean read wins** over a flaky empty or garbled result -- but only once the differential has ruled out a moved file. Against a file that is being written, the later read is not more TRUE, only more RECENT, and it refutes nothing about the state the first read saw. A "no files found" Glob is NOT proof of absence under a flaky channel -- confirm absence through a second channel before relying on it. → CB § "E-230 — findings characterized before they were read"

## Prose you AUTHOR is a claim too

The rules above govern what you READ. The same discipline binds what you WRITE: a comment, docstring, spec citation, or CLAUDE.md sentence asserting how the code behaves is an unverified claim until resolved against the repo. Prose is unexecutable, so **a green suite says NOTHING about it**. Before reporting prose complete:

1. **Enumerate every symbol AND path the prose cites** -- test names, functions, flags, files, headings -- not just the ones in your diff, and resolve each against the repo. Where a reference is missing, establish WHY rather than noting it.
2. **EXECUTE behavioral claims rather than reasoning to them.** "This would raise X" is a hypothesis until you make it raise X.
3. **Name the OBJECT, not the POSITION.** A position is resolved when the READER arrives, so it names whatever is there then -- rarely what you meant. Cite by test name, symbol or heading rather than a line range (line numbers rot); read from a **tree SHA**, never `git show HEAD:` or `git show :`, both of which move under you; review a **frozen tree** rather than working-directory state; and record a measurement as **`<figure> @ <tree>`**, because a bare number is a position too and gets applied after the tree has moved. Found three times independently in E-280, by different agents on different problems, before anyone saw it was one rule.
4. **QUOTE THE LITERAL BYTES to a reader who will check them. "Announcing before writing" is not the same mechanism and catches nothing** -- *"an announcement that says 'I am going to fix the docstring' would have caught neither defect."* **The mechanism is that quoting your own text into an announcement makes you read it as a READER rather than as its author** -- which is why it transfers where *look harder* does not. **Bound, and it matters against the 8-of-8 author record below: only the PROCEDURAL catch transfers** -- the other of those two was attention at drafting and generalizes to nothing, and **the 8-of-8 count is not amended by either.**
5. **Verify a prose fix by ABSENCE, not by presence.** Do not confirm the corrected sentence arrived; grep for the FALSE forms and require **zero matches**. A botched edit that leaves BOTH forms standing reads fine to a skimmer, so confirming the falsehood is gone is strictly stronger than confirming the correction landed.

**A claim you RELAY is a claim you AUTHOR.** The heading says "author", but this defect travels by INHERITANCE: a sentence handed to you in an epic spec, a story, an upstream doc, **or a prose line inside a `diff` you are reviewing** becomes yours the moment you write it down, and a spec that passed internal review plus a Codex pass is not verification -- it is borrowed authority, which is precisely why it gets restated unchecked. **That list reads closed and is not** -- an exhaustive-class claim of exactly the kind this file warns about, and the diff member was added only after it bit. **A diff is the one channel that announces itself as PRIMARY evidence**, which it is -- about the code. The prose between the `+`/`-` lines is someone else's claim arriving under the surrounding evidence's authority and none of the suspicion a brief attracts. The transferable form is the **mode switch that never happens**, not "read diffs carefully": one artifact carries evidence and hearsay under a single apparent epistemic status, so a sentence you first met inside a diff is INHERITED -- check it as you would a brief before restating it. Check an inherited safety claim at the point you restate it. **A verdict's stated REASON rots independently of the verdict**, and a correct conclusion immunizes its false premise: any check that asks "was the call right?" passes, so only reopening the cited file catches it. This bites hardest in a RETRACTION, where the relief of having caught an error is what stops the reason being read. Once such a claim is retired, sweeping out its residue is its own discipline -- see `.claude/rules/doc-sweep.md`, "Retired Claims Survive in Forms Carrying None of Their Tokens".

**A handoff artifact is a claim with a timestamp.** A handoff note, research file, or kickoff prompt written for another session to consume is mutable until it is committed, and correcting it afterwards does not reach a reader who has already read it or a prompt already handed out. So: when you correct material you have already handed off, reissue BOTH the artifact and any prompt built from it; and when you are seeded FROM such an artifact, check its mtime against your own start before treating it as the state.

**A STATUS claim decays exactly like a verdict, and nobody brackets those** -- *"I bracketed my reviews and did not bracket my reporting."* A correct zero is EVIDENCE of a past state; using it as a CRITERION about the current one has stopped an implementer mid-story. **Attach the measurement and its time to a status assertion, or do not make one.** Companion: **a repeated assertion is not a repeated measurement** -- one measurement re-stated is not two observations, and reporting it as two nearly bought a permanent residual against every clean verdict a reviewer had issued.

**The safety-comment sub-class (where this defect concentrates).** Alarming prose is self-protecting: a claim naming the SCARIER outcome feels right for a safety note and is therefore least likely to be challenged. Sharpest form -- **the tidy general rule at the END of a safety note is where this lands, because that is the sentence that sounds most authoritative and gets checked least.** It is also where over-correction lands. When you write a closing generalization, check it against the codebase's dominant pattern; if that pattern would violate your rule, the rule is wrong. **The check is NOT "does this sound appropriately grave" -- it is "are BOTH sides of the trade stated?"** Neither the alarming nor the reassuring qualifier is the defect; **the asymmetry is**, and the two-sided form is the only one a non-author can run from the text alone, having read nothing else. → CB § "E-270 — six prose defects across five shapes, on a green suite", "E-277 — the announcement that made an author a reader", "E-278 — the false claim inherited from a diff", "E-272 — one false safety sentence, three downstream carriers", "2026-07-25 — the retraction that was wrong twice while the verdict stayed right", "2026-07-25 — the handoff corrected 45 seconds too late", "E-277 — a correct zero used as a criterion about the present", "E-276 — six one-sided drifts, in both directions"

## A check that RAN is not a check that WORKED

**The PRODUCIBILITY check, and it governs how you VERIFY a figure: a figure inside a correct conclusion gets checked for whether it SUPPORTS the conclusion, never for whether it could have been PRODUCED.** A false figure that changes no verdict is exactly the one review passes let through, because every pass asks whether the number fits the argument -- which it does. **Re-derive a figure from the thing that would produce it, and treat its agreement with the conclusion as no evidence at all.**

**And once you HAVE found a stale figure, the CRITERION-vs-EVIDENCE cut says what to do with it -- a different rule from the producibility check above, governing DISPOSITION rather than verification, and conflating the two is how one of them gets lost.** ***A figure is a CRITERION when a reader must meet it, and EVIDENCE when a reader must see what was observed. Correct the first; preserve the second.*** It descends from the same ruling for line numbers -- a line number is a citation when a reader is meant to GO there, and evidence when the reader is meant to see that it MOVED. One number can carry both roles in one file. Note the disposition for a stale CRITERION: **removed rather than updated**, since updating an absolute baseline that a later change will move again merely resets a timer. **So a consistency sweep that "fixes every stale-looking figure" is not a safe default; it destroys records. Ask what the reader is meant to DO with the number before you touch it.**

**The detection record, because it says who can catch what.** Two classes, and merging them overstates a true finding into a false one. **Class A -- a FALSE PREMISE under a CORRECT conclusion**: four instances in one dispatch, caught by EXECUTION or MEASUREMENT 4 of 4 and by careful re-reading 0 of 4 -- not for want of reading, since someone had the material open every time and two were produced by the people who had written the rule against them hours earlier. **Class B -- a MISSING MEMBER of an enumeration**: these ARE caught by reading, but never by the author. **Unifying fact: in 8 of 8, the author never caught their own.** Reading works only from OUTSIDE the claim's authorship, and against a false premise under a right conclusion, not even then. Companion shape: where an artifact states one conclusion twice at different strengths, EXECUTE the stronger statement; where it is not executable, the pairing is itself the trigger, because the weaker claim would be true either way and so certifies nothing about the stronger.

**Class A's MIRROR -- a TRUE clause welded to a FALSE INFERENCE -- and the two are only legible together.** Class A defeats the check "was the conclusion right?"; the mirror defeats the check "was the premise right?", which is the remedy Class A hands you. In the recorded case **neither party held a false premise; premise-checking would have cleared both**, and every individual sentence in the episode was true, so no truth-check anywhere would have flagged any of it. **When a premise checks out and the conclusion still looks wrong, check the INFERENCE -- "was the premise true?" terminates too early.** And **count the topology as a TREE before reporting N independent sightings** -- carriers that look independent are often siblings from one author, or descended from each other through a diff; establish it by asking, not by inferring. The individual form is in `dispatch-pattern.md`: conceding felt like the disciplined move, and it produced a new false claim inside a thread about false claims.

**And the running can lie: a broken check's output is SHAPE-IDENTICAL to a working one's.** This BOUNDS the remedy above rather than sitting beside it. A bad positive control's empty looks exactly like a tool failure's empty, so **confirm your control exists CONTIGUOUSLY in the target before concluding the tool failed** (a control drawn by eye from rendered prose is the high-risk case, because rendering hides the wrapping that breaks it). A mutation probe whose mutation never applied reports the same green as one that did, when the alarm prints above the summary line nobody reads: **a precondition check whose alarm is discarded is not a check.** Same shape one layer out is a green test over a fixture that does not do what its name says. **So run the check AND validate the check's own preconditions, and require an instrument to emit evidence that it OPERATED, separate from its result -- then do not filter that evidence away.**

**And the vacuity concentrates in the ANTI-VACUITY line itself, because that is the line that reads as the rigour.** Recorded instances all sat INSIDE guards -- an assertion unreachable by construction, a conjunct comparing two module constants, a query returning identically whether or not the behavior under test occurred, a substring assertion that could never fire. Each was written as the check PROTECTING a criterion, each passed, and **every one was found by someone other than its author** -- consistent with the 8-of-8 authorship record above. The remedy is the one already on this page, aimed one line lower than feels necessary: **make the guard FAIL on purpose before you trust it**, and prefer an assertion whose negative form is constructible (a regex with a lookahead, an explicit `pytest.raises`) over a substring or inequality whose non-match has many innocent causes.

**Severity ordering is a claim, and it is the least-checked kind, because every finding under it is true.** An instrument can be accurate and rank its own output backwards. A self-announcing failure (a `TypeError`) teaches anyone who runs it immediately; **the quiet finding, which produces a plausible number and reports nothing wrong, is the dangerous one**, and no amount of verifying the findings will catch a wrong ordering of them. → CB § "E-276 — `18 of 18`, the figure that was never producible", "E-276 — one figure that was criterion and evidence four criteria apart", "The detection record — who can catch what, and the 8-of-8", "E-278 — Class A's mirror: a TRUE clause welded to a FALSE INFERENCE", "E-276 — the control that was line-wrapped, and the alarm nobody read", "E-278 — four vacuous assertions, all of them inside guards", "E-276 — the audit that ranked its own output backwards"

## Prohibitions

1. **Never assert or relay file content or a tool outcome you have not seen cleanly in your own context.** Report what you observed, not what you expect.
2. **Never co-batch a relay or report with the same-batch command whose output it reports.** A report must describe output already in context from a prior, completed call -- never expected output and never output produced in the same tool batch as the report.
3. **Never rule on a grep / OR-pattern match -- Read and quote the literal line.** A grep hit proves a line matched *something*; it says NOTHING about which alternative of an OR-pattern matched, and an omitted or truncated matching line (`[Omitted long matching line]`) is not evidence of any particular content -- it just means the line was long. grep finds candidates; only a clean Read of the exact line range confirms the current literal text. Never report a defect, rule a claim stale-or-current, or characterize content from a match alone.
