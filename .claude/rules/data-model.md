# Data Model

The schema is defined in `migrations/001_initial_schema.sql` (base) with incremental migrations layered on top (run `ls migrations/*.sql` for the live set; see `.claude/rules/migrations.md` for numbering). Key design decisions:

- **Programs**: Umbrella entity grouping teams under an organizational program (e.g., `lsb-hs` = Lincoln Standing Bear HS). Types: `hs`, `usssa`, `legion`.
- **Teams**: INTEGER PRIMARY KEY AUTOINCREMENT (`teams.id`). External GC identifiers live in dedicated UNIQUE columns: `gc_uuid` (authenticated API) and `public_id` (public URL slug). All FK references to teams use `teams(id)`. INTEGER PK applies to `teams` only -- programs, seasons, and players keep TEXT PKs.
- **Membership type**: `teams.membership_type` (`member` or `tracked`). Member teams are those the operator manages in GameChanger; tracked teams are opponents or other teams added for scouting.
- **Season year**: `teams.season_year INTEGER` -- the year this team belongs to, populated from GameChanger API (`season_year` on authenticated endpoints, `team_season.year` on public). NULL falls back to current calendar year in `get_team_year_map()`. Self-healed by pipeline on sync. **Footgun**: stub team auto-creation (in roster/season_stats loaders) must pass `season_year` to `ensure_team_row()` to avoid the current-year fallback producing wrong values for historical data.
- **Classification**: `teams.classification` column. Valid values: `varsity`, `jv`, `freshman`, `reserve` (HS); `8U`-`14U` (USSSA); `legion`. Division dropdown in the admin UI.
- **TeamRef pattern**: Pipeline code uses a `TeamRef` dataclass (`id: int`, `gc_uuid: str | None`, `public_id: str | None`). `.id` for all DB operations; `.gc_uuid` / `.public_id` for API calls. Tracked teams may have `gc_uuid=None`.
- **Game ordering convention**: Every `ORDER BY game_date` MUST include `start_time` as a same-direction tiebreaker with `NULLS LAST` (e.g., `ORDER BY game_date DESC, start_time DESC NULLS LAST`). Doubleheaders, rescheduled games, and multi-site days all produce same-date collisions that `game_date` alone cannot resolve. For game boxscore pitching lines, additionally sort by `appearance_order ASC NULLS LAST` (starter first, then relievers in order).
- **Appearance order**: `player_game_pitching.appearance_order INTEGER` (migration 015). Value 1 = starter, 2+ = relievers in order of entry. NULL = unknown (not zero -- zero is not a valid appearance order). Populated by the game loader from boxscore JSON pitcher ordering (the `stats` array under each team's pitching group is ordered by appearance). Backfillable from cached boxscore JSON via `bb data backfill-appearance-order`. Scouting aggregation computes GS as `COUNT(*) WHERE appearance_order = 1` using a NULL-safe CASE expression (NULL `appearance_order` contributes 0, not NULL).
- **Game status values**: Completed games use `status = 'completed'` (not `'final'`). All queries across `src/` filter on `'completed'`; the `game_loader.py` inserts with this value. Do not use `'final'` in game queries.
- **Game time data ownership**: The schedule loader is authoritative for `game_date` and `start_time` -- it writes directly (no COALESCE). The game loader (game-summaries) lacks time data and uses `COALESCE(existing, new)` to preserve values already set by the schedule loader. Do not add COALESCE to schedule loader time columns; do not remove COALESCE from game loader time columns.
- **7-day rolling window**: For inclusive 7-calendar-day windows, use `date(ref, '-6 days')` (NOT `-7` which creates an 8-day window). Example: games from Mar 28 through Apr 3 inclusive = `WHERE game_date >= date('2026-04-03', '-6 days')`.
- **Enriched stat columns** (schema-ready, not yet populated): `game_stream_id` on games (links to game-streams endpoints like `GET /game-streams/{game_stream_id}/events`; NOT a path parameter for game-stream-processing endpoints -- `event_id` from game-summaries is the path parameter for both `GET /game-stream-processing/{event_id}/boxscore` and `GET /game-stream-processing/{event_id}/plays`; the game loader indexes summaries by both `event_id` and `game_stream_id` for robust file matching), `bats`/`throws` on players, home/away and vs-LHP/RHP split columns on season batting/pitching, `pitches`/`total_strikes` on game pitching, `batting_order`/`positions_played`/`is_primary` on game batting, `stat_completeness` tracking on all stat tables.
- **Plays and play events**: Two-table schema (`plays` + `play_events`, migration `009_plays_play_events.sql`). `plays` stores one row per plate appearance with batter/pitcher linkage, pitch count, outcome, and pre-computed boolean flags (`is_first_pitch_strike`, `is_qab`). `play_events` stores individual events within a PA (pitch results, baserunner events, substitutions). Idempotency keys: `UNIQUE(game_id, play_order)` on plays, `UNIQUE(play_id, event_order)` on play_events. **Whole-game idempotency**: before processing, check if any `plays` row exists for the `game_id` -- if yes, skip entirely. Never delete-and-reinsert (parent-child re-insertion problem: `INSERT OR IGNORE` on existing parent returns no `lastrowid` for children). Populated in-memory by the report generator's plays stage (`_crawl_and_load_plays` → `PlaysLoader.load_payload`). 24 confirmed outcome types; 486 `final_details` patterns (regex-parsed, not enumerable). The plays endpoint (`GET /game-stream-processing/{event_id}/plays`) is NOT ownership-gated -- works for opponent games too (unlike season-stats). `play_events` also carries nullable `pitch_type` (TEXT -- open vocabulary, deliberately no CHECK so it can grow) and `pitch_speed_mph` (INTEGER) columns (migration `007`), captured independently per event from the pitch-template annotation (a speed-only or type-only pitch leaves the other NULL). These are storage-only -- analysis is deferred (IDEA-086).
- **Spray charts**: `spray_charts` table stores ball-in-play coordinate data (x/y, play type, result, fielder position). Populated in-memory by the report generator's spray stage (`ScoutingSprayChartCrawler` → `ScoutingSprayChartLoader`). Data quality: spray data is scorekeeper-dependent (~93% of games have offensive data, ~16% have defensive); `spray_chart_data` is `null` (not empty array) when the scorekeeper did not record. Display thresholds: 3 BIP minimum for per-player charts, 20 BIP for team aggregates.
- **Cross-perspective player UUIDs**: GameChanger returns different `player_id` UUIDs for the same human depending on which team's boxscore is viewed. This is a permanent API property, not a bug. When team A's boxscore lists team B's players, it uses different UUIDs (and often initial-only first names) than team B's own boxscore. All agents working with player data must account for this -- never assume `player_id` is globally unique per human. Same-team duplicates are detected by prefix-matching first names with matching last names on the same roster. See `.claude/rules/perspective-provenance.md` for the perspective tagging invariant and field classification table.
- **Empty `bb db reset`**: `bb db reset` (`src/db/reset.py`) produces an EMPTY database — migrations plus the `programs` `lsb-hs` bootstrap row from migration 001 only. There is NO seed/sample data (`seed_dev.sql` and `scripts/seed_dev.py` were removed in E-228). Operators populate real data afterward by generating reports (`bb report generate` or `/admin/reports`). Do not assume reset yields demo data when reasoning about DB state or writing tests.
- **`gc_athlete_profile_id` (dropped, E-250-02)**: The `players.gc_athlete_profile_id` column was removed in migration 008. It was never populated and had been reserved as the cross-team athlete-identity anchor for E-104 (athlete-profile endpoint); E-104 is now abandoned (E-250-07) and cross-team player identity is an explicit Non-Goal. Do not reintroduce the column or assume athlete-profile linkage exists.
- **Player dedup merge-every-run cycle**: The post-load dedup sweep in the scouting pipeline re-detects and re-merges duplicate player pairs on every run. Perspective tagging (E-220) reduces cross-perspective stub creation by isolating each perspective's data, but does not eliminate it entirely -- the plays loader still creates player stubs via `ensure_player_row()`. The dedup sweep remains necessary for both residual cross-perspective cleanup and genuine name-variant dedup (e.g., "O" vs "Oliver").
- **Plays pipeline dedup gap**: The plays stage of report generation is not wired into the post-load dedup sweep that `bb data dedup-players` performs. Perspective-scoped idempotency (`WHERE game_id = ? AND perspective_team_id = ?`) prevents cross-perspective play collisions -- each perspective's plays are isolated. Cross-perspective player stubs introduced by plays data are cleaned up by a subsequent `bb data dedup-players --execute` run.

## Cleanup-Detection Mirror Invariant

When extending a cleanup helper's surface (adding a new table to a DELETE cascade, broadening a WHERE clause, adding a new row-deletion pass), you MUST audit every detection/gate query that mirrors the cleanup surface and update it in the same change. Detection queries include informed-consent gates, precondition checks, row-count probes, and any query that enumerates "what this delete will affect" to the operator.

**Why**: A perspective-aware cleanup gap let foreign-owned data bypass the informed-consent gate and silently delete — the canonical cascade grew to cover a new table but the gate query didn't, so a team with only that table's cross-perspective footprint walked through an empty warning screen and wiped data belonging to other perspectives.

**Concrete example**: `src/reports/generator.py::_delete_team_anchor_and_orphan_data` deletes five stat tables (`player_game_batting`, `player_game_pitching`, `spray_charts`, `plays`, `reconciliation_discrepancies`). Historically the admin delete-team flow carried an informed-consent gate (`_get_delete_confirmation_data`'s `cross_persp_rows` UNION) that mirrored this cleanup surface; that gate was removed in E-239 along with the admin team-management UI. The principle still binds forward: if any future detection/gate query is added over this cleanup (e.g., a report-delete confirmation), it MUST enumerate the same tables with the `team_id = T AND perspective_team_id != T` shape, and grow with the cascade in the same commit.

**How to apply**: Any PR that modifies a DELETE statement, a cascade helper, or a cleanup pass in `src/reports/`, `src/db/`, or `src/api/` must grep for mirror queries (look for `COUNT(*)` / `SELECT ... WHERE team_id` / UNION shapes referencing the same table) and update them in lock-step. Code review checklist item: "Did the cleanup surface change? If yes, were all mirror queries updated?"

## Season-Aggregate Parity

Background for any future aggregate-integrity, identity, or guard work (Epic C and beyond). Stored `player_season_batting` / `player_season_pitching` rows are NOT always a faithful sum of per-game rows -- whether parity holds depends on provenance, and the two stat tables can disagree within one (team, season).

- **Parity provenance (`stat_completeness`)**: `boxscore_only` = scouting / summed-from-games rows -- these ARE parity-checkable against per-game rows. `full` / `supplemented` = member / season-stats-API rows -- these are NOT game-summed and MUST be excluded from parity checks. Member-vs-scouting provenance is detected cross-table: a `full`/`supplemented` value in EITHER season table implies member scope for that (team, season).
- **Season-row asymmetry across batting/pitching**: a (team, season) can be ASYMMETRIC across the two season stat tables -- e.g. `player_game_pitching` rows present but ZERO `player_season_pitching` rows. `canonical_recompute` writes batting and pitching season rows INDEPENDENTLY (a player gets a batting row only if they batted, a pitching row only if they pitched), so a player who only batted yields a batting season row and no pitching row. Future aggregate/identity work MUST NOT assume symmetric stored season rows across the batting/pitching tables. (The now-removed member `season_stats_loader` produced the same asymmetry; the caution predates E-239 but still holds for the surviving recompute path.)
- **The `cells_compared > 0` footgun**: a non-vacuity count proves OVERALL non-emptiness, not PER-SCOPE coverage. A guard driven solely from stored-present scopes can silently skip an entirely-missing scope while still reporting `cells_compared > 0` (this was the Codex-P1 root cause). When designing a guard or aggregation check, derive the scope set from the EXPECTED universe (per-game rows / roster), not only from rows already present in the stored aggregate.
- **Mixed-provenance scope invariant (the latent data-loss footgun, E-237)**: a single `(team_id, season_id)` scope can LEGITIMATELY hold MIXED provenance -- both a `full`/`supplemented` member row and `boxscore_only` rows -- because the canonical recompute (`canonical_recompute`, `src/db/season_aggregates.py`) owns only `boxscore_only` rows and preserves member rows via a `NOT EXISTS` provenance guard. CONSEQUENCE: any code that recomputes, aggregates, compares, OR deletes/rewrites `player_season_*` rows ACROSS A SCOPE (not single-player point reads) MUST apply the same `full`/`supplemented` exclusion -- never delete or downgrade a member row, never treat a mixed scope as single-provenance. Two sites violated this and were fixed in E-237: `aggregate_parity.py::verify_aggregates` (flagged preserved member players as false mismatches) and `player_dedup.py::merge_player_pair` (unconditionally deleted member `full` rows on merge, downgrading them to boxscore sums). The data-loss class is now closed for both non-merged (canonical guard) and merged (merge re-point) players.
- **Single-source projection AND compared-columns (the false-parity footgun, E-246)**: the parity check shares TWO axes with `canonical_recompute`, BOTH flowing from the `BATTING_RECOMPUTE_KEYS` / `PITCHING_RECOMPUTE_KEYS` tuples in `src/db/season_aggregates.py`: (1) the SUM projection (via `batting_recompute_select()` / `pitching_recompute_select()`) and (2) the compared-column (`diff_columns`) lists in `aggregate_parity.py` (`_BATTING_COLUMNS` / `_PITCHING_COLUMNS`), which DERIVE from the same `*_RECOMPUTE_KEYS` (with an explicit `gp`/`gp_pitcher`→`games_tracked` stored-alias prefix). NEVER reintroduce a separate hand-maintained column list on EITHER axis: a projection column that does not also flow into `diff_columns` would be recomputed but silently NOT compared -- a false-parity hazard where a mismatch passes undetected. A parity column must flow from the single key source into BOTH the recompute and the comparison; the `test_diff_columns_track_shared_keys` guard pins the derivation.
- **Twin-method collapse must preserve each path's distinct guards (the silent guard-drop footgun, E-247)**: when consolidating twin in-memory/disk loader methods into one shared core, the two paths may carry DIFFERENT guards — verify each against the pre-refactor code PER-PATH and preserve them exactly. Concrete near-miss (Codex caught): the pre-refactor in-memory load path early-returned on empty boxscores, while the disk path ran a post-boxscore tail; the naive single-core consolidation ran that tail unconditionally, which would have turned `canonical_recompute` into a stat-rewriting DELETE+rebuild on POPULATED DBs — a re-scout returning 0 boxscores would wipe and rebuild `boxscore_only` season aggregates and trigger player-dedup. A shared core is only safe once every collapsed path's distinct early-return/guard is reproduced inside it.
- **Idempotent-recompute characterization tests need a populated, stale-disagreeing fixture (E-247 corollary)**: a DELETE+rebuild / no-op recompute test has NO TEETH on a fresh or empty DB — the rebuild is observable only when it would CHANGE something. Such tests MUST seed a POPULATED state whose stored aggregate deliberately DISAGREES with the per-game sum, then assert the recompute is a no-op (or rebuilds to the per-game sum). A green test on a fresh DB proves nothing about the guard it claims to pin.

## Player Dedup: Components, Fork Refusal, Transaction Ownership (E-249)

Same-team duplicate players are deduped by ONE shared planner (`plan_player_dedup` + `execute_collapse`, `src/db/player_dedup.py`) consumed by both the load-path sweep (`dedup_team_players`) and the CLI (`bb data dedup-players`) -- "de-dup the dedup." Durable invariants/footguns:

- **Components are per-`(team_id, season_id)`.** The detection self-join AND `plan_player_dedup` MUST partition connected components by `(team_id, season_id)`. Keying by `team_id` alone unions prefix-pairs ACROSS seasons and mis-plans merges on the unscoped CLI path (the E-249 Codex P1). Any future dedup change MUST preserve the per-season partition.
- **Fork refusal ("refuse, don't guess").** A component whose maximal members carry ≥2 DISTINCT names (a fork) is REFUSED, not merged: prefix matching alone cannot tell one human (Jo/John/Jon) from two (O/Oliver/Owen) -- only same-game co-occurrence carries that signal (deferred to Tier 2, IDEA-089). Equal-named maximal members (same name, two UUIDs) still collapse.
- **Per-component transaction ownership.** `execute_collapse` owns the per-component transaction/savepoint and calls `merge_player_pair(manage_transaction=False)`. `manage_transaction=True` self-commits per merge and CANNOT nest under an outer per-component BEGIN -- do not pass it from the component executor.
- **CLI default-isolation recompute footgun.** The CLI's sqlite connection uses default (legacy) isolation, which ROLLS BACK uncommitted DML on close. Any standalone season-aggregate recompute on that connection MUST be followed by an explicit `conn.commit()` or it is silently discarded.
- **Player dedup is season-scoped (E-250-01).** `bb data dedup-players` requires a `season_id` and auto-derives it (the sole season when exactly one exists; no-op on zero; explicit `--season-id` required when 2+ seasons are present). There is no unscoped cross-season execute path -- every merge is partitioned by `(team_id, season_id)`, and the load-path sweep is likewise always season-scoped. Cross-season player identity is an explicit Non-Goal.

## Scheduled-Report Audit + Opponent Resolution (E-240)

The morning-run scheduler (`bb report morning-run`) adds an audit table and revives a dormant mapping table. Both feed the opponent-resolution ladder (`src/gamechanger/opponent_ladder.py`).

- **`scheduled_report_runs` (migration 005)**: one AUDIT row per scheduled opponent slot the morning run processes -- it records EVERY slot and its outcome, including unresolved / no-GC-presence / deferred slots that produced NO report (`report_generation_runs` cannot represent these: it is 1:1 NOT NULL `report_id` with a produced report). Key columns:
  - `resolution_outcome` (CHECK, NOT NULL): `auto_resolved` (a report was attempted) / `unresolved_mappable` (on GC, not auto-matched -> operator queue) / `no_gc_presence` (operator-declared via `map-opponent --no-presence`) / `deferred_placeholder` (TBD/Winner/Seed... re-polled near game time).
  - `delivery_status` (CHECK, NULLABLE): non-NULL ONLY when generation was attempted (an `auto_resolved` slot) -- `generated` / `no_games` / `failed` / `skipped`. NULL = generation not attempted; `resolution_outcome` carries the reason.
  - `report_id` FK `reports(id)` **ON DELETE SET NULL** -- the audit row MUST OUTLIVE report cleanup/expiry. This is the DELIBERATE MIRROR-IMAGE of `report_generation_runs.report_id` ON DELETE CASCADE (E-235): the per-generation run row dies with its report, but a scheduled-run row is an audit record that survives. `report_slug` is a frozen-string fallback so the trail still names the report after the FK is nulled. Do NOT copy the CASCADE pattern here.
  - `opponent_root_team_id` TEXT, **NO FK** -- the GC `root_team_id` registry namespace, an opaque GC token, NEVER a `gc_uuid` (storing `root_team_id` in a `gc_uuid` column is the documented namespace error in CLAUDE.md "Opponent entry duality").
  - In the team-deletion cascade: `_delete_team_scoped_data` (`src/reports/generator.py`) deletes `scheduled_report_runs WHERE own_team_id IN (...)` (team deletion REMOVES the audit rows -- distinct from report deletion, which only NULLs `report_id`). Per the Cleanup-Detection Mirror Invariant above.
- **Idempotency NULL footgun**: `UNIQUE(own_team_id, opponent_root_team_id, game_date)`. SQLite treats NULLs as DISTINCT in UNIQUE indexes, so a NULL in any of the three key columns silently breaks idempotency (a re-run duplicates the slot instead of UPSERTing it). The loader MUST guarantee a non-NULL key on all three columns -- `morning_run` falls back to an `unknown-{event_id}` token when `opponent_root_team_id` would be NULL.
- **`opponent_links` revival** (no new DDL -- migration 001 already has the shape): now the `root_team_id -> public_id` mapping store. The three states are read from `public_id` + `resolution_method` ONLY (never `resolved_team_id`):
  - not-resolved: `public_id NULL AND resolution_method NULL` (the auto-ladder's pending row).
  - resolved-positive: `public_id NOT NULL`, `resolution_method` in `progenitor` / `search` / `operator`.
  - resolved-negative / no-presence: `public_id NULL AND resolution_method='no_presence'` -- **operator-declared ONLY** via `map-opponent --no-presence`; the auto-ladder NEVER writes this.
  - Resolve-once per owning team: `UNIQUE(our_team_id, root_team_id)` (one real opponent faced by several LSB teams needs one mapping per team).
  - **Terminality gate keys on `resolution_method IS NOT NULL`, NEVER on `public_id`**: a `no_presence` row has `public_id` NULL, so a public_id-based gate would re-queue it every run -- the resurrection bug. The gate short-circuits any row whose `resolution_method IS NOT NULL` (covers both resolved-positive AND operator-declared `no_presence`).
  - Shared method constants live in `src/gamechanger/opponent_ladder.py` (`METHOD_PROGENITOR` / `METHOD_SEARCH` / `METHOD_OPERATOR` / `METHOD_NO_PRESENCE`) -- code MUST NOT inline the string literals.

## Data-Bearing Coverage (the scored-but-empty-game trap)

Any "coverage / freshness / how-many-games-do-we-have" signal MUST be **data-bearing** — derived from an `EXISTS` on per-game stat rows, NEVER a bare `COUNT(*)` of completed `games` rows.

- **The trap**: a completed `games` row can exist with ZERO player stat rows. `GameLoader` writes the games row + final scores UNCONDITIONALLY (scores come from the schedule summary), but loads `player_game_batting` / `player_game_pitching` rows only CONDITIONALLY (when the boxscore carries lineup/pitching groups). A scouted opponent commonly has a public final score but no GameChanger scorebook — so **scored-but-empty games are the MODAL scouting case**, not an edge case. A bare count of scored games overstates coverage AND lets a "no completed games" gate (N==0) miss a report whose games have scores but no stats — a silent empty report.
- **The canonical shape**: `src/reports/generator.py::_query_freshness` returns `(most_recent_game_date, N)` where N (`completed_games_with_data`) counts completed games with at least one stat row from THIS team's perspective (`perspective_team_id = team_id`, per the perspective-provenance invariant) via `EXISTS` on `player_game_batting`/`player_game_pitching`. The "Through {date}" freshness date is the MAX over the SAME data-bearing set — it anchors to the last game we have PLAYER DATA for, not a later scored-but-empty one.
- **Coach principle**: one honest count + one honest date everywhere. Two different game numbers on a report erode trust under pre-game pressure. Any new coverage/completeness/trust metric MUST be data-bearing and consistent with `_query_freshness`, not a fresh bare-games count.
- **Load-status corollary**: the report-stage status classifier is the run-record mirror of this trap — a scored-but-empty game (zero stat rows, zero errors) classifies as `completed` (not `partial`), and plays/spray coverage shortfalls are never `partial` because a missing scorebook is the modal case, not an error. See `.claude/rules/architecture-subsystems.md` (Report-stage status honesty).
- **Rate-stat denominator corollary (E-245)**: the same data-bearing principle gates pitch-detail rate stats — FPS% / P-PA / P-BF use a **charted-PA (`pitch_count > 0`) denominator** so an un-charted PA (which has no recorded first pitch) is not silently counted as a non-strike; QAB% deliberately keeps an all-PA denominator. This is an un-charted-PA exclusion, NOT an outcome exclusion. See `.claude/rules/key-metrics.md` (FPS%) for the full wording.

## Concurrent Team INSERT Recovery

`teams` has partial UNIQUE indexes on `gc_uuid` / `public_id` (`WHERE ... NOT NULL`) but NONE on `name`. Under the cross-process boundary (admin-UI + CLI + future cron on one SQLite file), a concurrent process can commit the same anchor between this call's cascade SELECT and its INSERT, tripping the partial UNIQUE index with an `IntegrityError`. The canonical insert path (`ensure_team_row_with_provenance`, `src/db/teams.py`) catches it and re-enters the cascade ONCE (`_insert_retry` flag) so the now-committed racing row resolves through the normal MATCH path — applying the same gc_uuid/public_id/name/season backfills a match would, not a bare id lookup — and returns `inserted=False`. The single-retry flag bounds re-entry (no infinite loop if the racing row vanishes again; a second collision without a match re-raises). Name-only inserts have no UNIQUE index on name and never reach this branch. New team-INSERT paths that bypass the canonical helper would lose this recovery.

## Seasons Row: Multi-Writer Agreement + Derived-vs-Seeded FK (E-241)

Two footguns around the `seasons` natural-key row and the year-only `season_id`:

- **Two writers, `ON CONFLICT(...) DO NOTHING`, first-writer-wins is SILENT (durable principle).** When two paths INSERT the same natural-key row with `DO NOTHING`, they MUST agree on ALL non-key columns: the first writer's values win and the second's are silently discarded — divergence is masked, not raised. *(Historical instance, now moot.)* E-241 surfaced this on the `seasons` table — a scouted opponent's row was written by both the scouting crawler's private `_ensure_season_row` and the canonical `ensure_season_row`, diverging on `season_type`. That specific instance no longer exists: E-250-02 dropped `seasons.season_type` and folded the crawler's private insert into the canonical `ensure_season_row`, leaving a single season-writer path. The general principle still binds any future multi-writer `DO NOTHING` insert.
- **A seeded compound/opaque `season_id` literal in a test is NOT automatically format-invariant.** If a test drives a LOADER that DERIVES the `season_id` from team metadata (`derive_season_id_for_team`, now year-only), the derived value must MATCH the seeded `seasons`/parent row or the insert hits a silent `FOREIGN KEY constraint failed`. E-241-06's recon missed this in `tests/test_game_start_time.py` (a compound seed survived a grep but broke once the loader derived year-only); the Phase-4b Codex pass + full-suite gate caught it. **Durable lesson** for any future season-format change: a grep-only "which test files seed the slug" recon is insufficient — only running the FULL suite proves which seeds are truly format-invariant.

## Single-Use Token Consume (DELETE-is-the-arbiter)

A DB-backed single-use token/nonce (passkey challenge in `webauthn_challenges`, magic-link token, session) is **NOT replay-proof if you read-then-verify-then-delete as separate steps and ignore the DELETE's rowcount**. Under the same cross-process boundary (multiple uvicorn workers + CLI on one SQLite file), two workers can both pass the non-atomic read/verify gate inside the TOCTOU window and both proceed -- a replay.

The fix is to make the **DELETE the atomic arbiter**: the consume helper returns `cursor.rowcount`, and the caller gates the privileged action (e.g. session creation) on `rowcount == 1`, treating `0` as "already consumed -> reject". SQLite's single-writer WAL serializes the racing DELETEs, so exactly one commits with rowcount 1 and the loser matches no row and gets 0. The earlier read (`get_challenge`'s live-row gate) is therefore only advisory -- the DELETE is the real gate. Canonical implementation: `consume_challenge()` in `src/api/passkey_challenges.py` (the login verify path in `src/api/routes/auth.py` gates on its return; E-238-06). New DB-backed single-use-token paths MUST gate on the consume rowcount, not on a prior read.
