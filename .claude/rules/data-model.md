# Data Model

The schema is defined in `migrations/001_initial_schema.sql` (base) with incremental migrations layered on top (run `ls migrations/*.sql` for the live set; see `.claude/rules/migrations.md` for numbering). Key design decisions:

- **Programs**: Umbrella entity grouping teams under an organizational program (e.g., `lsb-hs` = Lincoln Standing Bear HS). Types: `hs`, `usssa`, `legion`.
- **Teams**: INTEGER PRIMARY KEY AUTOINCREMENT (`teams.id`). External GC identifiers live in dedicated UNIQUE columns: `gc_uuid` (authenticated API) and `public_id` (public URL slug). All FK references to teams use `teams(id)`. INTEGER PK applies to `teams` only -- programs, seasons, and players keep TEXT PKs.
- **Membership type**: `teams.membership_type` (`member` or `tracked`). Member teams are those the operator manages in GameChanger; tracked teams are opponents or other teams added for scouting.
- **Season year**: `teams.season_year INTEGER` -- the year this team belongs to, populated from GameChanger API (`season_year` on authenticated endpoints, `team_season.year` on public). NULL falls back to current calendar year in `get_team_year_map()`. Self-healed by pipeline on sync. **Footgun**: stub team auto-creation (in roster/season_stats loaders) must pass `season_year` to `ensure_team_row()` to avoid the current-year fallback producing wrong values for historical data.
- **ERA basis**: `teams.innings_per_game INTEGER` (migration `012`, E-264) -- GameChanger's per-team-season regulation game length (observed 6 or 7), read from `settings.scorekeeping.bats.innings_per_game` on `GET /teams/{gc_uuid}`. It is the game-length basis GC uses to compute ERA (`ERA = innings_per_game x ER / IP`, via `era_basis_innings()` in `src/api/helpers.py`; also rescales the K-per-game display). Self-healed like `season_year` -- `ensure_team_row(innings_per_game=...)` on report regeneration is NULL-safe and never clobbers a stored int. **NULL is load-bearing provenance**: NULL = never fetched -> ERA computed on the assumed 7-inning fallback (`DEFAULT_ERA_BASIS_INNINGS`) AND the report flags "(assumed)"; a stored integer = fetched, shown without the flag. **Hard invariant**: never add a DEFAULT or NOT NULL, and never blindly backfill NULL->value -- either would silently erase the assumed-vs-fetched distinction the display disclosure depends on.
- **Classification**: `teams.classification` column. Valid values: `varsity`, `jv`, `freshman`, `reserve` (HS); `8U`-`14U` (USSSA); `legion`.
- **TeamRef pattern**: Pipeline code uses a `TeamRef` dataclass (`id: int`, `gc_uuid: str | None`, `public_id: str | None`). `.id` for all DB operations; `.gc_uuid` / `.public_id` for API calls. Tracked teams may have `gc_uuid=None`.
- **Game ordering convention**: Every `ORDER BY game_date` MUST include `start_time` as a same-direction tiebreaker with `NULLS LAST` (e.g., `ORDER BY game_date DESC, start_time DESC NULLS LAST`). Doubleheaders, rescheduled games, and multi-site days all produce same-date collisions that `game_date` alone cannot resolve. For game boxscore pitching lines, additionally sort by `appearance_order ASC NULLS LAST` (starter first, then relievers in order).
- **Appearance order**: `player_game_pitching.appearance_order INTEGER` (base schema, `001_initial_schema.sql`). Value 1 = starter, 2+ = relievers in order of entry. NULL = unknown (not zero -- zero is not a valid appearance order). Populated by the game loader from boxscore JSON pitcher ordering (the `stats` array under each team's pitching group is ordered by appearance). Scouting aggregation computes GS as `COUNT(*) WHERE appearance_order = 1` using a NULL-safe CASE expression (NULL `appearance_order` contributes 0, not NULL).
- **Game status values**: Completed games use `status = 'completed'` (not `'final'`); `game_loader.py` inserts with that value. Never use `'final'` in a game query. **A query selecting a SET of games to analyze or display SHOULD filter on `'completed'`** -- but treat that as the convention it is, not as a census. It is not one: several live report queries deliberately gate on `home_score IS NOT NULL AND away_score IS NOT NULL` instead, and by-`game_id` lookups, merges and deletes carry no status predicate at all. (Until E-278 this line read *"All queries across `src/` filter on `'completed'`"*. That absolute was never true, and it RECRUITED -- it named "add the filter" as the remedy for a query where declining the filter was a recorded decision.)
- **`_query_record` carries NO status filter, deliberately** (`src/reports/generator.py` -- the win-loss-tie record). E-278-01's AC-6 established the question three independent ways and DECLINED the guard: its cost and its benefit rest on the SAME unaudited population of legacy rows, and adding an unauditable filter to a coach-facing number whose failure mode is silent deletion is not a change to make against an unmeasured population. **The full reasoning -- including what would legitimately reopen it -- lives in that function's docstring; read it before "fixing" the query.** Settled on current grounds, not closed permanently: a later reader who adds the filter with reasons is making a choice, not correcting an oversight.
- **Game time data ownership**: The schedule loader is authoritative for `game_date` and `start_time` -- it writes directly (no COALESCE). The game loader (game-summaries) lacks time data and uses `COALESCE(existing, new)` to preserve values already set by the schedule loader. Do not add COALESCE to schedule loader time columns; do not remove COALESCE from game loader time columns.
- **7-day rolling window**: For inclusive 7-calendar-day windows, use `date(ref, '-6 days')` (NOT `-7` which creates an 8-day window). Example: games from Mar 28 through Apr 3 inclusive = `WHERE game_date >= date('2026-04-03', '-6 days')`.
- **Enriched stat columns** (schema-ready, not yet populated): `game_stream_id` on games (links to game-streams endpoints like `GET /game-streams/{game_stream_id}/events`; NOT a path parameter for game-stream-processing endpoints -- `event_id` from game-summaries is the path parameter for both `GET /game-stream-processing/{event_id}/boxscore` and `GET /game-stream-processing/{event_id}/plays`; the game loader indexes summaries by both `event_id` and `game_stream_id` for robust file matching), `bats`/`throws` on players, home/away and vs-LHP/RHP split columns on season batting/pitching, `pitches`/`total_strikes` on game pitching, `batting_order`/`positions_played`/`is_primary` on game batting, `stat_completeness` tracking on all stat tables.
- **Plays and play events**: Two-table schema (`plays` + `play_events`, created in `001_initial_schema.sql`). `plays` stores one row per plate appearance with batter/pitcher linkage, pitch count, outcome, and pre-computed boolean flags (`is_first_pitch_strike`, `is_qab`). `play_events` stores individual events within a PA (pitch results, baserunner events, substitutions). Idempotency keys: `UNIQUE(game_id, play_order)` on plays, `UNIQUE(play_id, event_order)` on play_events. **Whole-game idempotency**: before processing, check if any `plays` row exists for the `game_id` -- if yes, skip entirely. Never delete-and-reinsert (parent-child re-insertion problem: `INSERT OR IGNORE` on existing parent returns no `lastrowid` for children). This bars delete-and-reinsert as a LOAD strategy; it does not bar the E-267 game-grain retire, which deletes a removed game's full child surface (plays and their `play_events` included) with the `games` row LAST and reinserts nothing. Populated in-memory by the report generator's plays stage (`_crawl_and_load_plays` → `PlaysLoader.load_payload`). 24 confirmed outcome types; 486 `final_details` patterns (regex-parsed, not enumerable). The plays endpoint (`GET /game-stream-processing/{event_id}/plays`) is NOT ownership-gated -- works for opponent games too (unlike season-stats). `play_events` also carries nullable `pitch_type` (TEXT -- open vocabulary, deliberately no CHECK so it can grow) and `pitch_speed_mph` (INTEGER) columns (migration `007`), captured independently per event from the pitch-template annotation (a speed-only or type-only pitch leaves the other NULL). These are storage-only -- analysis is deferred (IDEA-086).
- **Plays-derived final score**: `game_perspectives.plays_final_home_score` / `plays_final_away_score` (nullable INTEGER, migration `013`) -- the game's final score as derived from the RAW plays payload, written by `PlaysLoader` per perspective. It exists because **the last parsed play is systematically short of the true final**: the game-ending run frequently lands on a play the parser SKIPS (an abandoned PA with empty `final_details`, or a `Runner Out` / `Inning Ended` marker), which is how walk-off and run-rule endings finish -- measured at 91 of 2,459 game-perspective units across 88 games, short 102 runs. So **never read a plays-derived final score off `MAX(play_order)`**; read this column. The seeding rule walks the raw payload backwards skipping INERT plays (empty `final_details` AND `did_score_change` false) and takes the first non-inert play's scores -- reading the RAW payload is what makes it immune to WHICH skip path fired. Three alternatives were tried against real payloads and rejected (last-raw-play zeroes every game on the trailing 0/0 phantom; non-empty-`final_details` cannot separate carrier from phantom; `max()` latches onto scorekeeper-rescinded runs); `PlaysParser._derive_final_score`'s docstring holds the evidence -- read it before "simplifying" the walk. **Grain is `game_perspectives`, NOT `games`**, deliberately: two perspectives of one game genuinely disagree (verified live: `8-7` under one, `10-7` under the other), so a game-level column would be last-writer-wins and would manufacture a false discrepancy. **NULL is load-bearing provenance** -- NULL = not yet derived (a row written before migration 013, or a payload with no plays / only inert plays / no score keys), and a DEFAULT or a blind 0 backfill would be indistinguishable from a real 0-0 final. Same hard invariant as `teams.innings_per_game`. Existing rows do NOT self-heal on regeneration (whole-game plays idempotency skips any game that already has plays); repair is a deliberate re-scout. The loader logs a WARNING when the derived final disagrees with the `games` row -- that is the standing detector for the two legitimate-disagreement classes (two scorebooks kept separately; a scorekeeper who abandoned charting mid-game), so a warning is not by itself a defect.
- **Spray charts**: `spray_charts` table stores ball-in-play coordinate data (x/y, play type, result, fielder position). Populated in-memory by the report generator's spray stage (`ScoutingSprayChartCrawler` → `ScoutingSprayChartLoader`). Idempotency key: `UNIQUE(event_gc_id, perspective_team_id, chart_type)` (migration `009_spray_chart_type_unique.sql`, E-253-02). Before E-253-02 the UNIQUE omitted `chart_type`, so the second chart type written for a game collided with the first and was silently dropped as an idempotent skip -- in practice this dropped 100% of defensive rows, and any "~16% of games have defensive data" figure was an artifact of that drop, not a real coverage rate. With the widened UNIQUE, offensive and defensive rows coexist and defensive coverage self-heals on the next report regeneration. Data quality: spray data is scorekeeper-dependent (~93% of games have offensive data; defensive coverage is likewise scorekeeper-dependent but is no longer measurable from historical rows given the pre-migration drop); `spray_chart_data` is `null` (not empty array) when the scorekeeper did not record. Display thresholds: 3 BIP minimum for per-player charts, 20 BIP for team aggregates.
- **Cross-perspective player UUIDs**: GameChanger returns different `player_id` UUIDs for the same human depending on which team's boxscore is viewed. This is a permanent API property, not a bug. When team A's boxscore lists team B's players, it uses different UUIDs (and often initial-only first names) than team B's own boxscore. All agents working with player data must account for this -- never assume `player_id` is globally unique per human. Same-team duplicates are detected by prefix-matching first names with matching last names on the same roster. See `.claude/rules/perspective-provenance.md` for the perspective tagging invariant and field classification table.
- **Empty `bb db reset`**: `bb db reset` (`src/db/reset.py`) produces an EMPTY database — migrations plus the `programs` `lsb-hs` bootstrap row from migration 001 only. There is NO seed/sample data (`seed_dev.sql` and `scripts/seed_dev.py` were removed in E-228). Operators populate real data afterward by generating reports (`bb report generate` or `/admin/reports`). Do not assume reset yields demo data when reasoning about DB state or writing tests.
- **`gc_athlete_profile_id` (dropped, E-250-02)**: The `players.gc_athlete_profile_id` column was removed in migration 008. It was never populated and had been reserved as the cross-team athlete-identity anchor for E-104 (athlete-profile endpoint); E-104 is now abandoned (E-250-07) and cross-team player identity is an explicit Non-Goal. Do not reintroduce the column or assume athlete-profile linkage exists.
- **Player dedup merge-every-run cycle**: The post-load dedup sweep in the scouting pipeline re-detects and re-merges duplicate player pairs on every run. Perspective tagging (E-220) reduces cross-perspective stub creation by isolating each perspective's data, but does not eliminate it entirely -- the plays loader still creates player stubs via `ensure_player_row()`. The dedup sweep remains necessary for both residual cross-perspective cleanup and genuine name-variant dedup (e.g., "O" vs "Oliver").
- **Plays pipeline dedup gap**: The plays stage of report generation is not wired into the post-load dedup sweep that `bb data dedup-players` performs. Perspective-scoped idempotency (`WHERE game_id = ? AND perspective_team_id = ?`) prevents cross-perspective play collisions -- each perspective's plays are isolated. Cross-perspective player stubs introduced by plays data are cleaned up by a subsequent `bb data dedup-players --execute` run.
- **Dead-by-descope, retained by decision (E-239)**: `crawl_jobs` and `coaching_assignments` have NO INSERT/UPDATE writers anywhere in `src/` -- E-239's reports-first descope removed the crawl-scheduling and coaching-assignment surfaces that populated them. They are kept deliberately, not by oversight: the cascade-delete cleanup in `lifecycle.py`/`reports_admin.py` still references them defensively, so re-adding either surface needs no migration. This retention is intentional; do not sweep them as "unused." **`user_team_access` is NOT in this set -- it is LIVE** (the non-admin team-access grant mechanism, with active INSERT writers in `auth.py` and `reports_admin.py`); never mark it dead.

## Cleanup-Detection Mirror Invariant

When extending a cleanup helper's surface (adding a new table to a DELETE cascade, broadening a WHERE clause, adding a new row-deletion pass), you MUST audit every detection/gate query that mirrors the cleanup surface and update it in the same change. Detection queries include informed-consent gates, precondition checks, row-count probes, and any query that enumerates "what this delete will affect" to the operator.

**Why**: A perspective-aware cleanup gap let foreign-owned data bypass the informed-consent gate and silently delete — the canonical cascade grew to cover a new table but the gate query didn't, so a team with only that table's cross-perspective footprint walked through an empty warning screen and wiped data belonging to other perspectives.

**Concrete example**: `src/reports/lifecycle.py::_delete_team_anchor_and_orphan_data` deletes five stat tables (`player_game_batting`, `player_game_pitching`, `spray_charts`, `plays`, `reconciliation_discrepancies`). Historically the admin delete-team flow carried an informed-consent gate (`_get_delete_confirmation_data`'s `cross_persp_rows` UNION) that mirrored this cleanup surface; that gate was removed in E-239 along with the admin team-management UI. The principle still binds forward: if any future detection/gate query is added over this cleanup (e.g., a report-delete confirmation), it MUST enumerate the same tables with the `team_id = T AND perspective_team_id != T` shape, and grow with the cascade in the same commit.

**How to apply**: Any PR that modifies a DELETE statement, a cascade helper, or a cleanup pass in `src/reports/`, `src/db/`, or `src/api/` must grep for mirror queries (look for `COUNT(*)` / `SELECT ... WHERE team_id` / UNION shapes referencing the same table) and update them in lock-step. Code review checklist item: "Did the cleanup surface change? If yes, were all mirror queries updated?"

## Season Aggregates (query-time; parity apparatus retired E-259)

The stored season-aggregate tables (`player_season_batting` / `player_season_pitching`) and their entire parity/recompute apparatus (`canonical_recompute`, `src/reports/aggregate_parity.py`, `bb report verify-aggregates`, the `BATTING`/`PITCHING_RECOMPUTE_KEYS`-derived diff-column single-source guard, and the E-237 mixed-provenance/E-247 twin-method footguns that protected them) were **retired in E-259** (migration 011 dropped both tables). Season totals are now derived at query time from `player_game_*` by `get_season_batting` / `get_season_pitching` (`src/api/db.py`). There is no stored aggregate to drift against, so **no aggregate-integrity gate remains** — the aggregate IS the query. (Provenance is likewise moot: no `full`/`supplemented` writer survived E-239, so every derived row is `boxscore_only`.)

The one invariant that SURVIVES the cutover is the **perspective filter**: a query-time season sum MUST scope by `perspective_team_id`, or it double-counts a game loaded from two perspectives (`get_season_batting`/`get_season_pitching` carry `WHERE perspective_team_id = ?`). This was the #1 cutover hazard — see `.claude/rules/perspective-provenance.md` (MUST-constraint 3).

## Player Dedup: Components, Fork Refusal, Transaction Ownership (E-249)

Same-team duplicate players are deduped by ONE shared planner (`plan_player_dedup` + `execute_collapse`, `src/db/player_dedup.py`) consumed by both the load-path sweep (`dedup_team_players`) and the CLI (`bb data dedup-players`) -- "de-dup the dedup." Durable invariants/footguns:

- **Components are per-`(team_id, season_id)`.** The detection self-join AND `plan_player_dedup` MUST partition connected components by `(team_id, season_id)`. Keying by `team_id` alone unions prefix-pairs ACROSS seasons and mis-plans merges on the unscoped CLI path (the E-249 Codex P1). Any future dedup change MUST preserve the per-season partition.
- **Fork refusal ("refuse, don't guess").** A component whose maximal members carry ≥2 DISTINCT names (a fork) is REFUSED, not merged: prefix matching alone cannot tell one human (Jo/John/Jon) from two (O/Oliver/Owen) -- only same-game co-occurrence carries that signal (deferred to Tier 2, IDEA-089). Equal-named maximal members (same name, two UUIDs) still collapse.
- **There are TWO refusal classes on `DedupPlan`, and reading one is reading half.** `refused_forks` (above) plus `refused_conflicts` (2026-08-12): a component whose members hold rows for the SAME `(game_id, perspective_team_id)` whose CONTENT differs, which a merge could only resolve by deleting a real observation. Any consumer asking "did the planner decline anything?" MUST read both — the `if not plan.collapses and not plan.refused_forks` shape reports a refused component as "0 duplicates found". Compared over ALL unordered member pairs, not canonical-vs-each-duplicate: `execute_collapse` merges sequentially, so a collision can first appear against a row that arrived from an earlier duplicate. Content is defined by EXCLUSION — every column of `player_game_batting`/`player_game_pitching` except `id`/`game_id`/`player_id`/`team_id`/`perspective_team_id`, derived from `PRAGMA table_info` so a new stat column joins automatically (a hand-listed column set on a merge path is what silently dropped two columns from `merge_duplicate_game`). Deliberately NOT `team_rosters` (a jersey/position difference is not a lost observation, and counting it refuses ~2.6× more) and NOT `reconciliation_discrepancies` (derived, regenerated on re-run). ⚠️ `team_id` IS compared, and reads like a key column while not being one — it is absent from that UNIQUE, so two colliding rows can disagree on it and the delete would discard participant-team attribution. That is the single column an exclusion-based definition gets wrong by default. **A refusal is a DEFERRAL, not a fix**: on an opponent block whose re-issued line disagrees, the refusal hands the deletion back to the player-line grain's accumulate-then-delete window (operator-ruled, IDEA-185) rather than preventing it — pinned by `test_the_content_refusal_leaves_regime_B_open_on_a_DIFFERING_opponent_line`.
- **The `PLACEHOLDER_NAME` stub is excluded from DETECTION, and fork refusal structurally cannot cover it.** `"Unknown"` (`src/db/players.py`) marks ABSENT identity, so two ids carrying it fold to IDENTICAL names, form a SINGLE-terminal-name component, and collapse — while fork refusal fires only on ≥2 DISTINCT names. **"Zero refused forks" is what that hazard looks like, not evidence of safety.** Measured: two `Unknown Unknown` ids in one game under one perspective were two different pitchers, and the conflict-delete would have destroyed one appearance. The guard is on the FIRST name only (the component prefix matching draws identity from) and is scoped to that exact stub value, not a "looks like a placeholder" heuristic. **Mirror obligation**: `reconcile_at_load._dedup_candidate_victims` must carry the same exclusion in its NAME half — its whole claim is that a victim looks like a pair `bb data dedup-players` would merge, so an unmirrored guard makes it name pairs that instrument cannot act on (the blank-name false positive, one dimension over). Its jersey half is a deliberate over-name and stays.
- **The load-path sweep covers every team the load WROTE, not just the scouted one** (2026-08-12). `GameLoader._upsert_roster_jersey` creates `team_rosters` rows for BOTH sides of every boxscore, so a scouted-team-only sweep let an opponent-side write re-split an identity a previous run collapsed — and league play is cyclic, so **no generation order converged**. `GameLoader.rostered_team_ids` records the touched set; `ScoutingLoader` loops it with the **SCOUTED TEAM FIRST**, which is load-bearing: `_pending_collapse_player_ids` already exempted that team's pending-collapse ids from the roster retire, and its `P1 ⊆ P2` argument breaks if an opponent merge runs first, because `merge_player_pair` re-points `team_rosters` GLOBALLY and can add a node that turns a P1 collapse into a refused fork. Opponents dedup under the SCOUTED team's `season_id` (the season their rows were written under). One SAVEPOINT + `try/except` PER TEAM, so one opponent's transient failure neither skips the rest nor rides the single `commit()` below it. ⚠️ A bare `rollback()` is the WRONG remedy at this seam even though the shared-connection partial-commit footgun (`.claude/rules/architecture-subsystems.md`) prescribes one: that rule addresses a loop with a per-item COMMIT, and here a rollback would discard the whole transaction — both reconcile grains' pending retires AND every opponent already merged this run — to contain one team's failure. **Known limit at season rollover**: an opponent that accrues roster rows in two seasons cannot be merged across them by season-scoped dedup.
- **Per-component transaction ownership.** `execute_collapse` owns the per-component transaction/savepoint and calls `merge_player_pair(manage_transaction=False)`. `manage_transaction=True` self-commits per merge and CANNOT nest under an outer per-component BEGIN -- do not pass it from the component executor.
- **CLI default-isolation commit footgun.** The CLI's sqlite connection uses default (legacy) isolation, which ROLLS BACK uncommitted DML on close. Any standalone DML on that connection (e.g. the dedup merge that re-points `player_game_*` rows) MUST be followed by an explicit `conn.commit()` or it is silently discarded.
- **Player dedup is season-scoped (E-250-01).** `bb data dedup-players` requires a `season_id` and auto-derives it (the sole season when exactly one exists; no-op on zero; explicit `--season-id` required when 2+ seasons are present). There is no unscoped cross-season execute path -- every merge is partitioned by `(team_id, season_id)`, and the load-path sweep is likewise always season-scoped. Cross-season player identity is an explicit Non-Goal.

## Scheduled-Report Audit + Opponent Resolution (E-240)

The morning-run scheduler (`bb report morning-run`) adds an audit table and revives a dormant mapping table. Both feed the opponent-resolution ladder (`src/gamechanger/opponent_ladder.py`).

- **`scheduled_report_runs` (migration 005)**: one AUDIT row per scheduled opponent slot the morning run processes -- it records EVERY slot and its outcome, including unresolved / no-GC-presence / deferred slots that produced NO report (`report_generation_runs` cannot represent these: it is 1:1 NOT NULL `report_id` with a produced report). Key columns:
  - `resolution_outcome` (CHECK, NOT NULL): `auto_resolved` (a report was attempted) / `unresolved_mappable` (on GC, not auto-matched -> operator queue) / `no_gc_presence` (operator-declared via `map-opponent --no-presence`) / `deferred_placeholder` (TBD/Winner/Seed... re-polled near game time).
  - `delivery_status` (CHECK, NULLABLE): non-NULL ONLY when generation was attempted (an `auto_resolved` slot) -- `generated` / `no_games` / `failed` / `skipped`. NULL = generation not attempted; `resolution_outcome` carries the reason.
  - `report_id` FK `reports(id)` **ON DELETE SET NULL** -- the audit row MUST OUTLIVE report cleanup/expiry. This is the DELIBERATE MIRROR-IMAGE of `report_generation_runs.report_id` ON DELETE CASCADE (E-235): the per-generation run row dies with its report, but a scheduled-run row is an audit record that survives. `report_slug` is a frozen-string fallback so the trail still names the report after the FK is nulled. Do NOT copy the CASCADE pattern here.
  - `opponent_root_team_id` TEXT, **NO FK** -- the GC `root_team_id` registry namespace, an opaque GC token, NEVER a `gc_uuid` (storing `root_team_id` in a `gc_uuid` column is the documented namespace error in CLAUDE.md "Opponent entry duality").
  - In the team-deletion cascade: `_delete_team_scoped_data` (`src/reports/lifecycle.py`) deletes `scheduled_report_runs WHERE own_team_id IN (...)` (team deletion REMOVES the audit rows -- distinct from report deletion, which only NULLs `report_id`). Per the Cleanup-Detection Mirror Invariant above.
  - **A THIRD team deleter exists, and it decides differently**: `reclaim_orphan_reference_data` (`src/reports/lifecycle.py`, E-273) INFERS unreachability, where `cascade_delete_team` and `cleanup_orphan_teams` act on a decision already made. The difference is readable off the signatures: those two RECEIVE their target (`team_id`, `orphan_ids`), while `reclaim_orphan_reference_data(conn)` COMPUTES its own orphan set from `_team_orphan_pred`. Since E-277-01 a `scheduled_report_runs` row is a reachability ROOT for its own team, so a team carrying one is EXCLUDED from that orphan set and is never deleted by the sweep. **It roots its OWN team only and confers nothing on the opponent** -- the opponent is identified by `opponent_root_team_id`, the opaque GC token above, which carries no `teams(id)` FK and therefore cannot root anything.
  - **The two statements above are not in tension, and both are needed**: the root blocks an INFERRED deletion; it does NOT block a DELIBERATE one, which still removes the audit rows exactly as the cascade bullet and migration 005 require. Read alone, the root would wrongly say "a team with a scheduled run cannot be deleted."
- **Idempotency NULL footgun**: `UNIQUE(own_team_id, opponent_root_team_id, game_date)`. SQLite treats NULLs as DISTINCT in UNIQUE indexes, so a NULL in any of the three key columns silently breaks idempotency (a re-run duplicates the slot instead of UPSERTing it). The loader MUST guarantee a non-NULL key on all three columns -- `morning_run` falls back to an `unknown-{event_id}` token when `opponent_root_team_id` would be NULL.
- **`opponent_links` revival** (no new DDL -- migration 001 already has the shape): now the `root_team_id -> public_id` mapping store. The three states are read from `public_id` + `resolution_method` ONLY (never `resolved_team_id`):
  - not-resolved: `public_id NULL AND resolution_method NULL` (the auto-ladder's pending row).
  - resolved-positive: `public_id NOT NULL`, `resolution_method` in `progenitor` / `search` / `operator`.
  - resolved-negative / no-presence: `public_id NULL AND resolution_method='no_presence'` -- **operator-declared ONLY** via `map-opponent --no-presence`; the auto-ladder NEVER writes this.
  - Resolve-once per owning team: `UNIQUE(our_team_id, root_team_id)` (one real opponent faced by several LSB teams needs one mapping per team).
  - **Terminality gate keys on `resolution_method IS NOT NULL`, NEVER on `public_id`**: a `no_presence` row has `public_id` NULL, so a public_id-based gate would re-queue it every run -- the resurrection bug. The gate short-circuits any row whose `resolution_method IS NOT NULL` (covers both resolved-positive AND operator-declared `no_presence`).
  - **TWO predicates read this column, and they DIVERGED deliberately (2026-08-05) -- do not "align" them.** The ladder's terminality gate above answers *what does the LADDER re-attempt* (nothing with a method) and is unchanged. `bb report map-opponent`'s eligibility predicate (`src/cli/report.py::_apply_opponent_mapping`) answers a different question -- *what may an OPERATOR correct* -- and is `resolution_method IS NULL OR resolution_method = 'search'`: a pending row, plus a rung-(c) auto-resolution, which is the one method that auto-accepts with no NAME corroboration and so can be confidently wrong. (Since 2026-08-09 rung (c) DOES require a season-year match — that closed the cross-YEAR wrong-team mode, but a same-year name-alike still auto-accepts, so this predicate's reason for existing is unchanged. Do not read the season filter as making `search` rows trustworthy.) Making either predicate match the other is a bug in both directions: widening the GATE would re-resolve every opponent every run, and widening MAP-OPPONENT to `IS NOT NULL` would resurrect a `no_presence` row. ⚠ The map-opponent predicate's parentheses are load-bearing -- `AND` binds tighter than `OR`, so dropping them makes the statement match every `search` row in the table regardless of `root_team_id`.
  - Shared method constants live in `src/gamechanger/opponent_ladder.py` (`METHOD_PROGENITOR` / `METHOD_SEARCH` / `METHOD_OPERATOR` / `METHOD_NO_PRESENCE`) -- code MUST NOT inline the string literals.

## Data-Bearing Coverage (the scored-but-empty-game trap)

Any "coverage / freshness / how-many-games-do-we-have" signal MUST be **data-bearing** — derived from an `EXISTS` on per-game stat rows, NEVER a bare `COUNT(*)` of completed `games` rows.

- **The trap**: a completed `games` row can exist with ZERO player stat rows. `GameLoader` writes the games row + final scores UNCONDITIONALLY (scores come from the schedule summary), but loads `player_game_batting` / `player_game_pitching` rows only CONDITIONALLY (when the boxscore carries lineup/pitching groups). A scouted opponent commonly has a public final score but no GameChanger scorebook — so **scored-but-empty games are the MODAL scouting case**, not an edge case. A bare count of scored games overstates coverage AND lets a "no completed games" gate (N==0) miss a report whose games have scores but no stats — a silent empty report.
- **The canonical shape**: `src/reports/generator.py::_query_freshness` returns `(most_recent_game_date, N)` where N (`completed_games_with_data`) counts completed games with at least one stat row from THIS team's perspective (`perspective_team_id = team_id`, per the perspective-provenance invariant) via `EXISTS` on `player_game_batting`/`player_game_pitching`. The "Through {date}" freshness date is the MAX over the SAME data-bearing set — it anchors to the last game we have PLAYER DATA for, not a later scored-but-empty one.
- **Coach principle**: one honest count + one honest date everywhere. Two different game numbers on a report erode trust under pre-game pressure. Any new coverage/completeness/trust metric MUST be data-bearing and consistent with `_query_freshness`, not a fresh bare-games count.
- **Load-status corollary**: the report-stage status classifier is the run-record mirror of this trap — a scored-but-empty game (zero stat rows, zero errors) classifies as `completed` (not `partial`), and plays/spray coverage shortfalls are never `partial` because a missing scorebook is the modal case, not an error. See `.claude/rules/architecture-subsystems.md` (Report-stage status honesty).
- **Rate-stat denominator corollary (E-245)**: the same data-bearing principle gates pitch-detail rate stats — FPS% / P-PA / P-BF use a **charted-PA (`pitch_count > 0`) denominator** so an un-charted PA (which has no recorded first pitch) is not silently counted as a non-strike; QAB% deliberately keeps an all-PA denominator. This is an un-charted-PA exclusion, NOT an outcome exclusion. See `.claude/rules/key-metrics.md` (FPS%) for the full wording.

## Concurrent Team INSERT Recovery

`teams` has partial UNIQUE indexes on `gc_uuid` / `public_id` (`WHERE ... NOT NULL`) but NONE on `name`. Under the cross-process boundary (admin-UI + CLI + future cron on one SQLite file), a concurrent process can commit the same anchor between this call's cascade SELECT and its INSERT, tripping the partial UNIQUE index with an `IntegrityError`. The canonical insert path (`ensure_team_row_with_provenance`, `src/db/teams.py`) catches it and re-enters the cascade ONCE (`_insert_retry` flag) so the now-committed racing row resolves through the normal MATCH path — applying the same gc_uuid/public_id/name/season backfills a match would, not a bare id lookup — and returns `inserted=False`. The single-retry flag bounds re-entry (no infinite loop if the racing row vanishes again; a second collision without a match re-raises). Name-only inserts have no UNIQUE index on name and never reach this branch. New team-INSERT paths that bypass the canonical helper would lose this recovery.

## Seasons Row: Multi-Writer Agreement + Derived-vs-Seeded FK (E-241)

Two footguns around the `seasons` natural-key row and the year-only `season_id`:

- **Two writers, `ON CONFLICT(...) DO NOTHING`, first-writer-wins is SILENT (durable principle).** When two paths INSERT the same natural-key row with `DO NOTHING`, they MUST agree on ALL non-key columns: the first writer's values win and the second's are silently discarded — divergence is masked, not raised. *(Historical instance, now moot.)* E-241 surfaced this on the `seasons` table — a scouted opponent's row was written by both the scouting crawler's private `_ensure_season_row` and the canonical `ensure_season_row`, diverging on `season_type`. That specific instance no longer exists: E-250-02 dropped `seasons.season_type` and folded the crawler's private insert into the canonical `ensure_season_row`, leaving a single season-writer path. The general principle still binds any future multi-writer `DO NOTHING` insert.
- **A seeded compound/opaque `season_id` literal in a test is NOT automatically format-invariant.** If a test drives a LOADER that DERIVES the `season_id` from team metadata (`derive_season_id_for_team`, now year-only), the derived value must MATCH the seeded `seasons`/parent row or the insert hits a silent `FOREIGN KEY constraint failed`. E-241-06's recon missed this in `tests/test_game_start_time.py` (a compound seed survived a grep but broke once the loader derived year-only); the Phase-4b Codex pass + full-suite gate caught it. **Durable lesson** for any future season-format change: a grep-only "which test files seed the slug" recon is insufficient — only running the FULL suite proves which seeds are truly format-invariant.

## Single-Use Token Consume (DELETE-is-the-arbiter)

A DB-backed single-use token/nonce (passkey challenge in `webauthn_challenges`, magic-link token, session) is **NOT replay-proof if you read-then-verify-then-delete as separate steps and ignore the DELETE's rowcount**. Under the same cross-process boundary (multiple uvicorn workers + CLI on one SQLite file), two workers can both pass the non-atomic read/verify gate inside the TOCTOU window and both proceed -- a replay.

The fix is to make the **DELETE the atomic arbiter**: the consume helper returns `cursor.rowcount`, and the caller gates the privileged action (e.g. session creation) on `rowcount == 1`, treating `0` as "already consumed -> reject". SQLite's single-writer WAL serializes the racing DELETEs, so exactly one commits with rowcount 1 and the loser matches no row and gets 0. The earlier read (`get_challenge`'s live-row gate) is therefore only advisory -- the DELETE is the real gate. Canonical implementation: `consume_challenge()` in `src/api/passkey_challenges.py` (the login verify path in `src/api/routes/auth.py` gates on its return; E-238-06). New DB-backed single-use-token paths MUST gate on the consume rowcount, not on a prior read.

**Consume on POST, never on a bare GET (E-254-02).** The rowcount-gated consume above MUST fire on a POST, not on a `GET`. A single-use token delivered in a link (magic-link verify) is fetched by mail-provider link scanners and browser prefetchers, which issue `GET`s — a side-effect-ful GET consume lets a scanner burn the token (operator lockout) and even receive a live session. The pattern is a side-effect-free GET interstitial (validate existence/expiry WITHOUT deleting or creating a session; render a form carrying the token in the POST body + the `csrf_token`) followed by the CSRF-protected POST that performs the atomic consume and issues the session. `verify_token` GET/POST in `src/api/routes/auth.py` is the canonical split. New link-delivered single-use-token flows MUST keep the GET safe/idempotent.

## Atomic Count Cap (single count-guarded INSERT)

An unauthenticated endpoint that INSERTs a row per call (e.g. `get_passkey_login_options` writing a `webauthn_challenges` `kind='login'` row) can be flooded within the row's TTL. A **count-then-insert** guard is a TOCTOU hole under the cross-process boundary: two connections both read `count < cap` and both insert, overshooting the cap. The fix is a **single count-guarded `INSERT ... SELECT ... WHERE (SELECT count(...) ) < :cap`** so the live-count check and the insert are ONE statement — SQLite's single-writer serialization makes the bound a true hard cap (at/over the cap zero rows insert; the endpoint returns 429). Keep the cap a module-level constant so a test can monkeypatch it small. Do NOT use a forwarded-IP header for the bound (proxy boundary). Canonical implementation: the `KIND_LOGIN` cap in the passkey-options path (E-254-03; scoped to `login` only — registration challenges are session-id-keyed UPSERTs, already bounded). New unauthenticated per-call INSERT paths that need a hard bound MUST use the atomic single-statement form, not count-then-insert.
