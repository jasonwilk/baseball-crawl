# Architecture Subsystems

Subsystem-specific implementation details. For general architecture principles and canonical MUST constraints, see CLAUDE.md's Architecture section.

## Scouting Pipeline

The scouting crawlers and loaders are driven in-memory by the report generator (`src/reports/generator.py`) -- there is no standalone scouting orchestrator. Five conceptual stages: (1) scouting crawl (`ScoutingCrawler` -- schedules, rosters, boxscores), (2) scouting load (`ScoutingLoader` -- load per-game boxscore rows; season totals are derived at query time, not stored, since E-259), (3) gc_uuid resolution (resolve `public_id` → `gc_uuid` via `POST /search` for spray chart access), (4) spray crawl (`ScoutingSprayChartCrawler`), (5) spray load (`ScoutingSprayChartLoader`). Source files: `src/gamechanger/crawlers/scouting.py`, `src/gamechanger/crawlers/scouting_spray.py`, `src/gamechanger/loaders/scouting_loader.py`, `src/gamechanger/loaders/scouting_spray_loader.py`.

**In-memory crawl-to-load**: Scouting crawlers return data in-memory (dataclasses/dicts) directly to loaders -- no disk intermediary (`data/raw/` files) for the scouting or spray stages. Game IDs come from crawl results, not filesystem globs. This eliminates stale-file contamination across runs. See `.claude/rules/perspective-provenance.md` for the full perspective tagging invariant.

## Canonical Team Creation (Detail)

`ensure_team_row()` in `src/db/teams.py` implements a deterministic dedup cascade: gc_uuid match → public_id match → name+season_year match (tracked only) → INSERT. A self-tracking guard prevents member teams from being re-created as tracked opponents. Back-fill rules are conservative: gc_uuid/public_id are NOT attached on name-only matches (step 3) to avoid irreversible misidentification.

## Canonical-Function Additive Extension Pattern

When a heavily-called canonical function needs to return MORE (provenance, fallback flags, telemetry) without churning its many call sites, add a sibling `*_with_provenance` variant that returns a small result dataclass, move the logic into the variant, and have the legacy function DELEGATE to it (returning the unchanged scalar). The cascade/derivation logic lives in exactly one place; existing callers are untouched. E-235 example: `ensure_team_row()` → `ensure_team_row_with_provenance()` returning `EnsureTeamResult(team_id, match_method, inserted)` (`src/db/teams.py`). New telemetry needs on a canonical function SHOULD use this additive-sibling shape rather than widening the legacy signature or duplicating the cascade.

## Canonical Team Deletion (Detail)

`src/reports/lifecycle.py` provides two consolidated deletion paths via common helpers `_delete_game_scoped_data_for_perspectives()` and `_delete_team_scoped_data()`: (1) `cascade_delete_team()` -- aggressive, deletes all games involving the team, used by report-deletion cleanup; (2) `cleanup_orphan_teams()` -- safe, only deletes games where the team is the sole participant, used during report generation to clean temporary data. `is_team_eligible_for_cleanup()` enforces 2 guard conditions (Guard 1: `is_active = 0`; Guard 2: no other `reports` row references the team) before any cascade.

## Season_id Derivation (Detail)

`derive_season_id_for_team(db, team_id)` in `src/gamechanger/loaders/__init__.py` returns `tuple[str, int | None]` -- `(season_id, season_year)`. The `season_id` is YEAR-ONLY: the team's `teams.season_year` as a string (e.g. `'2026'`), or the current year when `season_year` is NULL (`season_id = str(season_year or datetime.now().year)`). This **current-year fallback is the load-bearing kernel and SURVIVES** -- a missing `season_year` still yields a usable year-only `season_id`. **REMOVED (E-241)**: the `program_type` → suffix mapping (`hs` → `spring-hs`, `usssa` → `summer-usssa`, `legion` → `summer-legion`) and the `season_fallback` telemetry flag/chain -- there are no compound slugs and no fallback telemetry anymore; derivation is purely year-based. `ensure_season_row(db, season_id)` is the SOLE season-writer path -- E-250-02 folded the scouting crawler's private `_ensure_season_row` into it, so it now truly replaces all private `_ensure_season_row()` methods. (The `seasons.season_type` column was dropped in E-250-02, so there is no longer a `season_type` value to write.)

## Filesystem vs DB Season_id Decoupling

The filesystem path (`data/raw/{season}/scouting/{public_id}/`) organizes cached crawl files for discovery only; its season component is an OPAQUE organizational slug. The DB `season_id` column is data identity. These remain decoupled -- and the decoupling is a **live invariant a loader could violate**: loaders glob the season path component as an opaque literal (`season_glob = season_id if not None else "*"` in `scouting_spray_loader.py`) and MUST NEVER parse the DB `season_id` out of the directory name. They derive it independently from team metadata via `derive_season_id_for_team()` (now year-only). Because the on-disk slug and the DB `season_id` are produced separately, they MAY DIFFER: a LEGACY on-disk tree may carry a compound `data/raw/2025-spring-hs/...` directory (written before E-241) while the loaded DB rows are year-only `2025`. That divergence IS the decoupling, and it is exactly why a loader must never infer the DB `season_id` from the path. (Post-E-241 the scouting crawler's `_derive_season_id` is itself year-only and names BOTH the on-disk directory and the DB writes, so newly-written trees and DB rows agree -- but the glob-as-opaque-literal contract still binds because legacy compound trees persist on disk.) `scouting_runs.season_id` records the crawl directory's year-only slug (from `_derive_season_id`); it and the DB `season_id` are derived from different sources (earliest-game year vs. team metadata), so they normally agree but are not guaranteed identical.

## Chart Rendering

`src/charts/` package contains headless PNG rendering modules (matplotlib + numpy). Currently: `src/charts/spray.py` (spray chart renderer). Future chart types go in this package. Charts are rendered at report-generation time and embedded in the self-contained report HTML.

## Plays Pipeline

`src/gamechanger/parsers/plays_parser.py` (pure parser, no DB dependency) and `src/gamechanger/loaders/plays_loader.py` (DB writer). Plays are fetched in-memory by the report generator (`_crawl_and_load_plays` in `src/reports/generator.py`) and passed directly to `PlaysLoader.load_payload` -- there is no standalone plays crawler or CLI entry point. Parser/loader separation pattern: the parser is a pure function producing dataclasses from raw JSON, enabling unit testing without DB fixtures. The loader handles DB writes only. **Pitcher state tracking**: the parser maintains `current_pitcher_top` and `current_pitcher_bottom` state variables that persist across innings within the same half, updated on substitution events, with explicit pitcher references in `final_details` as ground truth override. **team_players keys**: each key is a `public_id` slug or a UUID, and the form does NOT mark which side it is -- both are slugs on a minority of payloads, and what decides the form is not established (a team with its own public GC presence can still be UUID-keyed, observed 2026-08-03). Any code that needs the own/opponent split must classify by identity, as `GameLoader._detect_team_keys` does. The plays path does not need it: `plays_parser.parse_game` never reads `team_players` at all (only its docstring names the key), and a consumer that did would build a flat lookup across both keys rather than splitting them.

**In-place offline plays repair (`reload_game_plays`, E-245)**: Already-loaded plays do NOT self-heal on report regen -- whole-game idempotency skips any game that already has `plays` rows (see `.claude/rules/data-model.md`). Historical repair of plays data is therefore an IN-PLACE re-derivation sourced from `play_events.raw_template` (the only DB copy of the annotated pitch text) -- NEVER a clear-and-re-ingest (clearing destroys `raw_template`) and NEVER `parse_game` (which needs unpersisted `final_details`). `reload_game_plays(conn, game_id, perspective_team_id)` in `src/gamechanger/loaders/plays_reload.py` is the canonical reusable per-game entry point: it re-reads home/away from the fresh `games` row and re-derives `batting_team_id` per half, re-classifies every `play_events` row from its `raw_template` (recovering stranded annotated pitches, populating `pitch_type`/`pitch_speed_mph`, re-deriving `is_first_pitch`), and recomputes the parent `plays` flags (`pitch_count`, `is_first_pitch_strike`, `is_qab`, `batting_team_id`). It does NOT commit (the caller owns the transaction boundary) and is idempotent. Future per-game plays re-derivations MUST reuse it rather than re-implementing the `raw_template` re-classification. The `is_qab` recompute is an OR-merge guarded by the forward `_QAB_EXCLUDED_OUTCOMES` (`plays_parser.py`) -- reuse that exclusion set; never run a from-scratch `_compute_qab` on reload. Operator entry points: `bb data reload-annotated-pitches` (batch re-derivation) and `bb data fix-self-games` (which calls `reload_game_plays` within its own self-game correction transaction).

**Shared-connection partial-commit footgun (multi-item CLI loops)**: A CLI/loader loop that processes many items on a SHARED `sqlite3.Connection` with a per-item `try/except` that catches-and-continues MUST call `conn.rollback()` in the `except` before moving to the next item. Otherwise the failed item's uncommitted partial writes stay pending on the connection and get silently committed by the NEXT successful item's `conn.commit()` -- corrupting data under the guise of a cleanly "skipped" failure. (Codex P1 on E-245's `fix-self-games`.) This binds every multi-item maintenance loop that shares one connection across items.

## Spray Chart Pipeline

`src/gamechanger/crawlers/scouting_spray.py` (crawler) and `src/gamechanger/loaders/scouting_spray_loader.py` (loader), driven in-memory by the report generator. The spray endpoint is team-scoped and asymmetric: calling with the owning team's UUID returns both teams' spray data; calling with a participant's UUID returns only that team's data (verified 2026-03-29). The crawler uses the owning team's UUID to get complete per-game data.

## Reports Package

`src/reports/` is a self-contained package for standalone report generation -- the sole scouting/delivery surface. `generator.py` orchestrates crawl→load→gc_uuid resolve→spray crawl→spray load→plays crawl→plays load→reconciliation→query→render→write; `renderer.py` produces self-contained HTML files written to `data/reports/`. The plays stage is non-fatal (auth expiry caught, per-game error isolation). The package is self-contained (`generator.py`, `renderer.py`); admin operators trigger and manage reports via `src/api/routes/reports_admin.py` (`/admin/reports`). `src/reports/morning_run.py` (E-240, `bb report morning-run`) is a cron-invoked orchestration shell OVER `generate_report()` -- it resolves each scheduled opponent (the resolution ladder in `src/gamechanger/opponent_ladder.py`) and calls the existing pipeline per auto-resolved slot, recording every slot's outcome to `scheduled_report_runs`; it adds NO new generation pipeline. See `.claude/rules/data-model.md` (Scheduled-Report Audit + Opponent Resolution).

**Serving and lifecycle conventions** (migrated from the retired `scouting-data-flows.md`):
- The serving route `/reports/{slug}` requires NO authentication. It MUST NOT query stats tables or render Jinja2 templates at serve time -- only a `reports`-table lookup plus a file read of the frozen HTML snapshot from disk.
- Reports have no opponent-registry dependency; generation takes any GC `public_id` directly (`bb report generate` or the `/admin/reports` UI).
- Reports are ephemeral: 14-day expiry, no versioning, no update-in-place. `cleanup_expired_reports()` unlinks expired HTML files (keeps the `reports` row, nulls `report_path`).
- **Naming convention**: "standalone report" or "generated report" = an artifact produced by this package. (The former dashboard "opponent flow" and its "scouting report" naming were removed in E-239.)

**In-memory crawl-to-load**: The report generator's scouting and spray stages use in-memory data flow (crawlers return data directly to loaders). Game discovery comes from crawl results, not filesystem globs or file-existence checks. This mirrors the scouting pipeline's in-memory pattern. See `.claude/rules/perspective-provenance.md`.

**In-memory payload loaders (E-237; disk twin removed E-256)**: `PlaysLoader.load_payload(plays_by_game)`, `GameLoader.load_payload(...)`, and the spray loader's `load_from_data(...)` are the **sole** loader entry points — they take already-parsed, in-memory data and write the DB directly, with no temp-file bridge and no disk intermediary. The former file-reading twin (`PlaysLoader.load_all`, `GameLoader.load_file`/`load_all`, `ScoutingLoader._load_team_from_disk`, and the private disk helpers behind them) was **deleted in E-256** (story 01) once the reports flow became fully in-memory crawl-to-load; no `src/` module reads `data/raw/` anymore. **New loaders must expose only an in-memory payload entry point — do NOT add a file-reading wrapper or a cached-file path.** (This reverses the original E-237 guidance, which described a payload-core / file-wrapper split that no longer exists — following that stale guidance would rebuild the twin E-256 just removed.)

**Dedup redirect map (E-244; widened 2026-08-15 — no longer cross-perspective-only)**: `GameLoader` collapses duplicate games to a single surviving `game_id`, so the collapsed game's event id no longer has a `games` row. Two collapse routes populate it, and they point in OPPOSITE directions: a **redirect** (E-244, the original) keys on the INCOMING source event id and usually deletes nothing — but when a `games` row already existed under that source id the in-pipeline twin merge DELETES it, so this route deletes too; a **promotion** (opponent-identity divergence, below) keys on the CANONICAL row's event id, because that row is merged away and HARD-DELETED so the incoming identity-bearing row can survive. ⚠ **BOTH deleting paths owe the chain repair** — any entry already pointing at a deleted row is rewritten to follow it (`_record_deleted_row_redirect`), or a chain `Y → S` then `S → C` strands `Y` and the plays/spray stages FK-skip that game silently. Reading this as promotion-only is how that defect (codex P1 on `0464f52`) comes back; any future `games`-deleting route inherits the obligation. A key therefore means "this id does not resolve to a `games` row", NOT "this id belonged to another perspective"; do not assume a key was never persisted. The natural key of the FIRST route is `game_date` + unordered team pair; the SECOND route exists precisely because that key cannot match its pairs — they share one team on the same side and name two different `teams` rows for one real opponent (see `.claude/rules/data-model.md`, Same-listing dedup). `LoadResult.redirect_map` (`{stale_event_id: surviving_game_id}` — populated at BOTH collapse sites above, surfaced via `ScoutingLoader.load_team`) carries this mapping forward. **Footgun**: any per-game generator stage that keys a DB write, idempotency precheck, reconcile call, or query-scope off the in-memory `crawl_result`/`boxscores` source event ids MUST remap those ids through `redirect_map` (identity via `.get(src, src)` for non-deduped games) before filing/reading — otherwise its FK guard silently SKIPS every deduped game (the bug E-244 fixed: plays/spray/reconciliation re-derived ids from source keys and no-opped on deduped games, computing plays-derived rate stats over a subset). Fetch stays keyed by the SOURCE event id (the API returns the scouted perspective by source id); only the DB-facing key becomes canonical. Live consumers: `_crawl_and_load_plays` and `_crawl_and_load_spray` in `generator.py`. See `.claude/rules/perspective-provenance.md` (Plays Pipeline) for the underlying collapse mechanism.

**Standalone report JS conventions**: Reports are self-contained HTML files with embedded `<script>` blocks for client-side enhancements (e.g., relative date display). JS in reports uses `var` (not `let`/`const`), targets elements by CSS class, and degrades gracefully (static content remains readable if JS fails).

**Report generation run record (`report_generation_runs`, migration 002)**: One WIDE row per report generation (NOT a per-stage child table) capturing per-stage status columns + per-stage counts + report-level trust flags, FK→`reports(id)` ON DELETE CASCADE, `UNIQUE(report_id)` (1:1 enforcer + idempotency key + admin-list join index). Mirrors the existing `scouting_runs` shape rather than inventing a new pattern: the stage set is fixed and the counts are heterogeneous, so a normalized child table would force generic `count_a/count_b` columns and a fan-out join. `reports` is intentionally NOT altered — it stays the thin artifact-identity row the public serve path reads; all trust flags live on the run record. This is the standard generation telemetry/audit trail and the storage foundation Epic E (morning-of-game scheduled, unattended report runs) builds on — a degraded report (half-loaded, spray-failed, zero-games) is indistinguishable from a complete one without it. New generation telemetry SHOULD extend this wide row, keeping recognizable per-stage column names.

**Per-run created-set orphan attribution (TN-4)**: To attribute orphan-team cleanup to a single generation run across a CROSS-PROCESS boundary (admin-UI + CLI + future cron all hitting one SQLite file), the generator tracks the set of team ids THIS run actually INSERTed — `self.created_team_ids`, fed by `EnsureTeamResult.inserted` at every `ensure_team_row` site (loaders record stubs they insert) — and cleans up only those (`orphan_ids = created_team_ids - {report_team_id}`). This replaces a global pre/post team-table snapshot diff, which would mis-attribute a concurrent run's teams. No DB lock, no migration, no snapshot — `inserted` (insert-vs-match) is the single signal.

**Report-stage status honesty (`run_status.py`, E-236)**: `classify_stage_status(loaded, errors, expected) -> STATUS_COMPLETED|STATUS_PARTIAL|STATUS_FAILED` (`src/reports/run_status.py`) is the SINGLE source of per-stage status semantics. Every load/crawl-type stage (crawl, load, plays, spray) routes its `*_status` through it and imports the `STATUS_*` constants — NO stage hardcodes status string literals. `"partial"` is a NEW value; the per-stage `*_status` columns are free-text (no CHECK), so no migration is needed.
- **ERROR-DRIVEN, not coverage-driven (the load-bearing principle)**: the classifier's `loaded`/`expected` are "units ATTEMPTED where a shortfall implies failure," NEVER raw data coverage. For plays/spray a coverage shortfall is the NORMAL scorekeeper-didn't-chart case (null != error) and MUST NOT register as `partial` — informational coverage counts (`plays_games_covered`, `spray_games_with_data`) must never be passed as `loaded`/`expected`. Only the boxscore crawl uses coverage-shortfall->partial (there a shortfall genuinely implies a fetch error). This is the reports-subsystem corollary of the data-bearing-coverage trap (`.claude/rules/data-model.md`).
- **Failure-signal precedence**: a stage with its OWN explicit failure signal (plays `recon.failed`; spray `_SprayOutcome.status == "failed"`; load total-failure guard) maps to `STATUS_FAILED` BEFORE calling the classifier, so the `expected == 0 -> completed` branch can't mask a real failure.
- **Degenerate single-unit load**: the load stage calls `classify(loaded=1, errors=load_errors, expected=1)` — the literal `1` is a unit-attempted flag, NOT `LoadResult.loaded` (a record count).
- **`overall_status` orthogonality**: `report_generation_runs.overall_status` has a CHECK (`running`/`completed`/`failed`) — do NOT widen it. "degraded" is DERIVED at read time (`overall_status == "completed"` AND any per-stage status in {partial, failed}), never stored.
- **Operator-vs-coach honesty split**: per-stage degradation surfaces to OPERATORS only (admin `/admin/reports`), never the coach footer.
- A GC "scored-but-empty" boxscore (both team-key envelopes present — key FORM is not a side marker and what decides it is unestablished, so do not read the observed slug+UUID pairing as the rule — groups present with empty stats) yields a games row + score, zero stat rows, `LoadResult.errors == 0` -> load/crawl status `completed` (correctly, not partial): the load-status mirror of the scored-but-empty trap.

**Run-record column allowlist footgun (`_RUN_RECORD_COLUMNS`)**: `_update_run_record()` (`src/reports/generator.py`) SILENTLY DROPS writes to any column not in the `_RUN_RECORD_COLUMNS` frozenset (unknown keys are filtered before the UPDATE, because column names are interpolated into the SET clause and the set must stay closed). Anyone adding a `report_generation_runs` column MUST add it to the allowlist AND prove the write lands with a real-schema round-trip test — otherwise the write is silently lost. This bit multiple E-236 stories.

## Reconciliation Package

`src/reconciliation/` is a post-load quality pass that cross-references plays data against boxscore data to detect and correct discrepancies (e.g., pitcher attribution errors). It reads from the DB (not raw API data) and operates after loaders have populated the database -- it does NOT belong in `src/gamechanger/`. Entry point: `reconcile_game(conn, game_id, dry_run=True)` in `engine.py` for per-game processing; `reconcile_all(conn, dry_run=True)` for batch. Discrepancy records are always written to `reconciliation_discrepancies` (created in `001_initial_schema.sql`); only corrections (e.g., `plays.pitcher_id` updates) are gated by `dry_run=False`. BF boundary correction algorithm: walks plays in `play_order`, assigns pitcher by boxscore appearance order and batters-faced counts; pitcher order is read from the `player_game_pitching.appearance_order` column (populated by the game loader from boxscore JSON pitcher ordering) -- a DB query since E-220, not disk JSON re-read or DB AUTOINCREMENT.

## LLM Package

`src/llm/` provides optional LLM integration via OpenRouter. `openrouter.py` uses plain `httpx.Client()` -- a documented exception to HTTP discipline (OpenRouter is a standard API, not GameChanger; no browser-identity headers needed). Env vars: `OPENROUTER_API_KEY` (required for Tier 2, absence = silent skip), `OPENROUTER_MODEL` (optional, canonical default `google/gemini-2.5-flash-lite` -- set as `_DEFAULT_MODEL` in `openrouter.py`; production overrides via `OPENROUTER_MODEL`; always use an undated slug that resolves to a live OpenRouter id). Future LLM integrations should reuse this client.

**JSON extraction (`json_extract.py`)**: `extract_json_object()` is a pure, HTTP-free, model-agnostic helper that recovers a JSON object from messy real-world LLM responses (bare, fenced, or prose-wrapped) via string-aware brace matching plus trial-parse; raises `LLMError` on unrecoverable input. Separation of concerns: `src/llm/` owns extraction (get a dict out of messy text); `llm_analysis.py` owns domain validation of that dict. Future Tier-2 integrations should reuse this helper rather than re-implementing JSON recovery.

**`response_format` request hardening**: `query_openrouter()` accepts an optional `response_format` pass-through (omitted from the request body when `None`); `enrich_prediction()` opts in with `{"type": "json_object"}` on both the initial call and the one retry. This is an additive belt-and-suspenders defense on top of the parser baseline -- the `extract_json_object` parser remains the model-agnostic baseline; never assume `response_format` alone is sufficient.

## Two-Tier Enrichment Pattern

Tier 1 (deterministic, pure Python, always runs) produces a typed dataclass. Tier 2 (optional LLM via OpenRouter, non-fatal) wraps the Tier 1 dataclass with narrative enrichment. Renderers select presentation path based on which dataclass they receive. New enrichment features should follow this pattern: deterministic first, LLM optional. **Operator-detectable Tier-2 status**: Tier-2 generation reports a cause-agnostic status (`success` / `unavailable-no-key` / `failed`) at log level so operators can distinguish "no API key" from a genuine enrichment failure without the absence of narrative being silently ambiguous.
