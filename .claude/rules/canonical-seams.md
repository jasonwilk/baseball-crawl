# Canonical Seams

The codebase funnels recurring operations through single entry points. Adding a
second path to something that already has one is the defect this file exists to
prevent: the two copies drift, and the one you did not update is the one that
runs. Before writing a new DB-path resolution, connection, team INSERT, admin
check, or deletion pass, look for the seam here first.

Moved out of CLAUDE.md on 2026-07-26. It lived there as always-loaded prose for
every agent on every interaction, at roughly 24KB, though it only ever binds an
agent writing code. Same content, scoped to the paths where it applies.

## Structure and boundaries

- Keep data extraction separate from analysis/processing. Use a clear directory structure: `src/` for source, `tests/` for tests, `data/` for local dev outputs, `docs/` for documentation.
- Extraction should be idempotent. All HTTP requests include proper error handling, retries, and rate limiting. The scouting and reports pipelines crawl-to-load in memory (no disk intermediary -- see the Perspective provenance line below), so there is no stored raw-response tier; transformation happens in-flight, not from a persisted raw payload.
- **The DIFF boundary and the BEHAVIOR boundary differ, in BOTH directions -- which is the price of a seam and the reason a caller audit is an obligation SEPARATE from reading your own diff.** Editing a single-sourced fragment changes behavior at every consumer **with no diff line at any of them**: in E-277 a one-line change to `_TEAM_BASE_PRED` altered what `_warn_stat_referenced_gameless_teams` reports, and that function appears nowhere in the diff. The converse also fires -- **adjacency produces FALSE candidates**, a block sitting below a rewritten region looking changed when it was not. So after touching any seam on this page, enumerate its consumers from the symbol and check each one; **a diff review alone is structurally incapable of seeing the change you just made.**

## The seams

- **Canonical team creation**: `ensure_team_row()` in `src/db/teams.py` — single entry point for all team INSERTs. New team-INSERT paths MUST use this function.
- **Canonical player upsert**: `ensure_player_row()` in `src/db/players.py` — single entry point for all player INSERTs/UPDATEs. Uses length-based name preference (longer name wins; "Unknown" treated as length 0). New player-INSERT paths MUST use this function.
- **Canonical team deletion**: `cascade_delete_team()` and `cleanup_orphan_teams()` in `src/reports/lifecycle.py` — consolidated deletion paths. New team-deletion paths MUST use these functions. Callers (e.g., `src/api/routes/reports_admin.py::_delete_report`) are thin wrappers that delegate cleanup to the canonical helper and add only path-specific concerns (HTTP response shaping, audit logging, flash messages). Callers MUST NOT duplicate cleanup logic in-place.
- **Canonical duplicate-game merge**: `merge_duplicate_game(conn, source_game_id, canonical_game_id) -> GameMergeResult` in `src/db/game_merge.py` (E-261) — the single primitive that collapses a cross-perspective *twin* (the same real game persisted under two `game_id`s from two team perspectives). Pure connection-in / **no-commit** (caller owns the transaction, mirroring `merge_player_pair(manage_transaction=False)`); re-points all six `games` FK children (`game_perspectives` unioned; `player_game_batting`/`player_game_pitching`/`plays`/`spray_charts`/`reconciliation_discrepancies` re-pointed — `play_events` follows `plays` automatically) then deletes the losing `games` row LAST (no FK child has `ON DELETE CASCADE`, so delete-last is load-bearing — a premature `games` delete aborts loudly). REFUSES (fail-closed, zero rows modified) when the two rows share ANY `perspective_team_id`, decided by **pre-classification** (intersecting perspective sets BEFORE any write), NOT by catching a mid-merge `IntegrityError`. Same module houses `is_offline_same_game(...)`, the OFFLINE same-game predicate for the operator repair pass, which REQUIRES near-play-count corroboration (disjoint-cross-perspective + bounded score-tolerance alone must NOT merge — same-total doubleheaders would fool it). This is the shared home for both the in-pipeline twin merge (`GameLoader` redirect site) and the operator repair pass (`bb data merge-duplicate-games`), mirroring the `player_dedup` "de-dup the dedup" precedent. New duplicate-game-merge paths MUST route through it — do not re-inline FK-child re-pointing.
- **Canonical team-name search**: `search_teams_by_name()` in `src/gamechanger/search.py` — single entry point for all `POST /search` by-team-name calls. Handles the GC punctuation zero-hit quirk (names containing `/`, `'` U+0027, `%`, `#` return zero hits) and Unicode apostrophe trap (indexed names use curly `'` U+2019) transparently via a normalized-name retry. New code MUST NOT call `client.post_json("/search", body={"name": ...}, ...)` directly for team name lookups — use the helper. See `.claude/rules/gc-uuid-bridge.md` for the full quirk, normalization shape, and retry gate.
- **Canonical public_id→gc_uuid resolution**: `resolve_gc_uuid_by_public_id(client, name, public_id)` in `src/gamechanger/search.py` — single paginate-and-filter loop that yields each candidate `gc_uuid` whose hit `public_id` matches exactly. Routes every query through `search_teams_by_name` (NOT `POST /search` directly), so the punctuation/Unicode-apostrophe quirk handling stays centralized; the page-level short-circuits (page-0 empty for a punctuation-dirty name, partial page = no more pages) are owned here. Callers (report generator, own-team opponent resolver) layer their own per-match id validation on the yielded candidates. New public_id-resolution paths MUST use it — do not re-inline the search-and-filter loop.
- **Canonical GC-UUID predicate**: `is_gc_uuid(s)` in `src/gamechanger/url_parser.py` — single source of canonical-UUID matching (the `_UUID_RE` regex lives here only; `ParsedRef.is_uuid` delegates to it). Consolidated three byte-identical `_UUID_RE` copies across `url_parser.py`, `opponents.py`, and `game_loader.py`; the exact anchoring/`IGNORECASE` is load-bearing for `game_loader`'s own-vs-opponent boxscore-key classification, so the pattern must not drift. New canonical-UUID checks MUST call it — do not re-inline the regex.
- **Canonical admin predicate**: `_user_is_admin(conn, user)` (connection-injected, for middleware/`_get_permitted_teams`) and its own-connection wrapper `user_is_admin(user)` in `src/api/auth.py` — single source of the admin check. Admin = `ADMIN_EMAIL` env matches user email OR `users.role = 'admin'`. The reports-admin route module (`reports_admin.py::_require_admin`) delegates to it. New code MUST NOT add another copy of the admin check — delegate to the auth.py predicate.
- **Team access (admin-sees-all)**: `_get_permitted_teams()` in `src/api/auth.py` resolves admins to ALL `teams` rows; non-admins resolve to their explicit `user_team_access` grants. Applies in dev and production. Security-relevant invariant: admins are never gated by `user_team_access`; non-admins always are. Do not reintroduce membership-based auto-grant as the team-access mechanism for admins.
- **Import boundary**: `src/` modules MUST NOT import from `scripts/`. Reusable logic lives in `src/`; scripts are thin wrappers.
- **Repo-root resolution**: Modules in `src/` use `Path(__file__).resolve().parents[N]` for repo-root-relative paths. Never use cwd-relative paths or `sys.path.insert()`.
- **`migrations/` is a Python package**: Has `__init__.py` and is in `pyproject.toml` because `src/db/reset.py` imports from it.
- **Season_id derivation**: `derive_season_id_for_team()` and `ensure_season_row()`. The season row is ensured by the **entry-point** loader (`ScoutingLoader`) and the report generator; `GameLoader.load_payload` **presumes the row already exists** — E-256-01 narrowed the contract so `GameLoader` no longer calls `ensure_season_row()`, and a direct `GameLoader` caller that does not ensure the row first will hit a foreign-key error. The rule still binds the entry-point loaders. Callers must unpack the tuple return type.
- **Canonical DB-path resolution**: `resolve_db_path(override=None)` in `src/db/paths.py` — single entry point for resolving the SQLite database path (precedence: explicit `override` > `DATABASE_PATH` env, relative resolved against repo root > default `<repo_root>/data/app.db`). The CLI (`bb data`, `bb report`), backup/reset utilities, and the FastAPI app all delegate to it. New DB-path-resolution paths MUST route through `resolve_db_path()` — do not re-implement the override→`DATABASE_PATH`→default cascade inline.
- **Canonical APP_URL resolution**: `get_app_url()` in `src/api/helpers.py` — single read of the `APP_URL` env var with the `http://baseball.localhost:8001` local-dev default (trailing slash stripped). The report generator (`_get_base_url`), reports-admin, and auth routes (magic-link base) all delegate. Production sets `APP_URL` explicitly, so the default only affects local-dev links. New code MUST NOT re-add an inline `os.environ.get("APP_URL", ...)` — use the helper.
- **Canonical production detection**: `is_production()` in `src/api/helpers.py` — the single production-detection seam, built on the `get_app_env()` normalizer (`os.environ.get("APP_ENV", "").strip().lower()`) so casing AND whitespace variants (`Production`, `PRODUCTION`, `" production "`) all select the production posture; unset/empty resolves to non-production (the load-bearing local-dev default — `Secure`-off cookies over HTTP). A companion `validate_app_env()` (also in `helpers.py`) is a refuse-to-start startup guard: a non-empty `APP_ENV` normalizing OUTSIDE the recognized set `{production, development, dev, test, staging}` (a typo like `prod`/`prd`) raises `RuntimeError` + a CRITICAL log at app construction, called alongside the `DEV_USER_EMAIL`-in-production guard in `SessionMiddleware.__init__` — so a typo fails loudly at boot instead of silently downgrading cookie `Secure` at runtime. Delegating consumers: `email.py` (send-email tri-state + `validate_alerting_config`), the morning-run CLI alerting preflight, `routes/auth.py::_is_dev_mode` (`not is_production()`), `src/api/csrf.py` (CSRF cookie `Secure`), and the `src/api/auth.py` `SessionMiddleware` DEV_USER_EMAIL guard. E-254-01 folded in the last two — they previously inlined divergent case-sensitive / `.lower()`-only reads that could select the insecure posture on a whitespace/case variant; do NOT reintroduce an inline `APP_ENV` read in either. New code needing prod-detection MUST route through `is_production()` — do not re-inline `os.environ.get("APP_ENV", ...) == "production"`. One real non-delegator remains: `src/db/reset.py` still inlines an `.lower()`-only `APP_ENV == "production"` check on the destructive `bb db reset` guard (a whitespace-variant bypass — tracked as IDEA-101; leave it here). `main.py`'s startup `app_env` read is a diagnostic log line, not a security gate.
- **Canonical operating timezone**: `get_operating_timezone() -> ZoneInfo` and `operating_today(now=None) -> date` in `src/util/timezone.py` — the single venue-local "today" seam. Reads the `OPERATING_TIMEZONE` env var (IANA name, default `America/Chicago`), degrading to the default with a logged WARNING on an invalid zone (never raises). Morning-run's default target date uses `operating_today()` so an evening run in a UTC container does not roll to tomorrow's games. **CE-3 / E-253 `game_date` derivation MUST reuse this seam and MUST NOT introduce a second timezone convention** — import from here.
- **Canonical instant→local-date conversion**: `derive_local_date(start_datetime, tz_name)` in `src/util/timezone.py` — the single converter from a UTC start instant + IANA timezone name to a game's venue-local `"YYYY-MM-DD"` calendar date (returns `None` when `start_datetime` is absent). Relocated here from `src/reports/morning_run.py` in E-253-04 so lower-layer callers can reuse it without inverting the layering (loaders importing from reports); both `morning_run` and `game_loader`/backfill import it from this stdlib-only seam. Pass an IANA name, not a `ZoneInfo` (bridge via `.key`). New instant→local-date derivations MUST use it — do not re-inline a UTC-sliced date, which would miss late-evening games that roll past UTC midnight.
- **Canonical SQLite connection factory**: `get_connection(db_path=None)` in `src/api/db.py` — the single connection factory for every SQLite writer sharing the cross-process WAL file (admin UI, interactive report CLI, morning-run cron). Sets `busy_timeout=30000` + `synchronous=NORMAL` (plus WAL + `foreign_keys`) on every connection so a lock overlap waits instead of raising `database is locked`. INVARIANT: `busy_timeout` is false safety without commit discipline — a writer MUST NOT hold an open write transaction across a network fetch on the shared file (morning-run commits after `ensure_team_row` before the crawl). This covers the scheduled-reports path; the `bb data` writers are a tracked out-of-scope follow-up, not yet routed through the factory. **BOUNDARY (E-270)**: this factory is scoped to WRITERS, and its `PRAGMA journal_mode=WAL` is a PERSISTENT file property — so a caller that must not MODIFY its target cannot use it, however read-only its SQL. A pre-confirmation read on a destructive path (`preview_purge`) opens a `mode=ro` URI connection instead. The predicate is "must not modify the target", NOT "is a reader": readers that may touch the file SHOULD use the factory, for the `busy_timeout`.
- **Shared query functions**: Reusable query logic lives in shared functions in `src/api/db.py` (e.g. `get_pitching_workload` / `get_pitching_history` / `build_pitcher_profiles`, and the query-time season-aggregate readers `get_season_batting` / `get_season_pitching`, which derive season totals from `player_game_*` at read time with the `perspective_team_id` filter — E-259 retired the stored `player_season_*` tables in favor of this query-time derivation). These are protected-core seams consumed by the reports flow — the sole forward surface. New query needs that the reports flow consumes belong here.
- **Reconciliation-scoreboard conventions (E-257)**: `src/reports/recon_scoreboard.py` is the read-only plays-vs-boxscore fidelity core (pure connection-in / dataclass-out; writes nothing, so it lives in `src/reports/`, not `src/db/`). One convention future work MUST honor: the plays-derived stat-definition constants (the SO/BB/H outcome-membership sets and the AB-exclusion set) are CODE-CANONICAL here — the E-245 baseline doc (`.project/research/E-245-plays-boxscore-reconciliation-baseline.md`) MIRRORS them (source-of-truth direction is flipped: code is authoritative, doc is kept in sync by hand). A constant-pin test + a behavioral outcome-to-stat test guard drift; do not re-derive these definitions elsewhere or treat the doc as canonical. (The second convention here was the ratchet's baseline-ownership rule; it retired with the gate on 2026-07-26.) The command remains a MANUAL operator diagnostic against the live dev DB, never a CI check — that DB is absent from worktrees and CI.
- **Prevention over cleanup**: Prefer preventing bad data at insert time over building cleanup tools after the fact. Example: `GameLoader._find_duplicate_game()` deduplicates cross-perspective games using a natural key (`game_date` + unordered `{home_team_id, away_team_id}`) before insertion, avoiding the need for post-hoc dedup. E-261 hardened the live signal (a **tolerant** schedule-count same-game comparison, fail-CLOSED on an undercount so a missing count never masks a genuine twin) AND added the offline corrective sibling `bb data merge-duplicate-games` for twins already persisted before the fix — both route through the canonical `merge_duplicate_game` seam above.
- **Canonical reconcile-at-load (retire-absent)**: `classify_absences()` plus the per-grain retire helpers in `src/db/reconcile_at_load.py` (E-267) — the single seam for retiring rows that VANISHED from a fresh crawl, run as part of the normal re-scout load across three grains (game, player-line, roster). There is NO snapshot table and no migration: the DB IS the prior set and the fresh crawl is the authority, so corroboration is a **health gate on the fresh payload** (fetched OK, still vouching for prior ids, not catastrophically shrunk) rather than a diff against history — reconcile-at-load was chosen over an offline repair pass, and the forward load path is the only correction mechanism (existing corruption is handled by `bb db purge-scouting`, not repaired). Read "prior" precisely, because the seam has **two** prior sets and E-276 separated them. The **CANDIDATE** population — what a retire may even consider — is a LIVE DB read taken at retire time on every grain, AFTER that grain's fresh rows are written, so it returns `old ∪ fresh`, NOT the previous run's state; that is unchanged, deliberate, and uniform. (On player-line those writes are merely visible-uncommitted inside the load's transaction; on game they are already COMMITTED, because the payload loader commits per game — which is why no isolation-level change could have fixed the gate and the capture had to move to the caller.) The **HEALTH-GATE** population is a different set, and it is NOT uniform — **the three grains did not converge on one answer, so never write "the gate now reads its prior correctly on all three grains"**: on one of them there is no gate left to read anything. **game and player-line** compute the gate over a caller-supplied PRE-UPSERT snapshot — `snapshot_prior_loaded_game_ids()` captured in `ScoutingLoader` above the boxscore load, `snapshot_prior_line_player_ids()` captured in `GameLoader` before the per-game upsert — passed in as a REQUIRED parameter (`prior_snapshot` / `prior_snapshots`) because only the caller knows *when*, with the player-line snapshot keyed IDENTICALLY to the live read (`(table, team_id)`) and FAIL-CLOSED on a missing key (an absent key is not the same fact as an empty one). Numerator `snapshot ∩ fresh` over denominator `snapshot`, both drawn from that one pre-upsert population; both grains pass `permit_empty_prior=True`, because a first-ever load's snapshot is legitimately empty and refusing there strands its own rows into the next run's snapshot and can deadlock the grain. **roster has NO floor gate at all**: `retire_departed_roster_players` does not call `crawl_is_authoritative`, and its permit is exactly `(fresh roster payload non-empty) AND (|absent ∩ previously_rostered_ids| ≤ MAX_ROSTER_DEPARTURES)` — that cap is the grain's **SOLE** guard, not a cap layered under a floor. **That grain ends E-276 with LESS gating than it started with, deliberately**, on the operator's ruling to prefer delete over refuse there: a correctly-populated roster floor PERMANENTLY LOCKS the grain on a reachable input, because its own refusals strand rows that inflate the next run's absent set until the cap refuses forever. Do NOT "restore" the roster floor and do NOT harmonize the grains — the asymmetry is the design. State both sides of what the correction buys: it does NOT make a sustained truncated or churned feed safe. A refusal does not roll back the same run's upsert (the write half is ungated), so on player-line a refused retire leaves the UNION of stale and fresh rather than the prior state, and the population it refuses over grows every run; partial id churn still retires (accepted residual, closer is IDEA-185); and `MAX_ROSTER_DEPARTURES` bounds a per-invocation RATE, never cumulative loss. Grain contract: `classify_absences` is PURE (id sets in, classification out — no DB handle, no I/O, no logging); the retire helpers are connection-in / no-commit / caller-owns-the-transaction and own both the DELETE and the WARN-per-retire and WARN-per-refusal. Retire is HARD-DELETE uniform across all grains — a soft-retire marker would force a `WHERE is_retired IS NULL` filter into EVERY reader (`get_season_*`, `_query_record`, `_query_roster`, `recon_scoreboard`), and one missed reader silently re-inflates the exact corruption this fixes. Two invariants that are easy to break: on the grains that HAVE a gate, its numerator and denominator must be drawn from the same population (`snapshot ∩ fresh` over `snapshot`) **and that population must be the PRE-UPSERT one — same-population-on-both-sides is NECESSARY but NOT SUFFICIENT**, because a set read AFTER the fresh upsert satisfies it while measuring `|fresh| ≥ |stale|`, which is not a health gate at all; that satisfied-but-meaningless form is what passed four review layers at E-267, so the temporal clause is the load-bearing half and "same population, therefore sound" is never proof of soundness. And `extra_guard` is narrowing-only — it structurally cannot widen a retire. Bias-to-refuse on game and player-line: an uncorroborated absence is TRANSIENT, never REMOVED, and a bare HTTP 200 is NEVER authority to retire, because the scored-but-EMPTY boxscore (envelope and categories present, per-player `stats: []`) is the MODAL opponent-scouting payload. **Not on roster** — E-276-03 inverted the bias there on the operator's ruling, leaving an empty fresh payload and the departure cap as that grain's only refusers. New retire paths MUST route through this seam — do not re-inline a set-difference delete. **Guard surface == delete surface (E-270, binding)**: the cross-perspective protection predicate reads the SAME `_PERSPECTIVE_CHILD_TABLES` constant (`src/db/game_merge.py`) that the whole-game delete loops — never a hand-written list — so a future sixth child table extends the guard and the delete at once, with zero drift. A hand-list omitting one table would wave through exactly the game whose only foreign footprint is a row in it.
- **Canonical orphan-reference reclamation**: `reclaim_orphan_reference_data(conn) -> ReclaimResult` in `src/reports/lifecycle.py` (E-273) — the single reachability-based terminal pass that hard-deletes unreachable `teams` / `team_rosters` / `players` (the reference tier a per-report cascade structurally cannot reclaim, because "is this team still reachable?" is a GLOBAL question no local cascade answers). New reclamation paths MUST route through it — do not re-inline the orphan set-difference. Single-source id-set producers `_orphan_team_ids` / `_orphan_player_ids` feed BOTH the DELETE and the invariant `count_orphan_reference_data`, so the count and the delete cannot drift (TN-8). The orphan-team predicate KEEPS four operator/security roots across three tables (`opponent_links.resolved_team_id`, `opponent_links.our_team_id`, `user_team_access.team_id`, `scheduled_report_runs.own_team_id` — the fourth added by E-277-01 — exclude-not-clear, never destroyed or NULLed; note that unlike the other two tables, `scheduled_report_runs` IS still a retained `_TEAM_PIN_TABLES` entry, deliberately kept though unreachable while that root stands, so being a root does NOT imply absence from the pin list) AND every team referenced by a surviving game's CHILD FK across all SIX game-child tables (`player_game_batting`/`player_game_pitching`/`spray_charts`/`reconciliation_discrepancies`/`plays`/`game_perspectives` — the sixth child a grep-based enumeration missed and Codex caught), with WARN-on-fire so a corrupt non-participant row is gracefully skipped instead of aborting the whole sweep with `IntegrityError`. The pass OWNS its transaction — reap-then-gate on `status='generating'`, then gate/compute/delete in ONE `BEGIN IMMEDIATE` — a NAMED EXCEPTION to the codebase's caller-owns-the-transaction convention (`merge_player_pair(manage_transaction=False)`, reconcile-at-load), required so the check→compute→delete is atomic against the pre-`reports`-row concurrency window (a TOCTOU-safe guard); a live generating report DEFERS the sweep (`ReclaimResult.deferred`), a liveness delay, not a safety hole.
- **Report deletion AND generation are DESTRUCTIVE** (E-267 + E-273): report GENERATION runs TWO hard-deleting passes — `generate_report()` → `load_team` runs reconcile-at-load (can hard-delete `games` and their full child surface, E-267), and `generate_report()` → `cleanup_expired_reports()` → `reclaim_orphan_reference_data()` runs orphan reclamation (can hard-delete unreachable `teams` / `players` / `team_rosters`, E-273). Report DELETION (`_delete_report`) and `bb report cleanup` also run the reclamation pass. So generating a report is NOT read-only, purely additive, or safe to re-run blindly against live data — it is destructive on BOTH axes (games via reconcile-at-load, reference tier via reclaim), and both passes are wired terminally/opportunistically rather than gated behind an explicit destructive command.
- **Perspective provenance**: Every per-player stat INSERT must include `perspective_team_id` (the team whose API call produced the data). Scouting and reports pipelines use in-memory crawl-to-load (no disk intermediary).
