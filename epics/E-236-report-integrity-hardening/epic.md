## Overview
Make the standalone report honest about its own completeness on the two surfaces that will become the SOLE trustworthiness signal once Epic E runs reports unattended (morning-of-game cron): the **operator run record** (`report_generation_runs`) and the **coach-facing report footer / no-games page**. This is harmless only because Jason eyeballs every report; Epic E removes that human backstop. This epic closes the verified self-reporting gaps before the backstop goes away — five found in discovery (#1-#5) plus a 6th of the same class (the load stage, #6) surfaced during the internal review (TN-11).

## Technical Notes

### TN-1: The unifying invariant + shared classifier (DE D1; error-driven semantics per DE F1/F2/F3 + CR MUST-3 + SE-B)
The invariant: **no stage writes a success/`"completed"` status when it had failures OR loaded zero of an expected non-zero set.** A single shared helper `classify_stage_status(loaded, errors, expected) -> "completed" | "partial" | "failed"` (plus module-level status constants) is the one place that maps stage outcomes to status strings — every stage calls it; no stage hardcodes status literals. Semantics:
- `completed` = full expected set loaded AND zero errors.
- `partial` = some loaded but `errors > 0` OR `loaded < expected`.
- `failed` = zero loaded of a non-zero expected set, OR a hard error.
- `expected == 0` (nothing attempted) = `completed` (no work, no failure). **This branch must never mask a known failure — see the precedence rule below.**

**CRITICAL — error-driven, NOT coverage-driven (the most important review finding; four-way reviewer convergence DE F1+F2 / CR MUST-3 / SE-B).** The `loaded < expected → partial` rule is only honest for stages where a coverage shortfall NECESSARILY implies a failure. This holds for the **boxscore crawl** (story 03): `games_crawled < M` only happens via a fetch error (empty-but-fetched bodies still increment the count). It is FALSE for **plays** and **spray**: there, `loaded < expected` happens ROUTINELY with ZERO errors — the MODAL scouting case (no GameChanger scorebook → plays empty; scorekeeper didn't chart → spray null). Driving `plays_status` / `spray_status` off raw data-coverage shortfall would mark the NORMAL case `"partial"`, reintroducing the EXACT false-alarm class that finding #4 exists to kill.

**Guardrail (DE F3):** each stage MUST define `expected` and `loaded` as **"units ATTEMPTED where a shortfall implies failure"** — NOT raw data coverage. Concretely: `expected` = items the stage tried to process; `loaded` = items that did NOT error; `errors` = the stage's error count. Pure data-coverage numbers (K = `plays_games_covered`; `spray_games_with_data`) are INFORMATIONAL columns, never the classifier's `loaded`/`expected`. Per-stage bindings are pinned in TN-7 (plays, crawl) and the spray note in TN-7.

**Failure-signal precedence (DE F1 / SE-B):** a stage that carries its OWN explicit failure signal (spray `_SprayOutcome.status == 'failed'` / `spray_result.errors`; plays `recon.failed`) MUST map that to `"failed"` BEFORE calling the classifier — the `expected == 0 → completed` branch must never mask a real crawl/load failure that produced zero units.

`"partial"` is a NEW per-stage status value. Per-stage `*_status` columns are free-text TEXT with NO CHECK constraint (only `enrichment_status` has one), so introducing `"partial"` requires ZERO migration for the status values. The status string IS the at-a-glance unattended-cron signal; count columns (TN-2) only help when a human reads them.

Location of the helper: the reports package (e.g. `src/reports/`). Exact module is the implementer's call; it must be importable by `generator.py` and unit-testable in isolation. The helper's docstring must state the F3 guardrail (expected/loaded = attempted-units-where-shortfall-implies-failure, not raw coverage) so the distinction does not erode in future stages.

### TN-6: SQ1 — all-boxscores-blocked outcome (FINAL — Jason signed off 2026-06-14)
When the boxscore crawl reads ZERO games of a non-zero expected set (M > 0 AND `games_crawled == 0`), the team was effectively BLOCKED (every fetch 403'd/errored — `scouting.py:290-303`), which is distinguishable from the genuinely-dataless case (where fetches succeed with empty bodies, so `games_crawled == M` but N == 0). Today this slips silently to `no_games` because the dormant tier-1 fatal gate (`generator.py:1460`) keys off an `errors` count that is always 0.

**Resolution — full team consensus (SE + DE + baseball-coach SQ1):** the all-blocked case produces a **`failed`** outcome (`overall_status="failed"`, `GenerationResult.outcome="failed"`, CLI exit 1, NO shareable page, operator alert via `report_generation_runs.overall_status="failed"`) — repairing the dormant fatal gate so it fires on `games_crawled == 0 AND completed_games > 0`. Rationale (coach): the `no_games` page tells a coach "no box score data available," which is FALSE here — the data exists in GameChanger, we just couldn't reach it; showing that page is an honest-information failure (the coach would assume the opponent is untracked when it is merely inaccessible). This is a SYSTEM problem, not a data absence, so it belongs entirely in operator space (re-auth / check access), especially for unattended Epic E runs. **Jason signed off on this as FINAL on 2026-06-14** (it flips a user-visible terminal outcome — a team that today gets a shareable `no_games` page now hard-fails — and was confirmed deliberately). (Implementation note: the firing condition is `games_crawled == 0 AND completed_games > 0`, consistent with the count-based approach in TN-7 — no separate `boxscore_errors` tally.)

**Documented limitation — 403 vs 404 is NOT distinguished (explicitly OUT of scope for E-236; api-scout + coach converged 2026-06-14):** the all-blocked gate fires on `games_crawled == 0 AND completed_games > 0` regardless of WHY the fetches returned zero (403 blocked vs 404 no-game-stream). This raised a theoretical honesty-inversion concern (a 404 "no scorebook ever created" opponent being mislabeled `failed` instead of `no_games`), but live data shows it does NOT occur in practice: GC's `game_status == "completed"` is itself the scorebook-exists marker (filtered by both the crawler and the M count), so a genuinely no-scorebook opponent surfaces as **M=0 → `no_games`**, never reaching the failed gate; api-scout measured 72/72 completed games returning 200-with-data and 0/130 403s on public boxscore reads. The failed gate's only real-world trigger is therefore auth-expiry / transient mass-failure (`games_crawled==0` with `M>0`), which is correctly operator-actionable. Distinguishing 403 from 404 (an HTTP status-class lever) is a future nicety, deliberately not built here.
