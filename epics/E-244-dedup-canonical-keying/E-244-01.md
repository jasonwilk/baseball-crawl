# E-244-01: Thread dedup redirect map to plays, spray, and reconciliation stages

## Epic
[E-244: File Plays & Spray Under Canonical Game IDs After Cross-Perspective Dedup](../E-244-dedup-canonical-keying/epic.md)

## Status
`TODO`

## Description
After this story is complete, the report pipeline will file plays and spray rows -- and run reconciliation -- under the canonical `game_id` for cross-perspective-deduped games, instead of silently skipping them under the now-orphaned source event ids. The `GameLoader` will expose the `{source_event_id: canonical_game_id}` redirect map it produces during dedup, and the generator's plays and spray stages will consume it so that plays-derived rate stats (FPS%, QAB%, pitches/BF, pitches/PA) cover the full game set for the scouted perspective.

## Context
This is the entire fix for E-244 -- see the epic for the diagnosis, impact, and the two expert consultations. The map production (the seam) is the bulk of the work; the consumers are small, symmetric remaps at the generator boundary. The fix is kept as one story because splitting it risks a half-fix (plays restored, spray still skipping) and the consumers share the single redirect-map carrier. Read epic Technical Notes TN-2 (the carrier seam), TN-3 (the three plays sites + spray), TN-4 (the audit AC-9 depends on), TN-5 (invariants), and TN-6 (test obligation) before starting.

## Acceptance Criteria
- [ ] **AC-1**: Given a cross-perspective duplicate game that `GameLoader` redirects to a canonical id during a report run, when the game-load stage completes, then the redirect is recorded as a `{source_event_id: canonical_game_id}` entry on the run's redirect map and surfaced to the generator via the single carrier defined in Technical Notes TN-2. A non-redirected game produces no map entry.
- [ ] **AC-2**: Given the deduped game from AC-1, when the plays stage runs, then plays rows for that game are stored under the CANONICAL `game_id` with `perspective_team_id` = the scouted team (verified by a DB query on a deduped-game fixture), AND no plays rows exist under the source event id. Plays coverage for the scouted perspective matches boxscore coverage.
- [ ] **AC-3**: Given the deduped game, when the plays stage runs, then `reconcile_game` is invoked with the canonical `game_id` (not the source id), per Technical Notes TN-3 site 2.
- [ ] **AC-4**: Given the deduped game, after the plays stage runs, then `self.plays_game_ids` contains the CANONICAL id and NOT the source id, and is deduped (no duplicate id when two source perspectives collapse to one canonical). Consequently all three plays-derived rate queries (`_query_plays_pitching_stats`, `_query_plays_batting_stats`, `_query_plays_team_stats`) AND the footer coverage count `plays_games_covered` include the deduped game's data -- FPS%/QAB%/pitches-per-BF/pitches-per-PA are computed over the full game set. Per Technical Notes TN-3 site 3.
- [ ] **AC-5**: Given a deduped game that has spray data, when the spray stage runs, then spray rows for that game are stored under the canonical `game_id` AND no spray rows exist under the source event id AND `_query_spray_charts` returns them (the spray query is game-id-agnostic, so the dict-key remap alone suffices -- there is no spray return-value remap; per the plays/spray asymmetry in Technical Notes TN-3).
- [ ] **AC-6**: Given a report run that already loaded a deduped game's plays and spray, when the report is generated a SECOND time, then two distinct idempotency guarantees hold (note: spray and plays have different idempotency layers -- see Technical Notes TN-3):
  - **(plays)** the plays API is NOT re-fetched for the deduped game (assert via a mocked client call count for the plays endpoint), because the precheck remap (TN-3 site 1) finds the canonical id already loaded.
  - **(spray)** the second run inserts NO DUPLICATE spray rows under the canonical `game_id` (assert via a DB row-count on `spray_charts`, NOT a client call count -- the spray CRAWLER has no pre-fetch idempotency and re-fetches every run today; idempotency is row-level in the spray LOADER, now keyed on the canonical id). Do NOT add a spray-crawl precheck -- it is out of scope.
- [ ] **AC-7**: Given a report run with ZERO deduped games, when the pipeline runs, then plays, spray, reconciliation, and the rate queries behave exactly as before this change (identity passthrough via `.get(src, src)`), per Technical Notes TN-5.
- [ ] **AC-8**: A regression test built on a cross-perspective DEDUPED-game fixture (two source event ids collapsing to one canonical id via `_find_duplicate_game`) asserts AC-2, AC-3, AC-4 (the deduped CANONICAL `plays_game_ids` list -- the most error-prone path, distinct from AC-2's load-keying), AC-5, AC-6 (both the plays and spray clauses), and AC-7 (the zero-dedup identity passthrough). A single-event-id fixture is explicitly insufficient, per Technical Notes TN-6.
- [ ] **AC-9**: The audit in Technical Notes TN-4 is confirmed and recorded in this story's Notes section (a durable repo artifact). The recorded confirmation MUST enumerate the specific stages checked (the plays load, plays precheck, plays reconcile loop, plays query-scope, spray load, the boxscore stat load, and `reconcile_all`) and the search method used (e.g., a grep over `crawl_result`/`boxscores` key usage across `src/reports/generator.py`) so a later reviewer can re-run the audit deterministically. The confirmation must state that no generator stage other than those changed by this story keys a DB write or idempotency check off the source `boxscores`/`crawl_result` ids.
- [ ] **AC-10**: The full pytest suite passes (`python -m pytest tests/`), including any tests that import from the modified modules (discover per `.claude/rules/testing.md` Test Scope Discovery).

## Technical Approach
Follow epic Technical Notes TN-2 (capture the map on the `GameLoader` instance at the redirect site, carry it via a new `LoadResult.redirect_map` field, assign it once in `ScoutingLoader.load_team` and the disk-flow counterpart) and TN-3 (consume the map at the generator boundary as a dict-key remap before the plays/spray loads; remap the three plays sites -- idempotency precheck, reconcile loop, return value). The fetch keys stay source; only the DB-write/idempotency/reconcile/query-scope keys become canonical. Do NOT recompute the redirect via a second `_find_duplicate_game` call (TN-5). The recommended remap location is the generator boundary (keeps the loaders redirect-agnostic); in-loader remap immediately before the FK guards is an acceptable alternative as long as rows land under canonical ids -- implementer's choice.
