## Description
After this story is complete, the report opens with a "Tonight's Game Plan" section (Technical Notes TN-5 Section 1) — the headline the coach reads first — that synthesizes the loss-forensics blueprint (SIG-005, LIFT-based) into a deterministic plan conditioned on the probable starter, rendered as the robust/fork+cue/fallback ≤3-bullet shape with a live in-game identification cue folded into the fork. This is the section that directly fixes the 2026-07-12 live-validation miss.

## Context
Per Technical Notes TN-4 and the design-doc §8, the report's one systemic miss was a season-average blueprint that was never joined to the probable starter; the correct plan is two-branch ("if he's wild (his norm) → work counts/take walks; if he locates → he can't miss bats, put it in play and run"). The 2026-07-18 adversarial reviews sharpened this into three concrete corrections this story implements (baseball-coach `deep-scout-signal-catalog.md`): the blueprint is **LIFT-based** (loss_rate − win_rate, gated to "blueprint" vs "historical thread" — AC-2/AC-7), the fork carries a **live in-game identification cue** because season stats set only the prior and cannot tell the coach which world they're in tonight (AC-8), and the committee rendering is the **robust/fork/fallback ≤3-bullet shape** rather than one bullet per arm (AC-4). Per Technical Notes TN-5, this section is deterministic (templated), NOT LLM-narrated — the LLM two-pass synthesis is a v2 non-goal; both branches are driven by fact-sheet values (the "wild" branch keyed on the starter's season strike%, the "locates" branch on his whiff rate, both from SIG-004) and the cue prints the starter's season FPS% (SIG-006) baseline. The scoped self-scout callout (our own starter's first-inning line) is deferred to v2 with the `--vs` matchup context (Technical Notes TN-6) — it is NOT in this section for v1. This story depends on SIG-001 (E-263-02b) and SIG-004+SIG-006 (E-263-04).

## Acceptance Criteria
- [ ] **AC-1**: The report renders a Tonight's Game Plan section at the top (Technical Notes TN-5 Section 1), placed per the E-263-01 layout spec, within the ≤3-bullet / ≤600-word / 60-second-read budget. It fills the pre-created blueprint stub module + Game Plan stub partial from E-263-02a.
- [ ] **AC-2**: SIG-005 loss-forensics blueprint is computed as **LIFT over base rate**, NOT "majority of losses" (methodology correction, 2026-07-18 reviews — `.claude/agent-memory/baseball-coach/deep-scout-signal-catalog.md` §2). For each candidate thread (opponent issued 4+ walks, allowed 2+ steals, gave up the first run, committed 2+ errors, held scoreless through 2, etc.) compute `loss_rate` = share of LOSSES with the thread and `win_rate` = share of WINS with it, and surface the **Lift = loss_rate − win_rate** (the lift math kills generic threads like "they scored first" that are ~equally present in wins). Both rates count across the opponent's **data-bearing** game set — games WITH charted `play_events` (who scored first, walks drawn, steals taken, when the losing pitcher was pulled), NOT all games from `games` (a scouted opponent's scored-but-empty games are the modal case — SE-F2 / the data-bearing-coverage principle). Rendering is raw fractions that ARE the lift ("happens in 6 of their 9 losses but only 2 of their 14 wins"); the raw-count denominator MUST match the reconstruction set. A test proves lift = loss_rate − win_rate over the data-bearing set.
- [ ] **AC-3**: The blueprint is conditioned on SIG-001's probable starter and rendered as a DETERMINISTIC two-branch plan per Technical Notes TN-4/TN-5 — both branches populated from fact-sheet values (the "wild" branch on SIG-004 strike%, the "locates" branch on SIG-004 whiff%), paired with the live cue per AC-8, NOT from an LLM call. A test proves the two branches reflect the starter's own strike%/whiff numbers. **Brand-new-arm edge case (Technical Notes TN-4):** when SIG-004 is `no_data` (0 prior IP this season), the section renders the two-branch STRUCTURE in generic/hedged read-and-adjust language rather than data-driven branches — a test covers the `no_data` starter path.
- [ ] **AC-4**: The Game Plan renders the **robust / fork+cue / fallback shape** from Technical Notes TN-5 §1 (REPLACES one-bullet-per-committee-arm, which — at ~40% top-2 accuracy — makes the coach key on the wrong bullet ~60% of the time) as ≤3 bullets: (1) what holds no matter who starts; (2) the ONE fork + the live cue folded in (AC-8); (3) the unknown-arm fallback (read the first inning cold). A single clear HIGH-confidence ace **collapses to 2 bullets** (the arm's read + the live cue) — the story MUST NOT manufacture a fork when there is one clear starter. When SIG-001 resolves to "committee" (Technical Notes TN-4): a 2-arm committee → the fork bullet compresses both arms' difference to one line; a 3+-arm committee → ONE composite bullet naming all eligible arms with a generic-but-actionable instruction resolved by the same first-at-bats cue — never per-arm branches that blow the ≤3-bullet budget. (Full per-arm detail lives in Who's Pitching, E-263-04.) A test covers the single-ace 2-bullet collapse and the 2-arm vs 3+-arm committee shapes.
- [ ] **AC-5**: The section strips cleanly to instruction voice with no LLM dependency; if the OpenRouter key is absent the section renders identically (it is deterministic — this section does NOT call the LLM).
- [ ] **AC-6**: When `FEATURE_PREDICTED_STARTER` is OFF (SIG-001 absent — per Technical Notes TN-4), the Game Plan renders a LOUD, visible degraded/warning state (not a silent empty card), consistent with E-263-02b AC-5 and the report-run honesty mechanism. A test covers the flag-off path.
- [ ] **AC-7** (blueprint-vs-historical-thread gate, Technical Notes TN-2 + the 2026-07-18 methodology correction): the "blueprint" label (build the game plan on it) is applied to a thread ONLY when it is present in **≥60% of the data-bearing losses AND lift ≥ +25 pts**; otherwise the thread renders as a "historical thread (note it, don't build on it)". Below the **5-loss floor** there is NO blueprint at all — every thread renders as "historical thread (small sample)", never a percentage (a ~29-game summer season yields only ~8–12 losses, so this floor bites often). A test covers: (a) a thread clearing both gates → "blueprint"; (b) a thread present in losses but with low lift → "historical thread"; (c) <5 losses → everything is "historical thread (small sample)".
- [ ] **AC-8** (live in-game identification cue, methodology correction #1 + Technical Notes TN-5 §1): the two-branch fork bullet renders a concrete live cue FOLDED IN (the cue is how the coach resolves the fork, NOT a separate 4th bullet): read the first ~5 hitters — strike-one to ≤2 of 5 OR 2+ three-ball counts in the first two innings → WILD tonight (take until he proves the strike); strike-one to ≥4 of 5 and out of deep counts → LOCATING (get a good pitch early, put it in play, then run); 3 of 5 → stay patient. The starter's own season FPS% (SIG-006, from E-263-04's fact) prints next to the cue as the baseline (anchor: league average ~58–60%). The cue is STATIC templated instruction text with the FPS% baseline filled in — deterministic, no LLM, no new crawling, no day-of computation. A test asserts the cue renders with the starter's FPS% baseline and the correct thresholds.
