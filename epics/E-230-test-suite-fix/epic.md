## Overview
E-229 removed RTK (Rust Token Killer), whose output compression had been silently hiding pytest failures. With RTK gone and plain pytest output restored, the full suite now reports **56 failed / 4397 passed**. This epic does two things: **make the suite green** (stories 01-03 — investigate each failure, decide the correct behavior first, then fix whichever side is wrong; explicitly **not** a blind "make tests green" pass) and **keep it green** (story 04 — a lightweight context-layer convention so failures can't silently accumulate again).

**Net finding (stated plainly):** first-hand SE + DE investigation found **zero confirmed product bugs**. All 56 failures are **test-maintenance** — stale fixtures and stale assertions — and for each, production behavior was **proven correct** by applying the decision framework (reproduce → `git`-trace the source line → verify the production path). The user's "fix code OR fix test" question resolves to **"fix test" for all three buckets**, but only after evidence. The documented per-bucket evidence trail is the deliverable, satisfying the "evaluate what the behavior SHOULD be" requirement.

## Background & Context
RTK compressed pytest output so that pass/fail counts and suite truncation were invisible (the documented ~67 silent failures across E-173/E-179 that triggered the now-removed E-224 pytest guardrails). E-229 removed RTK and dropped that compensating tooling as a full drop; plain pytest output is honest again. E-229 touched zero `src/` runtime code, so these 56 failures are **pre-existing and were masked**, not caused by E-229.

A full-suite run on clean `main` (HEAD `46edaaa`, plain `python -m pytest tests/`, ~91s) produced 56 failures that resolve to **three buckets**, characterized first-hand by software-engineer (code trace + `git log`/`git show`) and data-engineer (data-layer review). All three are test-maintenance:

- **Cluster 1 — `gs` fixtures omit a key production always supplies (52 failures)**: the template guard is **correct and load-bearing**; the failing test fixtures omit the `gs` key. Fix = the fixtures, plus user-confirmed hardening of all four `gs` templates as defense-in-depth (Story 01).
- **Cluster 2 — spray-chart geometry tests are stale (2 failures)**: a deliberate source redesign (commit `a8d6ac6`) the tests never tracked. Fix = the tests (Story 02); design intent confirmed square by the user via the live production report.
- **Cluster 3 — game-coverage assertions are stale (2 failures)**: a later-added fixture game the assertions never accounted for. Fix = the assertions (Story 03).

A fourth story (Story 04, claude-architect) adds lightweight regression prevention so failures cannot silently accumulate again. This epic is the **forward fix** of the now-visible failures (plus prevention). It is distinct from **IDEA-072 (RTK Compression Retrospective Audit)** — the backward-looking investigation of what *else* RTK's compression may have hidden across `git diff`/`git log`/reviews. E-230 references IDEA-072 but does **not** absorb it; the two remain separate per the ideas-vs-epics rule.

## Technical Notes

### Per-Failure Decision Framework (the heart of this epic)
For each failure, the implementer applies the framework software-engineer used during discovery — and records the verdict + evidence in the story:

1. **Reproduce in isolation** — run the single failing test, confirm the error.
2. **Trace the source history** — use `git log -L`/`git show` on the relevant source line to determine whether the **source changed under a stale test** (→ fix the test) or a genuine **code/contract gap** exists (→ fix the code).
3. **Confirm real behavior** — run the production query/render path (or read the authoritative contract: `key-metrics.md`, `migrations/*.sql`, function docstrings) to confirm what the behavior *should* be.

The investigation result here is that **all three buckets resolve to "fix the test," with proof that production is correct in each case**. A fix MUST NOT mask a real regression — but because production was proven correct first-hand for every bucket, fixing the tests is the evidenced-correct action, not a shortcut to green. The evidence trail per bucket is the deliverable.

### Cluster 1 — `gs` fixtures omit a key production always supplies (Story 01, 52 failures)
- **Failure**: `jinja2.exceptions.UndefinedError: 'dict object' has no attribute 'gs'`. Spread: 40 `tests/test_report_renderer.py` + 9 `tests/test_report_workload.py` + 3 `tests/test_dashboard_workload.py` = 52.
- **Why it raises**: the guard `{% if pitcher.gs is none %}&mdash;{% else %}{{ pitcher.gs }}/{{ pitcher.games - pitcher.gs }}{% endif %}` protects *present-but-None*. When the key is **absent**, Jinja treats it as `Undefined` (not `None`), so `is none` is False, the `{% else %}` branch runs, and `pitcher.games - pitcher.gs` raises. The crash is triggered by the **fixtures**, which omit the key — not by a production data path.
- **The guard is CORRECT and load-bearing — do NOT remove or weaken it.** DE + SE traced EVERY production pitcher-dict path and confirmed all supply `gs`: `_query_pitching` (`src/reports/generator.py:203`/`:222`), `get_team_pitching_stats` (`src/api/db.py:188`), the opponent-scouting query (`src/api/db.py:888`), and the dashboard mutators (`src/api/routes/dashboard.py:997`) all SELECT/preserve `gs`. NULL `gs` IS a normal production state (manual-entry opponents with no `appearance_order`; pre-backfill rows; member teams when the GC season-stats payload lacks "GS" — `src/gamechanger/loaders/season_stats_loader.py:503`), and the `is none` guard exists precisely to render those as em-dash. Removing it would break real rendering.
- **The actual gap**: the failing tests' pitcher-dict builders omit the `gs` key — they predate the column and were never updated. RTK hid the resulting render exception.
- **Fix part A — fixtures (clears the 52 failures)**: populate `gs` in the three fixture helpers — `_make_pitcher` in `tests/test_report_renderer.py:30`, the pitcher builder in `tests/test_report_workload.py`, and `_make_pitcher` in `tests/test_dashboard_workload.py:223` — to match the real query contract. `gs` semantics (DE): **NULL = unknown** (→ em-dash); **`0` = known pure reliever** (real data → `0/5`); **int > 0 = starter** (→ `{gs}/{g-gs}`). Fixtures must exercise at least one None case and one int case.
- **Fix part B — template-guard hardening (user-confirmed in-scope, all 4 templates)**: harden the guard so a *missing* key degrades to em-dash identically to present-None (e.g. `pitcher.gs is none` → `pitcher.get('gs') is none`, or tolerate `undefined`), so a future caller that forgets `gs` degrades to em-dash instead of a 500. The same pattern appears in four templates: `src/api/templates/reports/scouting_report.html:711` and `src/api/templates/dashboard/opponent_print.html:398` (crash today via the fixtures) plus `src/api/templates/dashboard/opponent_detail.html:392` and `src/api/templates/dashboard/team_pitching.html:84` (no failing test, same pattern). Hardening must preserve present-None → em-dash, `0 → 0/N`, and the positive-int split. The user chose to harden all four (Open Question 2, RESOLVED).
- **Display contract (already settled — no coach needed)**: `key-metrics.md` → GS/GR shows `{gs}/{g-gs}`; NULL `gs` (unknown) = em-dash; `0` is data (pure reliever), never em-dash. `display-philosophy.md` → never suppress.

### Cluster 2 — spray-chart geometry tests are stale (Story 02, 2 failures)
- **Failures**: `tests/test_charts/test_spray.py::test_render_uses_3x4_figsize` (`:198-204`) and `::test_render_png_dimensions_approx_3x4_at_150dpi` (`:362-375`; the `height > width` portrait check at `:375` is the actual failing line). Deterministic (3/3 reproductions), not flaky.
- **Root cause** (SE git-traced): commit `a8d6ac6` ("redesign scouting report print layout") **deliberately** changed `src/charts/spray.py` to `figsize=(3,3)` (line 451) and cropped the axes (`set_ylim(365, 8)` / `set_xlim(-4, 324)`, lines 479-480, `dpi=150` + `bbox_inches="tight"` at line 494) to remove dead whitespace. That commit changed the source but never updated these two tests. Current near-square output **is** the intended redesigned output. (Note: the "3x4" in the commit message and the test names refers to the **page card grid** — 12 cards per page — NOT the figure aspect ratio. The figure itself is intentionally square.)
- **Verdict (RESOLVED — fix the tests)**: design intent is settled by **ground truth** — the user confirmed the desired output is the live production report `https://bbstats.ai/reports/zoVS7ElENReB4Kkr`, which renders near-square spray charts (exactly what the current code produces). Combined with the deliberate redesign commit, this confirms **square is intended**. Story 02 is a **test-fix only** (no code-fix branch): update the figsize assertion to `(3,3)`, realign **all three orientation-encoding assertions** (`:373` `width>=200`, `:374` `height>=300`, `:375` `height>width` — the last two/three encode the old portrait expectation; `:375` is the actual failing line, `:373-374` pass only incidentally) to the implementer's **measured** near-square output, rename both tests + the `:199` docstring away from "3x4", and pin to measured dimensions. `src/charts/spray.py` is not modified.

### Cluster 3 — game-coverage assertions are stale (Story 03, 2 failures)
- **Failures**: `tests/test_dashboard.py::TestGameCoverageIndicator::test_opponent_detail_shows_coverage_indicator` and `::test_opponent_print_shows_coverage_indicator` (assertions at `tests/test_dashboard.py:3248` and `:3266`). Both assert `"Through Mar 1 (3 games)"`.
- **Root cause** (SE reproduced): the fixture seeds a **4th** completed opponent game (`game-opp-2025`, `tests/test_dashboard.py:277`) added later for a different test. `get_game_coverage()` correctly returns `game_count=4`. Production and the format string are correct.
- **Verdict**: fix the **test** assertions to `"(4 games)"`. Behavior is intended all-time coverage; do NOT change `get_game_coverage()`.

The same edit reconciles the adjacent Phase 5 prose Step 1b makes false (the `:419` "no review logic in Phase 5" caveat and the `:608` workflow-summary diagram). Supporting edits: scope the per-story "no pytest" ban (implement/SKILL.md:254 + code-reviewer.md:280) so it applies to per-story worktree review and names the closure pass as the exception (worktree pytest tests main's code via the editable-install meta-path-finder, so it is misleading per-story; at closure the changes are in main where pytest is authoritative — a reconciliation, not a loophole); document the gate in a new `## Full-Suite-Green Closure Gate` section of `.claude/rules/workflow-discipline.md` (alongside the sibling Documentation/Context-Layer Assessment gates); and append the inverse direction to the existing Test-Validates-Spec line in `.claude/rules/testing.md`. No new hook, CI, rule file, or `addopts`; no pytest-verbose/exitfirst reintroduction — it is a verification PASS at closure, mirroring Step 1a. The gate is **unconditional** (decided): silent accumulation is exactly the masked failure mode; gating only "invariant" epics reopens the door (~90s/closure, cheap). This is a standing change to how every future epic closes; the main session surfaces that to the user in the READY summary. claude-architect owns the exact wording/placement (domain-expert-designs); the story ACs specify outcomes.
