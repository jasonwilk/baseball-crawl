## Overview
Productize the plays-vs-boxscore reconciliation scoreboard that data-engineer built once as a manual, session-local SQL baseline (`.project/research/E-245-plays-boxscore-reconciliation-baseline.md`) into a standing, repeatable measurement + gate. CLAUDE.md's north-star Operating Principle ("Always Get Closer to Byte-Identical Play Ingestion") names this scoreboard — plus the rule that ingestion changes must not regress it — as its enforcement mechanism, and states it "lands when that scoreboard exists; until then, this principle binds intent." This epic makes the scoreboard exist as a durable artifact so the principle starts binding mechanically. It also adds a fast report-time plausibility guard so an implausible headline rate is flagged before a report ships (the operator was the only QA that caught an 18x-off FPS in a shipped report).

## Background & Context
E-245 shipped the parser and self-game data fixes but explicitly DEFERRED scoreboard productization. E-253 (CE-3) planning referenced resuming it but filed no tracking artifact, so it was on no list until this stub homed it. The metric itself is already fully defined in the E-245 baseline and is NOT re-derived here:

- **Per-stat fidelity metric**: exact% + abs-Δ, at the **player-level grain** (`game_id` + `perspective_team_id` + `player_id`), **perspective-scoped** (the honest grain for report fidelity — a perspective-agnostic grain over-credits coverage), **excluding no-plays units** (boxscore has the player, plays has zero matching rows — those measure coverage, not parser accuracy).
- **Stat set** (definitions from the baseline, encoded as code-canonical constants per TN-7): pitching `{BF, SO, BB, H, HBP}`, batting `{AB, H, BB, SO, HBP}`.
- **Three axis counters** tracked ALONGSIDE the per-stat metric (not folded in): (1) dropped-pitch-events, (2) no-plays units (coverage / perspective misalignment), (3) self-games (`home_team_id = away_team_id`).
- **The gate rule**: "no gated stat's abs-Δ increases AND no axis counter increases" for any ingestion / parser / reconciliation change (gated stat set and severity per TN-3).

This epic is the *measurement + gate* artifact. It is DISTINCT from the *corrective* reconciliation engine (IDEA-062 → E-198, which detects and fixes misattribution) — do not conflate. It does NOT re-plan the stat-key drift canary E-253 already shipped; it consumes/complements it.

## Goals
- A standing `bb report reconcile-scoreboard` operator diagnostic that computes the per-stat fidelity metric + three axis counters from the live DB, renders a human-readable table, and emits a stable machine-readable JSON block via `--json` (mirroring `bb report verify-aggregates`).
- A committed baseline JSON snapshot the command diffs a fresh run against, with a one-way ratchet gate (non-zero exit only when a number INCREASES / worsens) and an operator-run `--update-baseline` refresh.
- A fast report-time plausibility guard that flags an implausible headline rate (FPS%, P/PA) at report render time as an operator-facing WARNING rather than shipping it silently.

## Non-Goals
- **NOT a data-fix epic.** The parser, self-game, and appearance-order fixes shipped in E-245/E-253. This epic measures and guards; it does not correct data.
- **NOT the corrective reconciliation engine** (IDEA-062 → E-198).
- **NOT re-planning the stat-key drift canary** (shipped in E-253). This epic consumes it.
- **NOT a CI-enforced gate.** The live DB (`./data/app.db`) is dev-only and host-mounted — absent from worktrees/CI — so the gate is a manual operator diagnostic, never a CI enforcement point (TN-2).
- **NOT re-deriving the metric.** Stat definitions, grain, and axis definitions come from the E-245 baseline, encoded as the code-canonical constants the doc now mirrors (TN-7).
- **NOT a hard render block** in the report path. The plausibility guard emits an operator WARNING; it does not block or auto-clamp the report (TN-4).
- **NOT persisting the plausibility signal** on the run record — that is the deferred follow-on IDEA-108; E-257-03 ships the WARNING-log form only (TN-4).

## Technical Notes

### TN-1 — Scoreboard core mirrors the aggregate-parity precedent (location + shape)
New pure module `src/reports/recon_scoreboard.py` (data-engineer confirmed `src/reports/`, NOT `src/db/` — the scoreboard writes nothing, so it is not a write-seam; it sits next to its sibling `aggregate_parity.py`). It exposes a pure, read-only, connection-in / result-dataclass-out core following `src/reports/aggregate_parity.py::verify_aggregates(conn) -> ParityResult` exactly. The dataclass carries per-stat fidelity rows plus the three axis counters as distinct named fields. A pure core is what makes the human table, the `--json` output, and E-256's smoke assertion all fall out of one function. The scoreboard reads only from `plays` / `play_events` / `player_game_batting` / `player_game_pitching` (bare SQL; the SQL is 100% net-new, lifted from the baseline's `recon.sql` — no SQL shared with `aggregate_parity`). The CLI wrapper mirrors `bb report verify-aggregates` at `src/cli/report.py:153` (resolves the DB via `resolve_db_path()`, Rich table, `raise typer.Exit(code=1)` on gate failure); the CLI plumbing (`resolve_db_path`, `closing(sqlite3.connect)`, PRAGMA) is ~60% verbatim reuse. **The "mirror" is scoped to the CLI plumbing, the DB-missing guard, and the Rich-table shape — NOT the output surface: `--json` is net-new here (`verify-aggregates` has no `--json`), so do not assume a `verify-aggregates` precedent for the machine surface (CR-S1).** The subcommand is the single source of truth; a thin pytest wrapper exists only as a shape/smoke guard on synthetic seed data (`tests/fixtures/`), NOT as the real-data gate.

### TN-2 — Gate binding point: manual operator diagnostic (CONFIRMED)
data-engineer CONFIRMED: the gate binds as a **manual operator diagnostic, exactly like `verify-aggregates` — NOT a CI gate.** The dev-only host-mounted `./data/app.db` is absent from worktrees/CI, so a real-data regression check has no data in CI. The operator runs the command against live data before/after an ingestion change and reads the diff. The non-zero exit makes it opt-in scriptable into a local pre-push hook, but the authoritative binding is manual-operator-diagnostic. **Do not design any CI enforcement point.**

### TN-3 — Committed baseline snapshot, one-way ratchet gate, severity (all resolved)
- **Baseline form (data-engineer)**: a committed **JSON** file at `.project/baselines/reconciliation-scoreboard.json` carrying the per-stat block (pitching + batting: exact% + abs-Δ) + the three axis counters + a metadata header (git SHA at snapshot, DB game-count, snapshot date). The `--json` machine surface (TN-1) and the baseline share the per-stat + axis-counter VALUE shape; the metadata header is baseline-only (a live `--json` run has no source SHA/date to emit), so **the ratchet diff compares ONLY the per-stat + axis-counter values and IGNORES the metadata header (CR-S2)** — "same schema" means the compared value block, not byte-identical files.
- **One-way ratchet gate (data-engineer)**: a fresh local run diffs against the committed snapshot and exits non-zero if any GATED stat's abs-Δ INCREASED OR either ratcheted axis counter (dropped-pitch-events, no-plays units) INCREASED. **`self_games` is gated as a HARD ZERO, not on the ratchet (C6): any `self_games > 0` fails the gate, matching E-256's closure-smoke `self_games == 0` assertion (TN-6) — a self-game is always an opponent-resolution bug, never an acceptable floor, unlike the coverage-driven other two counters.** The stat/counter ratchet is structurally one-way — a fix that shrinks abs-Δ or drops a ratcheted counter is an improvement and NEVER trips the gate. After a fix, the operator re-snapshots so the improved number becomes the new floor (ratchet).
- **Refresh (data-engineer)**: an explicit `--update-baseline` flag on the same subcommand overwrites the JSON, committed as a reviewed change. The baseline-JSON commit diff is the human review point (e.g. "dropped_pitch_events 5841→213, self_games 23→0" visible in the PR). **Owner of re-snapshot: the operator (Jason), gated by human review of the JSON diff. No agent auto-refreshes it.** **The INITIAL committed baseline is the same operator-owned case (Codex-P1, DE-confirmed): it is produced by the operator via `--update-baseline` against the live DB as an explicit E-257 CLOSURE step, NOT by the E-257-02 implementer (the live DB is absent from worktrees). The E-257-02 implementer delivers only the gate code + synthetic-fixture tests; `.project/baselines/reconciliation-scoreboard.json` is an operator/closure artifact, off the implementer's create-list. The gate's baseline-absent bootstrap (E-257-02 AC-8) covers the window before that first snapshot exists.**
- **Gate severity (baseball-coach, CONFIRMED)**: a FLAT equal-weight regression gate over the OUTCOME/decision stats — the stats behind OBP, K%, BB%, K/9, BB/9, K/BB: batting `{AB, H, BB, SO}` and pitching `{H, SO, BB}` — all weighted equally. Coach CONFIRMED both families are gated (the pitching family is read directly from coach's naming of K/9, BB/9, K/BB as decision stats; data-engineer confirmed the data-layer decomposition is sound — CR-S5, no longer provisional). **BF is NOT gated** (it is a workload/denominator number, and its worse fidelity is mostly perspective-misalignment noise). **HBP is shown but NOT equal-weighted** (smallest sample; tracked as context). **FPS / pitch-level fidelity is guarded separately via the axis-1 counter (dropped-pitch-events) as a dedicated tripwire, NOT blended into the averaged regression score** (blending would dilute it).
- **Abandoned-PA residual (baseball-coach)**: EXEMPT from firing the gate but NEVER hidden. The current baseline abs-Δ is the accepted FLOOR — this is handled structurally by the one-way ratchet (the residual is baked into the committed baseline; the gate fires only ABOVE the floor, holding steady is a pass). The scoreboard display MUST always show and LABEL the residual on the batting `{AB, H}` rows ONLY (e.g. "AB abs-Δ: N units, known residual — quick-scored/abandoned-PA noise"), never suppress it. **The labeled set is EXACTLY `{AB, H}` batting (baseball-coach confirmed, Codex-P2): cause-5 residual is diagnosed strictly in batting terms (±1 on AB/H from abandoned at-bats). Batting BB/SO are already 0–1 off (labeling them would mislead), and pitching carries NO abandoned-PA label — BF isn't gated and pitching-H drift is attribution-driven (causes 2–4, different provenance). A non-zero floor on a pitching gated stat is carried by the general ratchet UNLABELED, never tagged as abandoned-PA noise. This epic adds exactly ONE residual label, belonging to batting AB/H.** This is the north-star's named-acceptable residual. **Note (DE-F5): any specific abs-Δ figure quoted in this epic (the baseline doc's "34" over its 597-game snapshot) is ILLUSTRATIVE, not a target — the committed baseline's actual values are generated from the current dev DB (~73 games; self_games/dropped-pitch currently near-zero) via an operator `--update-baseline` run, not copied from the doc.**

### TN-4 — Report-time plausibility guard: WARNING-log form (DECIDED)
- **Surface mechanism (DECIDED — option (a), WARNING-log only)**: when a headline rate falls outside the coach's band, emit an operator-facing WARNING log line at report generation time. NO schema change, NO migration, NO run-record column — SE-only. This is the fast render-time guard the flow-review asked for and satisfies coach's framing ("operator-facing flag, review before sharing"). The persisted/queryable trust-flag-on-run-record form (option (b), which would need a migration + `_RUN_RECORD_COLUMNS` allowlist update + round-trip test) is DEFERRED to IDEA-108.
- **Bounds (baseball-coach)**: first-pitch-strike% **30–75%** (floor widened from 40% — a genuinely wild HS/Legion pitcher can have a real full-season FPS in the low-30s; a 40% floor risks flagging a real "can't find the zone" performance as a parser error), pitches-per-PA **3.0–4.5**. These are operator-facing flags ("outside expected range, review before sharing"), NOT a silent auto-clamp/discard — reproduce the human-eyeball catch, do not replace human review.
- **TEAM-LEVEL headline rates ONLY (C1 — SE-F1 + CR-M2 convergent)**: the guard checks the TEAM aggregate rates `team_fps_pct` and `team_pitches_per_pa` (assembled into the report `data` dict at `src/reports/generator.py:2445–2446`), NOT per-pitcher/per-batter rows. Rationale: the motivating 18x-off bug was a TEAM headline (Empire Netting `team_fps_pct`); range-checking every per-pitcher `fps_pct` (at L2399) would flood the operator log with legitimate small-sample relievers (a reliever facing 2 charted batters can be a real 0%/100% FPS) and conflict with `.claude/rules/display-philosophy.md` ("never flag small samples"). Per-player checking, if ever wanted, needs a min-charted-PA sample gate — out of scope here.
- **Wiring (software-engineer)**: the team rates are already computed and in-hand where the `data` dict is assembled (`src/reports/generator.py:2445–2446`). The range-check is a pure comparison over already-computed values — no new query, and NO touch to `build_pitcher_profiles` (that lives in `src/api/db.py`, a separate path). These rates are already charted-PA-gated (E-245 TN-5). **Testability (SE-F2): extract the range-check into a pure helper (e.g. `_check_rate_plausibility(team_rates) -> list[str]` returning the out-of-range messages) so the test is a fast unit test over the helper, NOT a full `generate_report()` drive** — the latter risks the disk-backed-fixture deadlock gotcha in `.claude/rules/testing.md`.

### TN-7 — Stat-definition drift guard: code-canonical constants + behavioral pin (C2 — DE-F1 + SE-F3)
The scoreboard's plays-derived stat definitions are `SO = Strikeout + Dropped 3rd Strike`; `BB = Walk + Intentional Walk`; `H = Single+Double+Triple+Home Run`; `HBP = Hit By Pitch`; `BF/PA = row count`; `AB = PA − (BB + IBB + HBP + Sac Bunt + Sac Fly + Catcher's Interference)`; no-plays unit = boxscore has the player but plays has zero matching rows; self-game = `home_team_id == away_team_id`.

The original AC ("a test asserts the definitions match the E-245 baseline verbatim") is NOT mechanically testable — the baseline is a Markdown doc and a test cannot diff code against prose. The testable mechanism (E-257-01 AC): (1) the outcome-set definitions live as **named module-level constants** in `recon_scoreboard.py` (the outcome membership sets for SO/BB/H and the AB-exclusion set), a test pins each constant to its literal expected set, AND a fixture exercises each outcome-to-stat mapping behaviorally (feed a row of each outcome type, assert it lands in the right stat). (2) **Source-of-truth direction is FLIPPED: the code constants are canonical and the baseline doc mirrors them** (an annotation in the baseline notes that `recon_scoreboard.py` is authoritative), not the reverse — so "drift" is caught by the constant-pin + behavioral test, and the doc is kept in sync by hand as reference. Exact constant names are the implementer's call (SE/DE own naming); the AC verifies the pin exists, not the names.
