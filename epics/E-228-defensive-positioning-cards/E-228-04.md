# E-228-04: Positioning cards design spec (wireframes + print-CSS spec)

## Epic
[E-228: Defensive Positioning Pocket Cards](../E-228-defensive-positioning-cards/epic.md)

## Status
`DONE`

## Description
After this story is complete, there is a concrete design specification for the two positioning print artifacts -- the landscape coach call sheet and the multi-up portrait player cards -- detailed enough that E-228-05 can implement the Jinja2 template without design guesswork. The deliverable is a reference HTML/Tailwind mockup plus annotations covering layout, component inventory, print CSS, edge states, and the opponent-dashboard link treatment.

## Context
The design plan at `/home/vscode/.claude/plans/i-need-to-plan-joyful-cloud.md` describes the two artifacts at a brief level, but it is a design brief, not an implementation spec. It does not pin down column widths and order, the two distinct print-CSS page types (landscape call sheet vs. portrait player-card sheet), cut-grid geometry, black-and-white dugout-printer fidelity, the component inventory, or empty/edge states. Those decisions are UX work and must be made before the template is implemented -- otherwise the implementer makes them ad hoc.

This story is grounded in E-228-02's engine output: the design must reflect the fields the engine actually produces per batter/position (`call_state`, `direction_shade`, `depth_shade`, `bip_count`, `hr_count`, `is_thin`, `zone_concentration`, plus the team-state call). The `call_state` values are **absolute field direction** (batter handedness is unavailable on every data path E-228 uses -- epic TN-3 and the Non-Goal): the stored enum keys are `TRUE`/`LEFT`/`LEFT_SHALLOW`/`LEFT_DEEP`/`RIGHT`/`RIGHT_SHALLOW`/`RIGHT_DEEP`/`MIXED`, and the recommended DEFAULT display call-words are "STRAIGHT UP" / "SHADE LEFT" / "SHADE LEFT IN" / "SHADE LEFT DEEP" / "SHADE RIGHT" / "SHADE RIGHT IN" / "SHADE RIGHT DEEP" / "MIXED" (epic Technical Notes section TN-5). The concrete MIXED rule is in epic Technical Notes section TN-4a.

**Lexical vocabulary is this story's to lock** (epic TN-5 ownership split, codified during Codex iteration 2 / CX2-1). The lexical vocabulary -- which display word E-228-05's render layer shows for each stored `call_state` / `team_state_call` enum key -- is a design decision (the words the coach sees), so it is owned by this story. E-228-02 (engine) writes only stored enum keys and carries no display words; E-228-05 (render layer) implements the constants block in code per this story's locked table. The recommended DEFAULT starting set from epic TN-5 is `TRUE`→"STRAIGHT UP", `LEFT`→"SHADE LEFT", `LEFT_SHALLOW`→"SHADE LEFT IN" *or* "SHADE LEFT SHALLOW", `LEFT_DEEP`→"SHADE LEFT DEEP", `RIGHT`→"SHADE RIGHT", `RIGHT_SHALLOW`→"SHADE RIGHT IN" *or* "SHADE RIGHT SHALLOW", `RIGHT_DEEP`→"SHADE RIGHT DEEP", `MIXED`→"MIXED" -- this story may take the defaults as-is or override any of them. The one open lexical choice flagged by TN-5 is the shallow-variant word: "SHADE LEFT IN" (shorter, mildly ambiguous with "infield shift") vs. "SHADE LEFT SHALLOW" (unambiguous, longer); stored key is `LEFT_SHALLOW`/`RIGHT_SHALLOW` either way. Consult baseball-coach via PM relay if a tiebreaker is needed.

**Cards-per-sheet is for this story to determine** -- the brainstorm said "8-up" but that number was never reconciled against the actual card count (6 position cards plus the utility variant) or card dimensions. Derive the per-sheet count from card size and the position list (for reference, the existing spray-chart grid in `scouting_report.html` fits 12 per page).

**Print-CSS precedent**: do not design print CSS from scratch -- follow the existing mixed-orientation pattern in `src/api/templates/reports/scouting_report.html`: named `@page` blocks (around lines 307-314) and a multi-up portrait grid with `break-inside: avoid` (around lines 395-407).

## Acceptance Criteria
- [ ] **AC-1**: Given the design spec, when it is reviewed, then it includes a wireframe for the landscape call sheet showing one row per opposing batter. **The locked call-sheet column set is**: jersey #, name (if available in the data), the team-state CALL, per-position shade cells for all 6 covered positions, a confidence column (BIP count + HR count + thin tag), and a slot for the LLM rationale line. **There is no "lineup slot" column** -- batting order is game-scoped, so any season-grain lineup slot is a lossy heuristic; a stale heuristic slot is worse than nothing (clutter or false doubt), and jersey # + name already solve the dugout lookup. Lineup construction is coach-knowledge at game time, not system-knowledge (baseball-coach's call; software-engineer concurs). **There is no "bats L/R" column** -- batter handedness is unavailable on every data path E-228 uses (epic Non-Goal); a column NULL in every row would damage coaching trust. (The LLM rationale MAY still infer handedness contextually from spray direction -- that is E-228-07 prose, not a call-sheet column.) **Per-position column order**: column order is a design decision the spec sets and documents with rationale; baseball-coach's field-read order -- "LF/CF/RF/3B/SS/2B" (outfield then infield, each left-to-right from the dugout) -- is the recommended starting point.
- [ ] **AC-1d** (deviation magnitude -- explicit decision): Given the design spec, when it is reviewed, then it makes an **explicit, documented decision** on whether and how the call-sheet confidence column surfaces the per-position optimal-point deviation magnitude (the `direction_deviation` / `depth_deviation` values E-228-02 produces, in the unit E-228-02 defines -- epic TN-3 Stage A). This is a real info-design question -- raw deviation magnitude next to a categorical call can add precision OR add noise -- so the spec must decide it, not leave it dangling. "Does not surface it in v1" is an acceptable documented decision; silently omitting the question is not.
- [ ] **AC-1e** (locked vocabulary table -- the call-words): Given the design spec, when it is reviewed, then it contains a **locked vocabulary table** mapping each of the 8 stored enum keys (`TRUE`, `LEFT`, `LEFT_SHALLOW`, `LEFT_DEEP`, `RIGHT`, `RIGHT_SHALLOW`, `RIGHT_DEEP`, `MIXED`) to a single chosen display call-word -- no "or" / no alternatives in the locked table. The shallow-variant choice (epic TN-5: "IN" vs. "SHALLOW") is resolved by this table. The table is the single source of truth that E-228-05's render-layer constants block implements verbatim (epic TN-5 ownership split, Codex iteration 2 / CX2-1). The spec MUST also record the rationale for the shallow-word choice (one or two sentences).
- [ ] **AC-2**: Given the design spec, when it is reviewed, then it includes a wireframe for the portrait player card (one per fielding position) showing a large "STRAIGHT UP" default and a jersey-number-keyed exceptions list. It also includes a wireframe for the 2-position utility-player card variant **as a design-for-future-use deliverable only** -- v1 always generates one card per the 6 covered positions; the utility variant is not a required v1 rendering behavior (it is wireframed so the layout is ready when it is needed).
- [ ] **AC-3**: Given the design spec, when it is reviewed, then it specifies the print CSS for both page types: `@page` orientation/size for each, `break-inside: avoid` rules, the cut-grid geometry for the multi-up player-card sheet (with the per-sheet card count determined per the Context section), and black-and-white print fidelity (the dugout printer) -- following the `scouting_report.html` precedent named in the Context section.
- [ ] **AC-4**: Given the design spec, when it is reviewed, then it includes a component inventory: the named-state cell, the confidence/thin-tag rendered at full visual weight (per `.claude/rules/display-philosophy.md`), the "STRAIGHT UP" block, the MIXED per-position-cells treatment, the partial-data row treatment (10-24 BIP: direction lean, NULL depth, `is_thin=1`), and -- if AC-1d's decision is to surface the deviation magnitude -- the deviation-magnitude display component.
- [ ] **AC-5**: Given the design spec, when it is reviewed, then it defines edge/render states: zero scouted batters, an all-TRUE lineup (no exceptions), a batter with a MIXED call, and the **partial-data batter** (10-24 BIP -> direction lean, NULL depth, `is_thin=1`) -- the partial-data row is the most common real row for a regular and must read as intentional, not broken (display-philosophy).
- [ ] **AC-6**: Given the design spec, when it is delivered, then it includes a reference HTML/Tailwind mockup that renders the call sheet and the player cards with the AC-1 column set, the AC-2 card layouts, and the AC-3 print CSS -- concrete enough to serve as E-228-05's implementation target.
- [ ] **AC-7**: Given the design spec, when it is reviewed, then it specifies the opponent-dashboard "Defensive Positioning" link treatment: placement, label, the no-report-yet empty state, and -- per ux-designer's CX-2 caveats -- (a) the link is a **real link to an existing `ready` report** (`/reports/{slug}`), not an on-click generate-with-spinner; (b) the link area carries the project's game-coverage freshness cue ("Through [date] ([N] games)"), not a system sync date; (c) the empty state covers the case where no `ready` report exists yet for the tracked opponent. **Empty state is the transitional / failure-recovery state under (B) Pre-generate** (v1 scope per epic TN-7; flipped from iteration-2's provisional (A) on 2026-05-15). E-228-06's scout pipeline auto-generates the report bundle on every scout run, so an actively-scouted opponent has a `ready` report under normal operation. The empty state is shown when (i) a tracked opponent has not yet been scouted (brand-new tracking) or (ii) the auto-generate call failed during a scout (`generate_report()` is non-fatal per E-228-06 AC-6a, so a scout run can complete with no fresh report). The empty state must still read as intentional, not broken (display-philosophy) -- it is a transient state, not a permanent one -- and ideally cues the operator that a scout run will populate it. The freshness cue ("Through [date] ([N] games)") therefore reflects when the *displayed* report was generated, not the most recent scout time. Per epic Technical Notes section TN-7, the link resolves to the standalone report bundle (reuse) -- there is no separate dashboard card view to design.
- [ ] **AC-8** (baseball-coach review record -- observable deliverable): Given the call sheet and player card wireframes, when this story is delivered, then the design spec contains a **baseball-coach review record** (a named, dated section of the spec) with all four of: (i) baseball-coach's binary verdict -- **PASS** or **FAIL** -- on the question *"do the wireframes support a glove-on, ~20-seconds-before-a-pitch lookup, as a recognition task not an analysis task?"*; (ii) the date of the review; (iii) on a **FAIL** verdict, an itemized list of specific failure points naming the affected wireframe element (known failure modes baseball-coach checks for: small font, dense tables, more than 5-6 exception rows per card, anything requiring a two-column read to decode one call); (iv) on a **PASS** verdict, an explicit confirmation that none of the known failure modes are present. The AC is satisfied by the **presence of a complete review record** in the spec -- a PASS verdict is not required to satisfy the AC, but a FAIL verdict triggers the non-AC revision step below before the story can be marked DONE. baseball-coach is consulted via PM relay during dispatch.

  **Non-AC revision step (PM-gated, not part of the AC)**: if AC-8's review record carries a FAIL verdict, the implementer must revise the wireframes to address each itemized failure point and re-run AC-8 (a second review record appended to the spec, dated). The PM gates whether a revision is required (FAIL on a known failure mode = required; FAIL on a stylistic preference may be waived with rationale in the spec). This revision step is a process gate, not an acceptance criterion -- it does not change AC-8's "record exists and is complete" contract.
- [ ] **AC-9**: Given the call sheet and the player card, when they are reviewed, then both are keyed by jersey number so a coach's "#23 SHADE LEFT"-style call resolves on the player's own card -- the jersey number is the shared key across both artifacts (epic Technical Notes section TN-8).
