## Description
After this story is complete, the database has a new `batter_positioning` table that holds the Tier 1 deterministic positioning decision per batter / team / season / perspective / position. The table is created by an idempotent numbered migration and is the storage target for the positioning engine built in E-228-02.

## Context
The positioning engine (E-228-02) computes a deterministic alignment recommendation per opposing batter per fielding position. That recommendation must be precomputed and stored so the report bundle can read it cheaply at render time and so it can be rebuilt as an automatic pipeline stage. This story creates only the schema -- no engine logic, no pipeline wiring. It is the dependency root for the whole epic.

The schema, primary key, and index are specified in the epic's Technical Notes section TN-2, including why `perspective_team_id` is part of the primary key (the perspective-provenance invariant) and why the two `direction_deviation` / `depth_deviation` columns are persisted rather than engine-return-only (they are the finer-grained signed ordinal deviation that sits under the categorical shade buckets -- the categorical `call_state` discards the per-axis step magnitude, and the render path consumes it).

**Unit-coordination flag**: the deviation columns store a signed ordinal step bucket (`0` / `±1` / `±2`), quantized from an SVG-space delta. Both the reference origin (`BASE_POSITIONS`, epic TN-3 Stage A) and the two per-axis quantization threshold ladders are **defined by E-228-02** -- one single-source-of-truth concern. This migration's `direction_deviation` / `depth_deviation` column comments reference that definition, they do NOT independently restate the reference origin or the threshold ladders. The implementer must keep the migration comment consistent with what E-228-02 defines. (E-228-02 is `Blocks`-downstream of this story, so at the time this migration is written E-228-02's constants may not yet be implemented -- write the column comment to reference "the per-axis `# RECALIBRATE` threshold ladders + `BASE_POSITIONS` defined in E-228-02 (TN-3 Stage A)" rather than restating them. The column *type* is settled: `INTEGER`, nullable -- the ordinal-bucket decision is locked, only the threshold-ladder values live in E-228-02.)

It is a per-batter value denormalized onto all 6 of the batter's rows (the same pattern as `is_thin`), persisted so the render path reads it directly rather than re-deriving the TN-4a MIXED-rule lattice in SQL.

## Notes
The schema was specified by data-engineer during E-228 discovery and revised during review iteration 1, the math-vs-LLM refinement, and Codex spec review iteration 1 on four counts: (1) the discovery draft had wrong column types (TEXT instead of INTEGER for team ids, INTEGER instead of TEXT for `season_id`, and a nonexistent `teams.team_id` FK target); (2) the `call_state` / `direction_shade` enums were handedness-relative (pull/oppo) but batter handedness is unavailable on every data path E-228 uses -- so they are now **absolute field direction** (`LEFT`/`RIGHT`, `left`/`right`); (3) the math-vs-LLM refinement added the per-batter optimal-point computation, and data-engineer's verdict plus the de+se coordinate-space/unit reconciliation (2026-05-15) is to **persist** its 2D deviation as two `INTEGER` columns `direction_deviation` / `depth_deviation` -- signed ordinal step buckets (`0`/`±1`/`±2`), not continuous `REAL`, because the SVG-space delta they quantize is anisotropic and unanchored; (4) Codex iteration 1 (CX-1) added `team_state_call TEXT NOT NULL` -- the batter's team-state call denormalized onto every row (software-engineer's call) so the render path reads it directly instead of reimplementing the TN-4a MIXED-rule lattice in SQL. TN-2 carries the current corrected DDL with all column comments; use it verbatim. `call_state` stores stable absolute enum keys (e.g. `LEFT_SHALLOW`), not display call-words -- the configurable vocabulary is resolved at render time (epic TN-5).
