# E-228-03: Standalone delivery path: dedup-gap fix + positioning recompute

## Epic
[E-228: Defensive Positioning Pocket Cards](../E-228-defensive-positioning-cards/epic.md)

## Status
`TODO`

## Description
After this story is complete, the standalone `bb report generate` path runs the player-dedup sweep it currently lacks, then runs the Tier 1 positioning recompute, so a standalone report's `batter_positioning` rows are computed from deduplicated spray data. This closes a genuine pre-existing correctness gap and makes the standalone path produce the same ordered pair (dedup -> recompute) as the scouting pipeline.

## Context
`src/reports/generator.py::generate_report()` runs scouting load -> spray load -> plays, but has NO `dedup_team_players` call -- dedup is currently only a scouting-pipeline hook. The positioning recompute must run after dedup (epic Technical Notes section TN-6: dedup-first prevents a high-BIP hitter fracturing into low-BIP stubs and misfiring the sample gates). If the standalone path ran the recompute without first deduping, it would produce wrong rows and break the cross-path parity requirement. So the dedup-gap fix and the standalone recompute ship together in this story.

This story wires the standalone path only. The scouting-pipeline wiring and the cross-path parity verification are E-228-06 -- split out per the epic's slicing rationale to isolate the dedup-ordering risk on the self-contained path first.

## Acceptance Criteria
- [ ] **AC-1**: Given `generate_report()` runs for a team with spray data, when the pipeline executes, then `dedup_team_players(conn, team_id, season_id, manage_transaction=True)` is called after the spray/plays stages and before the positioning recompute, per Technical Notes section TN-6.
- [ ] **AC-2**: Given the dedup sweep has completed, when the positioning recompute runs, then it calls the identical pipeline-agnostic engine function from E-228-02 (`src/reports/positioning.py`) with `(conn, team_id, season_id)` -- the engine commits its own writes per the transaction contract in epic Technical Notes section TN-6 -- and `batter_positioning` is populated for the report team.
- [ ] **AC-3**: Given the positioning recompute raises an error, when `generate_report()` handles it, then the failure is non-fatal -- it is logged at WARNING and report generation continues (consistent with the spray-stage error contract in `generate_report()`); because the engine is self-committing, a failed recompute leaves any prior committed `batter_positioning` state intact.
- [ ] **AC-4**: Given a standalone report is generated for a team with a known cross-perspective duplicate player, when the report completes, then the duplicate is merged before the positioning recompute and `batter_positioning` reflects the merged player's full BIP count.
- [ ] **AC-5**: Given the existing standalone report generation tests, when this story's changes are in place, then no existing test regresses.

## Technical Approach
In `src/reports/generator.py::generate_report()`, after the spray and plays stages (around the existing post-plays point, ~line 1110) and before the stats-query/render block, open a **new** `with closing(get_connection()) as conn:` block and run the `dedup_team_players` call then the positioning recompute call inside it. Note: unlike `run_scouting_sync`, `generate_report()` has **no long-lived shared `conn`** -- every stage opens its own short-lived `with closing(get_connection())` block, so there is no open connection at the post-plays point to "run inside." The new block MUST `conn.execute("PRAGMA foreign_keys=ON;")` immediately after opening -- `dedup_team_players`'s docstring requires the FK pragma on. Wrap the recompute in try/except with a WARNING log so it is non-fatal, matching how `_crawl_and_load_spray` and the plays stage already handle failures. Import the recompute function from `src/reports/positioning.py` (E-228-02). Do not modify the engine itself.
