## Description
After this story is complete, the system has a deterministic Tier 1 positioning engine in `src/reports/positioning.py` that reads a team's spray-chart data and, per opposing batter and covered position: (Stage A) computes the batter's optimal fielding point and its deviation from the textbook base position; (Stage B) classifies absolute field-direction and depth tendency via the swappable geometry seam; (Stage C) applies the hard sample gates and quantizes to one of the 8 `call_state` values (TRUE + 6 directional shades + MIXED) -- then writes those rows to the `batter_positioning` table. The engine is the auditable core of the feature: no LLM in the decision path.

## Context
This is the heart of the epic. The engine encodes the three-stage model -- optimal-point computation, the two-knob direction/depth classification, and the sample-gate trust backbone plus quantization -- described in epic Technical Notes sections TN-3, TN-4, and TN-4a. It must be a pure, pipeline-agnostic function so that both delivery paths (E-228-03 standalone, E-228-06 scouting pipeline) call the identical code -- parity by construction.

**Story-sizing note**: review iteration 1's math-vs-LLM refinement added the Stage A optimal-point computation to this story (it was not in the original brainstorm spec, which went zone-classification -> named-state directly). This makes E-228-02 a larger story. It is specified here as one story because all three stages are one cohesive pipeline producing one vertical increment (the populated `batter_positioning` table + the engine dataclasses) -- splitting Stage A out would create a story with no independently testable downstream-consumable output. If the implementer finds the combined scope exceeds a single focused session, that is a split decision to raise with the PM at dispatch time with concrete information, not a pre-emptive split here.

The engine reuses existing geometry primitives from `src/charts/spray.py` (`classify_field_zone`, `contact_type_label`, the `_raw_to_svg` coordinate transform and its constants, and the `atan2` sectoring pattern) -- it does NOT rebuild them. **Import only the pure geometry functions** -- `src/charts/spray.py` also imports matplotlib, so the engine should avoid pulling in the matplotlib import chain where it can (import the specific functions, not the module wholesale, if the module structure allows). Sector geometry and gate thresholds are module-level constants annotated for later recalibration; the configurable vocabulary is a separate documented constants block in the same module.

**Geometry is a swappable seam (epic TN-3 Stage B)**: v1 ships fixed angular-sector geometry as module-level constants, but the zone-geometry / zone-assignment component MUST be an isolated, swappable unit -- the engine's `direction_shade` / `call_state` output shape is identical whether zones come from today's fixed sectors or a future clustering-derived zone set. This is a v1 design constraint on the module structure, not extra runtime feature work. No clustering in v1.

**Absolute field direction, no handedness branch**: the direction vocabulary is absolute (`LEFT`/`RIGHT` + depth), not handedness-relative pull/oppo -- batter handedness is unavailable on every data path E-228 uses (epic TN-3 and the Non-Goal). This makes the engine *simpler*, not more complex: `classify_field_zone(x, y)` already returns absolute `left`/`center`/`right`, so the engine stores that output directly as `direction_shade` with no translation layer and no handedness branch. The 8 `call_state` values are `TRUE`, the symmetric directional set `LEFT`/`LEFT_SHALLOW`/`LEFT_DEEP`/`RIGHT`/`RIGHT_SHALLOW`/`RIGHT_DEEP`, and `MIXED` (epic TN-3).

**Column semantics (do not get these backwards)**: `batter_positioning.team_id` = the scouted opponent's team id (the batter's team); `perspective_team_id` = the perspective whose API pull produced the spray rows. The engine reads `spray_charts` filtered by `team_id` AND `season_id` AND `perspective_team_id`, and groups by `perspective_team_id` -- the NOT NULL column that is also in the `batter_positioning` PK -- NOT by `spray_charts.team_id`, which is nullable. See epic Technical Notes section TN-6 for the full read contract, including the NULL-`season_id` skip rule and the transaction contract.

The engine's return shape is the concrete Tier 1 / Tier 2 interface defined in epic Technical Notes section TN-1a -- this story owns the exact dataclass names and field names.

## Acceptance Criteria
- [ ] **AC-1**: Given a batter with spray-chart events, when the engine runs, then it produces one `batter_positioning` row per covered fielding position (SS, 2B, 3B, LF, CF, RF) with `call_state`, `team_state_call`, `direction_shade`, `depth_shade`, `bip_count`, `hr_count`, `is_thin`, and `zone_concentration` populated per Technical Notes sections TN-3 and TN-4 -- `direction_shade` holds the absolute `classify_field_zone()` output (`left`/`center`/`right`) stored directly, `call_state` is this position's own call (one of the absolute symmetric enum keys `TRUE`/`LEFT`/`LEFT_SHALLOW`/`LEFT_DEEP`/`RIGHT`/`RIGHT_SHALLOW`/`RIGHT_DEEP`/`MIXED`), and `team_state_call` is the batter's team-state call from the same enum, denormalized identically onto all 6 rows (see AC-4 / TN-4a).
- [ ] **AC-1a** (Stage A -- optimal point): Given a batter with sufficient BIP for a position, when the engine runs, then for that position it computes the batter's optimal fielding point in SVG space, takes the signed delta from `BASE_POSITIONS`, and quantizes each axis to a **signed ordinal step bucket** (`0` / `±1` / `±2`) -- `direction_deviation` (L-R / x axis) and `depth_deviation` (in-out / y axis) -- per epic Technical Notes section TN-3 Stage A. Both are `int | None` on the per-position row dataclass (epic TN-1a) AND persisted to the `INTEGER` `batter_positioning.direction_deviation` / `depth_deviation` columns. `direction_deviation` is NULL exactly when `direction_shade` is NULL (`call_state='TRUE'`); `depth_deviation` is NULL exactly when `depth_shade` is NULL (below the 25-BIP depth gate) -- the NULL rules piggyback on the existing gates, no new NULL logic.
- [ ] **AC-1b** (Stage B -- swappable seam): Given the engine module, when its structure is inspected, then the zone-geometry / zone-assignment logic is an isolated component -- a distinct function or class with a documented seam interface -- and the direction/depth classification consumes only that component's return value, not its internals. Per epic Technical Notes section TN-3 Stage B. (Rationale, not part of the verifiable AC: this seam is what makes a future clustering-derived zone set a one-layer swap rather than an engine rewrite.)
- [ ] **AC-1c** (reference origin + quantization ladders -- single source of truth): Given the Stage A computation, then this story defines and documents, at the computation site in `src/reports/positioning.py`, all three of: (a) the `BASE_POSITIONS: dict[str, tuple[float, float]]` reference-origin constant -- one `# RECALIBRATE`-annotated entry per covered position (`SS`, `2B`, `3B`, `LF`, `CF`, `RF`), in **SVG-space** coordinates; (b) **two separate per-axis `# RECALIBRATE` quantization threshold ladders** -- one for `direction_deviation` (x / L-R axis), one for `depth_deviation` (y / in-out axis) -- that map the signed SVG-space delta to the `0` / `±1` / `±2` ordinal bucket; (c) the resulting stored unit, which is the signed ordinal step bucket (NOT a continuous distance -- per epic TN-3 Stage A, there is no honest SVG→feet conversion, so a continuous value would be fabricated precision). The two ladders MUST be named and documented as two distinct ladders -- `_raw_to_svg` is anisotropic, so the x and y thresholds are different numbers, and a single shared ladder would silently re-introduce the anisotropy bug. This story is the single source of truth for all three; E-228-01's migration column comment references this definition rather than restating it.
- [ ] **AC-2**: Given a batter with fewer than 10 balls in play, when the engine runs, then it still writes **all 6 covered-position rows** (the batter is never skipped), each with `call_state = 'TRUE'` and `is_thin = 1`, per the sample gate in Technical Notes section TN-4.
- [ ] **AC-3**: Given a batter with 10-24 balls in play, when the engine runs, then rows carry a direction lean but `depth_shade` is NULL; given 25+ balls in play, then `depth_shade` is populated -- per Technical Notes section TN-4.
- [ ] **AC-4**: Given a batter whose per-position `call_state` values land in 2 or more non-adjacent named states, when the engine runs, then the batter's `team_state_call` is `MIXED` (written identically onto all 6 of the batter's rows) and the per-position rows carry their individual `call_state` shades -- per the concrete MIXED rule in Technical Notes section TN-4a.
- [ ] **AC-5**: Given a per-zone shade candidate, when it has fewer than 4 BIP in the zone OR less than 35% concentration, then that shade is not applied -- per the per-zone gate in Technical Notes section TN-4.
- [ ] **AC-6**: Given the engine writes results, when it runs a second time for the same `(team_id, season_id, perspective_team_id)` scope, then it first deletes all existing rows for that scope and then inserts the fresh rows within one transaction (delete-then-insert per Technical Notes section TN-2) -- so stale rows for positions or batters no longer present do not persist, and rows are never duplicated. Each inserted row populates all columns, including `direction_deviation`, `depth_deviation`, and `team_state_call` (the batter's team-state call written identically onto all 6 of that batter's rows).
- [ ] **AC-7**: Given an edge-case input (empty spray data, over-the-fence HRs with NULL x/y, a batter with all BIP in a single zone), when the engine runs, then it produces a well-formed result without error -- NULL-coordinate HRs are counted in `hr_count` but excluded from zone classification.
- [ ] **AC-8**: Given `spray_charts` rows for the team/season that have a NULL `season_id`, when the engine runs, then those rows are excluded from the computation and the count skipped is logged at WARNING, per Technical Notes section TN-6.
- [ ] **AC-9**: Given the engine module, when it is inspected, then sector geometry, gate thresholds, and the MIXED-rule threshold are module-level constants each annotated `# RECALIBRATE after first opponent dataset`. The engine writes only stored enum keys to `batter_positioning` and does NOT carry a vocabulary constants block -- the display-word constants block lives in the render layer (E-228-05) per epic Technical Notes section TN-5.
- [ ] **AC-10**: Given the engine module, when its public entry point is inspected, then it has the signature `(conn: sqlite3.Connection, team_id: int, season_id: str)`, returns the typed dataclasses defined per Technical Notes section TN-1a (per-batter result, per-position row carrying the optimal-point deviation, and the reachable per-zone aggregation), and commits its own writes per the transaction contract in Technical Notes section TN-6.
- [ ] **AC-11**: Given `tests/test_positioning.py`, when the test suite runs, then it covers the Stage A optimal-point computation and the signed-delta -> ordinal-bucket quantization on both per-axis ladders (including the `direction_deviation` / `depth_deviation` NULL rules tracking the shade gates, and the `0` / `±1` / `±2` bucket boundaries on each axis), zone classification through the swappable seam, contact-type tallies, depth-from-y, every sample-gate boundary (<10 / 10-24 / 25+), the per-zone 4-BIP and 35% gates, quantization to each named state and to MIXED (per TN-4a), `team_state_call` being written identically onto all 6 of a batter's rows (and equal to the per-batter result's team-state call), the NULL-`season_id` skip (AC-8), and the edge cases in AC-7.

## Technical Approach
Create `src/reports/positioning.py`. Expose a pipeline-agnostic entry point with the signature `(conn: sqlite3.Connection, team_id: int, season_id: str)` that reads `spray_charts` filtered by `team_id` AND `season_id` AND `perspective_team_id` and grouped by `perspective_team_id` (see epic Technical Notes section TN-6 for the full read contract, the NULL-`season_id` skip rule, and the self-committing transaction contract). The engine runs the three stages of epic Technical Notes section TN-3: (A) compute the per-batter optimal fielding point in SVG space, take the signed delta from `BASE_POSITIONS`, and quantize each axis to a signed ordinal step bucket (`direction_deviation` / `depth_deviation`) via the two per-axis `# RECALIBRATE` threshold ladders -- all defined and documented at the computation site; (B) classify direction and depth via the two knobs, with the zone-geometry / zone-assignment isolated as a swappable component; (C) apply the sample gates (TN-4), derive the team-state call via the MIXED rule (TN-4a), and write `batter_positioning` rows -- all columns including the two `INTEGER` deviation columns -- via a delete-then-insert within the recomputed scope (TN-2). Return the typed dataclasses defined in epic Technical Notes section TN-1a so callers (E-228-03, E-228-06) and the Tier 2 layer (E-228-07) have a stable, named interface. Reuse `classify_field_zone`, `contact_type_label`, and the coordinate transform from `src/charts/spray.py` -- do not duplicate them, and import the specific functions to avoid the matplotlib import chain where possible. Geometry/gate/MIXED-rule constants are module-level and documented (epic TN-3, TN-4, TN-4a). The vocabulary constants block (display call-words) is **not** in this module -- it lives in the render layer (E-228-05) per epic TN-5's ownership split; the engine writes only absolute enum keys. No clustering, no pipeline wiring, and no LLM in this story.

## Notes
The vocabulary constants block does **not** live in this module -- it lives in the render layer (E-228-05), per epic TN-5's ownership split (the lexical vocabulary is E-228-04's design decision; the constants-in-code home is E-228-05). `call_state` and `team_state_call` values stored in `batter_positioning` are stable absolute enum keys (`LEFT_SHALLOW`, etc.); display call-words (e.g. "SHADE LEFT SHALLOW") are resolved at render time via the render-layer constants block.

**Deviation persistence -- resolved (data-engineer verdict + de/se reconciliation, 2026-05-15)**: the optimal-point deviation is **persisted** to `batter_positioning` as two `INTEGER` columns, `direction_deviation` and `depth_deviation` -- signed ordinal step buckets (`0` / `±1` / `±2`), one per axis (epic TN-2 carries the DDL and the rationale). Two columns, not one -- the optimal point is 2D. They are persisted because they are not derivable from the categorical shade buckets and are consumed by the E-228-04/05 render path. They are ordinal, not continuous, because the SVG-space delta is anisotropic and unanchored -- there is no honest continuous unit, so a coarse bucket is honestly matched to the signal quality (epic TN-3 Stage A). This story's Stage A computes in SVG space, deltas from `BASE_POSITIONS`, and quantizes via the two per-axis `# RECALIBRATE` threshold ladders; the delete-then-insert (AC-6) writes the buckets. `BASE_POSITIONS` + the two ladders are defined here (AC-1c) and referenced by E-228-01's migration comment. Both the earlier open question and the de+se coordinate-space/unit reconciliation are closed.
