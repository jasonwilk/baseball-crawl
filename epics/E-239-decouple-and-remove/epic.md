# E-239: Decouple Pipeline Imports, Then Remove the Unused Surfaces

## Status
`READY`

## Roadmap
Implements `docs/ROADMAP.md` §5 **Epic D2** ("removal, after A+B green and D1 has soaked"). Per the §0 tracking convention, the §0 table flips slice D2 → E-239 / `PLANNING` at the planning commit and → `COMPLETED` at closure.

## Overview
D1 (E-238) quarantined three unused surfaces — the dashboard, member-team sync, and opponent discovery — marking them deprecated and retargeting navigation off `/dashboard`. **D2 removes them.** It first severs the import coupling that would otherwise crash app startup (and the entire `bb` CLI) when the pipeline modules disappear, then deletes ~25-30% of the codebase that serves surfaces the operator never uses — with the reports flow (the live product) protected at every step.

## Background & Context
The product as actually used is reports-first: log in → generate a one-off scouting report for a GameChanger `public_id` → share the link (`docs/ROADMAP.md` §1). Everything else — dashboard browsing, member-team sync, tracked-opponent management — is unused weight that every refactor, review, and test run pays for (§2 "the big number"). D1 quarantined those surfaces; D2 is the deliberate removal epic the quarantine rule and §6 rule 2 ("quarantine before remove; code before tables; decouple imports before deleting modules") set up.

**The import hazard (why decoupling comes first).** Two verified module-level coupling chains mean a naive deletion breaks running surfaces (SE recon, `.project/research/E-239-deletion-inventory.md` §2a):
1. `src/api/main.py:35 → src/api/routes/admin.py:84` (`from src.pipeline import trigger`) `→ trigger.py:34-35` (`crawl`/`load`) → member crawlers/loaders. `admin.py` also hosts the **protected-core reports admin routes**, so deleting the pipeline without decoupling breaks app startup.
2. `src/cli/data.py:22-24` (`from src.pipeline import bootstrap/crawl/load`, module-level) — used only by the to-be-deleted `sync`/`crawl`/`load` commands, but because Typer imports command modules wholesale at CLI startup, deleting the pipeline modules breaks the **entire `bb` CLI on import**, killing the surviving KEEP commands (`reconcile`, `dedup-players`, `backfill-appearance-order`). (Discovered during D2 discovery; not in the roadmap text.)

This epic was planned with software-engineer (import-graph + deletion inventory, `.project/research/E-239-deletion-inventory.md`), data-engineer (season-machinery + cascade-table inventory, `.project/research/E-239-season-machinery.md`), and claude-architect (context-layer impact) recon. Those artifacts are the authoritative file/symbol/test lists; this epic references them rather than restating every path.

## Goals
- Sever both pipeline import chains so deleting pipeline/member modules cannot break app startup or the `bb` CLI.
- Delete the dashboard surface (routes, templates, dashboard-only season-selection/cross-season-career machinery) with the season-derivation primitive and the `seasons`/`player_season_*` tables untouched.
- Delete member-team sync orchestration, member-only crawlers/loaders, opponent-discovery code, their `bb data` CLI commands, `teams.yaml`, and the dead admin team-management/opponent/programs surface (routes + templates + dead `db.py` helpers).
- Preserve the reports flow (protected core) with zero stat-value or behavior regression, verified by Epic A goldens, aggregate parity, the full suite, and a real `login → generate → share` against production data.
- Shrink the context layer (rules + CLAUDE.md) to describe the reports-only surviving system.

## Non-Goals
- **Dropping any database table.** Per §6 rule 2 (code before tables) and the DE cascade reconciliation, all six quarantined tables stay INERT; the protected report-delete cascade's DELETEs against them are harmless no-ops, so D2 requires **no cascade rewrite**. Table drops are a future epic (Technical Notes §G).
- **Removing the season-derivation primitive.** `derive_season_id_for_team()`/`_with_fallback()`, `ensure_season_row()`, and the `seasons` table are protected core; only the dashboard's season-selection + cross-season-career layer is removed (Technical Notes §C).
- **Removing Epic-E-reserved opponent-resolution code.** `src/gamechanger/resolvers/gc_uuid_resolver.py` (the `progenitor_team_id` bridging Epic E reuses) MUST be preserved even though it has zero importers after D2 (Technical Notes §E).
- **Epic C view-cutover.** D2 does not free `player_season_*` (reports read them); it only simplifies the reader/writer graph for a later Epic C re-plan (Technical Notes §H).
- **Any new feature work.** Pure removal + decoupling under guard.

## Success Criteria
1. App starts and the protected reports surface works end-to-end: `login → /admin/reports → generate a report → open the public /reports/{slug} link`. Verified by the **canary** (Technical Notes §A) — operator-run against production data before the closure commit, eyeballed against prior output.
2. `bb --help` and every surviving command (`reconcile`, `dedup-players`, `backfill-appearance-order`, plus `status`/`creds`/`db`/`report*`) import and run without the deleted pipeline modules.
3. The Epic A report goldens (`tests/test_report_golden.py`) and `bb report verify-aggregates` parity are **unchanged/green** — zero report stat-value movement (§6 rule 4).
4. `GET /dashboard*` and the removed admin routes return 404; the full test suite is green (0 failed) in the main checkout with all changes applied.
5. No surviving module imports a deleted module (verified by grep); the preserved-but-orphaned modules in Technical Notes §E remain present.
6. The context layer describes only the reports-first surviving system; no rule `paths:` frontmatter references a deleted file.

### §C — Season machinery: the removal target is the dashboard layer, NOT the primitive
There is **no separable multi-season path inside `derive_season_id_for_team()`/`_with_fallback()`** — they always derive ONE `season_id` for ONE team (inherently single-season). The roadmap's "keep only the year-only path" phrasing was imprecise. KEEP WHOLE (protected core): `derive_season_id_for_team()`/`_with_fallback()` (`loaders/__init__.py`), `ensure_season_row()`, the `seasons` table, and the reports' single-fixed-season filter in `_query_batting`/`_query_pitching` (`generator.py`). REMOVE (all dashboard-only, zero non-dashboard consumers per the DE artifact Q1): `get_available_seasons()`, `_pick_season_for_year()`, `get_player_profile()` (cross-season career), `get_team_batting_stats`/`get_team_pitching_stats` (`api/db.py`). An implementer MUST NOT hunt for a multi-season path inside the derivation primitive. The within-season dedup guards (`player_dedup.py`, the CLI cross-season-merge block) are correctness guards, **KEEP** (DE Q3).
