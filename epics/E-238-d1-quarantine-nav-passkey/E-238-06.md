# E-238-06: Move passkey challenges to a TTL'd SQLite table

## Epic
[E-238: D1 — Quarantine + Navigation Retarget + Passkey Fix](../E-238-d1-quarantine-nav-passkey/epic.md)

## Status
`TODO`

## Description
After this story is complete, WebAuthn passkey challenges are stored in a TTL'd SQLite table
created by migration 004 instead of two in-process module-global dicts. This makes passkey
login survive multiple workers and app restarts, with login behavior byte-identical to today.
A `src/api/passkey_challenges.py` helper keeps the SQL out of the route handlers.

## Context
Today the challenge stores are `_PASSKEY_LOGIN_CHALLENGES` and `_PASSKEY_REG_CHALLENGES` module
globals in `src/api/routes/auth.py` (TTL 300s, cleanup-on-read only via
`_purge_expired_challenges`). That is single-worker-only and lost on restart mid-login — a real
auth bug, since the operator logs in to generate reports. DE's discovery produced the schema and
lifecycle (folded into epic Technical Notes "Passkey challenge store"). The single biggest
correctness risk is the login lookup-key normalization, which must stay byte-identical.

## Acceptance Criteria
- [ ] **AC-1**: Migration `004_webauthn_challenge_store.sql` creates the `webauthn_challenges`
  table and `expires_at` index per epic Technical Notes ("Passkey challenge store"); the
  migration is idempotent and the app starts clean against a fresh schema.
- [ ] **AC-2**: A login challenge is stored on `GET /auth/passkey/login/options` and
  consumed-and-DELETEd on `POST /auth/passkey/login/verify`; a second verify of the same
  challenge is rejected (replay-proof — the row is gone, returns the current 401 behavior).
- [ ] **AC-3**: A registration challenge is keyed by the session-id hash, overwrites on a repeat
  GET (`ON CONFLICT DO UPDATE`), and is consumed on verify; a missing/expired row yields the same
  400 "session expired" as today.
- [ ] **AC-4**: Expired challenges are rejected on read (`expires_at > datetime('now')` gate) and
  swept on write (`DELETE WHERE expires_at <= datetime('now')` at each create); no background job
  is introduced. `expires_at` is SQLite datetime text everywhere (no epoch floats).
- [ ] **AC-5**: A challenge written by one connection is readable by another connection
  (multi-worker proof) — a test using the FILE-BACKED db fixture (NOT `:memory:`, which would be
  two separate DBs and a vacuous test) writes via one connection and reads via a second; the
  helper's store/consume COMMIT so the second connection sees the row.
- [ ] **AC-6**: The login challenge key derivation is byte-identical to the current code on BOTH
  sides — the STORE side (`/passkey/login/options`: `b64encode(challenge)`) AND the LOOKUP side
  (`/verify`: `b64encode(urlsafe_b64decode(browser_challenge + padding))`) must agree. Asserted by
  a round-trip test: store via the options-path derivation, look up via the verify-path
  derivation, assert a hit. (If only one side is "cleaned up", keys diverge and every passkey
  login fails silently while a lookup-only test still passes — see epic Technical Notes.)
- [ ] **AC-7**: A `src/api/passkey_challenges.py` helper (store/get/consume/sweep) holds the SQL;
  route handlers call the helper rather than embedding SQL. py_webauthn remains the crypto check;
  the DB only gates live-and-unconsumed.
- [ ] **AC-8**: All `_PASSKEY`-referencing tests are migrated to seed/read `webauthn_challenges`
  (grep `tests/` for `_PASSKEY`); table coverage is added to the schema/migration test set
  (`test_migrations.py`, `test_schema.py`, `test_e100_schema.py`, `test_migration_001_auth.py`);
  the full suite is green.
- [ ] **AC-9 (canary — testable half)**: The passkey login and registration store/consume flow
  is verified in-worktree via the migrated table tests (store on options/register, consume on
  verify, replay rejected) per AC-2/AC-3; the full live login → generate → open-share-link path
  (passkey AND magic-link) is designated an operator post-merge check (no live GC creds/pipeline
  in the worktree) per epic Technical Notes ("Canary verification mechanism").

## Technical Approach
Follow epic Technical Notes "Passkey challenge store" exactly. The replay protection is
DELETE-on-consume (do not introduce a mark-used flag). Multi-worker correctness comes from all
workers sharing `data/app.db` (WAL on). Do not add speculative indexes beyond the `expires_at`
index. For tests, avoid `db.backup()` onto a disk-backed test path and capture pytest return
codes without a pipe (per prior dispatch lessons). Confirm the live next migration number is
004 (the `migrations/` dir is authoritative; `.claude/rules/migrations.md` is stale).

Additional implementation constraints (DE discovery):
- **Parenthesize the SQLite column default**: a bare unparenthesized expression default is a
  syntax error — use `expires_at TEXT NOT NULL DEFAULT (datetime('now','+5 minutes'))` (or
  supply it from the helper). Be explicit; if using the column default, parenthesize it.
- **Migration must be concatenation-safe**: `conftest.py::load_real_schema` globs
  `[0-9][0-9][0-9]_*.sql` and concatenates ALL migrations, so `webauthn_challenges` is
  auto-present in every real-schema test once 004 exists — NO conftest edit and NO harness
  plumbing needed. Use `CREATE TABLE/INDEX IF NOT EXISTS`. AC-8's explicit-coverage tests are the
  only test-infra additions.
