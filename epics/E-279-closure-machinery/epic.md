## Overview
Two defects in the closure machinery share one signature: both are invisible to every check the closure sequence performs, and both were found only because someone happened to look. A passive telemetry hook creates worktree directories from command *text*, and the write guard reads directories as dispatch state — so quoting a worktree path near `git add` locks every agent on the machine out of the main checkout. Separately, the archive rename at closure strands references in agent-owned files during a window in which no one is permitted to fix them. This epic closes both, and deliberately does not grow past them.

## Technical Notes

### TN-1: Dispatch order is a design constraint
Two independent reasons, both from claude-architect's §5:

1. **The wedge fix must land first, because dispatching this epic is what triggers the wedge.** Stories here necessarily quote worktree paths next to `git add`. Any Bash command containing both creates a phantom worktree directory for whatever epic number appears in the string. During dispatch this is invisible (a real worktree already has mode 1 active); it surfaces *after* closure as a session-wide write block for the next session. IDEA-230 records this happening for real — the agent investigating the hook wedged the repository by reading about it.
2. **E-279 modifies the machinery that closes it, and the changes go live mid-closure.** `.claude/settings.json` invokes the guard as `"$CLAUDE_PROJECT_DIR"/.claude/hooks/worktree-guard.sh` — the main checkout — so the new guard becomes live when sub-step 4 applies the patch, worktree still standing, five sub-steps to go. `git config core.hooksPath` is `.githooks` (verified), so the new backstop fires on E-279's own closure commit at sub-step 10.
   - **Bounded honestly:** the invocation *path* is verified; whether the harness re-reads a hook per invocation or caches its contents at session start is NOT. If hooks are cached, the guard change lands by the next session rather than mid-closure — the *timing* claim would be wrong, the conclusion would not. TN-2's posture is safe under both readings, which is why it is stated as a rule rather than a prediction.

### TN-3: The instrument — one script, two call sites, no override
`scripts/check_archive_refs.sh E-NNN` greps the literal `epics/E-NNN-` outside `.project/archive/`, non-zero exit on hits.

- **In-window hold** — step (iii) of the restructured sub-step 3, after the worktree rename and before `git add -A`. Repair is cheap here: fix in the worktree, it rides the patch.
- **Fail-closed backstop** — `.githooks/pre-commit`. This is the half that survives nobody looking, which is IDEA-228's actual complaint ("provided somebody looks").

**The two call sites cover different trees, so the backstop is NOT redundant with the in-window hold.** The in-window sweep runs in the worktree and sees the worktree. Step 7a stages *main-checkout* ancillaries — vision signals, idea captures, plan leftovers — which are not in the worktree and are invisible to it. Only the pre-commit gate sees the complete staged set. Stated here because someone will otherwise propose dropping the backstop as duplicative.

**Backstop trigger must be rename-shape-independent.** `git apply --3way` may land the move as delete+add rather than a rename when similarity drops — plausible here, since `epic.md` is rewritten during the epic. Do NOT condition on `rename from` appearing in the patch. Correct form: discriminate on ARCHIVING — a `D` under `epics/E-NNN-` AND an `A` under `.project/archive/E-NNN-` for the same epic ID, enumerated with `--no-renames` (story 04 AC-5). This is agnostic to git's representation.

**"And it also fires on a hand-run archive" is TRUE ONLY UNDER AC-5's PLACEMENT — it is not a property of the trigger.** Measured: a pure-rename staged set yields ZERO entries from `git diff --cached --name-only --diff-filter=ACM`, so `.githooks/pre-commit:26-28` returns 0 before anything below it runs. A correctly-enumerating gate placed below that line is inert on exactly the hand-run case. This is why story 04 AC-5 requires the gate be invoked FIRST in the hook. Do not restate the hand-run claim without the placement it depends on.

**One-epic scoping is load-bearing.** The script takes a single epic ID and must reject a wildcard. A repo-wide `epics/E-[0-9]{3}-` sweep immediately collides with hard-coded epic-path literals in the test suite — the synthetic `epics/E-999-demo/` fixture in `tests/test_doc_pii_hook.py` (11 occurrences), and separately the hard-coded `epics/E-129-…` literals in `tests/test_pii_scanner.py` (~`:536`/`:539`/`:564`), which are **not** synthetic: E-129 is archived, so those are live dead paths that are nonetheless EVIDENCE — test inputs to a prefix predicate — and must never be repointed. *(An earlier form of this note attributed the `E-999-demo` fixture to both files; `E-999-demo` appears in `test_pii_scanner.py` zero times. The conclusion is unaffected and arguably strengthened.)* Story 04 AC-2 carries the full worked example.

**No override (claude-architect ruling, Q1).** The gate can only fire when the in-window hold was skipped or a reference was introduced after it — both are the "nobody looked" case the gate exists for, so an override has no legitimate user. `.githooks/pre-commit` has no per-gate override convention to be consistent with (this was verified; the earlier claim that it did is corrected in TN-7). Document `git commit --no-verify` as the sole escape **and state that it disables the PII scan too**, so it reads as an operator decision rather than an agent's tool. A per-line suppression marker was considered and **declined**: markers suppress matches without certifying safety, and a standing suppression can later hide a real dead pointer. The one narrow deadlock — a line legitimately quoting the pre-archive path as historical fact — has a cheap owner-side fix: reword so the line does not spell the dead path.

**A clean exit means "no literal path references," never "no stranded references."** State this bound in the skill so a clean exit is never over-read.

### TN-4: The repoint ceiling is a tightening, not a grant
`agent-routing.md`'s own-memory carve-out already reserves an agent's own directory to that agent and routes a story touching a *different* agent's memory to claude-architect. **claude-architect already holds the authority.** Writing a fresh grant would restate existing authority in looser words, and a looser restatement of an ownership rule is how the ownership erodes.

Add a **bound** instead, as one sentence beside the existing carve-out: in a closure archive-path repoint, **the only bytes that may change are the path literal**. Rewording, retiring a claim, updating a verdict, or adjusting a rating remains the owning agent's. **If the repoint cannot be made without touching more, it is not a repoint** — route it to the owner or capture it as an idea.

### TN-5: Who runs the sweep, and who rules on its hits
Running a deterministic script and reading an exit code is repository state, not content judgement — the same shape as sub-step 2's clean-tree preflight. **The main session may run it.** It **must not rule on the hits**: a non-zero exit is a HOLD, and each hit routes to its owner.

Owner routing (corrected — claude-architect's original two-way table would misroute): PM for `epics/` and `.project/`; claude-architect for `.claude/**`; **software-engineer for `src/`, `tests/`, `scripts/`; docs-writer for `docs/`.**

Adjudication is domain work because every hit is a criterion-versus-evidence call: an old-path citation may be a pointer to repoint (**criterion**) or a record of where something was observed (**evidence**, which editing would falsify). That cut is governed by `.claude/rules/tool-output-integrity.md`, and a sweep that "fixes every stale-looking path" destroys records.
