## Overview
The opponent scouting report's probable-starting-pitcher section is currently unhelpful: it opens with "this is a true committee situation" and sometimes elevates a tired arm over a fresh one. This epic reframes the section from a fragile "name one starter" prediction into an honest ranked list of the most likely arms (with rest and eligibility), corrects the ranking so fresh arms outrank tired ones, and stops travel-ball opponents from getting blank cards. The engine's ranking is already sound; the fixes are mostly presentation, one deterministic re-rank, and a league-coverage gap.

## Background & Context
The probable-starter feature shipped in E-212 (card) and E-214 (rest-days fix, behind the `FEATURE_PREDICTED_STARTER` flag). A backtest of the **actual** engine (`src/reports/starter_prediction.py`) was run against 17 real opponent seasons (357 labeled games) loaded into the dev DB. Findings (validated against real data, not hypothesized):

- **The engine's rotation-sequence ranking is sound** — it beats naive baselines 2-3x (engine top-1 20.2% / top-2 40.1%, vs "most-frequent" 7.6% and "most-rested" 15.7%). "Committee" is *structurally true* at this level: pitch-count caps make a dominant ace physically impossible (no team's top starter exceeds ~31% of starts). The model is not broken; the presentation is.
- **Defect 1 (presentation, the core fix).** The engine hides its ranked candidate list behind an all-or-nothing confidence gate. It names a single pick only 3.6% of games and is wrong 85% of those. The deterministic ranked top-2/3 is already computed (`StarterPrediction.top_candidates`) but only surfaced in the "low" tier. Surfacing it always — reframed as "most likely arms" — yields an honest ~40% top-2 and matches how a coach thinks ("it'll be one of these two").
- **Defect 2 (ranking, validated win).** The engine ranks a tired arm #1 in 22% of games and is only 8.9% right there — the user's exact complaint. A **hard** rest-discount tiebreaker (demote any candidate inside its preferred-rest window below any fully-available starter) moves aggregate top-1 20.2% → 24.9% and the tired-arm subset 8.9% → 30.4% (22 wins vs 5 breaks, ~4.4:1). Soft/graduated penalties were too timid and did nothing — the hard variant is required. This is a pure deterministic re-rank on the existing engine, not a new model.
- **Defect 3 (league/level gap).** 7 of 17 real opponents got no prediction at all — their team name resolved to youth/travel (`\d+U`), which has no rest-rules table, so the engine suppresses the whole card.
- **Accuracy lever.** The real lever for higher accuracy is scouting *coverage* (fuller opponent game history), not a fancier algorithm — backtest accuracy is deflated by incomplete game history in our DB.

Reports are the sole coaching surface (CLAUDE.md L21 / `docs/ROADMAP.md`). This epic is NOT a ROADMAP A-E slice, so no §0 Roadmap-Tracking entry is required.

**Backtest artifacts** (read-only, throwaway spikes that import the real engine): `.project/research/starter_backtest.py` (engine-vs-baselines), `.project/research/starter_backtest_rerank.py` (the hard/soft re-rank comparison). These are the planning-time validation evidence — they are NOT CI regression gates (see Technical Notes TN-2).

## Goals
- Surface the deterministic ranked "most likely arms" (up to 3 — as many genuine candidates as exist) on every report with sufficient data, each with start-share, days rest, and rest-eligibility — replacing the all-or-nothing "name one or go blank" presentation.
- Reframe the section's wording away from a single "predicted starter" toward "most likely arms / likely rotation slot," eliminating the "true committee situation" hedge as the opening line.
- Add a hard rest-discount tiebreaker so a fully-available starter always outranks a still-tired (preferred-rest-window) one.
- Stop youth/travel opponents from getting blank cards.
- Re-point the Tier-2 LLM narration at the ranked arms and their rest reasoning, and remove the prompt guideline that tells it not to predict.
- Record the corrected model (ranked top-2/3 output, hard discount) in the baseball-coach domain memory.

## Non-Goals
- Replacing or rewriting the rotation-sequence ranking model. The ranking is validated as sound; only a deterministic re-rank tiebreaker and presentation change.
- A true innings-based / outs-based USSSA or Perfect Game rules engine (structural extension per `.claude/rules/pitch-rules.md`). Youth/travel gets a labeled pitch-count *estimate*, not a new rule unit.
- Fuller opponent game-history coverage / ingestion. The scout-coverage analysis was split out of this epic (per user decision, 2026-06-28) and produced as a standalone research memo at `.project/research/scout-coverage-lever.md`; any ingestion build is separate follow-on work.
- Changing the `FEATURE_PREDICTED_STARTER` flag default or any production config (operator decision — see Open Questions).
- Any change to non-pitching report sections (batting, spray, recent form, trust footer).

## Success Criteria
- A report for an opponent with ≥4 games of pitching data renders a ranked list of the likely arms — up to 3, as many genuine candidates as exist (the one-candidate case renders that single arm plus the unavailable block; never the old single-name confidence gate, never a fabricated phantom arm, never a blank/committee-only card) — each line showing start-share, days rest, and rest-eligibility, with no "true committee situation" hedge as the leading text.
- Given a candidate set where the highest-ranked arm is inside its preferred-rest window and a lower-ranked starter is fully available, the fully-available starter is ranked first (per Technical Notes TN-1).
- A report for a youth/travel-named opponent (e.g., "GI Home Federal 18U") with sufficient data renders a prediction labeled as an estimate, instead of a suppressed/blank card.
- The Tier-2 LLM system prompt contains no instruction to withhold a prediction at low/committee confidence, and its narration describes the ranked arms.
- The baseball-coach `probable-starter-model.md` records the ranked top-2/3 output shape (not "one name at top, always") and the hard discount tiebreaker.
- Full test suite green.

## Technical Notes

### TN-1: The hard rest-discount tiebreaker (E-243-01)
The re-rank runs **in place** on the engine's already-ranked, already-**truncated** candidate list (the top-N the engine surfaces) — applied *before* the confidence-tier block, so the named `predicted_starter`/`alternative` and the Tier-2 LLM both consume the re-ranked order. It partitions those candidates into two groups by rest state, then orders all FULLY-AVAILABLE candidates ahead of all DISCOUNTED candidates, preserving the engine's existing relative order *within* each group (a stable partition). Partitioning **post-truncation** (not over the full pre-truncation pool) is what reproduces the validated +17-net numbers — pulling a fresh arm in from below the cut would diverge from `rerank_hard`. Each candidate dict additionally carries its attached rest-state (`days_rest`, `last_outing_pitches`, `rest_eligibility` = available/discounted) for E-243-03 to consume. Rest states (coach model, on top of the legal minimum the engine already enforces via `_is_excluded`):
- **DISCOUNTED** = cleared the hard rest gate but `days_rest < preferred`, where preferred rest by most-recent-day pitch count is: ≤30 pitches → 2 days, 31-60 → 4 days, 61+ → 5 days.
- **FULLY-AVAILABLE** = `days_rest >= preferred`.
- Pitch count unavailable on the most recent day → apply the **IP proxy** (≤2 IP → 0-30 bucket, 3-4 IP → 31-60, 5+ IP → 61+), flag as estimate, and treat as DISCOUNTED if the proxied bucket maps to a non-zero preferred-rest requirement (baseball-coach M1 ruling — conservative-when-uncertain; NOT treated as fully-available). This intentionally diverges from the throwaway backtest harness's `rest_state` (which treated null as available).
- Doubleheader aggregation (sum of pitches on the most recent day) matches the engine's existing exclusion aggregation in `_is_excluded`.

This re-rank operates only on candidates that already cleared the hard exclusion gate. It does not change which arms are excluded, only the order of those that remain. The partition semantics are exactly the `rerank_hard` function in `.project/research/starter_backtest_rerank.py`.

### TN-2: Regression verification is a unit test, not the backtest harness
The validated improvement (aggregate top-1 → ~24.9%, tired-arm subset → ~30.4%) was measured by applying `rerank_hard` *on top of* the engine's output in the throwaway harness. Once the re-rank lives inside the engine, the harness's "engine" baseline already reflects it and the harness can no longer cleanly isolate the delta. Therefore the regression gate for E-243-01 is a **deterministic unit test** asserting the partition behavior on a constructed candidate set — not a re-run of the harness. The harness remains valuable as planning-time provenance and an optional manual eyeball; it is not wired into CI and is not modified by this epic.

### TN-3: Two-tier availability — the engine currently implements only the hard gate
`starter_prediction.py` today computes only UNAVAILABLE (hard exclusion via `_is_excluded`). The "AVAILABLE BUT DISCOUNTED" tier described in the baseball-coach model is NOT yet in code — E-243-01 introduces the preferred-rest-window computation. E-243-03's per-candidate "rest-eligibility" display is **two-valued (available / discounted)** and consumes that same computation; hard-excluded (UNAVAILABLE) arms are not in `top_candidates` and surface in their own `unavailable_arms` sub-block, NOT as a per-line eligibility value (consistent with TN-5 and E-243-03 AC-2/AC-3). This is why E-243-03 depends on E-243-01.

### TN-4: Youth/travel fallback is a labeled pitch-count estimate, not a new rule unit (E-243-02)
`get_rules_for_league()` returns `None` for `youth_travel` (and `usssa` / `perfect_game` / `unknown`), which drives the `confidence="suppress"` blank-card path. The validated, simple fix is to give `youth_travel` a pitch-count rule set as a *labeled estimate* — `league-pitch-rules.md` and `.claude/rules/pitch-rules.md` both designate the USA Baseball Pitch Smart 15-18 curve as the soft prior for unknown leagues (the same tiers already encoded as `LEGION`). E-243-02 holds these tiers in a **distinct named constant** (`PITCH_SMART_15_18`), not a literal reuse of `LEGION`, so a future Legion-only change cannot silently move the youth/travel estimate; the prediction carries an `is_estimate` flag, and the card and LLM mark it as an estimate so a coach knows it is not a binding league rule. (Domain caveat: the curve is the 17-18 sub-bracket and youth teams skew younger, so it tends to under-rest them — which is exactly why the estimate label is load-bearing.) True innings-based USSSA rules are out of scope (Non-Goals). Scope was ratified in Phase 3 (coach + DE): `youth_travel` falls back to the estimate; `unknown` (no level signal at all) stays suppressed. Coded in E-243-02 AC-4.

### TN-5: Presentation reframe (E-243-03)
The engine already computes `top_candidates` (ranked, with `likelihood`, `games_started`, `reasoning`, `recent_starts`). E-243-03 (a) enriches each candidate with the fields the card needs to display — `start_share_pct` (`round(games_started / total_team_games * 100)`, displayed grounded in games per CLAUDE.md Data Philosophy, e.g. "8 of 30 starts (27%)"), days rest, two-valued `rest_eligibility` (available/discounted, from TN-1's attached rest-state), and optional handedness (`throws` passed through, shown when present); (b) adds a new additive engine output field `unavailable_arms: list[{name, reason}]` surfacing the engine's existing hard-exclusion reasons (hard-excluded arms are absent from `top_candidates`, so "unavailable" is its own sub-block, NOT a per-line eligibility value — this is the UXD-FLAG-1 fix); and (c) replaces the confidence-tier-driven card branches in `scouting_report.html` so the ranked list always renders for the non-suppressed data states, with wording reframed from "Predicted Starter" to "Most Likely Arms". The engine-surface change (a/b) is owned by E-243-03, not E-243-01.

**Estimate treatment (resolved this cycle — coach + UXD; heading per UXD Option A).** When `is_estimate` is True (youth/travel, from E-243-02): the heading stays "Most Likely Arms" (unchanged across estimate and non-estimate — UXD owns this copy decision), and the estimate signal is carried entirely by an amber "Estimated rest" badge and a one-line plain-English banner ("This level doesn't publish pitch-count rules, so rest and availability use a standard youth pitch-count guide. Treat as a directional read, not a hard rule."). The no-jargon rule is **absolute, no carve-out**: "Pitch Smart"/"Legion"/"USA Baseball"/"soft prior" NEVER appear in the rendered report (card OR LLM narrative) — the brand name is right for the code constant (`PITCH_SMART_15_18`) and the coach-model doc, wrong for the coach's eyes (UXD E-178 consequence-oriented-label principle). The badge appears ONLY on estimates (absence = full confidence); the word is "estimate", not "uncertain".

**No per-arm estimate marker (UXD ruling).** M1's IP proxy creates a finer-grained, per-arm estimate condition (a null-pitch arm that was IP-proxied), but the card does NOT add a per-line estimate marker on the rest chip. The section-level "Estimated rest" badge + banner contextually cover every arm in a youth/travel section (where the null path is live); the only residual is an IP-proxied arm in a non-estimate (e.g. NSAA-varsity) section, which is a rare edge since NSAA varsity mandates pitch-count tracking — and even then the IP proxy still discounts the arm correctly, so the gap is cosmetic (a missing visual cue), not a ranking error. "Simple first" — SE must NOT invent a per-arm estimate chip variant. Captured as a future-refinement idea (IDEA-083). The `suppress` state renders the spec's copy ("Not enough games yet to project likely arms — rest data still accumulating"). The **ux-designer card spec** (wireframe + field hierarchy + CSS in the report pt-unit idiom + suppress-state copy), persisted at `epics/E-243-probable-starter-usefulness/E-243-03-card-spec.md`, is the concrete handoff artifact the E-243-03 implementer consumes. Display follows `.claude/rules/display-philosophy.md`: contextualize with badges, never suppress a qualifying arm.

### TN-6: LLM reframe (E-243-04) — validated by the narrative bake-off
The Tier-2 system prompt in `src/reports/llm_analysis.py` (`_SYSTEM_PROMPT_TEMPLATE`) currently instructs: "At LOW/COMMITTEE confidence: explain the ambiguity honestly. Do not manufacture a prediction." That last guideline is the prompt-level cause of hedge-heavy "committee" narration and is removed. A pre-READY narrative bake-off (~12 models scored by a GPT-5.1 LLM judge + baseball-coach human review over 5 scenarios; artifacts in `.project/research/narrative-bakeoff/`) selected the concrete spec:

- **Prompt**: the validated **"Variant A"** prompt (verbatim source of truth in `.project/research/narrative-bakeoff/`, A/B evidence in `ab_report.md`) — leads with the named most-likely arm + concrete rest reason, names unavailable arms, plain English, no hedge.
- **Model**: `google/gemini-2.5-flash-lite` at **temperature 0.0** (won on quality, cost, latency; validated by judge AND human review). Wiring (SE-verified, zero blast radius — reports Tier-2 is the only production caller of `query_openrouter`/`_DEFAULT_MODEL`): make gemini the TRUE code default (`_DEFAULT_MODEL` at `openrouter.py:26`) while preserving the `OPENROUTER_MODEL` operator override (do NOT hardcode `model=` at the call site); fix the same-file stale docstring (`openrouter.py:11-12`), `.env.example:247-248`, and the stale default assertion in `tests/test_openrouter.py:~98-109` (all haiku→gemini) in the same change. Temperature is NOT env-controlled — change the hardcoded initial call `_invoke(0.3)` at `llm_analysis.py:282` to `_invoke(0.0)` (retry at `:287` already `0.0`). Lowest supported value if OpenRouter enforces a floor. **Closure context-layer item (claude-architect, NOT the E-243-04 implementer):** `.claude/rules/architecture-subsystems.md:92` records the canonical default model as `anthropic/claude-haiku-4.5` and goes stale with this change — update it to gemini at closure (flag in the context-layer assessment).
- **Data block**: **do NOT introduce a decimal IP field** — surface pitch count (the rest-relevant datum); decimal IP produced "6.3-inning" prose with no coaching payoff. SE-verified there is no decimal-IP field in the current production `_format_pitcher_table` (it lived only in the bake-off block), so this is a guard against adding it, not a removal. The existing integer "IP Outs" game-log column (`llm_analysis.py:131`/`:136`) is OUT OF SCOPE. LLM data block only — the card's rest table / game log are unchanged.

**REJECTED — do NOT re-attempt (recorded so it isn't re-tried):** an enhanced **"Variant B"** (rotation-slot rationale field + committee-honesty instruction) was tested and rejected — it regressed on 2 of 3 models; its rotation-rationale lever cannot fire because every real opponent classifies as "committee" (no differentiated rotation roles — consistent with the structural-committee finding), and its committee-honesty wording backfired, causing models to reintroduce the banned word "committee." Rotation-rationale is a future enhancement ONLY IF the engine is later changed to emit differentiated per-arm rotation roles AND the committee wording is reworked — out of scope for E-243.

Tier-2 remains optional and non-fatal (absence of `OPENROUTER_API_KEY` = silent skip); the deterministic Tier-1 card is unchanged by this story.
