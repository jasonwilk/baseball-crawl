## Overview
Report deletion leaves orphaned reference data — teams, players, and rosters that are no longer reachable from any surviving report and that no code path will ever reclaim. This epic adds a reachability-based reclamation pass, wired into every deletion path, so the ownership invariant holds after every delete. It is a completeness fix for a correct system, not a reliability incident.

## Background & Context
The operator deleted 94 of 96 scouting reports through the admin UI. Every cascade succeeded, referential integrity stayed intact (`PRAGMA foreign_key_check` clean, `PRAGMA integrity_check` `ok`), and all game-level data cleaned up perfectly. But the DB is now carrying **681 orphaned teams (of 737)** and **14,326 orphaned players (of 15,613 — 92%)**, none reachable from a surviving report.

The schema has an implicit ownership model — reports are the root set; teams, players, and rosters are transitively-owned reference data — that per-report imperative cascades structurally cannot enforce. `cascade_delete_team` (`src/reports/lifecycle.py`) answers a LOCAL question ("what does this team own?"); "is this team still reachable?" is a GLOBAL question no local cascade can answer.

There are **three independent root causes**:
- **RC#1 — order-dependent retention leak.** `cascade_delete_team` retains a `teams` row when a `games` row still FK-references it (a load-bearing guard — no FK child has `ON DELETE CASCADE`). That decision is correct at that instant and never revisited; when the referencing games are deleted by a later request, the retained team becomes a permanent orphan (46 logged retentions vs 15 full deletes; all sampled retained teams now have 0 games).
- **RC#2 — opponent stubs never in scope (the largest share).** `_delete_report` cascades only the report's own `team_id`; the opponent stub rows every report creates are never targeted by any delete-path sweep. 681 orphans against 96 reports means most were never in any cascade's scope.
- **RC#3 — players never deleted.** `DELETE FROM players` appears exactly once in the codebase — the merge path. `_delete_team_scoped_data` removes `team_rosters` but never the `players` those rows pointed at. This is independent of ordering and needs its own predicate (`players` has no FK to `teams`).

`PRAGMA foreign_key_check` is structurally blind to this orphan class (it verifies references resolve to live targets; it says nothing about targets with zero referrers), so the fix needs its own invariant check. Full scoping brief: `/workspaces/baseball-crawl/orphaned-reference-data-handoff.md` (a completed PM+SE+DE session with live-DB verification). Discovery for this epic decided the brief's seven §14 [OPEN] questions with DE and SE consultation.

## Goals
- A single reachability-based reclamation pass (`reclaim_orphan_reference_data`) that removes unreachable `teams`, `players`, and `team_rosters`, reclaims all three orphan classes, and holds the ownership invariant after every deletion path completes.
- Wire the pass into the deletion paths (`_delete_report`, `cleanup_expired_reports`) so the invariant self-heals, with a concurrency guard that never deletes an in-flight generation's data.
- Close the pre-`reports`-row concurrency window by making the generator's scouted-team-row and generating-`reports`-row writes atomic (the minimal piece of the `docs/ROADMAP.md:82` race that makes the guard airtight).
- Reclaim the existing 681 / 14,326 backlog via a controlled one-shot that invokes the same pass — no migration, no permanent CLI surface.
- An assertable invariant post-condition (a single-source orphan-count helper) verified by a batch test and by the operator's live-DB sequence.

## Non-Goals
- **Expiry as a reclamation TARGET.** `cleanup_expired_reports` unlinks HTML and nulls `report_path` but keeps the `reports` row — the report is still a live root; nothing becomes unreachable. Expiry is a reclamation TRIGGER only, not a target.
- **Morning-run** — creates only; inherits the invariant free if it later deletes.
- **Auth-table expiry** — `sessions` / `magic_link_tokens` have no reaper, but that is a different mechanism and a different epic.
- **`is_team_eligible_for_cleanup` guards** — those govern authorization to delete; this work is about completeness.
- **The broader `docs/ROADMAP.md:82` run-scoped concurrency fix** — only the minimal generator atomicity refactor (Goal 3) is in scope.
- **A `public_id` mapping cache** — rejected; the whole orphan `teams` row is deleted (per TN-13, `gc_uuid` is always re-resolved from operator-supplied input, never a stored-row dependency).
- **`VACUUM` / `sqlite_sequence` reset** — separate explicit operator decisions; never implicit inside a delete path (the 303 MB file is 95% freelist, recoverable by `VACUUM` independently of any orphan work; this is a correctness problem, not a space problem).
- **The narrow `play_events.play_id → plays.id ON DELETE CASCADE`** (handoff §7.3) — a possible simplification, explicitly "not a fix for this problem"; out of scope.
- **§12 operator-blindness / Post-Cascade Probe** (the admin flash says "Report deleted." even on retention/failure) — deferred and captured as an idea. Reclamation actually reduces its urgency: once the terminal pass runs, a retained team is swept by the end of the same delete request, so the flash becomes accurate again.
- **Schema / migration changes** — none. Confirmed with data-engineer: the reclamation is pure Python (a DAG → two ordered deletes); no table, column, index, or constraint change.

## Success Criteria
- After any deletion path completes **with no concurrent generation in flight**, the invariant orphan-count query returns zero for all three classes (tracked teams with no reports and no games; players with no roster-of-a-surviving-team and no stat rows across all four stat tables including `plays`; roster rows held by orphan teams). Per TN-5, a delete during a live generation legitimately defers the sweep (a liveness delay by design).
- A BATCH deletion (≥3 reports sharing an opponent stub, with at least one team retained by a cross-perspective `games` FK) followed by deleting all reports leaves the invariant query at zero — asserted as the invariant returning zero, NOT as "the delete succeeded."
- A team referenced only via a surviving game's `perspective_team_id` (or `plays.batting_team_id`) is NOT reclaimed; a team referenced by `opponent_links.resolved_team_id` or carrying a `user_team_access` grant is NOT reclaimed (intentional survivors).
- `opponent_links` operator-decision rows are never destroyed by the pass; `user_team_access` grants are never silently cleared.
- The generator commits the scouted-team row and its generating-`reports` row in one transaction; an injected failure between the two persists NEITHER row.
- The existing 681 / 14,326 backlog is reclaimed by a controlled one-shot invoking the same pass; post-run, `foreign_key_check` / `integrity_check` are clean and `bb report reconcile-scoreboard` shows an exact no-diff against a freshly re-snapshotted baseline.
- `python -m pytest tests/` is green at closure.

## Technical Notes

### TN-1: Reachability model — strict DAG, two-phase, no iteration
The ownership graph is a strict DAG: `reports → games → teams → team_rosters → players`. `players` are leaf nodes (nothing FK-references a player except stat/roster rows). Consequences (data-engineer, confirmed against the live schema):
- The orphan-TEAM set is fully determined up front (no reports row, no games row, not an excluded root per TN-7). Deleting teams/rosters/players never changes which teams are orphan → **one team pass, final.**
- The orphan-PLAYER set is determined AFTER the team pass deletes orphan rosters (the only transitive edge) → **one player pass, final**, reading POST-team-deletion roster state.
- A freed roster frees players; a freed player frees nothing; a freed roster/player never frees a team. There is no cycle. "Iterate to a fixed point" (handoff §4.1) describes the team-before-player ORDERING, not multi-round convergence. Wrap the two phases in a terminate-after-zero-delta loop only as a cheap self-assertion; no second real pass ever fires.

**Single transaction, NOT single pre-delete snapshot (data-engineer + software-engineer, load-bearing).** The whole pass runs on ONE connection in ONE transaction with no intervening commit (this is also the concurrency-guard soundness requirement — TN-5). But the two orphan sets are computed at DIFFERENT points WITHIN that transaction; the ordering is load-bearing:
1. reap-then-gate (TN-5).
2. `_orphan_team_ids(conn)` — PRE-delete read (the same point the gate decision is made).
3. delete the team tier (rosters + innocuous pins + team rows) — uncommitted, in-transaction.
4. `_orphan_player_ids(conn)` — POST-team-delete read (SQLite shows a connection its own uncommitted deletes, so the just-removed orphan rosters are absent here → the ~4,900 roster-only players correctly fall out).
5. delete players.
6. self-assert `count_orphan_reference_data(conn)` all-zero + terminate-after-zero-delta.
7. commit — the pass owns the full `BEGIN…COMMIT` internally on the injected connection (TN-5); steps 2–6 span one connection with no intervening commit.

The discriminator: single transaction / single connection / no intervening commit YES; a single pre-delete read for BOTH sets NO — collapsing the two reads into one up-front snapshot computes the player set before the roster deletes land, so roster-only players still look reachable → the exact ~4,900-player miss the DAG ordering exists to prevent. Gate + team-orphan set share the step-2 pre-delete point; only the player set is the deliberate later in-transaction read.

### TN-2: Orphan-team predicate
A `teams` row is an orphan iff ALL hold:
- `membership_type = 'tracked'` (member teams are NEVER orphans — handoff §6.1; the discriminator, since `ensure_team_row` inserts report/scouting teams as `tracked`).
- No `reports` row references it (`reports.team_id`) — the root.
- No `games` row references it (`home_team_id` OR `away_team_id`).
- Not referenced via any team FK on a surviving game's CHILD rows — `team_id`, `perspective_team_id`, `plays.batting_team_id`, AND `game_perspectives.perspective_team_id` (handoff §12.5 #2; `game_perspectives` added in the E-273 Codex-F1 remediation — see the belt-and-suspenders note below). This clause spans SIX game-child FK columns' tables, covering every same-class `teams(id)` FK child.
- Not an excluded root per TN-7 — THREE explicit root exclusions: `opponent_links.resolved_team_id`, `opponent_links.our_team_id`, and `user_team_access.team_id` (none resting on membership scoping to be safe; Option B).

**`is_active` is a DEAD guard — do NOT predicate on it.** `ensure_team_row_with_provenance` hardcodes `is_active=0` on every INSERT despite the column DEFAULT 1, so all 737 rows are 0, including both surviving report teams (handoff §6.3). A sweep guard predicated on `is_active=1` protects zero rows.

**Belt-and-suspenders game-child reference clause — KEEP, in the producer, with WARN-on-fire (data-engineer, reversed from an initial "redundant" reading).** The clause excludes any team referenced by a surviving game's CHILD row via `team_id` OR `perspective_team_id` (on `player_game_batting` / `player_game_pitching` / `spray_charts` / `reconciliation_discrepancies`), via `batting_team_id` OR `perspective_team_id` (on `plays`), OR via `perspective_team_id` (on `game_perspectives` — the sixth game-child table, added in the E-273 Codex-F1 remediation after it was the sole same-class `teams(id)` FK child the original grep-based enumeration filtered out; without it a gameless team carrying only a `game_perspectives` row would abort `DELETE FROM teams` and roll back the entire sweep). Properties:
- **Vacuously true on real data — never wrongly keeps a real orphan.** A gameless team cannot carry such a game-child row (the row would belong to a game the team participates in → the team would have a `games` row → contradiction). So on real data the clause excludes nothing; every real orphan is still deleted. It fires ONLY in a synthetic corrupt state (a game-child row whose `perspective_team_id` is a non-participant — which the loader never produces). AC-2 constructs that state synthetically.
- **Why keep it (the robustness reason, stronger than defense-in-depth).** The pass auto-runs at the end of every `_delete_report` and inside the opportunistic cleanup (TN-4). If the clause were omitted, a stray corrupt game-child row would make the team look like an orphan, and `DELETE FROM teams` would hit the surviving game-child row's FK → `IntegrityError` → ABORT the whole delete request / cleanup pass. The clause converts that reclamation-halting abort into a graceful correct exclusion.
- **WARN-on-fire (load-bearing).** Whenever the clause actually excludes a gameless team carrying a game-child row, log a WARNING with the team id + referencing table ("excluded from reclamation despite no games — possible orphaned game-child row, operator backfill"), mirroring the FK-safe-orphan stub+WARN convention in `.claude/rules/data-model.md`. Without the WARN, graceful-skip silently swallows exactly the corruption signal the loud abort would have surfaced.
- It lives INSIDE `_orphan_team_ids` (TN-8) as an extra AND-clause so the DELETE and the COUNT agree by construction — never a separate check.

### TN-3: Orphan-player predicate (the §15 `plays` correction is load-bearing)
A `players` row is an orphan iff it has NO surviving reference in ANY of:
- `team_rosters` belonging to a SURVIVING (non-orphan) team, AND
- `player_game_batting.player_id`, AND
- `player_game_pitching.player_id`, AND
- **`plays.batter_id` OR `plays.pitcher_id`** — this table was OMITTED from the handoff §15 query; a plays-only stub (the plays loader creates stubs via `ensure_player_row`) would be falsely counted dead and DELETED without it (data-engineer correction), AND
- `spray_charts.player_id` OR `spray_charts.pitcher_id`.

(`reconciliation_discrepancies.player_id` is bare `TEXT NOT NULL` with NO `REFERENCES players` FK — verified — so it is not a reachability edge and is correctly absent from the predicate. **Knowingly-accepted residual (CR minor):** deleting an orphan player can therefore leave a dangling `player_id` string in a surviving game's recon row. No integrity break (no FK) and practically unreachable — a player appearing in `reconciliation_discrepancies` carries `plays` rows the predicate already catches, so a genuinely-orphan player has no recon row — but it is a tiny instance of the epic's own "no knowingly orphaned data" thesis, accepted here rather than widening the predicate to a non-FK text column.) The player pass runs AFTER the team pass so freed rosters make the ~4,900 roster-only players unreachable (TN-1).

### TN-4: The seam and wiring
`reclaim_orphan_reference_data(conn) -> ReclaimResult` in `src/reports/lifecycle.py` — an ADDITIVE terminal pass (does NOT modify `cascade_delete_team` semantics, so the two behavior-pinning tests `test_cascade_delete_team_preserves_games_row_when_other_perspective_remains` and `..._drops_games_row_when_last_perspective` stay green). `lifecycle.py` is deliberately client-free (no httpx/jinja2/generator import), importable from the admin route, CLI, and script without inverting layering.

Team-tier cleanup of the innocuous team-scoped pins (`team_rosters`, `scouting_runs`, `crawl_jobs`, `coaching_assignments`, `scheduled_report_runs`) may reuse the existing FK-safe `_delete_team_scoped_data`, BUT that helper is a **BLIND executor** — it re-checks nothing and unconditionally deletes the `teams` row when `delete_team_rows=True`; ALL safety lives in the orphan-set predicate (TN-2). It is also **MONOLITHIC / all-or-nothing** (data-engineer F2): one function that deletes `team_rosters` + `scouting_runs` + `crawl_jobs` + `coaching_assignments` + `scheduled_report_runs` + `user_team_access` + `opponent_links` (both columns) + optionally the `teams` row — you CANNOT "route only the innocuous pins" through it. The two real options are: **(a)** call it WHOLESALE (safe BY CONSTRUCTION — the `_orphan_team_ids` predicate excludes all three destructive-column roots per TN-7 Option B, so the `opponent_links` DELETE/UPDATE and the `user_team_access` DELETE all no-op); or **(b)** write a TAILORED cleanup that omits those DELETEs. Under Option B both are EQUALLY SAFE (see TN-7); tailored is the mild preference only as CLEANER (it never issues no-op DELETEs against operator-decision tables), NOT safer. **Binding guardrail: the implementer MUST NOT modify `_delete_team_scoped_data` to skip clauses — it is SHARED with `cascade_delete_team` and `cleanup_orphan_teams`, and editing it to drop `opponent_links`/`user_team_access` handling breaks those live delete paths.** `_delete_team_scoped_data` does NOT delete `players`; the player tier is a separate pass (TN-3).

**Wiring (SE correction, supersedes handoff §7.4):** the pass attaches to the delete paths PLUS the opportunistic-cleanup trigger —
- End of `_delete_report` (`src/api/routes/reports_admin.py`), **unconditionally**, on a fresh connection AFTER conn2 commits. `_delete_report` is a 2N structure (conn1 report-row+file+eligibility+commit at :583-616; conn2 `cascade_delete_team` internal commit, opened only `if eligible`), so the pass must run at the very end regardless of `eligible` — a different report's deletion may have freed teams even when this one's team is not eligible (RC#2).
- `cleanup_expired_reports` (`lifecycle.py`). **Note (CR S1): this ALSO fires at the START of every `generate_report` (`generator.py:1503`), not only on deletion** — so the sweep runs on every report-generation start too. That invocation is SAFE by construction: the current run's scouted `teams` row is not committed yet (`_ensure_team_row` is a later `run()` step, after the opportunistic cleanup), and concurrent generations are covered by the reap-then-gate (TN-5). `cleanup_expired_reports` already reaps stale-generating internally; see the double-reap note below.
- Do NOT wire into `_cleanup_orphans` (`generator.py:2236`) — it already does precise TN-4 created-set cleanup, and the run's own `reports` row is `generating` there, so a gated global sweep would no-op.

**Double-reap note (SE MINOR-2):** `cleanup_expired_reports` already calls `reap_stale_generating_reports` (`lifecycle.py:231`), and the pass reaps internally (TN-5). This is harmless (the reap is idempotent), but leave BOTH — do NOT remove the pass's internal reap (it is what makes the guard self-contained per TN-5) and do NOT assume the call-site reap is dead code.

### TN-5: Concurrency guard — reap-then-gate on `status='generating'`, in ONE transaction
The pre-`reports`-row window is real. **Refinement (software-engineer): the scouted team is already protected by its own `reports` row (any status, incl. `generating`), so the REAL exposure the guard protects is opponent STUBS** — they never get a `reports` row and are game-less until mid-pipeline. Guard (software-engineer):
1. The pass REFUSES to run while any live `generating` report exists (a durable cross-process in-flight signal covering own-team and opponent-stub exposure).
2. **Reap first, then gate**: call `reap_stale_generating_reports` (`lifecycle.py:107`, `STALE_GENERATING_SECONDS=3600`) FIRST (its own committed transaction), then check for remaining generating rows — so a crashed generation is reaped, not treated as an hour-long block.
3. **The gate-check, the orphan-set compute, and the DELETEs MUST run in ONE transaction on ONE connection (single snapshot for the gate + team tier) — this is a soundness requirement, not a style choice.** Split across connections it is a TOCTOU hole: the gate-read on connection A sees 0 generating → passes; generation G then commits its team + `generating` reports row (atomic per TN-6) and later commits opponent stub S; an orphan-read on a FRESH connection B takes a NEW snapshot that sees S (no reports/no games → orphan candidate) and DELETES a live generation's stub, because the gate already passed on A and is never re-checked. The single-transaction shape closes it: S is committed AFTER the pass's snapshot, so it is not in the orphan set → never deleted. This resolves the commit-ownership question: **the pass takes `conn` and OWNS the full transaction, `BEGIN…COMMIT` internally at BOTH wiring sites; "caller-owns-no-commit" is NOT viable.** This is the NAMED EXCEPTION to the codebase's usual caller-owns-the-transaction convention (`reload_game_plays`, `merge_player_pair(manage_transaction=False)`): here the check→compute→delete must be atomic, so the pass cannot hand the commit boundary to the caller. The wiring sites pass a fresh `get_connection()` (`_delete_report` calls it on a fresh conn3 AFTER conn2 commits; `cleanup_expired_reports` calls it at its own point); tests/the one-shot inject their DB. (The player-set read is a later point WITHIN the same transaction — TN-1 ordering.)
4. The generator atomicity refactor (TN-6) closes the residual window so a `teams` row is never visible without its protecting generating row → the gate becomes airtight.

**Deferral is an explicit signal (software-engineer MINOR-1, CR S3, data-engineer F4 — one fix).** When the gate refuses, the pass deletes nothing and returns a `ReclaimResult` carrying an explicit `deferred: bool` (or `skipped_generating`). This is the `.claude/rules/python-style.md` missing-safety-signal shape: without it, "0 deletions, no error" is indistinguishable from success, and a non-zero post-run orphan count (the one-shot's failure signal, E-273-05) cannot tell "deferred — re-run when quiescent" from "ran, genuine leak remains." Consumers (the one-shot's exit-code semantics) MUST key on `deferred`, not on the count alone.

**Named failure mode:** a hard-killed generation between the team+reports commit and the reaper firing DEFERS the sweep up to `STALE_GENERATING_SECONDS`; its orphans are reclaimed by the next trigger after the reaper fires. This is a **liveness delay, not a safety hole** — nothing wrong is deleted; the guard fails toward "don't sweep" (the correct bias, matching `.claude/rules/python-style.md` "a missing safety signal defaults to REFUSE"). **Rejected:** reusing TN-4 `created_team_ids` (in-memory single-process; solves the inverse attribution problem; the sweep deletes teams it did NOT create and needs a cross-process on-disk signal, which `status='generating'` already is); a min-age predicate (arbitrary — a slow generation exceeds it and a live team gets deleted); capture-then-re-verify (useless — the in-flight team satisfies the orphan predicate throughout the window). The guard SHOULD live inside `reclaim_orphan_reference_data` so no caller can forget it.

### TN-6: Generator atomicity refactor — connection-injection
Merge the scouted-team-row commit and the generating-`reports`-row commit into ONE transaction in the generator's `run()` (the two current commits have no network between them). **Blast radius (SE, grep-verified):** contained to the single `run()` call site (`generator.py:1579`/`:1582`); `_ensure_team_row` and `_create_report_and_run_record` have no other src caller (`ScoutingCrawler._ensure_team_row` / `GameLoader._ensure_team_row` are DIFFERENT methods — unaffected). Three tests call `_ensure_team_row` standalone (the IDEA-127 identity tests at `test_report_generator.py:1314/:1341/:1375`); `_create_report_and_run_record` has zero direct test callers.

**Recommended shape:** connection-injection (optional `conn` param — `conn=None` opens+commits its own connection, backward-compatible so the three IDEA-127 tests stay green untouched; `conn` passed = use it, do NOT commit; `run()` opens one connection, calls both in FK order teams → reports → `report_generation_runs`, commits once). Matches the codebase "caller owns the transaction" convention (`reload_game_plays`, `merge_player_pair(manage_transaction=False)`). **Must-preserve:** the IDEA-127 public_id-backfill + match_method-downgrade block (`generator.py:1671-1707`) — the refactor moves ONLY the commit boundary, not that logic.

### TN-7: `opponent_links` / `user_team_access` are reachability ROOTS, not pins to clear
Per handoff §6.1/§10.2, an `opponent_links` row is an operator judgment no API recreates (hand-run `map-opponent` resolutions, `no_presence` declarations); a `public_id` is a lookup. `user_team_access` is a LIVE security-grant table.
- **Exclude, don't clear.** A team referenced by `opponent_links.resolved_team_id` OR carrying a `user_team_access.team_id` grant is EXCLUDED from the orphan set (TN-2), not deleted and not cleared. This preserves the operator/user decision AND makes the FK non-blocking (a kept team is never DELETEd — the two goals align).
- The pass MUST NOT DELETE `opponent_links` rows or NULL `resolved_team_id`, and MUST NOT DELETE `user_team_access` grants (this is why `_delete_team_scoped_data` cannot be reused for those tables — TN-4). Current exposure is LATENT (0 `opponent_links` rows, 0 member teams today) but the predicate must be correct for when they exist.
- **THREE destructive columns, each neutralized by its OWN explicit root-exclusion (data-engineer Option B + CR S2).** `_delete_team_scoped_data` destroys operator/user-decision rows in THREE ways, and the predicate excludes ALL THREE as roots (symmetric — `opponent_links` is outside the reachability graph, so a team referenced via EITHER column is a root): (1) `DELETE FROM opponent_links WHERE our_team_id IN (orphan_ids)` — excluded by the `our_team_id`-root clause. **Why a root and not "member-scoping": the "`our_team_id` is always a member team" invariant is CONVENTIONAL, not schema-guaranteed** — `opponent_links.our_team_id` is a bare FK with no `membership_type` CHECK (migrations/001:428), and it is member only because morning-run happens to iterate the operator's LSB teams; a future path passing a tracked team as `our_team_id` would break it silently. The explicit `our_team_id`-root exclusion closes that latent footgun and is a provable NO-OP on real data (a member `our_team_id` is already tracked-scoped out), so it costs nothing and only fires in the bent-invariant case. (2) `UPDATE opponent_links SET resolved_team_id=NULL WHERE resolved_team_id IN (orphan_ids)` — excluded by the `resolved_team_id`-root clause. (3) `DELETE FROM user_team_access WHERE team_id IN (orphan_ids)` (`lifecycle.py:521`) — excluded by the `user_team_access`-root clause. With all three columns as explicit predicate exclusions, **reuse-wholesale and tailored are equivalently safe** (the wholesale opponent_links DELETE/UPDATE and the user_team_access DELETE all no-op because none of their teams are in the orphan set) — Option B collapses the reuse-vs-tailored choice from a SAFETY tradeoff to a STYLISTIC one. Tailored is still the mild recommendation (cleaner — it never issues no-op DELETEs against operator-decision tables), but neither is unsafe. The guard test (E-273-01 AC-4) MUST seed all three survivor shapes and assert each survives and no `opponent_links`/`user_team_access` row is touched. Either way, MUST NOT edit the monolithic `_delete_team_scoped_data` (TN-4).
- **Predicate-vs-assertion guardrail — the assertion EXCLUDES roots too (data-engineer F5, corrects an earlier DRAFT inconsistency).** The exclusion lives in the DELETION predicate AND the invariant ASSERTION uses the SAME orphan predicate INCLUDING the roots exclusion. Roots are intentional survivors, NEVER counted as leaks. **Why this must be explicit:** a tracked, resolved-but-not-yet-reported opponent (referenced by `opponent_links.resolved_team_id`, no `reports` row, no `games` row) is orphan-SHAPED — so an assertion that counted bare `reports + games + tracked` WITHOUT the roots exclusion would flag that legitimate survivor as a leak and fail the zero-assertion even though the pass worked correctly. The F1 shared-source design (TN-8) makes this structurally unbreakable: because the COUNT derives from the SAME `_orphan_team_ids()` the DELETE targets, "delete excludes roots, assertion doesn't" is impossible.

### TN-8: Single-source orphan predicate — shared id-set producers (code-canonical)
The predicate must be defined ONCE and used by BOTH the pass's DELETE targeting AND the invariant COUNT — not merely shared between the two count consumers (data-engineer F1, one layer deeper than the original DRAFT). Otherwise the DELETE predicate and the COUNT predicate are two hand-written copies of the same logic and drift (the `plays` fix lands in one but not the other; the roots-exclusion in one but not the other) — the exact "de-dup the dedup" / `recon_scoreboard` code-canonical hazard. Shape (E-273-01):
- **`_orphan_team_ids(conn) -> set[int]`** — the ONE team predicate: `membership_type='tracked'` AND `NOT EXISTS reports.team_id` AND `NOT EXISTS games.home/away_team_id` AND `NOT EXISTS opponent_links.resolved_team_id` (root, TN-7) AND `NOT EXISTS opponent_links.our_team_id` (root, TN-7 — Option B) AND `NOT EXISTS user_team_access.team_id` (root, TN-7) AND the belt-and-suspenders game-child reference clause (TN-2 — spanning all SIX game-child FK tables incl. `game_perspectives`). `is_active` is NOT consulted (dead guard).
- **`_orphan_player_ids(conn) -> set[str]`** — the ONE player predicate (player_id is TEXT PK): calls `_orphan_team_ids(conn)` internally so "surviving roster" is state-independent; orphan iff none of `player_game_batting` / `player_game_pitching` / `plays`(batter OR pitcher) / `spray_charts`(player OR pitcher), and no `team_rosters` row whose `team_id` is NOT in the orphan-team set.
- **`count_orphan_reference_data(conn) -> OrphanCounts`** = `len(_orphan_team_ids)`, `len(_orphan_player_ids)`, and the orphan-held roster-row count — the SAME sets the DELETE targets, so the count and the delete cannot disagree.

**The COUNT/ASSERTION excludes roots by construction (F5).** Because the count derives from `_orphan_team_ids` (which excludes the TN-7 roots), the invariant assertion cannot flag a legitimate `opponent_links`/`user_team_access` survivor as a leak — the earlier "assertion stays reports+games+tracked [without roots]" wording is removed.

**Consumers.** The batch test (E-273-04) and the one-shot's post-run assertion (E-273-05) MUST consume `count_orphan_reference_data`, never re-inlining the query. The `plays` correction (TN-3) lands in `_orphan_player_ids` and nowhere else, so it is automatic for the pass, the count, 04, and 05.

**SQLite note (data-engineer, for the implementer):** build the "surviving team" test as a correlated `NOT EXISTS (SELECT 1 FROM teams ot WHERE ot.id = r.team_id AND <orphan-team predicate>)` rather than a Python-materialized `NOT IN (:orphan_ids)` f-string — the orphan set can be large (681 today), which risks SQLite's 999-bound-variable limit, and the correlated form also keeps ONE predicate definition.

### TN-9: One-time backlog vehicle — a `scripts/` one-shot invoking the same pass
No migration, no permanent `bb data` command, no duplicated SQL (data-engineer, OQ4). The graph is a DAG so pure SQL COULD express it, but a SQL migration/script would DUPLICATE the tracked-scoping + plays-inclusive-players + opponent_links-root predicates in a second location that drifts, and a migration runs on every fresh/CI/bootstrap DB where nothing exists to reclaim (a data condition, not a schema change). The ongoing pass wired into `cleanup_expired_reports` (TN-4) reclaims the backlog automatically on first invocation; the `scripts/` one-shot (E-273-05) is a controlled, quiescent-DB, decoupled-from-generation reclamation that IMPORTS and calls `reclaim_orphan_reference_data` (DRY — zero duplicated predicates). Per `.claude/rules/architecture-subsystems.md` the import boundary holds: `scripts/` may import `src/`, not vice versa.
