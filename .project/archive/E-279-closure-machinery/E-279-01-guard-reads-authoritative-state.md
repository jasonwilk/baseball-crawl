## Description
After this story is complete, `worktree-guard.sh` decides "is a dispatch active?" by asking git rather than by globbing a directory. A directory under `/tmp/.worktrees/baseball-crawl-E-*` that git does not know about no longer blocks every agent in the session from writing to the main checkout. A genuinely crashed dispatch still enforces the stricter mode — the guard gets stronger there, not weaker.

## Context
This is the live defect and it runs first (epic TN-1). Today the guard globs for a directory (`worktree-guard.sh:86`) while `send-message-counter.sh` creates directories from paths parsed out of *command strings* at PreToolUse time. Any Bash command that merely mentions a worktree path near `git add` — an audit, a grep, a quoted example — manufactures the directory and wedges the guard for every agent on the machine, including closure work and idea capture. IDEA-230 records this happening for real: the agent investigating the hook wedged the repository by reading about it, and a fabricated epic number was enough to reproduce it.

Fixing the guard rather than the counter is deliberate. It makes the guard read authoritative state instead of a filesystem side effect, which closes the whole class — any future hook or agent that creates a path under `/tmp/.worktrees/` re-opens the hole otherwise.

The design constraint that shapes every AC here: **this must not convert a fail-closed guard into a fail-open one.** The guard's own header states the current conservatism deliberately ("A stale worktree from a crashed dispatch safely enforces the stricter mode"). The hook already fails open when `jq` is missing, so precedent runs both directions inside one file — the predicate below is claude-architect's ruling, not an implementer's judgement call.

## Acceptance Criteria
- [ ] **AC-1** (authoritative read — the defect under repair, with a REAL reachable RED): Given a directory EXISTS under the worktree root for an epic that `git worktree list --porcelain` does NOT report, when an agent attempts a Write to a non-implementation path in the main checkout, then the write is ALLOWED (mode 2). **RED state: a glob-based detector resolving the SAME root DENIES this write**, because the glob finds the planted directory. The test plants that directory under an **injected temporary root** (AC-1b) and stubs `git`, so the RED is genuine, hermetic, and leaks nothing into the session.
  - ⚠️ **The literal pre-fix hook CANNOT exhibit this RED, and an implementer who checks it out to demonstrate the failure will be misled.** The pre-fix guard has no root injection — it globs `/tmp/.worktrees` unconditionally and is blind to an injected root, so against a test planting its directory under a temp root it **allows**, and the test passes. Anyone reading that as "the test is broken" has diagnosed the wrong thing. **The RED pins the BEHAVIOUR — detection must not be a directory glob — not a historical revision.** The regression it genuinely catches is detection reverting to a glob while the root variable remains, which is the reachable future defect. *(claude-architect, validation pass.)*
  - **⚠️ Read this before "simplifying" the Given — an earlier form of this AC had NO reachable RED and the reason is subtle.** It required only that `git` report no epic worktree, with no directory present, asserting the decision was "directory-independent." But with no directory present **the pre-fix guard ALSO allows** — its glob finds nothing, `WORKTREE_DIR` is empty, control falls to mode 2. The test passed against the unfixed code, AC-1 collapsed onto AC-5 (which already covers exactly that scenario), and **the epic's headline defect was left with no criterion that could go red anywhere.**
  - **The tension is real and cannot be drafted away: directory-independence is only OBSERVABLE when a directory exists.** Independence cannot be demonstrated in an arm where the directory is absent. That is why the injected root (AC-1b) is required rather than cosmetic — it is the only way to have the directory present and prove it is ignored, without creating one at the real `/tmp/.worktrees` path. *(claude-architect owns this correction: its earlier guidance that the AC was "provable with a stubbed `git` and no directory" was the defective wording, faithfully implemented.)*
  - **AC-1 and AC-5 must remain distinguishable.** AC-5 is the no-directory authoritative-no-dispatch case; AC-1 is the directory-present-but-unregistered case. If a change makes both provable by the same test, AC-1 has lost its RED again.
- [ ] **AC-1b** (the injectable worktree root, with five bounds): The detection block resolves the worktree root through a single variable — default form `WT_ROOT="${BB_WORKTREE_ROOT:-/tmp/.worktrees}"` — and the five bounds below hold. Rationale: it is what makes AC-1's RED reachable and hermetic, and it removes (rather than relocates) the session-leak risk AC-7 was written to manage.
  1. **ONE variable governs BOTH branches** — the registry match and the glob fallback. If they can diverge, the guard's two paths disagree about where worktrees live, which is worse than either alone. *(Verified during planning: these are the only two code sites referencing the worktree root. The worktree-path pass-through keys on `MAIN_PREFIX` and never references `/tmp/.worktrees`, so there is no third site to thread the variable through.)*
  2. **A set-but-missing root fails CLOSED (mode 1) — and this is a CONFIGURATION PRECONDITION evaluated FIRST, before the registry read.** A typo must not read as "no dispatch." This is loud and immediate — the whole session blocks — which is the correct direction for a misconfiguration. **RED state:** a bogus `BB_WORKTREE_ROOT` yielding mode 2.
     - **PRECEDENCE, stated because without it this bound and AC-5 give OPPOSITE answers on the same input.** git lists worktrees regardless of whether the configured root exists, so with a set-but-missing root AND a readable registry, AC-5 ("registry readable, control line present, no epic worktree listed → mode 2") and this bound both apply and disagree. An implementer could satisfy either ordering and honestly believe the spec was met. **A set-but-missing root short-circuits to mode 1 and AC-3/AC-4/AC-5 are NOT REACHED**; those three describe the predicate that runs once the root is valid.
     - ⚠️ **SET-ONLY. Generalising this bound to the DEFAULT root would brick the repository.** It applies **only** when `BB_WORKTREE_ROOT` is explicitly set. **An absent DEFAULT root is NORMAL** — `/tmp/.worktrees` need not exist when no dispatch has ever run — and MUST NOT fail closed. An implementer who reads "a missing root fails closed" and applies it to the default would deny **every main-checkout Write/Edit in every session with no dispatch running**. **RED state:** an unset environment with no `/tmp/.worktrees` directory denying a main-checkout write.
     - **Why this RED is written out rather than left to judgement:** `/tmp/.worktrees` happens to exist on the current machine, so the generalised form would very likely PASS local testing and fail on a fresh boot or a clean container. The failure is invisible where it will be tested and total where it will not. *(claude-architect, validation pass.)*
  3. **The default is the literal `/tmp/.worktrees`**, so an unset environment behaves byte-identically to today and AC-6's diff check still means something.
  4. **The hazard is documented at the variable**: it exists for hermetic testing, production never sets it, and a wrong-but-existing root is caught by bound 5 rather than silently disabling dispatch detection.
  5. **A SET-but-WRONG root fails CLOSED — the mismatch check.** When `BB_WORKTREE_ROOT` is **set**, additionally match the registry output for **any** `baseball-crawl-E-` worktree **irrespective of root**. If that finds an entry while the root-anchored match found none, **the configured root is wrong — select mode 1.** **RED state:** a real epic worktree registered under `/tmp/.worktrees` while `BB_WORKTREE_ROOT` points at some other existing directory, yielding mode 2.
     - **This is the bound that keeps AC-2 TRUE WITHOUT QUALIFICATION, and that is the whole point of it** (claude-architect ruling, Codex P2-4). Without it: the root is set to an existing-but-wrong directory, the registry read succeeds, the root-anchored match finds nothing, `WORKTREE_DIR` is empty, and the guard selects **mode 2 while a real prunable worktree is registered elsewhere** — so AC-2's guarantee is false exactly there. **Bound 2 cannot catch this**: bound 2 fires on a root that is MISSING, and this one EXISTS.
     - **Why hardening rather than scoping AC-2** — PM proposed scoping AC-2 to a correctly-configured root; claude-architect ruled against it and PM concurs. **Qualified safety claims lose their qualifiers when relayed**, which this epic demonstrated three times in one session (the `.gitignore` range, the "only non-blocking path" sentence, the two-file fixture attribution). **AC-2 is precisely the criterion a future epic will quote to justify not re-checking the guard, and it will be quoted without the scope line.** A safety AC true only under a configuration the reader must remember is a worse artifact than two lines of shell.
     - **Cost, stated because both sides belong in the record:** a path-spelling mismatch — a trailing slash, or a symlinked `/tmp` resolving differently in git's output — now **blocks the session** rather than passing quietly. That is a **loud failure in the conservative direction**, the same character as bound 2's behavior on a missing root, and it surfaces a misconfiguration instead of silently disabling dispatch protection. **A loud false block is better than a silent true one** under this repo's fail-closed doctrine.
     - **Cheap by construction:** one extra grep over registry output already in hand, **no additional `git` call**; **inert when the variable is unset**, so production behavior is byte-identical and AC-6's diff pin is undisturbed; and it lives only in the registry-readable branch, which is the only branch AC-2 describes. **No test shape changes** — AC-1 (stub reports nothing → no mismatch → mode 2), AC-2 (stub reports the worktree under the injected root → match → mode 1), AC-3/AC-4 (fall back before the registry is usable, so the check does not apply), AC-5 (only the main checkout listed → no epic worktree anywhere → no mismatch → mode 2).
  - **On the security question, answered rather than assumed** (claude-architect): the knob grants no capability the trust boundary does not already grant. The hook's environment is the Claude Code process environment; an agent's Bash call cannot mutate its parent's, so the only way to set `BB_WORKTREE_ROOT` is `.claude/settings.json` — and anyone who can edit that file can already unregister the hook outright. This is a configurability cost, not a security cost.

## Technical Approach
claude-architect's ruling on the predicate, reproduced because it is a design decision rather than a suggestion:

The shape below is the ruled predicate; the root variable and its **five** bounds (AC-1b) fold into it, and the exact expression of the root-aware match, the mismatch check (bound 5) and the fail-closed branches is the implementer's.

```
WORKTREE_DIR=""
if WT_LIST=$(git -C /workspaces/baseball-crawl worktree list --porcelain 2>/dev/null) \
   && printf '%s\n' "$WT_LIST" | grep -q '^worktree '; then
  # Registry readable: authoritative answer, empty included.
  WORKTREE_DIR=$(printf '%s\n' "$WT_LIST" \
    | sed -n 's#^worktree \(<WT_ROOT>/baseball-crawl-E-.*\)$#\1#p' | head -1)
else
  # Registry unreadable or anomalous -> fall back to the pre-existing glob.
  WORKTREE_DIR=$(ls -d <WT_ROOT>/baseball-crawl-E-* 2>/dev/null | head -1)
fi
```

Both `<WT_ROOT>` occurrences resolve from the SAME variable (AC-1b bound 1) — they are the only two code sites referencing the worktree root.

**No timeout, deliberately.** This reads a small directory under `.git/` and fires on every Write/Edit; a timeout adds a failure mode to buy protection against one for which there is no evidence.

**Header reconciliation is governed by AC-6b, not by this section.** It is four sites with a written verdict each and three RED forms — including a stale operator REMEDY, not only stale claims. Do not treat "update the header comment" as the requirement; AC-6b is.

The guard goes live mid-closure for this very epic (epic TN-2) — the fallback path is what makes that safe, because an unreadable registry yields exactly today's behavior.
