## Description
After this story is complete, the archive rename happens in the epic worktree before the closure patch is generated, rather than in the main checkout after the patch is applied. Fallout from the rename can then be repaired in the worktree — where the guard already permits the owning agent to write — and those repairs ride the closure patch. The main-checkout rename step and the three rename-ordering rules that exist only to manage it are deleted, and both rollback paths collapse to a single ordering-free pair of commands.

## Context
Three conditions in the current closure sequence are jointly unsatisfiable whenever an archive rename leaves references behind, which is the normal case rather than an edge one. Sub-step 6 renames `epics/E-NNN-slug/` into the archive, breaking outbound references in agent-owned files. Those files are agent-owned, so the orchestrator must not edit them. And the worktree guard blocks the owning agent from the main checkout until the worktree is removed at step 9 — after the commit. **The window in which those fixes must land does not exist.** Editing the worktree copy does not help either: by sub-step 6 the patch is already applied, the worktree is clean, and no second patch is coming.

**The restructure's real product is not a tidier patch — it is a repair window.** That is why a detection check alone is insufficient, and why proposal (b) from the idea file is the second half of this design rather than an alternative to it (story 04). Order matters: this story must land before the gate, or the gate is a dead end.

**Proposal (a) — early worktree removal — is superseded. Do not re-propose it.** It fixes the same deadlock but forfeits the remediation path: both remediation loops re-run the closure sequence *from sub-step 3, in the worktree*. It worked at E-278 only because no remediation round fired, so it trades a guaranteed capability for a situational one.
