## Overview
Fix two independent defects in `GameLoader`'s cross-perspective game dedup that make otherwise-complete scouting reports render as `degraded` and silently accumulate duplicate `games` rows. Both fire when the same real game is in the DB from two team perspectives (own crawl + a prior opponent crawl) — the modal case for any opponent we have already scouted. This directly threatens the morning-of-game unattended-report surface: with no operator watching, a `degraded` badge caused by a dedup edge case is indistinguishable from real breakage.

## Background & Context
Bug report received 2026-07-12; verified same day against origin/main @ 4d6916c (PM diagnosis, live + synthetic — see History).

**Defect A — `game_stream_id` UNIQUE collision on the redirect path (loud: load errors).**
When `_find_duplicate_game()` detects a cross-perspective duplicate, the redirect site (`src/gamechanger/loaders/game_loader.py:387-388`) rewrites ONLY `summary.event_id` to the canonical `game_id`; `summary.game_stream_id` keeps the incoming perspective's value. `_upsert_game()` then upserts with conflict target `game_id` only, while unconditionally clobbering `game_stream_id = excluded.game_stream_id` (line ~1131). Migration `010_game_dedup_backstop.sql` added a partial `UNIQUE INDEX ON games(game_stream_id) WHERE game_stream_id IS NOT NULL` on the stated premise that `game_stream_id` is NULL (tracked games) or stable across perspectives (member games). **That premise is false for tracked-opponent games** (api-scout confirmed, 2026-07-12): the premise was written from the now-RETIRED authenticated game-summaries model (which returned stable `event_id`/`game_stream_id` per E-220 TN-6), but post-E-239 the scouting/public path is the ONLY populator of `games` rows — and on that path `game_stream_id` is non-null and perspective-specific (each row's `game_stream_id` equals its own public `event_id`). The two identifiers are byte-identical per row on the public path, and both are per-perspective; the "`event_id` stable across perspectives" framing scopes to the retired auth flow ONLY. This is precisely why the dedup uses a natural key (`game_date` + unordered team pair), NOT `event_id`. Two consequences:

1. *Every* clean cross-perspective redirect silently poisons the canonical row's `game_stream_id` with the incoming perspective's event id (verified live: all 6 redirects in a fresh dev-DB report run for Pat Hagge Patriots Reserve overwrote the canonical rows' previously self-keyed stream ids).
2. When the incoming source event id ALREADY owns a `games` row (an un-merged twin left behind by Defect B or a prior crawl ordering), the redirect's upsert tries to set the canonical row's `game_stream_id` to a value that other row still owns — the UNIQUE index rejects it, the `ON CONFLICT(game_id)` handler does not cover the second-key collision, and the game's load counts as an error. The dedup never deletes/merges the losing source row, so the state persists and the error repeats on every regeneration.

**Defect B — exact-score-match gate misses same-game duplicates (silent).**
`_find_duplicate_game()`'s cross-perspective branch (lines ~1003-1027) treats two rows as the same game ONLY on an exact pairwise `(home_score, away_score)` match; any mismatch falls through to "distinct games." GameChanger's two perspectives of one real game can disagree by a run (observed 12-4 vs 12-5 — confirmed NOT a doubleheader: same 18-batter lineup on both rows, 70 vs 71 plays, differing only in `perspective_team_id`). **Caveat (api-scout, 2026-07-12):** this is a credible-but-single-observation property — the mechanism is sound (two independently-kept public scorebooks of the same game), but it technically contradicts `perspective-provenance.md`'s "scores stable across perspectives" classification, so it rests on this one live observation, not a verified invariant. Because of that, the same-game signal MUST NOT be regressed to score-equality: the resolved design uses schedule-count as the PRIMARY discriminator (TN-4), with score agreement only a fast-path/corroboration — no story may make a merge decision turn on scores matching exactly. The duplicate is never collapsed: a silent extra `games` row, flagged only by a post-load-validation WARNING (`scouting_loader.py::_check_duplicate_games`) that no operator surface shows — and that check is itself blind to pairs whose opponent resolved to different team ids across perspectives.

**Interplay**: B (or any dedup miss) creates the un-merged twin; A then fires on the next regeneration once scores align, converting a silent duplicate into per-game load errors, a `partial` load status, dropped spray/plays coverage for those games, and a `degraded` operator badge.

**Live evidence (2026-07-12)**:
- Production report for Pat Hagge Patriots Reserve (generated 2026-07-10) shows `degraded`: "crawl completed · load partial (2 err) · spray partial (32/32)".
- Dev-DB reproduction: first fresh report run redirected 6 cross-perspective games cleanly but clobbered all 6 canonical rows' `game_stream_id` (Defect A precondition now latent in the dev DB).
- Synthetic reproduction (in-memory DB, migrations 001+008+010, direct `GameLoader.load_payload`): Defect A reproduces exactly — `Dedup: redirecting game own-event-E → opp-event-X` followed by `ERROR ... Failed to upsert game opp-event-X: UNIQUE constraint failed: games.game_stream_id`, `LoadResult(errors=1)`; Defect B reproduces — 12-4 vs 12-5 perspectives yield two `games` rows, zero errors. The fixture recipe is in TN-2 for reuse as regression tests.

**Blast radius is bounded** (verified): headline stats are NOT double-counted — each duplicate's own-perspective stat rows live under one `game_id`, and season aggregation filters `WHERE perspective_team_id = team` (perspective-provenance invariant). Damage is the degraded badge, dropped spray points, orphan duplicate `games` rows, and poisoned `game_stream_id` values.

## Goals
- A cross-perspective redirect never overwrites the canonical row's non-null `game_stream_id` with the incoming perspective's value, and never errors on the second-key UNIQUE collision.
- Two perspectives of the same real game collapse to one `games` row even when their scorekeepers disagree on the score, without collapsing genuine doubleheaders.
- When a redirect detects an already-persisted twin row for the source event, the twin is merged into the canonical row in-pipeline (self-healing on regeneration), not left as a permanent orphan.
- Already-persisted duplicate pairs and poisoned `game_stream_id` values in existing DBs are repairable by an operator maintenance pass.
- Regenerating the affected team's report on a repaired DB yields a non-degraded run record (load `completed`, 0 load errors, spray `completed`).

## Non-Goals
- **NOT a stat-correctness fix**: season aggregates are already protected by the perspective filter; no aggregation query changes.
- **NOT a rework of member-game dedup** or the same-perspective legacy tiebreaker branch (start_time/score-total) beyond what the cross-perspective fix requires.
- **NOT removing migration 010's backstop index** — it correctly surfaced this bug; the fix makes the redirect path stop violating it, and corrects the migration's documented premise.
- **NOT changing the report-status classifier** (`run_status.py`) or the degraded derivation — once dedup stops erroring, the existing honesty semantics are correct.
- **NOT cross-team player identity or any longitudinal machinery** (permanent non-goals).

## Technical Notes

### TN-1 — Redirect-path `game_stream_id` semantics (Defect A fix shape)
The minimal, convention-consistent fix is **keep-existing** semantics on the conflict update:
`game_stream_id = COALESCE(games.game_stream_id, excluded.game_stream_id)`.
**Wording caution (Phase-3 finding C, verified):** this COALESCE is keep-existing — the EXISTING column is the FIRST argument. The adjacent `start_time`/`timezone` COALESCE in the same `_upsert_game` is `COALESCE(excluded.start_time, games.start_time)` = prefer-NEW, the OPPOSITE argument order. Do NOT "mirror the adjacent start_time pattern": copying that argument order yields `COALESCE(excluded.game_stream_id, games.game_stream_id)` = prefer-new, which still clobbers the canonical value whenever both are non-null and reintroduces the exact bug. Use the literal keep-existing form above (existing-first).
For tracked-opponent rows the canonical row's stream id is its own original event id (self-keyed), so keep-existing both preserves honest data and removes the cross-row UNIQUE write in the redirect case. Member games (stable stream ids across perspectives) are unaffected: existing == excluded. Note this changes `_upsert_game` for ALL callers, not just the redirect path — the non-redirect first-insert case still writes the incoming value (existing is NULL/absent). Alternative considered and rejected: rewriting `summary.game_stream_id` to the canonical row's value at the redirect site only — narrower, but leaves the unconditional clobber as a standing trap for any future caller. Whichever shape lands, `migrations/010_game_dedup_backstop.sql`'s header premise ("NULL for tracked games, stable for member games") must be corrected in the same story (comment-only edit; the index itself is unchanged and remains correct — see Non-Goals).

**Score-ownership on cross-perspective redirect (Phase-3 finding D + OQ2, RESOLVED).** `_upsert_game` today ALSO overwrites `home_score`/`away_score` unconditionally (`game_loader.py:1128-1129`). Once the tolerant signal (TN-4) makes redirects fire on DISAGREEING scores, last-writer-wins would flap the canonical scores on every regeneration. Resolution: the CROSS-PERSPECTIVE redirect path keeps the canonical row's existing scores (first-loaded perspective wins — deterministic, no flapping). This is scoped to the redirect context ONLY: a normal SAME-perspective reload still updates scores, so a legitimate scorekeeper correction on re-scout is NOT suppressed. A blanket score COALESCE on `_upsert_game` is therefore WRONG (it would suppress same-perspective corrections); the keep-existing-scores behavior must be gated to the redirect path. This change is owned by E-261-03a (the story that introduces disagreeing-score redirects), not E-261-01.

### TN-3 — Duplicate-game merge helper (child-table surface)
`merge_duplicate_game(conn, source_game_id, canonical_game_id)` in a new `src/db/game_merge.py`, pure connection-in (no commit — caller owns the transaction, matching `merge_player_pair`/`reload_game_plays` precedent). Six FK children of `games` must be re-pointed or merged: `game_perspectives` (INSERT OR IGNORE semantics — the pair's perspectives union), `player_game_batting`, `player_game_pitching`, `plays` (+ `play_events` via `plays`, which follow their parent rows), `spray_charts`, `reconciliation_discrepancies`. UNIQUE keys on the stat tables are perspective-scoped, and a genuine twin pair holds disjoint perspectives, so re-pointing normally cannot collide; a same-perspective collision (both rows carry rows for one perspective) means the "twin" is not cleanly mergeable — REFUSE and report rather than guess (mirror the player-dedup fork-refusal principle). **Refusal mechanism (Phase-3 finding DE-2):** detect the non-disjoint case by PRE-classification — intersect the `perspective_team_id` sets of the source vs canonical child rows (or read `game_perspectives`) BEFORE any write, and refuse cleanly if they intersect. This is a pre-classification like player-dedup's fork detection, NOT a mid-merge `IntegrityError` catch — a refusal must leave zero rows modified, never a half-applied merge. Delete the losing `games` row last. **No-cascade reality (Phase-3 finding DE-1):** every `games` FK child is a plain `REFERENCES` (no `ON DELETE CASCADE`), so delete-losing-row-last is mandatory — a premature `games` delete aborts loudly on the FK rather than silently cascading child loss; the helper docstring should state this. Cleanup-Detection Mirror Invariant applies: audit detection/gate queries that enumerate game-scoped children when finalizing the child list.

### TN-4 — Tolerant same-game signal (Defect B fix shape — RESOLVED at Phase-3 refinement)
The exact-score gate must widen without collapsing real doubleheaders. **Resolved policy (Phase-3 cluster A: Coach C1/C3/C4 + SE-5b + DE-4):** the discriminator is **schedule-count**, NOT score-tolerance. Score-tolerance alone is unsafe — HS/youth mercy-rule endings commonly make two REAL doubleheader games end at near-identical scores (both 10-0), so close scores cannot distinguish "same game, one book missed a run" from "two lopsided games hitting the same cutoff." The damage is asymmetric: wrongly keeping two rows is a visible, recoverable nuisance, but wrongly MERGING two real doubleheader games silently deletes a game's data AND can mask a pitcher rest/innings-limit violation on the next report (a safety concern). So the policy **biases to REFUSE when ambiguous.**

Signals available AT LOAD TIME:
1. **Schedule-count constraint (PRIMARY — the only standalone merge trigger)**: the incoming perspective's own crawl knows how many same-date games it has against this opponent (its game-summaries list). If the incoming schedule has exactly ONE game on that date vs that pair AND the DB holds exactly ONE cross-perspective candidate row, they are the same real game regardless of score disagreement — a real doubleheader appears TWICE in the team's OWN perspective (the verified discriminator). Requires plumbing a per-(date, pair) count into the dedup decision. **Correct seam (api-scout / Codex P2-4):** `GameLoader.load_payload` receives ONE summary at a time — it does NOT see all summaries. The full `games_index` lives in `ScoutingLoader._load_boxscores` (`scouting_loader.py`), which iterates payloads per game. So `ScoutingLoader` precomputes the per-(date, opponent-name) count from `games_index` and passes it to `GameLoader` (at construction or per-call); `GameLoader` does not receive the summary set.
2. **Bounded score tolerance (CORROBORATION ONLY — never a standalone trigger)**: pairwise scores differing by ≤1 run on one side with the other side exact (the observed 12-4 vs 12-5 shape). Used only to corroborate signal 1; it does NOT gate a merge on its own.
3. **NOT usable**: lineup/player-content overlap (cross-perspective player UUIDs and name forms differ by design — see perspective-provenance); start_time equality (observed ~30-min per-perspective offsets already forced the scores-match override in the current code).

**Default-OFF without count context (Phase-3 SE-5b reconciliation).** The existing test `test_cross_perspective_no_dedup_when_scores_disagree` (`tests/test_loaders/test_game_dedup.py:598`) asserts 11-1 vs 10-1 does NOT dedup — the byte-identical "one side off by 1, other exact" shape as Defect B's 12-4 vs 12-5 that we DO want to collapse. These reconcile ONLY because the trigger is schedule-count: with no count context the tolerant signal DEFAULTS OFF, so the 598 test (which supplies no count) correctly stays "no dedup," while Defect B's fixture (which supplies incoming_count==1) collapses. E-261-03a owns this reconciliation explicitly — it must preserve the 598 test's outcome and document why.

**Uniform candidate-loop guard (Phase-3 finding B / SE-1).** The tolerant signal MUST be applied UNIFORMLY across the whole `_find_duplicate_game` candidate loop, not only the `cross_perspective` sub-branch. After a twin merge the canonical row gains the own perspective in `game_perspectives`, so the NEXT report regeneration re-loads via the SAME-perspective branch (`game_loader.py:~1044-1061`) — which still has the exact-score/`start_time` blindness and would re-insert a new duplicate every regeneration (breaking idempotency). Applying the schedule-count guard perspective-agnostically closes this: a real doubleheader still shows incoming_count==2 so the guard is preserved.

**Plumbing constraints (Phase-3 finding E / SE-3 — problem-level, implementation left to SE).** (a) SPACE MISMATCH: game-summaries key naturally by (date, opponent-NAME) — `opponent_id` is empty in scouting and `GameSummaryEntry` carries no team IDs — but `_find_duplicate_game` decides in (date, team-id-pair) space; the count must be resolvable into the space the dedup decision uses. (b) The count's `game_date` must be derived by the SAME logic `_load_boxscore_data` uses (a `derive_local_date` mismatch would silently key-miss and disable the signal) — reuse one shared derivation. (c) A None/unresolved opponent identity MUST cause the tolerant signal to DECLINE (fail-safe: fall back to exact-score match, never merge on missing context).

**When the tolerant signal fires on disagreeing scores**, log at WARNING with both scorelines and both game ids (operator-visible data-quality note). Score ownership follows TN-1's RESOLVED decision: the cross-perspective redirect keeps the canonical row's existing scores (first-loaded perspective wins), and same-perspective reload still corrects.

### TN-5 — Repair pass scope (`bb data merge-duplicate-games`)
Follows the `bb data fix-self-games` precedent: `--dry-run` default printing the merge plan, `--execute` to apply, exit non-zero on any merge failure. Two repair actions:

(1) **Detect + merge duplicate pairs.** The schedule-count signal (TN-4) is unavailable offline, so detection uses the OFFLINE corroboration variant of the 03a predicate — **disjoint cross-perspective as the PRIMARY gate**, with score-tolerance + matching/near play counts as corroboration only. **Hard cardinality gate (Phase-3 finding DE-4):** merge only a same-`(season_id, game_date, unordered-pair)` group that has EXACTLY 2 rows with disjoint single perspectives; a group of ≥3 rows is ambiguous (a doubleheader that was ALSO cross-perspective loaded is 4 rows) → REFUSE per TN-3. Merge via the TN-3 helper.

(2) **Restore poisoned stream ids.** For rows whose `game_stream_id` differs from `game_id` AND equals another row's `game_id` or a known redirect source (tracked-perspective rows were self-keyed pre-clobber — verified live), reset `game_stream_id = game_id`. MUST NOT touch member-perspective rows (their stream ids are legitimately distinct from `game_id`). **Hardening (Phase-3 finding DE-4):** restore only when ALL of a game's perspectives are tracked (skip any game carrying a member perspective); keep the "poisoned value equals another row's `game_id` / redirect source" as a HARD corroboration condition (never restore on a bare value-differs check); and make the restore idempotent (a re-run over already-restored rows is a no-op).

Note the dev DB already carries 6 poisoned rows from the 2026-07-12 diagnosis runs; production carries at least the 2-error pair behind the degraded report.

### TN-6 — Reconciliation-scoreboard gate (operator, closure)
This is an ingestion-path change, so the standing ratchet binds: the operator runs `bb report reconcile-scoreboard` against the live DB before dispatch and after the repair pass; no gated stat's abs-Δ may increase and neither ratcheted axis counter may increase (`self_games` stays 0). Merging duplicate pairs aligns plays/boxscore perspectives, so `no_plays_units` may legitimately DECREASE — an improvement; if the operator wants the improved floor ratcheted, they re-snapshot via `--update-baseline` (operator-owned, never agent-refreshed).
