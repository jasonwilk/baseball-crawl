## Overview
Make the morning-of-game scheduled-report path (`bb report morning-run`, E-240) cron-grade. The unattended path is the forward feature of the product and currently its most fragile component: one HIGH data-integrity defect (the slot-wipe, F-H2) fires on a documented daily workflow, and a cluster of reliability gaps mean a single transient error aborts the whole run and suppresses the only missed-run signal (the always-sent summary email). This epic hardens the run so a transient per-team error is isolated, the operator is always notified, DB contention from the documented third-writer topology is survivable, and a runaway `Retry-After` cannot stall or silently abort the cron. It also closes two lifecycle gaps in the same serving path — reports stuck in `generating` after a dead process, and a 500-vs-404 race when the report file is unlinked mid-serve.

## Background & Context
`bb report morning-run` (E-240-07) is a cron-invoked orchestration shell over the untouched `generate_report()` pipeline: for each LSB team it reads the GC schedule, filters to the target local date, resolves each upcoming opponent via the resolution ladder, and generates a report for each auto-resolved slot, recording every slot's outcome to `scheduled_report_runs` and sending an always-sent end-of-run operator summary (its absence is the missed-run signal).

The 2026-07-03 platform audit (`PLATFORM-AUDIT.md`, repo root, UNCOMMITTED) found this path is not yet cron-grade. It is CE-2 in the audit's remediation program, sequenced 4th (after CE-1/E-251 dispatch repair, the curate-the-vision session, and E-250 dispatch), because the forward feature is the product's future and the slot-wipe HIGH is triggered by documented daily workflows.

This epic absorbs the audit's CE-2 docket: **F-H2 (HIGH) + 8 medium + 4 low** — the full "morning-run reliability cluster" plus the client-level 429 fix and the morning-run's own target-date timezone bug. The finding one-liners and audit provenance are preserved in Technical Notes (TN-1) and the story files.

No prior remediation has been attempted on these findings; they are the audit's original inventory.

## Goals
- Eliminate the F-H2 slot-wipe: a same-day re-run's idempotency skip never nulls the audit row's report linkage, so a subsequent run does not do a wasteful duplicate crawl+generate.
- A transient failure (5xx / 429 / connection error) on one team is isolated to that team; the remaining teams still process and the operator is always notified.
- The end-of-run summary email — the system's only missed-run signal — is guaranteed to be attempted on every non-dry-run, including when the run crashes, and the operator can tell a real send from a silently-dropped one.
- The morning-run writer survives the documented third-writer topology (admin UI + interactive CLI + cron) without one DB-lock error aborting the run, and never holds a write lock across a network fetch.
- A runaway `Retry-After` on a 429 cannot stall the cron for a server-controlled duration and then abort. 429 handling is capped (≤60s per fetch: one capped sleep + single inline retry; an over-cap `Retry-After` raises immediately). A same-team boxscore-429 storm accumulates per game (≤ ~60s each) but every game stays individually bounded and isolated, the run still completes, and a persistent systemic 429 surfaces at the next team's schedule fetch where the per-team seam stops further GC calls — so the worst case is bounded-and-deferred, never an unbounded stall (see TN-9).
- The morning-run's default target date is the venue-local operating date, not the container's UTC date, using a single operating-timezone seam that CE-3/E-253 will reuse for `game_date`.
- A report whose generation process dies mid-flight no longer stays stuck in `generating` forever.
- The public report-serving route returns a clean 404 (never a 500) when the report file is unlinked mid-request by the concurrent cleanup/reaper passes.

## Non-Goals
- **Deletion-cascade / data-integrity fixes belong to CE-3 (E-253)**, including the F-H1 shared-game deletion guard, `game_date` UTC + backfill, migration-runner transactionality, spray `chart_type` UNIQUE, and the stat-key drift canary. Only morning-run's OWN target-date timezone is in CE-2.
- **Changing `generate_report()`'s internals.** Morning-run is an orchestration shell over the untouched generator (E-240 TN-1); this epic does not alter the generation pipeline. (The stuck-`generating` reaper touches report *lifecycle* state in `generator.py`, not the generation pipeline.)
- **Rearchitecting the resolution ladder or the opponent-mapping model** (`opponent_ladder.py`, `map-opponent`). Their behavior is unchanged.
- **Surfacing per-game boxscore 429s out of `generate_report` up to the morning-run per-team seam.** E-252-04 adds `RateLimitError` isolation to the scouting crawler's per-game boxscore loop and E-252-02 handles team-level 429s at the per-team seam; the client-level cap bounds each fetch for free. Reaching into `generate_report`'s internals to propagate a per-game boxscore 429 up to 02's escalation is explicitly out of scope (respects Non-Goal #2) — the escalation is team-boundary-observed and bounded-and-deferred by design (TN-9, and the TN-6 last-team edge caveat).
- **Adopting the operating-timezone convention app-wide** (report reference date, game_date). CE-2 introduces the seam and applies it to the morning-run target date only; CE-3 applies it to `game_date`.

### TN-2 — Morning-run is an orchestration shell (unchanged invariant)
`src/reports/morning_run.py` composes reused seams and never enters the generator's internals (E-240 TN-1). This epic preserves that: it hardens the shell's error handling, transaction model, and audit-write path; it does NOT alter `generate_report()`. The one lifecycle touch is the stuck-`generating` reaper (E-252-08), which corrects a report's *status* after a dead generation process — it is not a change to the generation pipeline.

### TN-3 — Scheduled-report audit row semantics (do not regress)
The `scheduled_report_runs` contract is authoritative in `.claude/rules/data-model.md` (Scheduled-Report Audit + Opponent Resolution). Load-bearing points every story that touches the audit row must preserve:
- `UNIQUE(own_team_id, opponent_root_team_id, game_date)`; SQLite treats NULLs as DISTINCT, so all three key columns must stay non-NULL (the loader falls back to an `unknown-{event_id}` token). Idempotency silently breaks on a NULL key.
- `report_id` FK is `ON DELETE SET NULL` (the audit row outlives report cleanup); `report_slug` is the frozen-string fallback. Do NOT convert to CASCADE.
- `resolution_outcome` and `delivery_status` are CHECK-constrained; a crash slot is recorded as `unresolved_mappable` + `delivery_status='failed'` + an `error_message` that renders it inert for the operator (no `map-opponent` prompt). Preserve this discriminator.

### TN-4 — Shared operating-timezone seam (CE-2 ↔ CE-3 boundary)
The audit's "systemic UTC-date derivation" finding merges three sites (stored `game_date`, the report reference date, and morning-run's default target date). **CE-2 owns only the morning-run default target date** and **introduces the shared operating-timezone seam**: a single env-configured IANA operating timezone, read through ONE reusable helper, defaulting to the venue timezone (`America/Chicago`) when the env var is unset. The seam mirrors the existing per-game `derive_local_date` pattern in `morning_run.py` (which already resolves a game's own local date from its UTC start + IANA tz), but supplies the operating "today" for the default target date.

CE-3/E-253 will reuse this SAME seam for `game_date` — it MUST NOT re-derive its own timezone convention. The env var name, helper name, and helper location are the implementer's decision, but the seam MUST be a single reusable unit documented where CE-3 can consume it without redefinition.

**Divergence from the stub's literal wording (resolved):** the CE-2 stub says the fix should "adopt the same operating-timezone convention CE-3 introduces." But CE-2 is sequenced BEFORE CE-3 (position 4 vs 5), so CE-2 cannot adopt a convention that does not exist yet. Resolution: **CE-2 INTRODUCES the seam; CE-3 REUSES it.** This is the only coherent sequencing and is reflected throughout this epic. Flagged for the user's awareness at review.

### TN-5 — Connection factory / contention model (RESOLVED — data-engineer)
The morning-run CLI is a THIRD SQLite writer on one WAL file alongside the admin UI (uvicorn workers) and the interactive CLI. DE's source-verified guidance (owns E-252-06 and E-252-07):
- **Single factory, extended — do NOT add a second factory.** `get_connection()` in `src/api/db.py` becomes the single factory: add `PRAGMA busy_timeout=30000` (30s) and `PRAGMA synchronous=NORMAL` (the correct/safe pairing with WAL — loses only the last commit on OS/power crash, and cuts fsync stalls that lengthen the write-lock hold under three writers), plus an optional `db_path: Path | None = None` parameter so the CLI/cron pass their `resolve_db_path(override)` and drop the hand-rolled `sqlite3.connect`. WAL is a persistent DB-file property; `busy_timeout` and `foreign_keys` are per-connection and must be set on every connection.
- **The app path adopts the same busy_timeout — IN scope.** It is the same one-line change to the same function; a cron-grade three-writer epic REQUIRES the admin-UI connection to WAIT on the cron writer rather than 500 with "database is locked". Fix once, in the factory.
- **`busy_timeout` alone is NOT sufficient.** It must be paired with (a) `conn.commit()` immediately after `ensure_team_row` (before any network I/O) and (b) each `_upsert_slot` as its own complete committed write unit. **Invariant to codify: never hold an open write transaction across an HTTP fetch on the shared cross-process SQLite file.** Do NOT switch to `isolation_level=None` (full autocommit) — too large a silent behavior change to a shared factory. Keep default deferred isolation + the discipline.
- **06↔07 are two halves of one fix.** `busy_timeout` (06) without commit-after-`ensure_team_row` (07) leaves a path where morning-run holds a write lock across a minutes-long multi-team crawl, so a competing admin-UI writer's 30s timeout still expires — false safety. 06 must land before 07, and 07 must not slip/drop.
- **E-245 partial-commit footgun applies (see TN-10).**

### TN-6 — 429 / Retry-After handling (RESOLVED — api-scout)
**LOAD-BEARING CAVEAT: GC 429 behavior is UNOBSERVED** (`docs/api/error-handling.md:68` — "No 429 Too Many Requests responses observed in captures"). All decisions below are designed to be robust to the unknown, not tuned to an observed value; the stories MUST document this and flag a revisit if a real 429 is ever captured.

Client-level fix (`src/gamechanger/client.py` `_send_with_retry`, L499-512), owned by E-252-04:
- Add `_MAX_RETRY_AFTER_SECONDS = 60` and clamp before sleeping. Never let the server dictate an uncapped wait.
- Policy (replaces sleep-then-raise-anyway): if `Retry-After <= cap` → sleep the (clamped) amount, retry ONCE, return on 200, raise `RateLimitError` only if the retry also fails. If `Retry-After > cap` → raise immediately, NO sleep (an over-cap value most likely signals a systemic IP/WAF condition sleeping won't clear). Fall back to the existing `_DEFAULT_RETRY_AFTER_SECONDS=60` when the header is absent/unparseable, then clamp.
- **This cap/policy lives in the SHARED client → it changes behavior for EVERY GC caller, not just morning-run.** The story must call this out as a deliberate global change.

`RateLimitError` isolation — the escape point is the SCOUTING CRAWLER, not the plays loop (GAP B, resolved):
- `RateLimitError` is a standalone `Exception` (a sibling of `CredentialExpiredError`/`ForbiddenError`/`GameChangerAPIError`, NOT a subclass). **Keep it standalone — do NOT subclass it under `CredentialExpiredError`** (a 429 is not a credential problem; subclassing misroutes it into auth-refresh/"check .env" handling).
- The plays crawl loop (`generator.py:929-931`) already catches `except Exception` → a 429 is already isolated per-game there. **No change.**
- The real escape is the scouting crawler's per-fetch catches that OMIT `RateLimitError`. Two SHAPES (verified): `_fetch_schedule` (:217) and `_fetch_roster` (:238) use a 3-tuple `except (ForbiddenError, CredentialExpiredError, GameChangerAPIError)`; the `_fetch_boxscores_in_memory` per-game loop (`crawlers/scouting.py:268-281`) uses THREE SEPARATE `except` clauses — `except ForbiddenError` (continue), `except CredentialExpiredError` (**re-raises** — a 401 mid-boxscore intentionally aborts the team crawl), `except GameChangerAPIError` (continue). In both shapes a 429 escapes and aborts the whole team crawl. E-252-04 adds a NEW `except RateLimitError: continue` clause to the **per-game boxscore loop** (:268-281), preserving the `CredentialExpiredError` re-raise, so one game's 429 does not abort the team crawl.
- **02↔04 boundary (co-design):** the per-game boxscore 429 is isolated at the crawler (04). Team-level 429s (schedule/roster fetch, or a client raise-fast) MUST still surface to morning-run's per-team seam (02) so the systemic-escalation in TN-9 can see recurring 429s — they are NOT silently swallowed by the crawler. E-252-04 adds `RateLimitError` isolation ONLY to the per-game boxscore loop; it deliberately does NOT add it to `_fetch_schedule`/`_fetch_roster`, so those team-level 429s propagate to 02's seam. See the boxscore per-game catch STRUCTURE in E-252-04 (three separate `except` clauses, not a tuple — the `CredentialExpiredError` re-raise must be preserved).
- **Edge caveat — last team of the run (name it so a reviewer does not "discover" it):** if a boxscore-429 storm hits the LAST team, there is no subsequent schedule fetch, so the TN-9 systemic escalation never fires for that run. This is acceptable — the run is ending, and every game still stays individually bounded and isolated (E-252-04 AC-5). The worst case remains bounded, just not deferred-and-stopped.

### TN-7 — Summary-email guarantee (the missed-run signal)
The end-of-run summary is the ONLY missed-run signal (silence = something failed). Three gaps close together in E-252-03: (a) the CLI discards the send result and exits 0 even on a send failure; (b) an unset `ADMIN_EMAIL` silently disarms the heartbeat forever (`_send_operator_alert` warns-and-skips); (c) an unset `MAILGUN_API_KEY` logs the body to stdout and returns `True` ("sent") — a production false-positive. The alerting-channel config must be validated in the non-dry-run preflight (so a misconfiguration aborts loudly before the run rather than silently after), the send result must be checked (and retried per the story), and the dev stdout fallback must be tri-stated so it does not report success in production. The summary must be attempted even when the run body crashes (try/finally at the CLI). Production detection uses a shared `is_production()` helper added to `src/api/helpers.py` (the canonical env-read seam that already holds `get_app_url()`), consumed by the email tri-state and the CLI preflight, with `routes/auth.py::_is_dev_mode` repointed to `return not is_production()` for single-source prod detection (E-252-03). A direct import of `_is_dev_mode` is NOT viable — `routes/auth.py` already imports from `email.py`, so it would create an import cycle. (`is_production()` becoming a canonical env-read seam is a closure-time context-layer codification candidate for claude-architect at the context-layer assessment gate.)

### TN-8 — Test discipline
Never make real HTTP requests in tests (mock at the transport layer). Follow the trustworthy-pytest gotchas in `.claude/rules/testing.md` (no piped exit codes; the disk-backed `db` fixture self-`backup()` deadlock). Error-path tests are mandatory for the orchestration paths here (a failing dependency must surface, never a misleading success). The SQLite contention test (E-252-06) must be deterministic and non-flaky per data-engineer's shape (real on-disk file, `BEGIN IMMEDIATE`, a `threading.Event` set after the lock is acquired that the main thread waits on before the contender's write, and the `check_same_thread` discipline).

### TN-9 — Rate-limit outcome + systemic escalation (api-scout; owned by E-252-02)
A 429 is more likely systemic than a 403 (which is genuinely per-resource), so the per-team seam does NOT do a blanket skip-and-continue:
- Catch `RateLimitError` at the morning-run per-team seam so one team's 429 does not crash the process and the always-sent summary still fires (mirroring the existing `denied` 403 tally — add a parallel `rate_limited` counter on `MorningRunResult` + a summary line; this is a RUN-LEVEL tally, NOT a CHECK-constrained `scheduled_report_runs` audit value, since a team-level 429 produces zero slots).
- **Systemic escalation:** if a 429 RECURS across teams (e.g. a 2nd occurrence), STOP making further GC calls for the rest of the run and let the summary report "rate-limited — aborted early" rather than grinding through the remaining teams and hammering GC into the same wall. This respects HTTP-discipline "back off exponentially" and the "silence = something failed" summary contract.
- **Boundedness of the escalation (api-scout, confirmed).** The escalation observes 429s at TEAM BOUNDARIES — each team's `_fetch_schedule`/`_fetch_roster`, which routes through the capped `_send_with_retry` and does NOT catch `RateLimitError`, so a persistent systemic 429 surfaces on the next team's schedule fetch. Per-game boxscore 429s inside `generate_report` isolate at the crawler (E-252-04 AC-5) and never reach this seam. Exact wording to preserve verbatim against a Codex re-flag: *"Each boxscore 429 is bounded to ≤60s of client wait (one capped sleep + single retry; an over-cap Retry-After raises immediately). A same-team boxscore-429 storm accumulates per game (≤ ~60s each), so a sustained storm can add up on one team — but every game stays individually bounded and isolated (04 AC-5), the run still completes, and if the systemic condition persists it surfaces at the NEXT team's schedule/roster fetch, where the per-team seam's systemic escalation (02 AC-4/TN-9) stops further GC calls. So the worst case is bounded-and-deferred, never an unbounded stall."* This is a deliberate accept-and-soften decision (SE design concern + CR's next-team observation) that respects Non-Goal #2 (no reach into `generate_report` internals). See the TN-6 last-team edge caveat.

### TN-10 — Shared-connection rollback discipline (E-245 partial-commit footgun; binds E-252-02 AND E-252-07)
The morning-run loop shares ONE `sqlite3.Connection` across teams/slots with catch-and-continue. EVERY shared-connection catch-and-continue branch in the run loop MUST call `conn.rollback()` before the next iteration — the per-team catches broadened by 02, the per-slot `_upsert_slot` isolation added by 07, AND the PRE-EXISTING per-game `except` at `morning_run.py:513` — otherwise a slot/team whose write partially executed then raised leaves uncommitted DML pending, which the NEXT successful `conn.commit()` silently commits (the E-245 `fix-self-games` Codex P1; `.claude/rules/architecture-subsystems.md`, Plays Pipeline).
- **The :513 rollback is DEFENSE-IN-DEPTH (DE-confirmed).** Verified there is NO uncommitted shared-conn DML reachable at :513 today: the only shared-conn writer in `_process_opponent` is `opponent_ladder.resolve_opponent`, which SELF-COMMITS its `opponent_links` writes (`opponent_ladder.py:179/205`); the display-profile fetch is caught internally and `generate_fn` runs on its OWN connection. The rollback guards against a FUTURE ladder change that introduces a write→network→commit ordering — 07's Technical Approach carries a one-line code comment saying exactly this so it is not later "cleaned up" as dead code. The ladder's persistence of a pending `opponent_links` row before a raise is BY DESIGN (pending rows must survive for `map-opponent`), not a leak — so NO partial-persist fixture is required; the rollback AC is pinned by asserting `conn.in_transaction is False` (or spying that `conn.rollback()` ran) after the :513 path.
- This is an explicit AC on BOTH E-252-02 and E-252-07 and a code-review checklist item.
