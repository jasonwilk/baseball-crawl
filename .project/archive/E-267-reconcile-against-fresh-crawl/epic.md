## Overview
The scouting/report load pipeline is ACCUMULATE-ONLY: a re-scout upserts what is in the fresh payload but never retires what VANISHED from it. This epic makes the load path RECONCILE-AT-LOAD going forward — on every re-scout, a set-difference retire runs as part of the normal load across three grains: the **game grain** (a removed or rescheduled game), the **player-line grain** (a removed per-player stat row), and the **roster grain** (a departed roster player). This is PREVENTION-AT-LOAD, not a retroactive repair. The load-bearing safety rule: a genuinely removed row is retired, but a transient/postponed/not-yet-final absence NEVER deletes live data (bias-to-refuse).

## Background & Context
Surfaced by the 2026-07-19 accumulate-only re-run audit (master record: `.project/research/2026-07-19-rerun-accumulate-only-audit.md`). Season aggregates derive at QUERY TIME from `player_game_*` via `get_season_batting`/`get_season_pitching` (`src/api/db.py`), so a stale or duplicate row silently corrupts a coach-facing number. Three coach-facing accumulate-only gaps share one root and one fix shape:

- **Game grain** — IDEA-140 (rescheduled game re-inserted → double-counted) + CC-1 (removed/voided game persists in W-L, season lines, recent form, freshness N). `_find_duplicate_game` keys on `game_date` + unordered team pair, so a moved game does not match; nothing retires a deleted game.
- **Player-line grain (H1)** — a player dropped from a boxscore between runs keeps their `player_game_batting`/`pitching` row (UPSERT-only, no set-difference delete) → season SUMs stay inflated. Two-channel CONFIRMED/high.
- **Roster grain (H2)** — a departed player never leaves `team_rosters` (INSERT/UPSERT-only, no prune); the report roster grid renders ex-players indefinitely. Two-channel CONFIRMED/high.

**Operator design decision (2026-07-19, locks the approach):**
1. **Forward-only.** Do NOT build a retroactive `bb data` pass that retires/rewrites historical loaded data. The operator does not care about historical data or historical report content. The epic's job is prevention-at-load going forward — not correcting already-loaded rows.
2. **Clean slate by purge command.** After this epic lands, the operator starts from a clean data slate via the E-267-06 `bb db purge-scouting` command (a plain mass report-delete does NOT clean-slate — see the Clean-Slate section for the `teams.is_active` caveat). The "migration" for existing corrupted data is a wipe, not a repair. Design for a clean starting state post-purge.
3. Removed-vs-transient corroboration still matters for the FORWARD load path (don't delete live data on a transient absence during a normal re-scout), but there is NO retroactive-cleanup story.

CC-2 (cross-perspective score-misattribution) is DELIBERATELY OUT — different mechanism (COALESCE asymmetry), promoted to its own fix E-268.

## Goals
- Reconcile-at-load set-difference retire covering game, player-line, and roster grains, running as part of the normal re-scout load path.
- A removed-vs-transient corroboration decision (bias-to-refuse) so a transient absence never deletes live data on the forward path.
- Every retire path gated against the E-257 reconciliation-scoreboard ratchet (no fidelity regression).
- Every story ships a regression test that reproduces the corruption pre-fix and asserts the fix post-fix.

## Non-Goals
- **No retroactive `bb data` repair pass** and no rewrite of already-loaded historical rows — existing corruption is handled by the operator's clean-slate report deletion, not by this epic (per operator decision).
- CC-2 cross-perspective redirect score-misattribution (E-268 — different mechanism).
- Frozen-plays in-place refresh (H3 / IDEA-146) and orientation-driven `batting_team_id` re-derive (H4 / IDEA-147) — those REFRESH changed rows; this epic RETIRES missing rows.
- The accumulate-only hygiene cluster (IDEA-152) — no coach impact.
- Any multi-season / cross-team machinery (permanent project non-goal).

## Success Criteria
- Given a re-scout whose fresh crawl OMITS a game/player-line/roster entry that a prior run loaded, AND the absence is corroborated as genuinely removed, when the load runs, then the stale row is retired in the same load and the affected coach-facing number (season aggregate, W-L, roster grid) corrects.
- Given a rescheduled game (same real game at a new date), when the re-scout loads it, then it is deduped by the correct path (TN-3): a CROSS-perspective moved game is redirected/merged via the canonical `merge_duplicate_game` seam; a SAME-perspective reschedule is matched on the stable `event_id` and its `game_date` is UPDATED in place (no delete) — never double-inserted.
- Given a transient/postponed/not-yet-final absence, when the load runs, then it REFUSES to retire and the live data is untouched (bias-to-refuse), emitting one WARN per refusal.
- Given any story's change, when `bb report reconcile-scoreboard` runs before/after against live data, then no gated stat's abs-Δ increases, neither ratcheted axis counter increases, and `self_games` stays 0.
- Every story has a regression test that fails pre-fix and passes post-fix, INCLUDING a bias-to-refuse test.

## Technical Notes

**TN-1 — Delivery vehicle: RECONCILE-AT-LOAD (operator-decided).** The retire-absent set-difference runs as part of the normal re-scout load path (invoked from the loaders during `generate()`/`load_team`), NOT as a separate retroactive `bb data` operator-maintenance pass. There is no new operator command and no historical-repair sweep. This resolves the prior delivery-vehicle open question.

**TN-2 — Retire-absent corroboration = a HEALTH gate on the fresh crawl (DE-decided, bias-to-refuse).** NO stored "last successful crawl" snapshot table — the DB IS the prior-loaded set and the fresh in-memory crawl is the authority (keeps the epic migration-free). Corroboration is a completeness/health gate on the FRESH payload, not a diff against history. The shared primitive (E-267-01) is `classify_absences(prior_ids, fresh_ids, *, crawl_authoritative) -> {id: PRESENT | REMOVED | TRANSIENT_ABSENT}` — a PURE function over id sets (no DB handle, no logging, no I/O). The connection-in / no-commit / caller-owns-the-transaction contract, the actual DELETE, and the WARN-per-refusal belong to the grain RETIRE helpers (E-267-02/03/04), NOT the classifier. A retire is allowed ONLY for REMOVED. Universal bias-to-refuse: an absence is REMOVED only when the fresh crawl for that grain (a) fetched OK, (b) returned a NON-EMPTY payload, and (c) did not shrink catastrophically — `fresh_count >= prior_count * FLOOR_RATIO`, FLOOR_RATIO = 0.5. Any failure → the classifier returns ALL absences in that grain as TRANSIENT_ABSENT → the grain helper performs zero deletes and emits one WARN per refusal. Per-grain extra guards: GAME — a game present-but-scoreless / not-final is TRANSIENT (postponed/in-progress); only fully-absent-from-the-fresh-schedule is a removal candidate. PLAYER-LINE — scoped strictly per `(game_id, perspective_team_id)`; scored-but-EMPTY boxscores are the MODAL case, so an empty/absent boxscore must NEVER retire prior lines. ROSTER — reuse the existing empty-guard (`scouting_loader.py:343-345`) but use the STRICTER drop guard in TN-12 (NOT the flat floor-ratio, which is too loose for a 12-15 roster).

**TN-3 — Reschedule handling has TWO paths (DE risk 3; refined by TN-11 Probe 2).** A moved game is the same real game at a new date. (a) CROSS-perspective moved game → REDIRECT/merge via the canonical `merge_duplicate_game` seam (`src/db/game_merge.py`) — do NOT re-inline FK-child re-pointing; the perspective-specific `id` can't bridge perspectives, so the date+team-pair natural key is required here. (b) SAME-perspective reschedule (the common case: the same LSB team re-scouting the same opponent whose game moved date) — the stable `event_id` (public `/games` `id`) survives a GC reschedule PATCH-in-place (TN-11 Probe 2), so PREFER matching on that id and UPDATING the `game_date` in place (no delete, no double-insert); this also means the game never looks like a removal. The old-date-row-as-REMOVED hard-delete (full child surface per TN-10) is the FALLBACK only if id-matching is unreliable (the current `_find_duplicate_game` date+team-pair key breaks on a date move, which is what makes id-matching the better same-perspective key). E-267-02 must implement both paths (AC-2 cross, AC-3 same). A removed game (absent from the full array, corroborated removed per TN-2) is retired.

**TN-4 — HARD-DELETE, uniformly across all three grains (DE-decided; satisfies E-267-01 AC-3).** No soft-retire flag, no migration. Rationale: a soft-retire marker forces a `WHERE is_retired IS NULL` filter into EVERY reader (`get_season_*`, `_query_record`/recent-form/runs-avg, `_query_roster`, `_query_freshness`, `recon_scoreboard.py`) — miss one and the stale row silently re-inflates, the exact failure class this epic fixes. Hard-delete makes correctness structural. Auditability is delivered by a WARN-per-retire log line (what/why-REMOVED), NOT a reversible marker. Consistent with every existing seam (`merge_duplicate_game`, `player_dedup`, `lifecycle` all hard-delete).

**TN-5 — Ratchet gate (mandatory, all stories).** Every retire change MUST be gated against the E-257 reconciliation-scoreboard (`bb report reconcile-scoreboard`, baseline `.project/baselines/reconciliation-scoreboard.json`): no gated stat's abs-Δ increases, neither ratcheted axis counter (`dropped_pitch_events`, `no_plays_units`) increases, `self_games` stays 0. Manual operator diagnostic against live data (dev DB absent from worktrees/CI), recorded at closure — a hard release condition, not a CI gate.

**TN-6 — Canonical seams (context, not prescription).** `merge_duplicate_game` / `is_offline_same_game` (`src/db/game_merge.py`); `get_season_batting`/`get_season_pitching` (`src/api/db.py`, query-time season readers a stale player-line inflates); `_query_roster` (`src/reports/generator.py:626-641`, the roster grid H2 corrupts); `_query_record`/recent-form/runs-avg game-level reads a stale/duplicate game corrupts. The perspective-provenance invariant (`.claude/rules/perspective-provenance.md`) binds every touched write.

**TN-7 — Standing test requirement (operator directive 2026-07-19; CODE stories only).** Every CODE story (E-267-01/02/03/04/06) MUST ship a regression test that reproduces the corruption (fails pre-fix — inflated aggregate / duplicated W-L / stale roster row) and asserts the fix (passes post-fix), INCLUDING a bias-to-refuse test proving a transient absence is NOT retired on the forward path. **TN-8 — Purge keep-vs-purge partition + FK-safe order (E-267-06, DE-decided).**
- KEEP (identity/auth + bootstrap): `users`, `passkey_credentials`, `magic_link_tokens`, `sessions`, `webauthn_challenges`, `programs` (lsb-hs bootstrap; FK-safe parent), `_migrations`.
- PURGE (scouting/report — 20 live tables): reports, report_generation_runs, scheduled_report_runs, games, game_perspectives, player_game_batting, player_game_pitching, plays, play_events, spray_charts, reconciliation_discrepancies, team_rosters, scouting_runs, opponent_links, crawl_jobs, coaching_assignments, user_team_access, teams, players, seasons. (DE-verified 2026-07-19 vs live schema, migrations 001-011: `team_opponents` REMOVED — dropped by migration 008; `player_season_*` correctly absent — dropped by 011. KEEP(7) + PURGE(20) = 27 = complete live-table set; exhaustive and disjoint.)
- Ambiguous resolved by DE: `user_team_access` → PURGE (FKs teams; it is authorization not authentication — login survives via users/passkey/magic-link/sessions; admins see all teams, non-admin grants re-granted as teams regenerate). `coaching_assignments` + `crawl_jobs` → PURGE (dead but FK teams). `seasons` → PURGE (self-heals via `ensure_season_row`). `programs` → KEEP.
- FK-safe delete order (FK enforcement ON so a mistake aborts loudly): (1) play_events; (2) report_generation_runs, scheduled_report_runs; (3) plays, player_game_batting, player_game_pitching, spray_charts, reconciliation_discrepancies, game_perspectives, team_rosters, scouting_runs, opponent_links, crawl_jobs, coaching_assignments, user_team_access, reports; (4) games, players; (5) teams; (6) seasons.
- **The KEEP set is FK-CLOSED with respect to the purge — verified by code-reviewer 2026-07-19, and this is the property AC-2 actually depends on.** No KEEP table carries a foreign key into a PURGE table. This had not been verified by anyone (DE, SE, or PM) before CR checked it, despite the whole partition resting on it. If one KEEP→PURGE FK existed, the purge would either abort permanently (FK enforcement is ON by AC-3, so the constraint fires) or — with enforcement off — leave surviving auth data referencing deleted rows. **Standing obligation: a future migration that adds a foreign key FROM a KEEP table TO a PURGE table silently breaks `bb db purge-scouting`.** The AC-7 partition drift test catches a new unclassified TABLE but does NOT catch a new KEEP→PURGE FK — that gap is real and currently unguarded.
- **Migration 012 re-verified (PM, 2026-07-19):** `012_teams_innings_per_game.sql` is `ALTER TABLE teams ADD COLUMN` only — no new table — so the KEEP(7) + PURGE(20) = 27 partition holds against migrations 001-012, extending DE's original 001-011 verification. `migrations/` globbed to confirm 012 is the highest on disk.
- **AC-6's single-transaction guarantee rests on the CONNECTION FACTORY, not on the purge module (CR, 2026-07-19).** `get_connection` (`src/api/db.py:57-61`) deliberately preserves sqlite3's default DEFERRED isolation rather than setting `isolation_level=None`. Were the factory ever switched to autocommit, each of the 20 DELETEs would commit independently, `conn.rollback()` would become a silent no-op, and the AC-10(a) rollback test would still PASS — for the wrong reason, since there would be nothing left to roll back. Do NOT "optimize" the factory to autocommit: a destructive command's atomicity depends on this default.

**TN-9 — Purge production guard + HTML unlink (E-267-06; SE implementation notes 2026-07-19).** Mirror `src/db/reset.py`'s STRUCTURE (refuse on production unless `--force`, loud WARN with `--force`) but NOT its guard body: `reset.py`'s `check_production_guard` uses the inline `os.environ.get("APP_ENV",...).lower()==` compare (the IDEA-101 bypass class), so write a FRESH guard through the canonical `is_production()` seam (`src/api/helpers.py`, returns bool). Two more implementer-critical points SE flagged:
- **FK-ON is not free.** `sqlite3.connect()` defaults `PRAGMA foreign_keys=OFF` and `reset.py` never turns it on (it deletes the whole file). The FK-safe order (TN-8) only aborts-loudly on a mis-order if FK enforcement is actually ON — the purge module MUST explicitly `PRAGMA foreign_keys = ON` (or route through `get_connection()` in `src/api/db.py`, which sets it). A naive reset.py mirror leaves it OFF and silently orphans.
- **HTML unlink = the mechanism, not `cleanup_expired_reports()`.** That function filters `WHERE report_path IS NOT NULL AND expires_at < ?` (EXPIRED only) — the purge must unlink ALL purged reports' HTML regardless of expiry. Enumerate `SELECT id, report_path FROM reports WHERE report_path IS NOT NULL` (no expiry filter), resolve each against `_REPO_ROOT / "data"`, `unlink()` with per-row error isolation, and do it BEFORE the `reports` DELETE removes the rows (once gone, `report_path` can't be enumerated).
- **One transaction.** Wrap all ordered deletes in a single transaction — commit at end, rollback on error — so a mid-purge failure never leaves a corrupt half-state.

**TN-10 — Delete discipline (DE risks 1, 2, 4, 5, 6 — wired into E-267-01/02/03 ACs).**
1. **PLAYER-LINE grain only** — every set-difference AND retire DELETE on `player_game_batting`/`player_game_pitching` MUST include `AND perspective_team_id = ?` (those tables carry the column; GC gives different `player_id`s per perspective, so an unscoped delete corrupts the OTHER team's report — perspective-provenance applied to deletes). **ROSTER grain does NOT apply** (DE-confirmed 2026-07-19): `team_rosters` has NO `perspective_team_id` (PK `(team_id, player_id, season_id)`, from a single team-level roster crawl), so the roster retire scopes by the natural key `(team_id, season_id)` and deletes the team-season's rows whose `player_id` is absent from the fresh set — no cross-perspective collision is possible on this grain (one team-season = one roster source = one row set). Roster caveat (semantics, not an FK break): `game_loader._upsert_roster` (`game_loader.py:1548-1562`) also backfills `team_rosters` from boxscore appearances under the same `team_id`, so a player who appeared in an early game but is absent from the fresh roster crawl (e.g. cut mid-season) is retired from the roster display while KEEPING their `player_game_*` rows (stat tables FK to `players`, not `team_rosters`) — E-267-04 must state the intended departed-player semantics explicitly.
2. The player-line reconcile MUST run on RAW `(game_id, perspective_team_id)` boxscore ids BEFORE the `dedup_team_players` sweep (`scouting_loader.py:197-211`) — dedup merges `player_id`s, so reconciling after would false-flag "absent" and wrong-retire.
4. **TN-12 — Roster-grain drop cap: LOCKED (DE-decided 2026-07-19).** An ABSOLUTE cap, NOT a ratio — roster N is small/bounded (12-15) and real churn is ~1 departure/crawl, so the flat FLOOR_RATIO=0.5 (which would permit deleting 7 of 14) is absurd here and fails to tighten as N shrinks. LOCKED RULE (exact, implementable):
- Constant `MAX_ROSTER_DEPARTURES = 2`.
- Per `(team_id, season_id)` per run: `absent = {DB roster player_ids} − {fresh-crawl player_id set}`.
- If `len(absent) > MAX_ROSTER_DEPARTURES` (≥3): REFUSE the roster retire this run — DELETE nothing, leave all roster rows intact, log ONE WARN carrying `team_id`, `season_id`, `roster_db_count`, `fresh_crawl_count`, `absent_count`, and the absent `player_id` list (operator review). Departed players persist until a clean crawl or operator action.
- If `len(absent) <= 2`: proceed with `DELETE FROM team_rosters WHERE team_id=? AND season_id=? AND player_id NOT IN (<fresh set>)`.
- GATING SCOPE: only DELETEs are capped; the ADD path (new fresh-crawl players) is NEVER gated (additions can't corrupt existing data). Value justification: 2 covers a legitimate double-cut without false-refusing; ≥3 absent in a 12-15 roster is a strong truncated/partial-crawl signal, not real churn. Defense-in-depth with the TN-2 health-gate.
- **Accepted benign fallback (baseball-coach-flagged 2026-07-19):** a PRESEASON TRYOUT CUT (trimming a 20-player pool to 12-15 in one edit) legitimately drops >2 at once, so the cap REFUSES it and leaves stale tryout names on the grid until a clean crawl or an operator purge. This is accepted — the failure mode is benign stale-grid clutter, never a corrupted STAT (unlike the game/player-line grains). No special-case is added; the WARN gives the operator the signal to purge if desired.
