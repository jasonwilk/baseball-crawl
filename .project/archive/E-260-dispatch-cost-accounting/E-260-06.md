# E-260-06: Add the SendMessage counter hook (mechanism 2)

## Epic
[E-260: Dispatch Cost Accounting](../E-260-dispatch-cost-accounting/epic.md)

## Status
`DONE`

## Description
After this story is complete, dispatch message volume is visible and bounded. A new `PreToolUse` hook increments a worktree-local counter on every `SendMessage`, warns at 15 sends and denies at 25, and — on the `git add -A` staging boundary — appends one row to a dispatch log and resets the counter. This is the second of the epic's two added mechanisms.

## Context
Epic Scope (Additions #2): "A SendMessage counter. A `PreToolUse` hook on `SendMessage`, writing a counter file in the epic worktree, reset on `git add -A`. Warn at 15 sends, deny at 25. Appends one row per story to a dispatch log: story ID, sends, rounds." The E-256 dispatch produced ~640k characters of prose with no running count; this makes the volume observable per-story instead of invisible. Both thresholds carry provenance in the hook comment, and the operator is the only person who may edit them.

Per operator decision 7, the dispatch-log columns degrade to what the hook can observe without new instructions: epic ID + staging-boundary sequence index + sends; the 'rounds' column is best-effort/blank (the hook cannot reliably observe review rounds).

## Acceptance Criteria
- [ ] **AC-1** (hook exists and is registered): `.claude/hooks/send-message-counter.sh` exists and is registered in `.claude/settings.json` on two `PreToolUse` events: one matching `SendMessage`, one matching `Bash` commands containing `git add` (PreToolUse fires before the command runs).
- [ ] **AC-2** (increment + thresholds on SendMessage): On a `SendMessage` call, the hook increments a worktree-local counter file. At 15 accumulated sends it emits a warning (advisory, non-blocking — no operator-action text). At 25 it denies the call with the exact pinned message in AC-2a. Below 15 it is silent and passes.
- [ ] **AC-2a** (pinned deny-at-25 message): The deny-at-25 output is exactly this text (it names the release action so the first hard stop resolves by an operator decision, not an in-session reinterpretation — Falsifier 4):
  ```
  SendMessage BLOCKED — dispatch send cap reached (25 sends since the last staging boundary).
  This is a HARD STOP and an OPERATOR decision point, not an in-session one: do NOT reinterpret,
  rephrase, or route around this rule to keep sending.
  To proceed, the operator must either:
    (1) reset the count by deleting the counter file:  <worktree>/.dispatch-log/sends.count
    (2) or raise the threshold in .claude/hooks/send-message-counter.sh (operator-owned;
        see the provenance comment — 25 is a single-epic placeholder).
  Until the operator acts, further SendMessage calls are denied.
  ```
- [ ] **AC-3** (log row + reset on staging boundary): On a `Bash` call whose command **targets the epic worktree AND is a `git add` invocation**, the hook appends exactly one row to the dispatch log and resets the counter to zero. The matcher predicate keys the reset+log ONLY when the command string contains the worktree prefix `/tmp/.worktrees/baseball-crawl-E-` AND matches a `git add` invocation (architect's shell form): `if [[ "$CMD" == *"/tmp/.worktrees/baseball-crawl-E-"* ]] && [[ "$CMD" =~ (^|[^[:alnum:]])git[[:space:]]+add([[:space:]]|$) ]]; then`. This prevents main-checkout closure `git add` calls (Step 7a, Step-8 sub-step 8) from firing phantom rows / early resets. The row records: epic ID, the staging-boundary sequence index (incrementing per qualifying `git add` within the epic), and the sends count for the just-completed story; the 'rounds' field is blank/best-effort. Accepted residual (do NOT engineer around it): Phase-5 remediation worktree adds also match — harmless, and consistent with the best-effort rounds/story-ID posture.
- [ ] **AC-4** (file locations): The counter file and dispatch log live under the epic worktree (suggested: `<worktree>/.dispatch-log/sends.count` and `<worktree>/.dispatch-log/E-NNN.tsv`). The counter file is gitignored (transient); the `.tsv` dispatch log is tracked so it rides the closure patch (per operator decision 3 — worktree-local, no committed cross-epic aggregate).
- [ ] **AC-5** (threshold provenance in comment): The hook's comment records the provenance of both numbers: `15 ≈ the two-round breaker's implied 12-14-send budget`; `25 is a placeholder calibrated on a single epic`; and names the operator as the sole person who may edit either number.
- [ ] **AC-6** (fail-safe + scoping): The hook fails open on missing dependencies (mirroring `worktree-guard.sh`'s `jq`-absent behavior) and takes no action when no epic worktree / dispatch context is present, so it never interferes with non-dispatch sessions.

## Technical Approach
Model the hook shape on the existing `worktree-guard.sh` (JSON `permissionDecision` output for the deny at 25; warning surfaced via the permitted-with-message path or a non-blocking notice). Determine the epic ID and worktree root the same way `worktree-guard.sh` detects dispatch (glob `/tmp/.worktrees/baseball-crawl-E-*`). The `git add` matcher increments the sequence index and resets — because `PreToolUse` fires before the command, the reset brackets the just-finished story cleanly (the staging boundary is `git add -A` after each story passes review). Register both events in `settings.json` alongside the existing `PreToolUse` matchers. Add the `.dispatch-log/sends.count` (or the whole transient counter) to `.gitignore`; keep the `.tsv` tracked.

The 'rounds' column is intentionally best-effort per decision 7 — do NOT add any new skill instruction or agent-facing rule to populate it; leave it blank if the hook cannot observe it. This epic adds mechanisms, not instructions (epic Non-Goals).
