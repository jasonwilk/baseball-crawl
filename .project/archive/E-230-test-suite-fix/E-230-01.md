# E-230-01: Populate `gs` in Pitcher Fixtures + Harden `gs` Template Guard (All 4 Templates)

## Epic
[E-230: Fix the 56 Post-RTK Test-Suite Failures](../E-230-test-suite-fix/epic.md)

## Status
`DONE`

## Description
After this story is complete, the three stale pitcher-dict test fixtures supply a `gs` key matching the real production query contract (clearing the 52 `gs`-family failures), AND all four templates carrying the `gs` GS/GR pattern are hardened so a pitcher dict with a **missing** `gs` key degrades to em-dash identically to a present-`None` value, instead of raising `UndefinedError`. The existing `{% if pitcher.gs is none %}` behavior for real NULL `gs` is preserved — the hardening only adds tolerance for a missing key.

## Context
This is Cluster 1 from discovery — the dominant bucket (52 of the 56 failures). First-hand SE + DE investigation proved the production data layer is correct: every production pitcher-dict path supplies `gs` (`generator.py:203`/`:222`, `db.py:188`, `db.py:888`, `dashboard.py:997`), and NULL `gs` is a normal production state (manual-entry opponents with no `appearance_order`, pre-backfill rows, member teams when the GC payload lacks "GS" — `season_stats_loader.py:503`). The current guard renders those NULLs as em-dash and must keep doing so. The failures come from the **test fixtures**, which omit the `gs` key entirely (they predate the column); RTK's output compression hid the resulting render exception. The user chose to also harden the four templates so a *future* caller that forgets `gs` degrades to em-dash instead of a 500. See epic Technical Notes "Cluster 1" for the full first-hand trace, gs semantics, and file/line list.

## Acceptance Criteria
- [ ] **AC-1**: The three pitcher-dict fixture helpers populate a `gs` key consistent with the production query contract: `_make_pitcher` in `tests/test_report_renderer.py:30`, the pitcher builder in `tests/test_report_workload.py`, and `_make_pitcher` in `tests/test_dashboard_workload.py:223`.
- [ ] **AC-2**: Fixture coverage exercises the gs semantics per epic Technical Notes "Cluster 1": at least one case with `gs = None` (asserting the rendered cell is an em-dash), at least one with `gs` a positive int (asserting the rendered cell is `{gs}/{g-gs}`), and a `gs = 0` case (asserting the rendered cell is **`0/N`** — a known pure reliever — and explicitly **not** an em-dash; 0 is data, never blanked).
- [ ] **AC-3**: Given a pitcher dict with a **missing** `gs` key, when any of the four templates renders the GS/GR cell, then it renders an em-dash (`&mdash;`) and does **not** raise `UndefinedError`. Templates (line numbers approximate — match by the `pitcher.gs is none` guard pattern, since edits may shift later lines in the same file): `src/api/templates/reports/scouting_report.html:711`, `src/api/templates/dashboard/opponent_print.html:398`, `src/api/templates/dashboard/opponent_detail.html:392`, `src/api/templates/dashboard/team_pitching.html:84`.
- [ ] **AC-4**: The hardened guard preserves existing behavior: present-`None` → em-dash; positive int → `{gs}/{games - gs}` split; `gs == 0` → `0/N` (never em-dash). Applied consistently across all four templates. Any guard form that achieves this is acceptable (e.g. `pitcher.get('gs') is none`, or `pitcher.gs is undefined or pitcher.gs is none`) — the implementer picks; the AC verifies the four rendered outcomes (missing/None/0/positive-int), not a specific guard syntax.
- [ ] **AC-5**: `python -m pytest tests/test_report_renderer.py tests/test_report_workload.py tests/test_dashboard_workload.py tests/test_template_gs_guard.py` reports 0 failed (the new AC-6 guard test is included in the named command so the acceptance evidence actually runs the missing-key behavior this story adds); and the full `python -m pytest tests/` shows these 52 failures cleared with no regressions introduced elsewhere. - [ ] **AC-6**: A template-level unit test renders **each of the four `gs` templates** with a `gs`-LESS context dict directly through Jinja and asserts the GS/GR cell is an em-dash with **no `UndefinedError`**. The test lives in a Story-01-owned file **outside `tests/test_dashboard.py`** (recommend a new focused `tests/test_template_gs_guard.py` covering all four templates in one place), keeping Story 01 and Story 03 file-disjoint.

Fix = assert the class **token** is present (e.g. `'last-outing-header'` / `'last-outing-cell'`), not the full attribute string. **No production/template change.** First-hand evidence required: SE confirmed (by reverting the `gs` fixture edit and re-running on pristine HEAD) these pre-exist this story and are not `gs`-related. These live in `tests/test_report_workload.py`, which AC-5's named command already requires 0-failed — so this is within AC-5's existing acceptance surface, not new scope.

## Technical Approach
Apply the decision framework in epic Technical Notes (reproduce → trace source history → confirm the production path supplies `gs`). Two coordinated changes: (1) bring the three fixture helpers into line with the production contract; (2) choose a single consistent guard form that treats a missing key and `None` identically while preserving the `0 → 0/N` and positive-int split behaviors, and apply it across all four templates. Per the Test Scope Discovery rule, after editing the templates and fixtures discover and run every test file that exercises these render paths, not only the three named here.
