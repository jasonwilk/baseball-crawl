## Overview
Make every standalone report generation auditable, tell coaches how complete each report is, and make degraded or empty outcomes explicit instead of silent. The reports pipeline (`src/reports/generator.py::generate_report()`) today records only a coarse `reports.status` (`generating`/`ready`/`failed`) — a half-loaded, spray-failed, or zero-games report is indistinguishable from a complete one. This epic adds a per-stage run record, three hard quality gates, a coach-facing footer trust block, and closes a concurrent-generation team-deletion race — all without changing report stat values or the pipeline's existing degrade-gracefully semantics.

## Background & Context
The standalone reports flow is the product as actually used (ROADMAP §1): `bb report generate <url>` / `POST /admin/reports/generate` → an 8-stage in-memory pipeline → frozen HTML at `data/reports/{slug}.html`. ROADMAP §2 ("What's weak") documents the verified failure modes this epic targets, all of which become acute once Epic E generates reports unattended each morning:

1. **No per-stage run record.** `reports` has status/error but no stage visibility. A degraded report looks identical to a complete one — fine when an operator watches, fatal for scheduled runs.
2. **Ready-but-empty reports** (verified, `generator.py:1098`): the only crawl gate fires on `errors > 0 AND games_crawled == 0`. A team with zero completed games and zero errors (early season, wrong URL) skips the gate; `_query_freshness()` returns `(None, 0)` and an empty report renders as "ready" at the post-load render step.
3. **Orphan-cleanup concurrency race** (verified, `generator.py:1088/1198/1317`): orphan teams are computed by diffing a pre-run team-id snapshot against a post-run snapshot. Two concurrent generations each see the other's freshly-created team as an "orphan" → one can delete the other's legitimately-shared team rows. Generation cleanup does NOT re-check `is_team_eligible_for_cleanup` (that guard is on the report-DELETE path only).
4. **Silent wrong-scope risks**: `derive_season_id_for_team()` (line 1106) falls back to current-year/year-only on incomplete metadata (silent wrong season); `ensure_team_row` step-3 can match a team by name+season only with no `public_id`/`gc_uuid` anchor (silent wrong-team attachment). Neither is surfaced anywhere.
5. **No trust signal on the report.** Coaches cannot see "12 of 14 games found, spray unavailable, reconciliation clean."

Three domain consultations grounded the plan (all via main-session relay):
- **software-engineer**: full read of `generator.py` — stage-extraction seams, the two cross-stage state dependencies (snapshot boundary; `season_id`/`plays_game_ids`/`crawl_result` threading), the two-tier fail contract, gate slot points, and the orphan-cleanup race as the sharpest risk.
- **data-engineer**: the run-record schema — a single wide `report_generation_runs` row (NOT a child table) mirroring the `scouting_runs` precedent, all trust flags on the run row (do NOT ALTER `reports`), migration 002 as pure CREATE, the cleanup-mirror obligation, and the structural cross-process concurrency fix (per-run team attribution > DB lock > process lock).
- **baseball-coach**: the footer trust-block content — signal set, three severity tiers, the M = games-played-to-date semantic, the explicit no-games message, and the operator-vs-coach flag split (generic degraded-confidence indicator).

## Goals
- A `report_generation_runs` table records, per generation: per-stage status + counts (crawl, load, gc_uuid, spray, plays, reconciliation, enrichment) and report-level trust flags (season fallback, identity match method, completed-game count, enrichment/Tier-2 status).
- The admin reports list surfaces per-stage detail + counts + operator-only trust flags + the existing `error_message`, replacing the binary ready/failed view.

### TN-1: Run-record schema (story 01) — data-engineer
- **One wide `report_generation_runs` row per generation, NOT a child table.** The stage set is fixed (7 known stages) and the counts are heterogeneous (games vs plays-games vs discrepancies), so a normalized `(run_id, stage, ...)` child table would force generic `count_a/count_b` columns (breaking the recognizable-column-name convention) and a 7×N admin-list fan-out. A wide row gives a flat 1:1 join, one row per report. Mirror the existing `scouting_runs` table shape rather than invent a new pattern.
- **All trust flags live on the run row. Do NOT ALTER `reports`** — `reports` stays the thin artifact-identity row the public serve path reads.
- **Proposed columns** (DE owns final names/types/constraints; firm at dispatch):
  - identity/lifecycle: `id` PK, `report_id` FK → `reports(id)` ON DELETE CASCADE, `started_at`, `completed_at`, `overall_status` CHECK(`running`/`completed`/`failed`)
  - per-stage status (nullable; NULL = stage did not run): `crawl_status`, `load_status`, `gc_uuid_status`, `spray_status`, `plays_status`, `reconciliation_status`, `enrichment_status`
  - per-stage counts (named): `completed_games` (M), `completed_games_with_data` (N), `spray_games`, `plays_games_expected`, `plays_games_covered`, `discrepancies_found`, `discrepancies_corrected`
  - trust flags: `season_id_used` (FK → `seasons`), `season_fallback` INTEGER 0/1, `identity_match_method` CHECK(`anchor`/`name_only`)
  - failure: `error_stage`, `error_message`
- **`enrichment_status` IS the Tier-2 status — REUSE the canonical vocabulary** `success` / `unavailable-no-key` / `failed` from `.claude/rules/architecture-subsystems.md` (LLM package, established by E-233). Do NOT invent a new enum.
- **`identity_match_method`**: `anchor` when `ensure_team_row` matched/attached by `gc_uuid` or `public_id` (reliable); `name_only` when matched by name+season with no external-id anchor (lower trust — the silent-wrong-team risk).
- **`season_fallback` = 1** when `derive_season_id_for_team()` resolved via the current-year / year-only fallback rather than team metadata.
- **Migration 002 is pure `CREATE TABLE IF NOT EXISTS` + `CREATE UNIQUE INDEX IF NOT EXISTS`** — all telemetry lands on the new table, so the SQLite "no ADD COLUMN IF NOT EXISTS" caveat never applies; the FK target `reports(id)` already exists in migration 001. Per `.claude/rules/migrations.md`: next number is 002, zero-padded, idempotent.
- **`UNIQUE(report_id)`** triples as the 1:1 enforcer, the idempotency key, and the admin-list join index. (Each generation mints a fresh `reports` row/slug, so `report_id` never collides today; if in-place regeneration ever arrives, drop UNIQUE and add a `run_number` — out of scope here.)
- SQLite booleans are `INTEGER 0/1` (project convention).
- **Per-stage `*_status` columns intentionally carry NO CHECK constraint** (only `overall_status`, `identity_match_method`, and `enrichment_status` are CHECK-constrained). This is deliberate — per-stage status vocabularies vary and NULL means "stage did not run" (DE-3 affirm). `season_id_used` is correctly nullable.
- **Run-row creation timing**: `report_generation_runs` FK-references `reports(id)`, so the run row can only be created AFTER the reports row exists (`generate_report` step 3). Signals determined earlier in the pipeline (e.g. `identity_match_method` at the `ensure_team_row` site in step 2) MUST be stashed in the in-memory generation context and written to the run row once it exists — see §TN-2/§TN-3 (SE-F3).
- **Column names — LOCKED for READY (DE verdict, Codex P2)**: M = **`completed_games`** (distinct completed games on the schedule, played to date — matches the canonical `status='completed'` convention and removes the "scheduled incl. future" misread); N = **`completed_games_with_data`** (distinct completed games with loaded stat rows = the `_query_freshness` count, NOT `load_result.loaded` — the rename closes the `games_loaded`↔`load_result.loaded` ambiguity SE-F2/F4 had to disambiguate). The pair `completed_games ⊇ completed_games_with_data` makes N ≤ M self-evident (the footer's N-of-M point). The redundant `completed_game_count` trust-flag column is **REMOVED** — `completed_games` is the single canonical M. Plays counts (`plays_games_expected`/`plays_games_covered`) are unchanged.

### TN-2: Generator restructure (story 02) — software-engineer
- **Goal: extract the comment-delimited stages of `generate_report()` (≈ lines 987–1376) into named stage methods, each writing its status + counts to the `report_generation_runs` row as it completes.** Create the run row immediately AFTER the reports row exists (step 3 — the FK requires it, see §TN-1), set `overall_status='running'`, update per stage, finalize (`completed`/`failed` + `completed_at`) at the end. Signals determined before the run row exists (notably `identity_match_method` from the step-2 `ensure_team_row` call) are stashed in the in-memory generation context and written when the run row is created (SE-F3).
- **Restructure-as-refactor — NO behavior change beyond the named gates (story 03) and the concurrency fix (story 04).** Same stages, same order, same non-fatal/degrade-gracefully semantics. This is an acceptance constraint, not a suggestion (ROADMAP §6 rule #3).
- **Exact semantics to preserve:**
  - **Two-tier fail contract**: crawl `errors > 0 AND games_crawled == 0` is FATAL (`_fail_report` + early return); the load guard fires only on `errors > 0 AND loaded == 0`; spray, plays, reconciliation, and Tier-2 enrichment failures are NON-FATAL (logged, generation continues).
  - **Snapshot boundary**: the pre-run team-id snapshot is taken AFTER the reports-row creation but BEFORE the scouting crawl; `orphan_ids` is the post-pipeline diff. The restructure MUST keep this boundary intact (story 04 changes *how* orphans are determined, not story 02).
  - **Cross-stage state threading**: `season_id`, `plays_game_ids`, `crawl_result.games`/`.boxscores`, `resolved_gc_uuid`, and the public-API-fetched `team_name`/`season_year`/`ngb`/`age_group` thread across stages — preserve their availability.
- **Mechanism is the implementer's choice** (a context dataclass / small stateful object that carries cross-stage state and the run-record handle is the natural shape, but the story does NOT mandate a specific structure — avoid 8-argument free functions).
- **Per-stage counts written here** (all are PER-GAME distinct-game counts, NOT record counts):
  - `completed_games` (M) = distinct completed games on the fetched schedule. **Available from `crawl_result.games`** — the crawler already carries the full schedule and computes the completed-game count; story 02 confirms the exact completed-game field rather than defaulting to NULL (SE-F4). NULL is a last-resort only if the field genuinely is not exposed.
  - `completed_games_with_data` (N) = distinct completed games we actually have stat data for = the `_query_freshness()` `COUNT(*)` of distinct completed games. **It is NOT `load_result.loaded`** — that counts upserted stat RECORDS (≈ players × games) and would ship a wrong N/M ratio (SE-F2). The footer's N (§TN-7) and this column are the SAME number.
  - `spray_games`, `plays_games_expected`/`plays_games_covered`, `discrepancies_found`/`discrepancies_corrected` (from the reconciliation pass), and `enrichment_status` (reuse the Tier-2 status already computed at the enrichment site, E-233).
- **Verification**: the restructure MUST leave E-234's golden stat-table test and aggregate-parity test green (no stat-value/formula drift), and the negative-path characterization tests (E-234-04) must still pass for all paths NOT changed by story 03. Run the full report-generator test surface plus E-234's guards.

### TN-3: Three quality gates (story 03) — software-engineer
Builds on story 02's restructured stages + run-record writing. Each gate writes to the run record; only gate (a) aborts.

The gate produces an **explicit named outcome** instead of an empty report. The run record captures the **M=0 vs N=0 distinction**: `completed_games == 0` (no games played yet — early season) vs `completed_games > 0 AND completed_games_with_data == 0` (games played but none loaded). Coach wording for the rendered outcome is in §TN-7.
  - **Terminal-state shape (PINNED for READY)**: gate (a) sets `reports.status = 'no_games'` (a distinct value, NOT a bare `failed`) and writes a minimal explanatory HTML page to `data/reports/{slug}.html` so the public serve route renders the coach message instead of 404ing. `reports.status` is a free-text TEXT column (no CHECK), so the new value needs no migration. **Story 06's admin reports list must recognize `no_games`** when it renders status (the existing template badges switch on `ready`/`failed` at `reports.html` — a `no_games` state needs its own badge/handling). DE/SE may flag at dispatch only for a technical conflict; the spec commits to `no_games` + minimal page.

### TN-4: Close the concurrent-generation team-deletion race (story 04) — software-engineer
- **Outcome (the AC): two concurrent `generate_report()` runs must never delete each other's freshly-created teams**, proven by a regression test that interleaves two generations (or simulates the interleaving at the orphan-determination boundary).
- **Cross-process insight (DE, decisive):** the real concurrency boundary is CROSS-PROCESS — the admin-UI generation, the `bb report generate` CLI, and the future cron job (Epic E) are SEPARATE processes against one SQLite file. **A process-level / asyncio lock is INSUFFICIENT** — it guards only within one process and does not close this race. Do not ship a bare in-process lock as the fix.
- **Recommended approach (DE-1, prevention-over-cleanup): an IN-MEMORY per-run created-set — no migration, no persisted column.** Team creation and orphan cleanup both happen in the SAME process within one `generate_report()` call, so a process-local set of the team ids THIS call INSERTed fully closes the cross-process race (each process only deletes teams it inserted; a concurrent run's teams are never in this run's set). A persisted `created_by_run_id` column would add a migration AND couple the canonical `teams` table to report telemetry for no benefit — do NOT add one. Replaces the global pre/post snapshot diff entirely.
- **The set captures INSERTED teams, not MATCHED ones (DE-2).** `ensure_team_row()`'s dedup cascade returns existing team ids too; the created-set must record only teams this run truly INSERTed (else if two concurrent runs reference the same brand-new opponent, both would claim it). This likely needs `ensure_team_row()` to signal insert-vs-match to its caller (today it returns only `int`) — the SAME canonical-function extension story 03 needs for gate (c) identity (see §TN-3). One shared `src/db/teams.py` change, introduced by story 03, consumed by story 04 (04←03 serializes it).
- **The created-set must thread through `ScoutingLoader` (SE-F5).** The orphan teams that cause the race are opponent STUBS created DURING the scouting load via `ScoutingLoader` → `ensure_team_row()`; `ScoutingLoader` has no knowledge of the run today. The set (or its insert-recording hook) must thread through `ScoutingLoader` into its `ensure_team_row` calls. This adds `src/gamechanger/loaders/scouting_loader.py` to story 04's scope. **Timestamp-based attribution does NOT work** — concurrent runs overlap in time.
- DE vote: **in-memory per-run created-set > DB-backed lock > process lock.**
- **If SE chooses a lock instead:** it MUST be DB-backed (a single-row lock table with stale-lock recovery so a crashed holder cannot deadlock), and MUST NOT hold a `BEGIN IMMEDIATE` write lock across the network crawl (generation spans network I/O; holding SQLite's write lock across it stalls all writers).
- **SE + DE alignment required before this story freezes** (DE offered to review the mechanism choice). The mechanism is SE's call per the delegation boundary; the cross-process constraint + the regression-test outcome are fixed.
- **Preserve** the existing `cleanup_orphan_teams` blast-radius limit (only deletes games where BOTH participants are orphans; retains teams still FK-referenced by surviving games).

### TN-5: Cleanup-mirror invariant (story 05) — software-engineer
- **Mandatory in-scope per `.claude/rules/data-model.md` "Cleanup-Detection Mirror Invariant".** `report_generation_runs` FK-references `reports`, so every path that deletes a `reports` row (or a `teams` row whose reports are removed) MUST handle the run rows in the same change.
- **Known site**: `src/api/routes/admin.py::_delete_report` deletes the report row (`DELETE FROM reports WHERE id = ?`, ≈ line 3270) before cascading the team. The run rows must be removed there.
- **Mechanism**: `ON DELETE CASCADE` only fires when the deleting connection has `PRAGMA foreign_keys = ON`. SE either (a) relies on the cascade, OR (b) adds an explicit `DELETE FROM report_generation_runs WHERE report_id = ?`. Pick one and prove it with a test (delete a report → its run row is gone).
- **Two-connection trap (CR-F4) — the most likely place to get this wrong.** `_delete_report` (admin.py:3233) uses TWO separate connections: **conn1** runs `DELETE FROM reports WHERE id = ?` and **commits**, then a NEW **conn2** runs `cascade_delete_team`. Consequences:
  - If using the explicit-delete mechanism (b), `DELETE FROM report_generation_runs` MUST run in **conn1, BEFORE `DELETE FROM reports`** (same transaction, FK ordering). Putting it in the conn2 cascade block is too late — the reports delete in conn1 would already have hit the FK.
  - If relying on CASCADE (a), `foreign_keys = ON` must hold on **conn1 specifically** (the connection that deletes the reports row).
- **Pragma is confirmed available (SE-F6)**: `get_connection()` sets `PRAGMA foreign_keys = ON` (`src/api/db.py:55`) and `_delete_report` uses `get_connection()`, so CASCADE will fire on conn1. Story 05 confirms this rather than assuming it. **Test caveat**: AC tests MUST run against `get_connection()` (or replicate the pragma) — a bare `sqlite3.connect()` has foreign keys OFF and would give a false-green/false-red result.
- **Audit obligation**: locate every path that deletes a `reports` row or a `teams` row with associated reports (`_delete_report`, the admin team-delete cascade via `cascade_delete_team`, and any detection/confirmation query that mirrors the report/team delete surface, e.g. `_get_delete_confirmation_data`'s `cross_persp_rows`). Determine for each whether `report_generation_runs` needs handling and update in lock-step. (Note: `report_generation_runs` is report-scoped telemetry, not a per-player stat table, so it likely does NOT belong in the `cross_persp_rows` per-perspective UNION — but the audit must confirm rather than assume.)

### TN-7: Trust-block content (story 07) — baseball-coach (authoritative)
- **Signal set** (frozen HTML footer): `Through {date} (N of M games) · Pitch detail for {K} games · spray {available/unavailable} · Generated: {date}`. Note: "Generated: {date}" is SEPARATE from "Through {date}"; "Pitch detail" is the bench-readable rename of "plays data"; drop the word "loaded" (jargon) in favor of "found" or the bare numbers.
- **M = games PLAYED to date, not total scheduled.** N/M = "of the games this team has played, how many we found data for."
