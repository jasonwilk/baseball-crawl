# E-228-06: Scouting-pipeline wiring + cross-path parity verification

## Epic
[E-228: Defensive Positioning Pocket Cards](../E-228-defensive-positioning-cards/epic.md)

## Status
`DONE`

## Description
After this story is complete, the tracked-opponent scouting pipeline rebuilds `batter_positioning` as an automatic stage -- in both the background-task path (`run_scouting_sync`) and the CLI path (`bb data scout`) -- and the two delivery paths (standalone and scouting pipeline) are verified to produce identical `batter_positioning` rows for the same team.

## Context
E-228-03 wired the standalone path (dedup -> recompute). This story mirrors that ordering on the scouting pipeline and closes the second delivery path. The recompute is a pure DB-read materialization step that must run after spray load AND after the existing post-spray `dedup_team_players` sweep (epic Technical Notes section TN-6). It slots in as a new final step in `run_scouting_sync`, inside the shared connection block, non-fatal. The CLI path gets the equivalent step so the two scouting paths stay at parity (the scouting-pipeline parity principle in CLAUDE.md).

Because both delivery paths call the identical pipeline-agnostic engine function from E-228-02, parity is by construction -- but this story verifies it. The full parity check requires real spray data and the Docker stack, so it is an operator-run integration test (see Acceptance Criteria and the epic's Open Questions); the worktree-runnable portion is structural/unit coverage of the wiring.

**Both scouting paths already run dedup** (confirmed by software-engineer during review iteration 1): `run_scouting_sync` runs `dedup_team_players` as its existing post-spray sweep (Hook 2), and `src/cli/data.py::_scout_live()` Step 4 calls `_post_spray_dedup()` (around lines 375-435), which calls `dedup_team_players(conn, team_id, season_id, manage_transaction=True)` -- the CLI mirror of Hook 2. So there is **no third dedup gap**: this story only ADDS the recompute step after each path's existing dedup call. It does NOT add a dedup call to either scouting path.

## Acceptance Criteria
- [ ] **AC-1**: Given a tracked opponent with spray data, when `run_scouting_sync` runs, then the positioning recompute executes as a new final step immediately after the existing post-spray `dedup_team_players` sweep, inside the shared connection block, and populates `batter_positioning` -- per Technical Notes section TN-6.
- [ ] **AC-2**: Given the positioning recompute raises an error during `run_scouting_sync`, when the pipeline handles it, then the failure is non-fatal -- it is logged at WARNING and the crawl job remains `completed` (matching the spray-stage error contract).
- [ ] **AC-3**: Given `bb data scout`, when it runs for a tracked opponent, then the positioning recompute executes immediately after the existing `_post_spray_dedup()` call in `_scout_live()` Step 4 (around line 382), in the same `with` block, non-fatal -- so the CLI path and the background-task path produce equivalent `batter_positioning` artifacts (scouting-pipeline parity principle). This AC adds ONLY the recompute step; `bb data scout` already dedups (per the Context section), so no dedup call is added here.
- [ ] **AC-4**: Given both paths call the identical engine function from `src/reports/positioning.py`, when the wiring is reviewed, then no positioning decision logic is duplicated in `trigger.py` or `cli/data.py` -- they only invoke the shared function.
- [ ] **AC-5** (operator-run integration test): Given the same tracked opponent with real spray data, when the scouting pipeline is run and `bb report generate` is run for that team, then the resulting `batter_positioning` rows are identical across both paths. **Verification method**: this AC is verified by the operator in the Docker dev environment with real data -- it is not runnable in the epic worktree (no `data/`, no Docker). The story's worktree-runnable coverage is the structural/unit tests for AC-1 through AC-4.
- [ ] **AC-6** (auto-generate report bundle -- (B) Pre-generate): Given a tracked opponent and a successful positioning recompute, when the scout pipeline reaches the end of its run (in both `run_scouting_sync` and `bb data scout`), then it calls `generate_report()` for the scouted `team_id` as a new final step immediately after the positioning recompute, inside the same shared connection block. This produces a `ready` report row for the team so the opponent dashboard's "Defensive Positioning" link (E-228-07 AC-4) resolves to a real artifact for an actively-scouted opponent -- per epic Technical Notes section TN-7 ((B) Pre-generate is v1 scope; this is the automation step that makes (B) real, per the pipeline-automation principle that data-quality steps must be automatic, not manual CLI commands). Both scout paths invoke the existing `generate_report()` function -- import-and-call, no duplicated logic.
- [ ] **AC-6a** (auto-generate is non-fatal): Given `generate_report()` raises an error during the scout pipeline's auto-generate step, when the pipeline handles it, then the failure is non-fatal: it is caught and logged at **WARNING**, the scout run completes cleanly with exit code unchanged, and the crawl job remains `completed` -- mirroring the Tier 2 LLM non-fatal pattern already established in `src/reports/generator.py` and the AC-2 spray-stage error contract. A test fixture exercises the failure path and asserts both behaviors (WARNING logged; scout exit code unchanged from the success path).

## Technical Approach
In `src/pipeline/trigger.py::run_scouting_sync`, add the positioning recompute as a new final step after the existing post-spray `dedup_team_players` sweep (around `trigger.py:737-750`), inside the shared `with closing(sqlite3.connect(...))` block, wrapped in try/except with a WARNING log so it is non-fatal. In `src/cli/data.py::_scout_live()`, add the recompute immediately after the existing `_post_spray_dedup()` call (Step 4, around line 382), same `with` block, same non-fatal contract. Both paths call the shared `(conn: sqlite3.Connection, team_id: int, season_id: str)` function from `src/reports/positioning.py` (E-228-02), which commits its own writes per the transaction contract in epic Technical Notes section TN-6 -- import and invoke only, no duplicated logic.

The recompute needs the same `(team_id, season_id)` pair that `_post_spray_dedup()` operates on -- which it resolves from `scouting_runs`. Either factor that lookup out so both the dedup and the recompute share it, or have the recompute do the same `scouting_runs` query -- so the implementer does not re-derive `team_id` independently and get it wrong. The same care applies on the `run_scouting_sync` side: pass the `team_id` / `season_id` already in scope, do not re-derive.

After the positioning recompute on both scout paths, add an **auto-generate step** that calls `generate_report()` for the scouted `team_id` in the same shared connection block (AC-6). Wrap the `generate_report()` call in try/except with a WARNING log on failure so the scout run completes cleanly even if generation errors (AC-6a -- mirrors the Tier 2 LLM non-fatal pattern in `src/reports/generator.py` and the AC-2 spray-stage contract). The implementer imports `generate_report` from `src/reports/generator.py` and invokes it once per scout path; no generation logic is duplicated into `trigger.py` or `cli/data.py`. The same `(team_id, season_id)` discipline applies as for the recompute step: pass values already in scope, do not re-derive.

Add structural/unit tests for the wiring; add a failure-path test for AC-6a (scout exit code unchanged, WARNING logged when `generate_report` raises); document the AC-5 parity check as an operator-run integration test with its verification method.
