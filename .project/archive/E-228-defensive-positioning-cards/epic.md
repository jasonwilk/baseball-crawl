## Overview
Build two printable artifacts -- a landscape coach **call sheet** and a multi-up sheet of per-position **player cards** (cards-per-sheet determined by the design spec, not fixed up front) -- that turn an opposing batter's spray-chart tendencies into a defensive positioning plan a fielder can act on mid-game. A deterministic engine computes each batter's optimal fielding point per position, classifies direction and depth via two knobs through a swappable geometry seam, and quantizes to a named alignment -- stored in a new precomputed `batter_positioning` table; an optional LLM layer writes only a one-line rationale and never the decision. Delivered through both the standalone report path and the tracked-opponent scouting pipeline.

## Background & Context
LSB coaches game-plan defensive positioning from gut and memory. The spray-chart data to do it better already exists in the database (`spray_charts`, populated by the scouting and reports pipelines), but there is no artifact that converts "who's batting" into "where do I stand" at the speed and cognitive load a 15-year-old fielder can act on. This epic is the product of a completed three-expert design brainstorm (baseball-coach, ux-designer, data-engineer); the converged design recommendation lives at `/home/vscode/.claude/plans/i-need-to-plan-joyful-cloud.md` and is the authoritative design input.

The core insight from the brainstorm: the hard problem is not rendering a shift -- it is the *lookup*. The solution pushes analysis to the coach and the generation step and leaves the player a recognition task. And because HS sample sizes are small, "play straight up" (TRUE) is the honest default and a first-class answer, not a failure state.

This epic absorbs two prior ideas, both of which are about surfacing positioning/tendency information from spray charts:
- **IDEA-048** -- Fielder Position Labels/Zones on Spray Charts
- **IDEA-049** -- Pull/Center/Oppo Tendency Summary on Spray Charts

Both idea files are to be marked `PROMOTED` -> E-228 when this epic is created.

**Locked user decisions (not open for re-litigation):** full v1 scope (the full `call_state` set + the LLM rationale layer), configurable vocabulary, both delivery paths. (The user's "all 6 named states" was stated against the original handedness-relative draft; review iteration 1 replaced that with the symmetric absolute set -- 8 `call_state` values: TRUE + 6 directional shades + MIXED, see TN-3. The user decision being preserved is "full scope, not a reduced subset," which the symmetric set honors.)

## Goals
- A new precomputed `batter_positioning` table holding the Tier 1 deterministic positioning decision per batter / team / season / perspective / position, rebuilt as an automatic pipeline stage.
- A deterministic Tier 1 engine that computes each batter's optimal fielding point and its deviation per position, classifies absolute field direction and depth through a swappable geometry seam, applies hard sample gates, and quantizes to one of the 8 `call_state` values (TRUE + 6 directional shades + MIXED) -- reproducible and auditable, no LLM in the decision path.
- An optional Tier 2 LLM layer that writes only the one-line rationale; the call sheet is fully usable with the LLM disabled.
- Two print artifacts (landscape call sheet + multi-up portrait player cards) rendered into the report bundle, printing correctly on a dugout printer.
- Positioning delivered through BOTH the standalone `bb report generate` path and the tracked-opponent scouting pipeline, producing identical `batter_positioning` rows.
- The opponent dashboard surfaces a link to the positioning cards (feature parity).

## Non-Goals
- Positioning for P, C, 1B -- their positioning is driven by situation and role, not batter spray. v1 covers SS, 2B, 3B, LF, CF, RF only.
- An inline positioning view on the opponent dashboard -- v1 ships a "download cards" link only; an inline view is a deferred fast-follow.
- Wristband insert strips and a dedicated laminated dugout board -- deferred (paper does the job at zero cost).
- A standalone `bb data` recompute subcommand -- the pipeline stage is the rebuild path (recalibration = tweak constants, re-run the pipeline).
- A per-team UI setting for the vocabulary remap -- v1 ships a documented constants block in code; a per-team setting is deferred.
- Automated calibration of the sample gates or sector geometry -- v1 ships with provisional starting values; calibration is an operator activity (see Technical Notes, Rollout).
- Batter-handedness-aware pull/oppo framing -- explicitly out of scope. **Batter handedness is unavailable on every data path E-228 uses**: the public roster endpoint (`/teams/public/{public_id}/players`) has no handedness field, `players.bats` is unpopulated dead schema (zero read/write paths in the pipeline), and the endpoints that carry handedness are off the opponent-scouting path. (Handedness *does* exist and is ~96% populated on the owning-team opponent-registry endpoint `/teams/{team_id}/opponents/players` -- but that endpoint is keyed by the owning team's UUID and covers only team-lookup-entered opponents, so E-228's public-id-based scouting path cannot use it.) A pull/oppo vocabulary cannot be built on a field E-228 cannot read, so E-228's vocabulary is absolute field direction (LEFT/RIGHT) instead -- see TN-3. Pursuing reliable handedness (e.g. via the owning-team opponent-registry endpoint) would be a separate api-scout investigation and a separate epic.
- Runtime clustering / dynamic zone discovery -- out of scope for v1. v1 ships fixed angular-sector geometry as module-level constants behind the swappable seam (see TN-3 Stage B and E-228-02). Empirical zone refinement -- clustering per-batter optimal points into 2-3 discovered zones per position -- is a planned fast-follow (captured in the ideas backlog), **gated on the design-time calibration pass confirming per-batter centroid tightness**. The reason it is not in v1 is **signal-to-noise**: at 15-35 BIP per batter, each per-batter optimal point carries large sampling error, and clustering ~10-13 such points per lineup risks overfitting noise. (This is not a stability argument -- data-driven change between runs is a feature, not a defect; the gate is purely whether the per-batter inputs are precise enough to cluster meaningfully.)

## Technical Notes

### TN-1: Architecture -- Tier 1 / Tier 2 split
The proven pattern from `src/reports/llm_analysis.py` (`enrich_prediction` / Tier 1 starter prediction). The split -- **deterministic engine decides, LLM never touches the decision** -- was re-evaluated *un-anchored* from codebase precedent during planning and independently re-confirmed by data-engineer, software-engineer, and baseball-coach on the merits: the threshold cutoffs are irreducible (an LLM would only hide them in non-reproducible prose), this is a crisp-threshold problem for a pre-game card, and reproducibility matters. This is settled -- do not re-litigate. Two layers:
- **Tier 1 (deterministic, always runs)**: computes the per-batter optimal fielding point and its deviation, the direction/depth knobs via the swappable geometry seam, the sample/concentration gates, and the quantization to a named state or MIXED (see TN-3). This *is* the recommendation -- reproducible and auditable. Stored in `batter_positioning`.
- **Tier 2 (optional LLM via OpenRouter, non-fatal)**: takes the finished Tier 1 recommendation plus the aggregated zone table and writes ONLY the 1-2 sentence plain-English rationale. It never picks the alignment, never sees raw x/y, is fed pre-aggregated zone counts (not the chart image, not the coordinate list). It mirrors `enrich_prediction` exactly -- including discarding any LLM opinion on the decision itself (cf. the `confidence_adjustment` discard). **Guardrail: the call sheet must be fully usable with the LLM layer disabled.**

### TN-1a: Engine return shape (the Tier 1 / Tier 2 interface)
The Tier 1 engine in `src/reports/positioning.py` returns typed dataclasses -- this is the concrete, named interface that Tier 2 (E-228-07) and tests (E-228-02) build against, so neither has to reverse-engineer engine internals. E-228-02 names and defines these dataclasses; the shape is:
- A **per-batter result** dataclass carrying: the batter's `player_id`, `team_id`, `season_id`, `perspective_team_id`; the list of **per-position rows** (one per covered position); and the **team-state call** (the single named state, or `MIXED`). The batter's `bip_count` / `hr_count` / `is_thin` confidence values live on each per-position row (denormalized); the per-batter result does not separately duplicate them. The team-state call is the authoritative single value here; it is *also* denormalized onto each per-position row as `team_state_call` (next bullet) so that one persisted `batter_positioning` row is self-contained for the render path.
- A **per-position row** dataclass carrying the 11 non-key `batter_positioning` columns: `position`, `call_state`, `team_state_call`, `direction_shade`, `depth_shade`, `bip_count`, `hr_count`, `is_thin`, `zone_concentration`, `direction_deviation`, `depth_deviation` -- i.e. one `batter_positioning` row's worth of fields, excluding the four PK/provenance columns (`player_id`, `team_id`, `season_id`, `perspective_team_id`) which are carried on the per-batter result. `team_state_call`, `bip_count`, `hr_count`, and `is_thin` are **per-batter determinations written identically to all 6 of that batter's per-position rows** -- denormalized onto each row so a single `batter_positioning` row is self-contained for the render path, but they do not vary across a batter's positions. (`call_state` is this position's own call and *does* vary across positions -- per the per-position Stage B re-evaluation in TN-3; `team_state_call` is the batter's single team-state call and does not -- see TN-4a for how the per-position `call_state` values quantize into the team-state call.)
- A **per-zone aggregation** structure (the "aggregated zone table"): the pre-aggregated BIP counts per field zone and per contact type for the batter. This is what Tier 2 is fed -- it is part of the per-batter result return (not a separate recompute), so the Tier 2 layer reads it off the finished Tier 1 object and never touches `spray_charts` or raw x/y. E-228-02 decides whether it is a nested field on the per-batter result or a sibling dataclass, but it MUST be reachable from the per-batter result returned by the engine.

E-228-02 owns the exact dataclass names and field names; E-228-07's Tier 2 input is "the per-batter result dataclass from E-228-02," not a shape it defines itself.

### TN-2: `batter_positioning` schema
Migration file: `migrations/002_batter_positioning.sql`. The next migration number is **002** -- the E-220 rewrite consolidated old migrations 001-015 into `001_initial_schema.sql` (archived in `.project/archive/migrations-pre-E220/`); only `001_initial_schema.sql` currently exists. The implementing story MUST confirm the next number against `migrations/` and `.claude/rules/migrations.md` at implementation time.

```sql
CREATE TABLE IF NOT EXISTS batter_positioning (
    player_id TEXT NOT NULL REFERENCES players(player_id),
    team_id INTEGER NOT NULL REFERENCES teams(id),              -- batter's team (scouted opponent)
    season_id TEXT NOT NULL REFERENCES seasons(season_id),      -- season slug, e.g. '2026-spring-hs'
    perspective_team_id INTEGER NOT NULL REFERENCES teams(id),  -- whose API pull produced the spray rows
    position TEXT NOT NULL,             -- 'SS','2B','3B','LF','CF','RF'
    call_state TEXT NOT NULL,           -- this position's own call: 'TRUE','LEFT','LEFT_SHALLOW','LEFT_DEEP','RIGHT','RIGHT_SHALLOW','RIGHT_DEEP','MIXED'
    team_state_call TEXT NOT NULL,      -- the batter's team-state call (TN-4a): same 8-key enum as call_state. Per-batter determination denormalized onto all 6 of the batter's rows (same pattern as is_thin) -- never NULL, every batter has a call even if 'TRUE'. The render path reads this for the call sheet's CALL column instead of re-deriving the TN-4a MIXED-rule lattice in SQL.
    direction_shade TEXT,               -- 'left','center','right' (NULL when TRUE) -- absolute field direction, matches classify_field_zone() output
    depth_shade TEXT,                   -- 'in','normal','deep' (NULL below 25-BIP gate)
    bip_count INTEGER NOT NULL,
    hr_count INTEGER NOT NULL,          -- separate: over-the-fence HRs have NULL x/y
    is_thin INTEGER NOT NULL DEFAULT 0,
    zone_concentration REAL,
    direction_deviation INTEGER,        -- signed ordinal step bucket on the L-R axis (0 = on base, ±1 = slight shade, ±2 = significant shade); NULL when call_state='TRUE' (direction_shade NULL). Negative = toward LF, positive = toward RF (absolute orientation). Quantized from the SVG-space delta via the per-axis (x) # RECALIBRATE threshold ladder in positioning.py (E-228-02).
    depth_deviation INTEGER,            -- signed ordinal step bucket on the in-out axis (0 = on base, ±1 = slight shade, ±2 = significant shade); NULL below the 25-BIP depth gate (depth_shade NULL). Negative = shallower, positive = deeper. Quantized from the SVG-space delta via the per-axis (y) # RECALIBRATE threshold ladder in positioning.py (E-228-02).
    computed_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (player_id, team_id, season_id, perspective_team_id, position)
);
CREATE INDEX IF NOT EXISTS idx_batter_positioning_lookup
    ON batter_positioning (team_id, season_id, perspective_team_id);
```

- **Column types match the live schema** in `migrations/001_initial_schema.sql`: `teams` PK is `id` (INTEGER AUTOINCREMENT) -- so `team_id` and `perspective_team_id` are `INTEGER REFERENCES teams(id)`; `seasons` PK is `season_id` (TEXT slug) -- so `season_id` is `TEXT REFERENCES seasons(season_id)`; `players` PK is `player_id` (TEXT) -- so `player_id` is `TEXT REFERENCES players(player_id)`. This corrects an error carried over from discovery, where TEXT types and a nonexistent `teams.team_id` column were drafted. The implementing story MUST use the types above -- the discovery-era draft is superseded.
- The 5-part PK includes `perspective_team_id` -- this honors the perspective-provenance invariant (`.claude/rules/perspective-provenance.md`); filter-at-compute does not escape that invariant for a stored table.
- **Rebuild idempotency is delete-then-insert, not `INSERT OR REPLACE`.** Within a single transaction the engine first deletes all rows for the `(team_id, season_id, perspective_team_id)` scope being recomputed, then inserts the fresh rows. `INSERT OR REPLACE` alone replaces only colliding keys and never deletes -- so a batter who drops below 6 covered positions between runs (or drops out of the lineup entirely) would leave stale `batter_positioning` rows behind. See TN-6 for the transaction contract.
- One index only -- it covers the sole v1 read pattern (look up all positioning rows for a team/season/perspective).
- `call_state`, `team_state_call`, and `direction_shade` store **absolute field-direction** enum keys (`LEFT`/`RIGHT`, `left`/`right`) -- NOT handedness-relative pull/oppo. Batter handedness is unavailable on every data path E-228 uses (see TN-3 and the Non-Goal) -- and positioning is inherently absolute, so the stored values are absolute fact. `call_state` and `team_state_call` store stable enum keys (e.g. `LEFT_SHALLOW`), not the display call-words; the display call-words are resolved at render time from the configurable vocabulary (TN-5).
- **`team_state_call` is a denormalized per-batter value, not a per-position value.** `call_state` is each position's own call and varies across a batter's 6 rows; `team_state_call` is the batter's single team-state call (the TN-4a quantization of the 6 `call_state` values) written identically onto all 6 rows -- the exact same denormalization pattern as `is_thin` / `bip_count` / `hr_count`. It is persisted (not render-time-derived) so the render path reads the call sheet's CALL column directly instead of reimplementing the TN-4a MIXED-rule lattice in SQL -- that lattice is the engine's to own, and a second SQL implementation would be a drift risk. It is `NOT NULL`: every batter has a team-state call, even if it is `TRUE`.
- **`direction_deviation` / `depth_deviation` are persisted `INTEGER` ordinal buckets, not engine-return-only and not continuous.** Each is a signed ordinal step bucket -- `0` = on base, `±1` = slight shade, `±2` = significant shade -- one per axis (L-R / in-out). Two columns, not one: the optimal point is 2D, and a single combined scalar would collapse the two axes. They are persisted because they are **not derivable** from `direction_shade` / `depth_shade` / `zone_concentration` -- those are the coarser categorical buckets; the deviation buckets are the finer-grained ordinal *under* the categorical `call_state` -- and they are consumed downstream by the E-228-04/05 render path. A non-derivable, downstream-consumed value belongs in the precomputed table; engine-return-only would force the render path to re-run the engine or duplicate its logic. **They are ordinal, not continuous, on purpose**: the SVG-space delta they quantize from is anisotropic (the `_raw_to_svg` x and y scales differ) and the SVG canvas is an unanchored stylized graphic, so there is no honest conversion to real-world feet -- and the per-batter optimal point already carries wide sampling error at 15-35 BIP. A coarse 3-level bucket is honestly *matched* to the input signal quality; a continuous `REAL` would be precision theater. NULL rules piggyback on the existing gates -- `direction_deviation` is NULL exactly when `direction_shade` is NULL (`call_state='TRUE'`); `depth_deviation` is NULL exactly when `depth_shade` is NULL (below the 25-BIP depth gate) -- so no new NULL logic and no new edge case for E-228-02. **The reference origin (`BASE_POSITIONS`) and the two per-axis quantization threshold ladders are E-228-02's to define** (TN-3 Stage A) -- the migration column comments above reference that definition rather than re-specifying it.

### TN-3: The positioning model -- deterministic, optimal-point then quantize
The engine is deterministic end to end -- no LLM in the decision path (see TN-1 and the History note on the re-validated decision architecture). It runs in three stages:

**Stage A -- per-batter optimal fielding point.** For each batter and each covered position, compute the batter's **optimal fielding point** from their BIP distribution, take the signed delta from the textbook base position, and quantize that delta to a signed ordinal step bucket per axis. This is the mathematically grounded core: where would this fielder ideally stand against this hitter, and how far is that from where they normally stand. The resulting ordinal buckets are what the later stages quantize against and what the confidence column may surface.

Stage A is computed entirely in **SVG space** (post-`_raw_to_svg`). Raw GameChanger API coordinate space is not linear -- `_raw_to_svg` exists precisely so distance math is valid -- so `BASE_POSITIONS` is defined in SVG-space coordinates, the optimal point is computed in SVG space, and the signed delta is taken in SVG space.

The **textbook base position** is a defined reference, not an undefined term. It lives as a module-level constant `BASE_POSITIONS: dict[str, tuple[float, float]]` in `src/reports/positioning.py` -- one entry per covered position (`SS`, `2B`, `3B`, `LF`, `CF`, `RF`) mapping to its base SVG-space `(x, y)` coordinate. Like the sector geometry and gate thresholds, these are provisional starting values, each `# RECALIBRATE`-annotated. `BASE_POSITIONS` is E-228-02-owned and is the single source of truth for the reference origin; E-228-01's migration comment references it rather than restating it.

**The deviation is stored as a signed ordinal bucket, NOT a continuous distance.** The SVG-space delta is quantized to `0` / `±1` / `±2` (on base / slight shade / significant shade; sign = direction, − = LF or shallower, + = RF or deeper). This is deliberate: the `_raw_to_svg` transform is anisotropic (its x and y scale factors differ) and the SVG canvas is an unanchored stylized GC rendering graphic, so there is no honest SVG→feet (or SVG→"steps") conversion constant -- a continuous value would be fabricated precision. Combined with the wide sampling error on a 15-35-BIP centroid, a coarse 3-level bucket is honestly matched to the input signal quality. This is the same quantization pattern the engine already uses for `call_state`; the deviation columns are the finer-grained ordinal *under* the categorical `call_state`.

The quantization uses **two separate per-axis `# RECALIBRATE` threshold ladders** in `positioning.py` -- **one for `direction_deviation` (the x / L-R axis) and one for `depth_deviation` (the y / in-out axis)**. There must be two, and they must be named and documented as two: because `_raw_to_svg` is anisotropic, the SVG-delta-to-bucket thresholds for x and y are different numbers. A single shared "threshold ladder" would silently re-introduce the anisotropy bug. `BASE_POSITIONS` and the two per-axis threshold ladders together are the single-source-of-truth concern for the deviation computation -- E-228-02 AC-1c owns all of it; E-228-01's migration comment references it.

**Stage B -- the two knobs (direction + depth), per position, via the swappable geometry seam.**
Direction and depth are evaluated **per covered position**, not once per batter. For each (batter, position) pair, the engine restricts the batter's BIPs to the **subset relevant to that position** (defined by the position's responsibility sector, via the swappable seam), then derives direction and depth from that subset:
- **Direction knob (per position)**: the dominant zone of the position-relevant BIP subset (via the swappable seam, which v1 wraps with `classify_field_zone`). Stored as `direction_shade`. Different positions can land on different zones for the same batter.
- **Contact-type knob (per position, depth)**: the dominant contact type of the position-relevant BIP subset, mapped via `contact_type_label`. Stored as `depth_shade`. Different positions can land on different depths for the same batter. Depth is derived from raw `y`: lower `y` maps to deeper field position via the verified coordinate transform already in `src/charts/spray.py` (`_raw_to_svg` and the transform constants). Reuse this transform -- do not rebuild it.
- **Geometry is a swappable seam**: v1 ships **fixed angular-sector geometry** -- per-position responsibility sectors as module-level constants extending the existing `atan2` pattern in `src/charts/spray.py` (see TN-4) -- and the per-position BIP-subset operation lives behind the seam interface. The engine's `direction_shade` / `call_state` output shape is identical whether the position-relevant BIP subset comes from today's fixed sectors or a future clustering-derived zone set; the seam is the v1 design constraint that makes the clustering fast-follow (see Non-Goals and the ideas backlog) a one-layer swap instead of an engine rewrite. No clustering library in v1.
- **Absolute, not handedness-relative**: the direction vocabulary is absolute field direction (`LEFT`/`RIGHT`), NOT pull/oppo. Pull/oppo is handedness-relative ("pull" = left field for a RHB, right field for a LHB), and **batter handedness is unavailable on every data path E-228 uses** -- the public roster endpoint (`/teams/public/{public_id}/players`) has no handedness field, `players.bats` is unpopulated dead schema (zero read/write paths in the pipeline), and the endpoints that carry handedness are off the opponent-scouting path. (Handedness *does* exist and is ~96% populated on the owning-team opponent-registry endpoint `/teams/{team_id}/opponents/players`, but that endpoint is keyed by the owning team's UUID and covers only team-lookup-entered opponents -- E-228's public-id-based scouting path does not use it.) Because a pull/oppo vocabulary cannot be built on a field E-228 cannot read, the engine uses absolute direction instead. Absolute direction is also a net simplification: it removes the handedness dependency, removes the handedness-NULL edge case, and is symmetric (the original pull/oppo scheme was implicitly pull-biased -- it had PULL SHALLOW/DEEP but no OPPO SHALLOW). See the Non-Goal on handedness.

**Stage C -- quantize.** The two knobs quantize into **8 `call_state` enum keys**: `TRUE` (no shade), the 6 directional shades `LEFT` / `LEFT_SHALLOW` / `LEFT_DEEP` / `RIGHT` / `RIGHT_SHALLOW` / `RIGHT_DEEP`, and `MIXED` (the team-state fallback) -- see TN-4a for the concrete MIXED rule. The directional set is symmetric: both `LEFT` and `RIGHT` get shallow + deep variants. This is one more directional shade than the original handedness-relative draft (which had `PULL_SHALLOW`/`PULL_DEEP` but no `OPPO_SHALLOW` -- a pull-bias artifact) and is the more correct model.

### TN-4a: The MIXED rule (team-state quantization)
Each covered position gets its own `call_state` from the two-knob classification. The batter's **team-state call** is then derived from the six per-position `call_state` values:
- If all qualifying positions land in the **same named state** (or in **adjacent** named states -- e.g. `LEFT` and `LEFT_SHALLOW`), the team-state call is the dominant named state.
- The team-state call is **`MIXED`** when **2 or more positions land in non-adjacent named states** (e.g. one position reads `LEFT_DEEP` and another reads `RIGHT`). Adjacency is defined over the depth/direction lattice: `LEFT_DEEP`-`LEFT`-`LEFT_SHALLOW`-`TRUE`-`RIGHT_SHALLOW`-`RIGHT`-`RIGHT_DEEP` is the ordered chain; "adjacent" means neighbors on that chain. Positions at `TRUE` (thin data or no tendency) do not by themselves force `MIXED`.
- When the team-state call is `MIXED`, the call sheet falls back to showing the per-position cells rather than a single team-wide call-word; the per-position `batter_positioning` rows always carry their individual `call_state` regardless of the team-state call.
- This rule is a provisional starting value like the sample gates -- it is a module-level constant/threshold in `src/reports/positioning.py` annotated for recalibration.

### TN-4: Sample gates -- the trust backbone
Hard Python `if` statements, never an LLM judgment:
- **< 10 BIP** -> `TRUE` ("not enough data -- play straight up"), `is_thin = 1`. A thin-data batter still gets **all 6 covered-position rows written** (each `call_state = 'TRUE'`, `is_thin = 1`) -- the batter is never skipped. Skipping would break the player-card render, which iterates positions and expects a row per position.
- **10-24 BIP** -> direction lean only, no depth refinement (`depth_shade` is NULL). This partial-data state is the most common real row for a regular -- it must render as intentional, not broken (display-philosophy). A direction-only call (e.g. "SHADE LEFT" with NULL depth) is a **complete, actionable instruction** on its own: the fielder moves laterally, and depth is optional context, not a missing half. This is the domain grounding for the "render as intentional, not broken" treatment the design/render stories carry.
- **25+ BIP** -> full direction + contact-type + depth.
- **Per-zone gates**: a shade toward a zone requires >= 4 BIP in it AND >= 35% concentration; adjacent borderline zones combine.
- Confidence (`bip_count`, `hr_count`, the `is_thin` tag) is shown on every call-sheet row at full visual weight -- contextualize, never suppress (per `.claude/rules/display-philosophy.md`). `hr_count` is shown separately because over-the-fence HRs have NULL x/y and undercount fly-ball tendency.
- These thresholds are provisional starting values. They are module-level constants in `src/reports/positioning.py`, each annotated with a `# RECALIBRATE after first opponent dataset` comment. Calibration is an operator activity (see Rollout below), not a story.

### TN-5: Configurable vocabulary -- stored fact vs. display word
There are two distinct layers, and they must not be conflated:
- **Stored layer (the absolute fact)**: the `call_state` and `direction_shade` enum values in `batter_positioning` are absolute field direction -- `TRUE`, `LEFT`, `LEFT_SHALLOW`, `LEFT_DEEP`, `RIGHT`, `RIGHT_SHALLOW`, `RIGHT_DEEP`, `MIXED`. These are fixed enum keys, not configurable -- they are what the engine computed from absolute spray coordinates.
- **Display layer (the configurable call-words)**: a **documented constants block in code** maps each stored enum key to the call-word the coach actually sees. The recommended DEFAULT display words: `TRUE` -> "STRAIGHT UP", `LEFT` -> "SHADE LEFT", `LEFT_SHALLOW` -> "SHADE LEFT IN", `LEFT_DEEP` -> "SHADE LEFT DEEP", `RIGHT` -> "SHADE RIGHT", `RIGHT_SHALLOW` -> "SHADE RIGHT IN", `RIGHT_DEEP` -> "SHADE RIGHT DEEP", `MIXED` -> "MIXED". The display layer is the MUST-HAVE remap config; a per-team UI setting is explicitly deferred.

This split is the point: the system stores the absolute fact and the coach configures the word.

**Ownership -- design decision vs. code home**: the *lexical vocabulary* (which display word for each stored enum key) is a **design decision owned by E-228-04** -- it's the words the coach sees, which is design, not engine logic. The *constants block in code* (the Python dict mapping enum keys to display words) lives in the **render layer (E-228-05)**, not the engine module -- the engine writes only absolute enum keys to `batter_positioning` and never touches display words, so a vocabulary constants block has no reason to be co-located with it. This split removes the reverse dependency the discovery-era draft had (where E-228-02 implemented the constants block before E-228-04 locked the words). The forward chain is now E-228-02 (engine, enum keys only) -> E-228-04 (design spec, locks lexical vocabulary) -> E-228-05 (render code, implements the constants block per E-228-04's spec). The TN-5 default words below are a recommended starting set that E-228-04 may take as-is or override; the shallow-variant choice ("SHADE LEFT IN" vs. "SHADE LEFT SHALLOW" -- "IN" is mildly ambiguous with "infield shift"; "SHALLOW" is unambiguous but longer; stored key is `LEFT_SHALLOW`/`RIGHT_SHALLOW` either way) is one such choice E-228-04 locks.

### TN-6: Pipeline integration -- recompute stage
- The Tier 1 engine exposes a pipeline-agnostic function in `src/reports/positioning.py` with the signature `(conn: sqlite3.Connection, team_id: int, season_id: str)`. The `team_id: int` / `season_id: str` types match `dedup_team_players(db, team_id: int, season_id: str, ...)` in `src/db/player_dedup.py`. Both the scouting pipeline and the standalone path import and call the **identical function** -- parity by construction, no duplicated logic.
- **The engine reads from `spray_charts` filtered by `team_id` AND `season_id` AND `perspective_team_id`**, and groups by `perspective_team_id` (the NOT NULL column, also in the `batter_positioning` PK) -- NOT by `spray_charts.team_id`, which is nullable. Note the column semantics: `batter_positioning.team_id` = the scouted opponent's team id; `perspective_team_id` = the perspective whose API pull produced the spray rows. `spray_charts.season_id` is itself nullable -- the engine filters to the caller's `season_id` and **skips any `spray_charts` row with a NULL `season_id`, logging a WARNING** with the count skipped. The caller always has a concrete `season_id` in scope (`run_scouting_sync` derives it from the crawl result; `generate_report` derives it via `derive_season_id_for_team`).
- **Transaction contract**: the engine **commits its own writes**. Within one transaction it does the delete-then-insert for the `(team_id, season_id, perspective_team_id)` scope (per TN-2) and commits. This is consistent with `dedup_team_players`'s `manage_transaction=True` option and with treating the recompute as a self-contained materialization step. Consequence for the non-fatal contract: a recompute that raises mid-write leaves the prior committed state intact (the failed transaction rolls back); a recompute that succeeds is durably committed independent of whatever the caller does next.
- The recompute is a pure DB-read materialization step (it reads `spray_charts` and writes `batter_positioning`) -- it is NOT crawl-to-load. It must run AFTER spray load AND AFTER player-dedup, because dedup-first prevents a 40-BIP hitter fracturing into three 13-BIP stubs and misfiring the sample gates.
- **Scouting pipeline** (`src/pipeline/trigger.py::run_scouting_sync`): the recompute slots in as a new final step, immediately after the existing post-spray `dedup_team_players` sweep, inside the shared `with closing(sqlite3.connect(...))` block so it sees post-dedup rows. It is non-fatal -- wrap in try/except, log at WARNING on failure (matching the spray-stage error contract).
- **CLI parity** (`bb data scout` in `src/cli/data.py`): `bb data scout` already runs `dedup_team_players` -- `_scout_live()` Step 4 calls `_post_spray_dedup()` (around lines 375-435), the CLI mirror of `run_scouting_sync`'s Hook 2. E-228-06 adds ONLY the recompute step, immediately after that existing dedup call, so the CLI path and the background-task path produce equivalent artifacts (required by the scouting-pipeline parity principle in CLAUDE.md). No dedup gap exists on the scouting CLI path.
- **Standalone path dedup gap** (`src/reports/generator.py::generate_report()`): this path runs scouting load -> spray load -> plays but currently has NO `dedup_team_players` call -- dedup is only a scouting-pipeline hook. Because the recompute must run after dedup and produce identical rows across both paths, the standalone path MUST gain a `dedup_team_players(conn, team_id, season_id, manage_transaction=True)` call (after spray/plays, before the recompute). This closes a genuine pre-existing correctness gap, not a workaround. The dedup-gap fix and the standalone recompute ship together in E-228-03.

### TN-8: Communication model (informs the artifacts, not the code)
The coach flags only the 2-4 exception batters per game; silence = TRUE. The coach yells a *name* (common case) or a *jersey number* (MIXED case). The player card carries both -- named states as labels on the lookup, per-position moves for MIXED -- so the player decodes either call from the same small printed list. The named states are a label to pattern-match, not a vocabulary to memorize.

Absolute direction (LEFT/RIGHT, per TN-3 and TN-5) is *easier* for a 15-year-old than pull/oppo -- there is no mental handedness flip to perform. The absolute call-state is the instruction the player acts on. That split is intentional and fine: the call is absolute, the prose can be analytical.

### Rollout (operator activity -- not a story)
Before the coaching staff sees positioning output as authoritative, the operator (Jason) runs one internal validation pass: generate cards for a real opponent, compare the engine's recommendations against the actual spray chart, and tweak the gate thresholds / sector geometry constants if needed. The sample gates are deliberately conservative (they favor false negatives -- too many TRUE calls -- over false positives -- wrong shades), which is the safe side of the tradeoff, but the per-zone interaction (4 BIP AND 35% can suppress a real tendency in the 10-20 BIP range) is the specific thing the validation pass checks. This is a rollout note, not a shippability gate.

**Design-time calibration procedure** (operator activity -- not a story, no ACs): during the first-real-opponent calibration pass, the operator dumps both the aggregated per-zone / per-contact-type distributions **and** the per-batter optimal points (TN-3 Stage A), reasons through whether the threshold constants and the fixed sector geometry are sensible against that real data, and edits the constants in `src/reports/positioning.py`. An LLM conversation is a fine aid for this step -- it is exactly the judgment-heavy, one-time, non-reproducibility-tolerant task an LLM helps with (distinct from the engine's decision path, where the LLM is excluded). The calibration pass has a second job: **assess whether the per-batter optimal-point centroids are tight enough to justify pulling the clustering fast-follow forward** -- this is the empirical decider for the runtime-clustering Non-Goal's gate. Constant-comment convention: once a constant has been calibrated, its `# RECALIBRATE after first opponent dataset` annotation becomes `# Calibrated <date> against <opponent>, N games`.

3. **Footgun, failure mode, or boundary discovered** — **YES**. Phase 4b finding #1 surfaced the **delete-then-insert scope rule**: when a materialization step recomputes rows for a `(team_id, season_id)` scope, the DELETE must use the same `(team_id, season_id)` scope as the INSERT, NOT a finer-grained partition (e.g., per-perspective). Finer-grained DELETE leaves stale rows when a partition drops out between runs (e.g., a perspective stops producing data, or the data goes empty). Worth codifying because future pipeline materializers will need this rule and the original positioning engine had the bug.
4. **Change to agent behavior, routing, or coordination** — **NO**. The "and review" modifier flowed cleanly through Phase 4a and 4b; the baseball-coach AC-8 review (uxd → coach → uxd reconciliation) worked as an in-story pattern without needing a skill formalization. No new agents, no settings.json changes.

The handedness API-behavior precise framing (no handedness on the public roster endpoint or `players.bats` dead schema; ~96% populated on the owning-team opponent-registry endpoint) was discovered during E-228 discovery, but it is fully documented in the epic file (Non-Goal + TN-3) and in CLAUDE.md's GameChanger API section.
