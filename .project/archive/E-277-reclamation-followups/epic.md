## Technical Notes

### TN-1: The handoff's MAJOR-1 framing is wrong — do not re-derive it

The handoff states that deleting `scheduled_report_runs` rows contradicts migration 005 ("audit row OUTLIVES report cleanup"), and offers a choice between pinning the audit table and documenting the deletion, calling the status quo "the only wrong option."

**That is a mis-citation, confirmed independently by PM and data-engineer from the migration text.** The "OUTLIVES" sentence sits inside the `report_id` FK column comment (the `ON DELETE SET NULL` rationale) and is scoped to **report** deletion. The same migration's CASCADE MIRROR INVARIANT block states the opposite for teams in as many words: team deletion REMOVES the audit rows, report deletion only NULLs `report_id`, and the two cleanups are "distinct."

So the `("scheduled_report_runs", "own_team_id")` entry in `_TEAM_PIN_TABLES` is **compliant with migration 005**, and it is not changed by this epic.

**The real defect is one layer up and is an inconsistency, not a contradiction.** Migration 005 answers *"when a team dies, do its audit rows die?"* (yes). It is silent on *"does an audit row count as a reason the team is still alive?"* Those are independent axes, and the codebase already treats them so: `opponent_links` and `user_team_access` are simultaneously cascade targets in `_delete_team_scoped_data` AND reachability roots in `_TEAM_BASE_PRED` (E-273 TN-7). A keep-root governs how the deletion decision is *made*; the cascade governs what happens *downstream* of it.

Corroborating detail from the schema itself: migration 005 declares exactly one column-level `ON DELETE`, on `report_id`. `own_team_id` is `INTEGER NOT NULL REFERENCES teams(id)` with none, defaulting to `NO ACTION`. The author distinguished the two cases deliberately.

**Option A requires NO migration and NO new index.** Data-engineer built the candidate predicate and ran `EXPLAIN QUERY PLAN`: migration 005's existing `UNIQUE INDEX (own_team_id, opponent_root_team_id, game_date)` serves the new `NOT EXISTS` on its leading column, and serves it as a **covering** index (`SEARCH srr USING COVERING INDEX idx_scheduled_report_runs_slot (own_team_id=?)`). So the fourth root costs an indexed lookup and nothing more. Stated explicitly for two reasons: it forecloses a reviewer worrying the sweep got slower, and it forecloses an implementer speculatively adding an index — indexes need a query pattern, and this one already has its index.

**Operator ruling (2026-07-26): Option A — pin.** Rationale: today an own team is protected only if its first morning run happened not to land on a TBD bracket, because every non-placeholder ladder rung commits an `opponent_links` row. That arbitrariness is the defect. Permanent stranding of the few operator-configured `team_urls` teams was accepted explicitly, since the two existing roots already strand theirs the same way.

### TN-2: Exposure is placeholder-only — and the alarm that was raised and killed

`scheduled_report_runs` is **not a passive audit table.** It has three functional readers in `src/reports/morning_run.py`: `_prior_success` (the idempotency skip), `_existing_report_slug` (report-linkage carry-forward across a skip), and `_slot_reserved_fresh` (the E-252-07 reserve-before-generate concurrency lease that prevents double-generation). If the sweep could reach those rows it would destroy live control state, which would be a materially larger defect than losing history.

**It cannot, and the reason is recorded here so it is not re-raised.** PM raised this during discovery and then refuted it. `resolve_opponent` runs BEFORE the reservation write, and both its persistence paths self-commit an `opponent_links` row carrying `our_team_id` — `_upsert_resolved_positive` for a positive resolution, `_upsert_pending` for the rung-(d) pending row. All three functional predicates require `resolution_outcome='auto_resolved'`. Therefore any slot they can match belongs to a team already pinned and already excluded from the orphan set. Only `deferred_placeholder` slots — rung (b), which persists no row — leave a team exposed.

Consequence for implementers: this epic preserves **placeholder audit history**. It does not, and need not, protect the concurrency lease or the idempotency state, which were never at risk. Do not write an AC asserting that it does.

### TN-3: What is lost today, and why silent recovery argues FOR the fix

Executed by data-engineer against a synthetic DB, own team in the exposed shape. One `reclaim_orphan_reference_data` call deletes the entire team-scoped surface: the `teams` row, both `team_rosters` rows, both roster-only `players`, and rows in `scouting_runs`, `crawl_jobs`, `coaching_assignments`, and `scheduled_report_runs`. `ReclaimResult(teams_deleted=1, players_deleted=2, roster_rows_deleted=2)`.

**Of everything deleted, only `scheduled_report_runs` is non-regenerable.** Rosters and players re-crawl from GameChanger; `scouting_runs` is re-derivable; `crawl_jobs` and `coaching_assignments` have zero `INSERT` sites in `src/` and are always empty in production. The audit table is the only thing in the blast radius recording something GameChanger does not know.

**Recovery is complete and silent — and that is the argument FOR pinning, not against it.** The next run's `ensure_team_row` recreates the team from the same `public_id`/`gc_uuid`, raises nothing, and logs nothing; the subsequent `_upsert_slot` calls succeed with no FK error and no UNIQUE collision. The team gets a NEW `id` and nothing references the old one, because every `teams(id)` child died in the same sweep. The naive reading of that is reassurance. The correct reading is the opposite: **because recovery needs no operator action and emits no signal, the loss is invisible.** An operator asking "why did nothing generate for this team on the 10th?" — the exact question this table exists to answer — gets an empty table with no indication anything was ever there. Had recovery required intervention, someone would notice; because it does not, nobody will.

### TN-9: MAJOR-3's mechanism is narrower than the handoff states

The handoff claims `BEGIN IMMEDIATE` "also implicit-commits pending statements," presenting a second independent trigger. **Software-engineer REFUTED this by execution**: on Python 3.13.13 it *raises* `OperationalError: cannot start a transaction within a transaction`.

So `BEGIN IMMEDIATE` is not a second trigger.

**But "the reap's commit is the SOLE trigger" — which this note asserted until the review round — is itself a one-sided generalization, true of the scope its author checked and false of the reachable surface.** It holds for the two passes originally in scope. One layer out it does not: **`cleanup_expired_reports` carries its OWN unconditional `conn.commit()` on the borrowed connection**, independent of the reap, and that commit alone is sufficient to commit-then-delete a caller's in-flight work. Software-engineer confirmed it by re-running the trace with the reap neutralized to a no-op entirely and getting the identical outcome. So the reap's commit is *a* trigger, not *the* trigger, and a fix scoped to it does not close the hazard.

Recorded at length because of how it survived: `se` executed the original claim and `cr` audited it, and neither caught this — both were checking the claim within its stated scope, which is what a one-sided claim is proof against. It was found by reading `src/reports/lifecycle.py` for a different reason. **The instrument that catches a one-sided generalization is never a check that adopts its framing.** Same defect class as the MAJOR-2 comment this epic exists to repair, sitting in this epic's own Technical Notes.

No live caller passes a dirty connection to any of the three entry points, so all three guards are inert today — which is what a latent-defect fix should be. **Two separate enumerations back that, over DIFFERENT call graphs, and merging them would overstate what either checked.** Code-reviewer enumerated the callers of `reclaim_orphan_reference_data` and `reap_stale_generating_reports` (admin delete opens a fresh connection for the reclaim; the one-shot script and the app-startup reaper own theirs), and software-engineer instrumented `in_transaction` at those two entry points. Neither covers `cleanup_expired_reports`, whose call graph is a different and much smaller set — **exactly two live call sites**, measured separately by software-engineer at cleanup's own entry, all shapes clean. Both statements are accurate; they are about different functions, and the third guard's safety rests only on the second. Story 02 **AC-5b** requires the implementer to re-verify by instrumentation rather than inherit either enumeration. **Corrected 2026-07-27, and the correction is the note's own subject.** Until then this sentence named no AC, and the criterion it asserted **did not exist** — AC-5 carried no instrumentation requirement, so this closing sentence was itself a claim about a document nobody had opened, inside the note whose entire subject is that failure. ### TN-10: Add the keep-root; leave `_TEAM_PIN_TABLES` alone

Software-engineer executed both orderings. **Removing the `scheduled_report_runs` pin entry WITHOUT the keep-root raises `IntegrityError: FOREIGN KEY constraint failed` and rolls back the entire sweep** (`own_team_id` is `NOT NULL REFERENCES teams(id)` with no `ON DELETE`). **Adding the keep-root while LEAVING the pin entry is benign** — `teams_deleted=0`, team and audit row both survive; the entry simply becomes unreachable.

**This is an ORDERING constraint, not an atomicity one.** An earlier relay stated it as "both changes must land in the same story"; that is stronger than the evidence and would over-constrain the story split. The decision for E-277: **add the keep-root and do not touch `_TEAM_PIN_TABLES`.** If a future epic removes the entry, that removal must be same-commit with a keep-root already in place.

**A third reason to retain it, from the schema side (data-engineer), which neither of the above gives:** leaving the entry keeps the sweep compliant with migration 005's CASCADE MIRROR INVARIANT in every future state. The invariant requires that a deleted team's audit rows go with it. Today the keep-root means no audit-row-bearing team reaches the sweep's delete at all — but if a future change ever weakens or bypasses the root, the pin entry is what keeps the sweep honoring the invariant instead of silently violating it. **Removing the entry would make the sweep's migration-005 compliance contingent on the keep-root never changing.**

**But retaining it silently would reproduce MAJOR-2 in the same module (data-engineer, MEDIUM).** An entry that provably can never fire, carrying no explanation, invites exactly the reasoning MAJOR-2's reader would apply: a pin that never deletes a row must be dead code, so remove it — and that removal is the `IntegrityError`-rolls-back-the-whole-sweep hazard measured above. So the entry is retained **with a comment recording why**, per story 01 AC-4. **House precedent to match rather than invent:** `_TEAM_STAT_EXISTS` in the same file is the identical situation already solved — a clause documented as "VACUOUSLY TRUE on real data," deliberately kept, with a comment explaining that it converts a reclamation-halting `IntegrityError` into a graceful exclusion.
