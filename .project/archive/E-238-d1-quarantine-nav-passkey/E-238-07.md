# E-238-07: Expired-report file cleanup

## Epic
[E-238: D1 — Quarantine + Navigation Retarget + Passkey Fix](../E-238-d1-quarantine-nav-passkey/epic.md)

## Status
`DONE`

## Description
After this story is complete, expired report HTML files are removed from disk via a single
`cleanup_expired_reports()` helper, reachable both opportunistically at the start of report
generation and via a new `bb report cleanup` CLI command. The `reports` row is kept (with
`report_path` nulled) so the report list still shows the report as expired.

## Context
Today expired reports 404 on serving (`reports.py` gates `now > expires_at`) but the HTML files
at `data/reports/{slug}.html` are never unlinked — they accumulate on disk. There is no cleanup
path. SE's discovery produced the design (folded into epic Technical Notes "`bb report cleanup`
/ opportunistic cleanup"). The existing `_delete_report` admin path is the model for safe file
removal (`.is_file()`-guarded `.unlink()`, canonical `_REPO_ROOT` resolution).

## Acceptance Criteria
- [ ] **AC-1**: A `cleanup_expired_reports()` helper in `src/reports/generator.py` selects
  expired rows (`expires_at < now`) with `report_path NOT NULL`, unlinks each file with per-file
  error isolation, and NULLs `report_path` — but KEEPS the `reports` row.
- [ ] **AC-2**: The cleanup gate is strictly `expires_at < now` (not-yet-expired reports are
  never touched); file removal uses the canonical `_REPO_ROOT` resolution and an `.is_file()`
  guard per the `_delete_report` model.
- [ ] **AC-3**: `generate_report()` calls the helper opportunistically at its start; a failure
  inside cleanup never blocks or fails the generation.
- [ ] **AC-4**: A new `bb report cleanup` CLI command (`src/cli/report.py`) invokes the same
  helper and reports how many files were removed.
- [ ] **AC-5**: After cleanup, an expired report still appears in `bb report list` /
  `/admin/reports` as expired (row kept, path nulled), and serving it still returns the existing
  404 behavior.
- [ ] **AC-6 (canary)**: A test asserts the opportunistic `cleanup_expired_reports()` call at
  `generate_report()` start does not disrupt generation (e.g., a cleanup failure is swallowed and
  generation proceeds — AC-3), and that a seeded report's share link still serves. The full live
  login → generate → open-share-link path is designated an operator post-merge check per epic
  Technical Notes ("Canary verification mechanism").

## Technical Approach
Add the helper to `generator.py` and reuse it from both the opportunistic call and the CLI
command. Model the file-removal on the existing `_delete_report` path. Per-file error isolation
means one unremovable file does not abort the sweep. For tests, avoid `db.backup()` onto a
disk-backed test path and capture pytest return codes without a pipe (per prior dispatch
lessons).
