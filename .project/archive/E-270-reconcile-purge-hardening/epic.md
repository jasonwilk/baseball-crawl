## Overview
E-267 shipped reconcile-at-load (forward-only retire-absent across the game / player-line / roster grains) and `bb db purge-scouting`, making report generation destructive for the first time. A completed 9-agent independent audit of commit `0c85623` found that two of those destructive surfaces are under-guarded and that the destructive path itself is untested end-to-end. This epic closes those gaps: an absolute cap on game retirements, a hardened purge guard, a true end-to-end destructive-path test, a companion test for a mis-annotated coverage gap, and a batch of small correctness cleanups. It is HARDENING of a shipped surface, not a feature.

## Background & Context
E-267's game-grain retire (`retire_absent_games`, `src/db/reconcile_at_load.py`) protects only with the universal `FLOOR_RATIO = 0.5` catastrophic-shrink gate, while the roster grain — whose failure mode is merely "grid clutter, never a corrupted stat" by the code's own words — got a stricter absolute cap (`MAX_ROSTER_DEPARTURES = 2`). The game grain hard-deletes a `games` row plus its FULL child surface (batting/pitching lines, `plays`, `play_events`, spray, reconciliation). So the milder-failure grain has the stronger guard: a truncated-but-HTTP-200 schedule returning 12 of 20 prior games passes the floor (`12 >= 10`) and hard-deletes 8 live games unattended via morning-run. The audit also found the purge production guard is bypassable by a typo-class `APP_ENV=prod` (normalizes to non-production), the confirm prompt never shows the resolved DB path or row counts, `--force` disarms both the prod refusal AND the prompt, and no backup precedes a purge. Finally, no test drives `generate_report()` itself with a shrunk crawl (the E2E class mocks `ScoutingLoader` out entirely), and one E-267 test that claims per-game-404 safety actually exercises the whole-dict-empty early-return, not the per-game skip path.

Each scope item traces to a verified audit finding. Two findings were already filed as backlog ideas at E-267 closure — [[IDEA-160]] (`MAX_GAME_RETIREMENTS`, "ready to implement / bundle-ready") and [[IDEA-159]] (stripped-perspective un-protects the game retire, "live mechanism, currently zero instances") — and are promoted into story E-270-01.

## Technical Notes

### TN-1: Game-grain cap — population correctness (the deadlock trap)
`classify_absences` computes `absent = prior_ids − fresh` and calls `extra_guard(absent)`. The game grain currently passes `extra_guard=lambda _absent: boxscores_complete` (`src/db/reconcile_at_load.py`, in `retire_absent_games`). The cap is composed WITH that existing guard.

**The cap MUST measure retire-eligible removals, NOT raw `len(absent)`.** (Owner decision: data-engineer, retire-path semantics; software-engineer concurred after initially proposing raw count.) The game grain has a permanent-refusal population directly analogous to the roster grain's backfill-churn deadlock: a **cross-perspective-owned game** — in this team's `prior_ids`, absent from this perspective's fresh schedule (this run's redirect missed it), still owned by another perspective — classifies REMOVED, hits the `_other_perspectives` refusal, and is KEPT. It never leaves `prior`, so it recurs in `absent` every run. If a team accumulates `≥ MAX_GAME_RETIREMENTS` such games, any later run that ALSO has one genuine removal has `len(absent) > cap`, refusing the WHOLE pass and permanently false-refusing the genuine removal — reintroducing the stale-game bug the grain exists to close. This is the roster deadlock reproduced. Reachability confirmed by software-engineer: a schedule-edited game G stays in T's `prior`, is absent from the fresh array (so it does NOT sit in `fresh_completed_ids` and does NOT flip `boxscores_complete` False), reaches REMOVED, and is refused-and-kept.

Therefore the cap is evaluated over `absent − exempt`, where `exempt` is precomputed ONCE over the ABSENT set before `classify_absences` and closed over (the guard receives only the frozen `absent` set, no connection — the same shape as the roster grain's `previously` closure). **The binding constraints are: precomputed ONCE (not per-call inside the guard), computed BEFORE `classify_absences`, closed over, and the guard itself takes no connection.** The population is scoped to `absent`, not to all of `prior_ids` (amended 2026-07-24 during dispatch; the original text said `prior_ids`). Only `exempt ∩ absent` is ever observable — all three consumers (`_guard`'s `absent_ids - exempt`, `retire_eligible_absent`, and the cap WARN's `exempt & absent`) intersect with `absent` — so a PRESENT game's protection status is unreachable, while computing it costs up to six single-row queries per entry: ~180 wasted queries per team-load on a 30-game season, on a path morning-run walks once per team, versus ZERO on the ordinary re-scout-with-nothing-missing. `absent` is derived first as a pure set difference over two already-materialized locals, so deriving it needs no connection and preserves every binding constraint above. The guard still SUBTRACTS rather than assuming `exempt` and its own `absent_ids` agree, so the code stays correct (and fail-safe — a narrower `exempt` can only raise the count and refuse more) if the scoping is ever widened back. `exempt` is the set of prior games that the retire loop would refuse-and-keep on cross-perspective grounds. Excluding them does NOT weaken mass-delete protection: they are not deletable by this grain anyway, and a genuine truncation still leaves many *deletable* games absent (tripping the cap), with `FLOOR_RATIO` (numerator `prior ∩ fresh` over full `prior`) untouched as the gross-truncation backstop.

**Independent corroboration (api-scout).** The perspective-control requirement is not just a deadlock concern — it is the ONLY apparent-loss signal at scale. api-scout's 636-record probe found ~4% of stored game_ids (22 of ~583) absent from the queried team's array, and ALL 22 were FALSE removals — cross-perspective twins whose surviving game_id is the OTHER perspective's event_id (the E-261 twin-merge consequence). api-scout's verdict: "if the retire diff compares raw game_ids against the fresh array WITHOUT deduping cross-perspective twins, the ~4% phantom-removal rate produces ~22 false removals on a 583-game corpus — which would trip a cap of 2 constantly and even nibble at 4. Perspective-control the diff, and then any small cap (2 or 4) is safe." This is exactly what the `exempt` set does: the ~4% twin phantoms are precisely the cross-perspective-protected population `_game_is_cross_perspective_protected` (TN-2) removes from the cap count — `_other_perspectives` catches the merged twin (two `game_perspectives` rows on one `game_id`), and the foreign-child branch catches the redirect-miss / stripped-perspective residue. Triple-independent convergence (data-engineer, software-engineer, api-scout) on the same design. AC-3's no-deadlock regression test exercises this real-world population.

### TN-2: Game-grain cap — the shared protection predicate (exempt == refusal, structurally)
The exempt set and the retire-loop refusal MUST use the SAME two-branch decision, or they drift and the deadlock reopens. Define ONE shared predicate — `_game_is_cross_perspective_protected(conn, game_id, team_id) -> bool` — that ORs the two protection branches:
- `_other_perspectives(conn, game_id, team_id)` non-empty (a foreign `game_perspectives` row exists — the existing E-267 guard; catches a scored-but-empty foreign perspective with zero child rows), OR
- `_foreign_perspective_child_rows_exist(conn, game_id, team_id)` — the new [[IDEA-159]] guard: a row exists under `perspective_team_id != team_id` in ANY table of the `_PERSPECTIVE_CHILD_TABLES` constant (`src/db/game_merge.py`). **Guard-surface == delete-surface (binding).** This check MUST query the SAME `_PERSPECTIVE_CHILD_TABLES` constant that `_delete_game_and_children` loops (`_GAME_CHILD_TABLES = ("game_perspectives", *_PERSPECTIVE_CHILD_TABLES)`), NOT a hand-enumerated table list. `_PERSPECTIVE_CHILD_TABLES` is the FIVE tables `player_game_batting` / `player_game_pitching` / `plays` / `spray_charts` / `reconciliation_discrepancies` (all carry `perspective_team_id NOT NULL`). This is the STRONGER guard: a whole-game delete removes ALL five child tables' rows by `game_id` across every perspective, so a foreign row in ANY of the five means another team's data lives here. A hand-list that omits `reconciliation_discrepancies` would MISS a game whose only foreign footprint is a reconciliation row and hard-delete another perspective's data — the [[IDEA-159]] hole, one table narrower. Querying the constant makes the two branches of the shared predicate cover EXACTLY the delete surface, so a future 6th child table auto-extends both delete and guard with zero drift (the same DRY discipline as the shared predicate, one level down). Lift the proven loop shape from `game_merge.py` (`SELECT DISTINCT perspective_team_id FROM {table} WHERE game_id = ?` over `_PERSPECTIVE_CHILD_TABLES`) with a `!= team_id` filter and `LIMIT 1` existence semantics.

Both the `exempt` precompute (mapped over the absent set — see TN-1) and the retire loop's refusal GATE call this ONE helper. The gate is the decision; the individual branch checks live strictly BELOW it and only select the WARN text. A future third protection branch is then added in one place and both the refusal and the cap-exempt pick it up automatically — drift becomes structurally impossible, not merely test-caught. The WARN reason strings STAY separate: the helper returns bool; when building a refusal message the loop still checks `_other_perspectives` vs foreign-child individually to name which branch fired. Do NOT widen `_other_perspectives()` itself ([[IDEA-159]] scope note — a game with one legitimate perspective must stay retirable, or removed single-perspective games become permanently unretirable).

### TN-3: Game-grain cap — composition and constant
Replace the `lambda _absent: boxscores_complete` slot with a named closure that composes BOTH narrowing conditions and returns True only when both hold: the existing `boxscores_complete` signal AND the retire-eligible absent count (`absent` minus the closed-over `exempt` set) is at most `MAX_GAME_RETIREMENTS`. Compose with a short-circuiting `and` so either condition alone can refuse, mirroring the roster grain's `_cap_on_genuine_departures`. The guard is consulted only after the health gate already permitted removal (`classify_absences` applies `extra_guard` after `crawl_authoritative`), so the cap can only tighten — consistent with the extra_guard cannot-widen invariant. Add `MAX_GAME_RETIREMENTS` as a module constant next to `MAX_ROSTER_DEPARTURES` in `src/db/reconcile_at_load.py`. `FLOOR_RATIO` already catches >50% shrink; the cap catches an alarming absolute mass-delete BELOW that ratio (e.g. 8 of 30 = 27% passes the floor). **Value: `MAX_GAME_RETIREMENTS = 2` (operator decision, 2026-07-21).** api-scout's truncation envelope (1200+ records, 17 teams; `docs/api/endpoints/get-public-teams-public_id-games.md`) settles the calibration: `GET /public/teams/{public_id}/games` is un-paginated and returns the complete array in one body (up to 50 games observed); a truncated body is INVALID JSON (a parse error the non-empty/floor gate already aborts on), NOT a short valid array — so "HTTP 200 + valid JSON + silently missing N games" is essentially not a shape this endpoint produces. Genuine simultaneous loss of prior-loaded COMPLETED games has no observed mechanism (`completed` is terminal; 583 prior-completed games re-fetched over 6-20 day windows → 0 reversions, 0 removals; the only genuine-removal vector is a scorekeeper voiding a single game, one-at-a-time). The cap is therefore a backstop against an unobserved mode, not the primary defense; the choice was immaterial to correctness because the perspective-controlled `exempt` set (TN-1/TN-2) means the cap counts only genuine removals and those never exceed ~1. The operator chose **2** — api-scout's recommendation — as the tightest backstop, matching the `MAX_ROSTER_DEPARTURES = 2` precedent: a refused retire is loud and recoverable (cosmetic stale games that self-heal on the next clean crawl), a wrong delete is irreversible child-surface destruction.

### TN-4: Game-grain cap — refusal-reason distinguishability
Extend the TRANSIENT_ABSENT refusal-reason string in the retire loop so an operator can tell the three refusal causes apart in the WARN: cap-tripped (name the cap constant + the retire-eligible absent count `len(absent − exempt)`), boxscores-incomplete (the existing `boxscores_complete=False` case), and the floor/health-gate case (existing). Mirrors the roster grain's which-gate-refused distinction.

### TN-5: Purge guard hardening — sequence and layering
Sequence in the CLI (`src/cli/db.py`, `purge_scouting` command): **guard → preview/count-display → typed-confirm (or `--yes` skip) → backup (fail-closed) → purge.** Backup runs AFTER confirmation (backing up before the prompt wastes a full-DB snapshot on every aborted attempt; post-confirm it is the last thing before the irreversible act and a backup failure still aborts with nothing destroyed).
- (a) `validate_app_env()` (`src/api/helpers.py`) is called at the TOP of `check_purge_production_guard` (`src/db/purge_scouting.py`), before `is_production()`. It raises `RuntimeError` on an out-of-set value (e.g. `APP_ENV=prod`), converting the silent non-production downgrade into a loud abort. Because it raises `RuntimeError` (not `SystemExit`), the CLI must add an `except RuntimeError -> typer.Exit(1)` for clean UX (the existing `except SystemExit` will not catch it).
- (b) A read-only `preview_purge(db_path) -> PurgePreview(resolved_path, {table: count})` in `purge_scouting.py` (keeps table knowledge out of the CLI) runs `SELECT count(*)` over `PURGE_DELETE_ORDER`. The CLI renders the resolved path + a per-table count table BEFORE the prompt. Counts are ADVISORY DISPLAY ONLY ("as of prompt") — a point-in-time snapshot read OUTSIDE the transaction; the authoritative figures are the in-transaction DELETE rowcounts the command already collects. No control-flow may key off the pre-transaction counts. Typed confirmation on production (`is_production()`): `typer.prompt(...)` comparing to the resolved DB filename (`resolved_path.name`) or the literal `'purge'`; a mismatch aborts and `purge_scouting_data` is NOT called.
- (c) Split the overloaded flag: `--force` overrides the PRODUCTION REFUSAL ONLY (keeps flowing to `check_purge_production_guard` / `purge_scouting_data`, whose `force` semantics stay = prod override); `--yes` skips the interactive PROMPT ONLY (pure CLI, never reaches the library). Both default False; a scripted production purge needs `--force --yes`.
- (d) Auto-backup via `backup_database` (`src/db/backup.py`) passed the RESOLVED path (`preview.resolved_path`, not the raw `--db-path`), fail-closed. *(Amended 2026-07-24 during dispatch — this note originally said `backup_database(db_path=db_path)`. `backup_database` uses its argument as-is while `purge_scouting_data` routes through `resolve_db_path`, so on a relative `--db-path` the raw form backs up a different file than the one purged. See E-270-02 AC-5.)* It uses the SQLite online backup API (a consistent WAL-checkpointed snapshot; safe against the live WAL DB and the cross-process boundary) and raises on an absent or locked DB — that raise is the desired fail-closed behavior. Wrap so ANY exception aborts the purge BEFORE the library's `BEGIN IMMEDIATE`, with a clear message. Backup lives at the CLI orchestration layer (keeps the library entry point pure/testable). **Accepted residual:** a direct `purge_scouting_data()` library caller (only tests today) does NOT auto-backup; the sole production invocation is via the CLI. Documented, not closed — the production GUARD stays duplicated in the library (defense-in-depth) but the backup convenience is CLI-level per "simple first."

### TN-7: Player-line per-game companion tests — the real skip path
