# E-257-01: Scoreboard core + CLI (human table + `--json`)

## Epic
[E-257: Plays→Boxscore Reconciliation Scoreboard (productization)](epic.md)

## Status
`DONE`

## Description
After this story is complete, the system has a standing `bb report reconcile-scoreboard` operator diagnostic that computes the plays-vs-boxscore per-stat fidelity metric and the three axis counters from the live DB, renders them as a human-readable Rich table, and emits a stable machine-readable JSON block via `--json`. This is the durable, repeatable form of data-engineer's one-off manual `recon.sql` baseline, mirroring the existing `bb report verify-aggregates` diagnostic. This story MEASURES; the regression gate and committed baseline are the next story (E-257-02).

## Context
CLAUDE.md's north-star Operating Principle names this scoreboard as its enforcement mechanism and states it "lands when that scoreboard exists." This story makes the measurement exist as a repeatable command. The pure connection-in / dataclass-out core is what makes the human table, the `--json` output, and E-256's closure smoke assertion all fall out of one function — so `--json` belongs here, not in a separate story (per SE's sizing). The metric is already fully defined: the implementer reuses the stat definitions, grain, perspective scoping, and no-plays exclusion from the E-245 baseline — encoding the definitions as the code-canonical constants that are now authoritative (the E-245 baseline doc mirrors them, per Technical Notes TN-7) — and does NOT re-derive them.

## Acceptance Criteria
- [ ] **AC-1**: Given the live DB, when `compute_scoreboard(conn)` runs, then it returns a result dataclass carrying (a) per-stat fidelity rows for pitching `{BF, SO, BB, H, HBP}` and batting `{AB, H, BB, SO, HBP}` with exact% and abs-Δ, and (b) the three axis counters as distinct named fields, computed per Technical Notes TN-1 and TN-5 (player-level grain, perspective-scoped, excluding no-plays units).
- [ ] **AC-2**: Given the scoreboard core, when it runs, then it performs NO writes to the database (read-only, mirroring the `verify_aggregates` read-only guarantee — verified by a no-mutation assertion).
- [ ] **AC-3**: Given the DB resolves, when `bb report reconcile-scoreboard` runs, then it renders a human-readable Rich table showing the per-stat fidelity rows and the three axis counters, mirroring the `bb report verify-aggregates` CLI shape at `src/cli/report.py:153`, and the batting `{AB, H}` residual rows — the ONLY stats carrying the abandoned-PA/quick-scored residual label per Technical Notes TN-3 (baseball-coach confirmed: cause-5 residual is strictly batting AB/H; no pitching stat and no batting BB/SO carries this label) — are LABELED as such ("known residual — quick-scored/abandoned-PA noise"), never suppressed, and perspective-only misses appear as a DISPLAY-ONLY sub-line under the `no_plays_units` counter per Technical Notes TN-5 (a diagnostic breakdown of the total, not a separate gated field).
- [ ] **AC-4**: Given `bb report reconcile-scoreboard --json`, when it runs, then it emits a stable JSON block to stdout whose axis-counter keys are exactly `dropped_pitch_events`, `no_plays_units`, and `self_games`, AND whose per-stat block keys (each stat's exact% / abs-Δ field names) are ALSO stable — since E-257-02's ratchet diffs the per-stat block cell-by-cell against the committed baseline, the per-stat keys need the same locked stability as the axis keys (C3). A test pins BOTH the axis-counter key names and the per-stat block shape so a refactor cannot silently rename either.
- [ ] **AC-4b**: Given `--json` mode, when the command runs, then ONLY the JSON object is written to stdout — the human Rich table is suppressed (or routed to stderr) so a consumer's `json.loads(stdout)` never breaks on interleaved table text (C4 — CR-M1; E-256's smoke parses stdout). A test asserts stdout is clean, parseable JSON in `--json` mode.
- [ ] **AC-5**: Given the DB path does not resolve, when the command runs, then it prints an error and exits non-zero (mirroring the `verify-aggregates` DB-missing guard).
- [ ] **AC-6**: Given the synthetic teeth fixture `tests/fixtures/recon_scoreboard_seed.sql`, when the scoreboard computes, then (a) for players whose plays and boxscore agree, per-stat exact% is 100%, AND (b) the fixture deliberately seeds KNOWN NON-ZERO axis values — at least 1 self-game (`home_team_id == away_team_id`), N dropped-pitch events (an `event_type='other'` row carrying a `(PitchType)` suffix per AC-9), and M no-plays units — and a test asserts each axis counter equals its seeded value (`self_games == 1`, `dropped_pitch_events == N`, `no_plays_units == M`), not merely the all-zero case (CR-S4). The fixture seeds a populated, known state, not an empty DB.
- [ ] **AC-7**: Given the scoreboard's plays-derived stat definitions, when the drift guard runs (per Technical Notes TN-7), then (a) the outcome-set definitions (the SO/BB/H outcome-membership sets and the AB-exclusion set) live as named module-level constants in `recon_scoreboard.py`, a test pins each constant to its literal expected set, AND (b) a fixture exercises each outcome-to-stat mapping behaviorally (a row of each outcome type lands in the correct stat) — the code constants are canonical and the baseline doc mirrors them (source-of-truth flipped per TN-7). Constant NAMES are the implementer's call; the AC verifies the pin + behavioral fixture exist, not specific names. (c) the E-245 baseline doc (`.project/research/E-245-plays-boxscore-reconciliation-baseline.md`) is annotated to note that `recon_scoreboard.py` is the authoritative source it now mirrors (the source-of-truth flip per TN-7), so the reference doc does not silently go stale.
- [ ] **AC-9**: Given the dropped-pitch-events axis counter, when it is computed, then the detection predicate for a stranded annotated pitch (an `event_type='other'` `play_events` row whose `raw_template` carries a `(PitchType)` suffix) matches the exact pattern documented in `.claude/agent-memory/data-engineer/pitch_type_annotation_parser_gap.md` — NOT a naive `LIKE '%(%)%'` that over-counts (C5 — DE-F2). A test pins the predicate against both a matching row and a near-miss non-matching row. This counter is a headline value E-256's closure smoke asserts on, so the predicate must be exact.
- [ ] **AC-8**: Given the `bb` console entry point, when the new subcommand is invoked via subprocess (`bb report reconcile-scoreboard --help`) in `tests/test_script_entry_points.py`, then it succeeds — the subprocess smoke test per `.claude/rules/testing.md`.

## Technical Approach
Follow the `src/reports/aggregate_parity.py` precedent per Technical Notes TN-1: a pure, connection-in / result-dataclass-out core module at `src/reports/recon_scoreboard.py`, with the CLI wrapper mirroring the `verify-aggregates` command at `src/cli/report.py:153`. The "mirror" is the CLI plumbing / DB-missing guard / table shape only — `--json` is net-new (CR-S1; `verify-aggregates` has none). The scoreboard SQL reads only from `plays` / `play_events` / `player_game_batting` / `player_game_pitching` (100% net-new SQL lifted from the baseline's `recon.sql`; no SQL shared with `aggregate_parity`). Encode the plays-derived stat definitions as named module-level constants (the SO/BB/H outcome sets + AB-exclusion set) so the drift guard (AC-7, TN-7) is mechanically testable and the code is the canonical source; the baseline doc mirrors the constants. Pin the dropped-pitch detection predicate to the exact `raw_template` pattern in `.claude/agent-memory/data-engineer/pitch_type_annotation_parser_gap.md` (AC-9) — not a naive `LIKE '%(%)%'`. Keep player-level grain, perspective scoping, and no-plays exclusion per the baseline and TN-5 (perspective-only misses are a DISPLAY-ONLY sub-line under the total `no_plays_units`, not a separate gated field). Design the result dataclass so the three axis counters are distinct named fields; `--json` is then a serialization of the dataclass to stdout ONLY (Rich table suppressed in `--json` mode per AC-4b) with the stable keys pinned in AC-4.
