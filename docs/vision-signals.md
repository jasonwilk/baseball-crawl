- **2026-03-29**: Display thresholds must be calibrated for youth/HS season length, not pro baseball. A 25-game season is normal at 8U-14U; even HS varsity may only play 30. Current thresholds (10 BIP for spray, 10 AB for heat maps) are too conservative -- they suppress useful data for most of the season. The system should show whatever data exists at a pragmatically reasonable minimum and improve as depth grows. "One BIP probably shouldn't generate a spray chart, but 3-4 should." This coaching-reality calibration must be baked into the context layer so every agent building thresholds thinks in terms of 25-game seasons, not 162. *(user feedback after E-186 report generation -- Millard South had 5 games, no heat maps despite 18 batters)*
- **2026-03-29**: Never suppress rate stats just because the sample is small. A 189.0 ERA on 0.1 IP tells the coach "this kid got shelled" -- that's useful information, not noise. Show all stats, mark small samples with context (asterisk + footnote), let the coach decide what matters. The system presents data; the coach is the analyst. Rate stat suppression at low sample sizes (hiding behind "--") removes signal a coach would want. *(user feedback on Lincoln Southwest Freshman report -- C Johnson's 189.0 ERA on 0.1 IP)*
- **2026-04-12**: Coaches need a trust-verification mechanism so bbstats.ai reports can be spot-checked against the GC app view. - **2026-07-18**: **Prediction-accuracy eval loop** — grade EVERY predictive report output (opponent probable starter, OUR probable starter, the per-arm two-branch command read, the steal light, the loss-blueprint levers, hitter tendencies — anything we try to predict) against the finished game, accumulate, and sharpen only on patterns across many games (never overfit one result). Architecture the operator specified: predictions are PERSISTED at generation time (you can't grade what you didn't record) as runtime data on the server in git-ignored `data/` — NEVER committed (real minors' names + stats must not enter git history; the doc-PII gate exists for this). Lightly automated (a post-game grader joins prediction → box score when the game lands in the DB); it is a single-season, per-game *accuracy log*, inside scope — NOT the deleted cross-season/longitudinal machinery. Live seed (2026-07-18, we won 10–2): the opponent's predicted #2 starter was a top-2 hit (correct arm in our ranked pair); the memo over-led with the steal light (0 steals in a walk-driven blowout), which surfaced an emphasis-calibration lesson, not a data error — exactly the kind of pattern the loop should catch across many games rather than one. **Mechanism the operator is converging on (make it tunable, not re-guessable):** every predictor is a DETERMINISTIC function of `data + a small set of NAMED, VERSIONED params` (thresholds/weights) centralized in one config — the predictions are already deterministic by design (`probable-starter-model`: "the LLM writes words, it does not rank arms"), so the work is making the scattered/implicit knobs explicit (e.g. the command-volatility → both-tails thresholds, the steal-light green/red CS% cutoff, the blueprint majority cutoff, the role-share cutoffs, the sample floors). "Sharpen" = adjust a named param and record which params-version produced each prediction; never rewrite logic or re-prompt an LLM. **Guardrail:** few knobs, moved only on cross-game patterns — the probable-starter-model's own backtest (17 seasons / 357 games) already found soft graduated weights INEFFECTIVE and a hard partition better, so more knobs ≠ better; determinism gives a fair test, the eval loop says when a knob has earned a turn. **Correctives from two adversarial reviews (Codex gpt-5.6-sol + Fable, 2026-07-18, saved PII-free at `.project/research/2026-07-18-deep-scout-adversarial-reviews.md`) — DO NOT build the naïve version:** (1) most report outputs are NOT box-score-gradeable "predictions" — classify each (forecast / rule-determination / conditional decision-aid / historical-association / rate-estimate) before grading, or you manufacture accuracy for unfalsifiable claims; a two-branch plan needs a PRE-DECLARED live switch-cue or it's unfalsifiable. (2) The grader needs coverage/abstention states (`no_opportunity`, `missing_charting`, …) — a missing box score must never score as a "miss," and a red-light-never-run must not read as "perfect." (3) The ~15-game/season LIVE log can't tune anything within a season — the ~357-game BACKTEST (retrodict as-of-date, leakage discipline) is the tuning gate; the live log is an anecdote collector. Every rule extracted from a live game must reproduce as a backtest delta before it ships. (4) Beware same-source self-confirmation (the same parser making both the prediction and the "truth"). (5) "Params-only, never logic" is impossible/dishonest — version code+params together, old predictions immutable, the real guardrail is "no change without a backtest delta"; split the manifest (ruleset / logic / params / trust-floors / presentation) so accuracy-tuning can't silently move a safety floor. (6) Self-scout/eval-log PII: git-ignore is necessary-not-sufficient — the leak vector is the WORKFLOW (named examples pasted into epics/commits/transcripts); role-labeled/opaque IDs never names, data dies with the season, and self-scout must not enter the unauthenticated public-link artifact until a staff-private delivery exists. *(session 2026-07-18)*
