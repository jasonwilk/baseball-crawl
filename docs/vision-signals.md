- **2026-03-29**: Display thresholds must be calibrated for youth/HS season length, not pro baseball. A 25-game season is normal at 8U-14U; even HS varsity may only play 30. - **2026-07-18**: **Prediction-accuracy eval loop** — grade EVERY predictive report output (opponent probable starter, OUR probable starter, the per-arm two-branch command read, the steal light, the loss-blueprint levers, hitter tendencies — anything we try to predict) against the finished game, accumulate, and sharpen only on patterns across many games (never overfit one result). Architecture the operator specified: predictions are PERSISTED at generation time (you can't grade what you didn't record) as runtime data on the server in git-ignored `data/` — NEVER committed (real minors' names + stats must not enter git history; the doc-PII gate exists for this). Lightly automated (a post-game grader joins prediction → box score when the game lands in the DB); it is a single-season, per-game *accuracy log*, inside scope — NOT the deleted cross-season/longitudinal machinery. Live seed (2026-07-18, we won 10–2): the opponent's predicted #2 starter was a top-2 hit (correct arm in our ranked pair); the memo over-led with the steal light (0 steals in a walk-driven blowout), which surfaced an emphasis-calibration lesson, not a data error — exactly the kind of pattern the loop should catch across many games rather than one. **Mechanism the operator is converging on (make it tunable, not re-guessable):** every predictor is a DETERMINISTIC function of `data + a small set of NAMED, VERSIONED params` (thresholds/weights) centralized in one config — the predictions are already deterministic by design (`probable-starter-model`: "the LLM writes words, it does not rank arms"), so the work is making the scattered/implicit knobs explicit (e.g. the command-volatility → both-tails thresholds, the steal-light green/red CS% cutoff, the blueprint majority cutoff, the role-share cutoffs, the sample floors). "Sharpen" = adjust a named param and record which params-version produced each prediction; never rewrite logic or re-prompt an LLM. **Guardrail:** few knobs, moved only on cross-game patterns — the probable-starter-model's own backtest (17 seasons / 357 games) already found soft graduated weights INEFFECTIVE and a hard partition better, so more knobs ≠ better; determinism gives a fair test, the eval loop says when a knob has earned a turn. **Correctives from two adversarial reviews (Codex gpt-5.6-sol + Fable, 2026-07-18, saved PII-free at `.project/research/2026-07-18-deep-scout-adversarial-reviews.md`) — DO NOT build the naïve version:** (1) most report outputs are NOT box-score-gradeable "predictions" — classify each (forecast / rule-determination / conditional decision-aid / historical-association / rate-estimate) before grading, or you manufacture accuracy for unfalsifiable claims; a two-branch plan needs a PRE-DECLARED live switch-cue or it's unfalsifiable. (2) The grader needs coverage/abstention states (`no_opportunity`, `missing_charting`, …) — a missing box score must never score as a "miss," and a red-light-never-run must not read as "perfect." (3) The ~15-game/season LIVE log can't tune anything within a season — the ~357-game BACKTEST (retrodict as-of-date, leakage discipline) is the tuning gate; the live log is an anecdote collector. Every rule extracted from a live game must reproduce as a backtest delta before it ships. (4) Beware same-source self-confirmation (the same parser making both the prediction and the "truth"). (5) "Params-only, never logic" is impossible/dishonest — version code+params together, old predictions immutable, the real guardrail is "no change without a backtest delta"; split the manifest (ruleset / logic / params / trust-floors / presentation) so accuracy-tuning can't silently move a safety floor. (6) Self-scout/eval-log PII: git-ignore is necessary-not-sufficient — the leak vector is the WORKFLOW (named examples pasted into epics/commits/transcripts); role-labeled/opaque IDs never names, data dies with the season, and self-scout must not enter the unauthenticated public-link artifact until a staff-private delivery exists. *(session 2026-07-18)*
- **2026-07-25**: **The pitch-rules engine cannot serve the youth audience the vision already claims.** `docs/VISION.md` has committed since 2026-07-05 to "any coach with a team on GameChanger" and explicitly names "a 9U USSSA coach"; the operator confirmed this is live reality, not aspiration — they help friends coaching USSSA 9U/10U/14U teams. But a full live probe of all **752** teams in the database shows the engine is still shaped for high-school/Legion and structurally fails that audience on two axes. **(1) Every unsupported governing body is a youth body.** `usssa` and `perfect_game` resolve but get NO card (**131 teams** — 17% of the database) because `PitchCountRules` is pitch-count-only and cannot express USSSA's innings-based or Perfect Game's outs+pitches dual-unit form, even though both rule sets are already transcribed in `.claude/rules/pitch-rules.md` as "reference data only"; and `little_league`, `babe_ruth_cal_ripken` and `pony` dead-end at `starter_prediction.py:463`, returning `unknown` before the bracket/name ladder ever runs. **(2) Where a young arm DOES get a number, it may be the wrong one** — 43 teams with a bracket of 14U or below receive a 105-pitch cap, which the code itself documents as "the labeled Pitch Smart 15-18 estimate" (line 266). That is defensible for a high-school tool where 14U is an edge case; for a youth-coach audience it is a core path, in the under-resting direction, and it contradicts baseball-coach's same-day ruling that `Under 13` must hard-suppress because "every table we have is calibrated for 15+ and would under-rest a 7-12-year-old arm." Net: the same child is treated oppositely depending on whether their coach picked the rec or travel family in GC's create-team flow. Youth support is not a feature gap at the margin — it is the difference between the vision's stated reach and what the product can actually deliver, and it concentrates precisely where immature-arm injury risk is highest. Related: `IDEA-182` (rules-engine innings/outs forms), the `little_league` ruling in `.claude/agent-memory/baseball-coach/e275-classifier-hardening-rulings.md`, and a pending coach ruling on 13U/14U. *(measured during the 752-team classification probe, 2026-07-25; audience scope confirmed by the operator in-session after `CLAUDE.md`'s stale LSB-only scope nearly caused 84 of these teams to be dismissed as import noise)*
- **2026-07-28**: **The tool can be MORE correct than GameChanger, and nothing in the vision says so.** E-278 established by execution that a GC profile record is a **raw count of that team's own schedule listings**, not of games played — so when GC double-lists a game, *matching GC means reproducing GC's error*, and our deduplicated record is the better number. Measured on a team with a confirmed double-listing: profile 30-12-0 (42) == raw listing count exactly, while deduped is 28-12-0 (40). **This sits in tension with the north star as written** — "Always Get Closer to Byte-Identical Play Ingestion" is about plays-to-boxscore fidelity, and we now deliberately diverge from GC on a different axis. Worth an explicit curation decision, because it is coach-facing (the record header is the first number a coach checks against memory): is the framing still *"faithful mirror of GameChanger"*, or is it *"faithful to what happened on the field, with GameChanger as the source"*? The second is a stronger claim and the product now partly delivers it. Note the epic deliberately declined to make "matches GC" an acceptance target anywhere. *(E-278 TN-16, measured against four live payloads)*
