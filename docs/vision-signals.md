## Signals

- **2026-03-13**: Coach interview: Proactive flags are non-negotiable. System must auto-surface: short rest (≤3 days), high pitch count (>85), hot/cold hitter streaks, high walk rate. "Their ace threw 98 pitches 4 days ago" -- coaches shouldn't have to calculate this. *(E-100 coach consultation via UXD)*
- **2026-03-13**: Coach interview: Wants a "clean one-pager that summarizes the opponent in plain English" for bench use. PDF export preferred over browser print. B&W printable, no color dependency. *(E-100 coach consultation via UXD)*
- **2026-03-13**: Coach interview: System-generated matchup suggestions based on L/R splits and recent form. "Consider moving [Player A] up — .380 OBP vs. lefties." Validate suggestion logic before building lineup builder UI. *(E-100 coach consultation via UXD)*
- **2026-03-14**: Data model parity with GameChanger: the schema should include every stat GC tracks, populated by direct API pull or crawled/compiled from play-by-play. The goal is to make our data model as rich as GC's and maintain parity over time. Stats not yet available via API get nullable columns now, filled when the data source becomes available. "What is the reason we wouldn't store a stat?" *(E-100 schema design session)*
- **2026-03-16**: Player handedness (bats/throws) may not be populated in GameChanger by most teams. L/R splits may require operator-entered data rather than API-sourced. "I don't think teams enter it often. Unless we populate it ourselves as we watch games." This reframes IDEA-029 from API field mapping to a manual data entry + API hybrid approach. *(E-100 Codex review triage — IDEA-028/029 scoping)*
- **2026-03-16**: Coach consultation: the most valuable HS coaching splits are query-time computations over per-game data — recent form (last 5-7 games), doubleheader fatigue (game 1 vs 2), season phase (early/mid/late). Traditional home/away splits have low value at HS level (no real home field advantage, small samples). Per-game stat population (E-117) is the prerequisite for all high-value analytics — pre-aggregated columns are secondary. *(baseball-coach consultation during IDEA-028 promotion)*
- **2026-03-18** *(recast 2026-07-05 for report layout — originally dashboard-era)*: Reports should lead with **pitching before batting** for an opponent — the coach's first question is "Who am I facing on the mound?" Order: (1) likely starters + availability (K/BB, recent outings, pitch count/rest), (2) team batting tendencies (K%, BB%, OBP), (3) power vs. contact, (4) record + recent form, (5) familiar faces. This is now report-layout work on ux-designer's refocused docket (the original "opponent dashboard" framing is dead post-E-239; the pitching-first *principle* carries into the report). *(E-127 refinement — baseball-coach consultation, recast during the 2026-07-05 vision curation)*
- **2026-03-25**: May adopt Cloudflare Email OTP as the app's primary auth mechanism (replacing or supplementing E-023 magic links). CF Access is present on bbstats.ai but not currently enforcing auth -- the app handles auth internally. CF Email OTP would shift auth responsibility to Cloudflare's edge, simplifying the app layer. *(E-157 planning -- user decision during Cloudflare deployment setup)*
- **2026-03-29**: Display thresholds must be calibrated for youth/HS season length, not pro baseball. A 25-game season is normal at 8U-14U; even HS varsity may only play 30. Current thresholds (10 BIP for spray, 10 AB for heat maps) are too conservative -- they suppress useful data for most of the season. The system should show whatever data exists at a pragmatically reasonable minimum and improve as depth grows. "One BIP probably shouldn't generate a spray chart, but 3-4 should." This coaching-reality calibration must be baked into the context layer so every agent building thresholds thinks in terms of 25-game seasons, not 162. *(user feedback after E-186 report generation -- Millard South had 5 games, no heat maps despite 18 batters)*
- **2026-03-29**: Never suppress rate stats just because the sample is small. A 189.0 ERA on 0.1 IP tells the coach "this kid got shelled" -- that's useful information, not noise. Show all stats, mark small samples with context (asterisk + footnote), let the coach decide what matters. The system presents data; the coach is the analyst. Rate stat suppression at low sample sizes (hiding behind "--") removes signal a coach would want. *(user feedback on Lincoln Southwest Freshman report -- C Johnson's 189.0 ERA on 0.1 IP)*
- **2026-04-12**: Coaches need a trust-verification mechanism so bbstats.ai reports can be spot-checked against the GC app view. Current reports highlight OBP-framed leaders (Top Bat callout, spray chart PA counts) while the GC app surfaces an AVG-ranked batting table — correct data, hard to eyeball against. When these two were compared for Gretna Varsity (report generated 2026-04-11 with data through Apr 10, GC app screenshot 2026-04-11 4:53 PM), the apparent "they differ quite a bit" feeling was fully explained by (1) different sort metrics, (2) PA vs AB framing, (3) a one-day freshness gap — no data contamination, no architecture problem. But the perception gap is itself the signal: coaches need to be able to build trust in the data without doing arithmetic by hand. Candidates: full AVG-ranked batting table in reports matching the GC layout; a `bb data verify <public_id>` cross-check tool that fetches GC public data and diffs against our DB; more prominent "through Apr 10 · 13 games · 8-5" freshness header. *(session debugging divergent-stats concern during E-220 → E-221 → E-222 recovery, 2026-04-12)*
- **2026-06-08**: If the Tier-2 LLM narrative becomes a regular part of coaches' pre-game workflow, revisit the no-coach-visible-label decision from E-233 — Tier-2 silently disappearing on LLM-failure days can erode trust in report consistency over time. Mitigation in the meantime: keep Tier-1 quality high so Tier-2 reads as "bonus context" rather than a load-bearing section. *(baseball-coach consultation during E-233 planning)*
- **2026-06-15**: Once Epic E runs reports unattended (morning-of-game cron), the operator run record (`report_generation_runs`) and the coach-facing footer / no-games page become the SOLE trustworthiness signal — there is no human eyeballing each report anymore. E-236 hardened both surfaces to be honest (per-stage `partial`/`failed` statuses, count columns, the all-blocked→`failed` outcome, the two-case no_games copy, the derived operator-degraded flag) precisely so Epic E's monitoring/alerting can be built ON these signals: an unattended run is "trustworthy" iff `overall_status='completed'` AND no per-stage status is `partial`/`failed`. Epic E should surface/alert on `overall_status` + per-stage statuses + the derived operator-degraded flag rather than re-deriving report health from raw data. *(E-236 closure 2026-06-15 — the self-reporting honesty layer is the trust substrate for unattended operation)*
- **2026-06-17**: "Regenerate now" button on the admin reports page. If a scheduled report came out empty (early season) or a coach wants a refresh for a late-added opponent, one-click regenerate from the admin UI beats the manual CLI. *(baseball-coach consultation during E-240 discovery)*
